# 답변 문제 패킷 처리

## 0. 이 파일을 다루는 규칙 — 먼저 읽는다

패킷에는 **사내 질문·답변 원문과 사용자 피드백 원문**이 들어 있다. 고치는 일은
그 내용을 읽어야 되지만, 그 내용이 저장소에 남으면 안 된다. 둘은 다른 이야기다.

| 하는 것 | 하지 않는 것 |
|---|---|
| 읽고 원인을 판정한다 | 질문·답변·피드백 문장을 코드·테스트 픽스처·문서·커밋 메시지·PR 에 옮겨 적는다 |
| QA ID(`record_id`)로 가리킨다 | 사람 이름·채널명·사업장명을 새 파일에 적는다 |
| `qa-issues/` 에 둔 채로 작업한다 | 패킷을 `git add` 한다(`.gitignore` 에 있지만, 강제 추가하지 않는다) |

재현 테스트를 쓸 때도 **실제 문장을 쓰지 않는다.** 고장을 일으킨 것은 문장의 내용이
아니라 그 문장의 *모양*이다 — 길이, 특수문자, 빈 값, 날짜 표현, 첨부 유무. 그 모양만
남긴 최소 픽스처를 짓는다. 내용을 그대로 복사하면 테스트는 통과하지만 저장소에
사내 대화가 영구히 박힌다.

작업이 끝나면 패킷을 지울지 사용자에게 묻는다. 지우는 것은 사용자 몫이다 — 다음
회차와 비교하려고 남겨 둘 수도 있다.

## 1. 패킷을 찾는다

경로를 받았으면 그것을 쓴다. 안 받았으면 `qa-issues/` 에서 **가장 최근 파일**을
고르고, 어느 파일을 골랐는지 한 줄로 말한다 — 사용자가 여러 장을 받아 두었을 수 있고,
엉뚱한 회차를 고친 뒤에 알면 늦다.

```bash
ls -t qa-issues/answer-issues-*.md | head -3
```

폴더가 비어 있으면 거기서 멈추고 말한다: 콘솔 > 운영 현황 > 「문제 패킷 내려받기」
에서 받아 `qa-issues/` 에 넣으면 된다고.

## 2. 먼저 접는다 — 통째로 읽지 않는다

패킷은 문제를 200건까지 담고, 건마다 질문·답변·출처·추적이 통째로 들어간다.
처음부터 끝까지 읽으면 두 가지가 같이 일어난다.

- 문맥이 원문으로 찬다. 그런데 **원문은 고칠 대상이 아니다.** 고칠 것은 원문을
  그렇게 만든 코드다.
- 같은 원인의 100건이 서로 다른 100개 문제로 보이고, 같은 조사를 100번 하게 된다.

```bash
python .claude/skills/qa-issue-fix/scripts/summarize_packet.py qa-issues/<파일>
```

분류·워크스페이스·의도/결과·오류 종류·채널별 건수와, **「고칠 단위」(분류 × 오류
종류) 묶음**과 각 묶음의 QA ID 가 나온다. 어느 묶음을 열지 정한 다음에만 편다.

```bash
# 묶음 하나를 대표 몇 건으로 확인 (본문은 접힌 채로)
python .claude/skills/qa-issue-fix/scripts/summarize_packet.py qa-issues/<파일> --detail QA-1 QA-2

# 판단이 갈릴 때만 질문·답변 본문까지
python .claude/skills/qa-issue-fix/scripts/summarize_packet.py qa-issues/<파일> --detail QA-1 --with-text
```

패킷 앞머리의 「문제 분포」와 「연결되지 않은 피드백」은 짧으니 그대로 읽어도 된다.
연결되지 않은 피드백은 **QA 기록이 조회 기간 밖**이라는 뜻이라, 대개 기간을 늘려
다시 받아야 할 신호다.

## 3. 증상을 원인으로 옮긴다

패킷의 분류(`error` · `no_evidence` · `slow` · `specialist_failure` · `feedback`)는
**증상이다.** 같은 증상이 전혀 다른 곳에서 난다. 고칠 곳을 정하려면 파이프라인
단계로 옮겨야 한다. 이 매핑이 이 스킬의 핵심이고, 매번 처음부터 더듬지 않기 위해 적어 둔다.

| 단계 | 이 단계가 원인일 때 보이는 것 | 주로 보는 곳 |
|---|---|---|
| **수집** | 있어야 할 자료가 아카이브에 아예 없다. 특정 채널·기간만 비어 있다 | `collect.py`, `archive/writer.py`, `archive/channel_files.py`, `archive/convert.py`, `slack/pilot.py` 수집 경로 |
| **권한** | 질문자만 못 본다. 다른 사람은 같은 질문에 답을 받는다 | `access/`, `archive/store.py` 의 `visible_docs`, `workspaces.py` |
| **검색** | 자료는 있는데 안 잡힌다. 낱말을 바꾸면 잡힌다 | `search_index.py`, `archive/store.py`, `documents.py`, `orgsearch.py` |
| **분류(의도)** | 질문을 엉뚱한 갈래로 읽었다. `의도 → 결과` 조합이 어긋나 보인다 | `intent.py`, `master_planner.py` |
| **전문 봇** | `specialist_failure`, 폴백, `unavailable`, `invalid-output` | `specialist_router.py`, `specialist_contract.py`, `specialist_adapters.py`, `specialist_tools.py` |
| **렌더링·근거** | 답은 맞는데 출처가 없거나 틀렸다. 근거 건수와 답 내용이 안 맞는다 | `answer.py`, `compose.py`, `evidence_refs.py`, `document_evidence.py`, `thread_followup.py` |
| **운영 설정** | 어느 날 갑자기, 한 워크스페이스만, 시각대로 몰려서 | `gateway/cost.py`·`gateway/budget.py`(상한), `heartbeat.py`, 서버 env, 타이머 |

판정이 갈리면 **가장 이른 단계**를 먼저 의심한다. 수집이 비면 검색·답변은 반드시
따라서 틀리고, 그때 검색을 고치면 증상만 옮겨 간다.

한 묶음의 원인을 단정하기 전에 코드를 실제로 열어 확인한다. 패킷은 무엇이
일어났는지 말하지만 **왜**는 말하지 않는다 — 그건 코드에 있다.

## 4. 계획을 내고 승인을 받는다

고치기 전에 이 표를 낸다. 표가 짧을수록 좋다 — 묶음이 잘 접혔다는 뜻이다.

```
| # | 묶음 | 건수 | 단계 | 추정 원인 | 고칠 곳 | QA ID |
```

순서는 **반복 × 영향**으로 정한다. 사람이 실제로 겪는 것부터다.

1. 답이 틀렸다 / 없는 것을 있다고 했다 — 신뢰가 깨진다
2. 근거를 못 찾아 「모른다」 만 반복한다 — 쓸모가 없다
3. 오류로 끝난다 — 눈에 띄므로 사람이 다시 묻는다
4. 느리다 — 불편하지만 답은 나온다

같이 적을 것: **이번에 고치지 않을 묶음과 그 이유.** 남은 것이 보이지 않으면 다음
회차에 같은 조사를 처음부터 다시 한다.

사용자 승인을 기다린다. 승인 없이 고치면, 엉뚱한 것을 고쳤을 때 되돌리기가
고치기보다 비싸진다.

## 5. 고친다 — 재현 먼저

묶음 하나씩, 순서대로.

1. **재현 테스트를 먼저 쓴다.** 지금 실패해야 한다. 실패하지 않으면 원인을 아직
   모르는 것이고, 그 상태의 수정은 증상만 가린다.
   - 이 저장소의 테스트는 「무엇을 왜 막는지」를 이름과 docstring 으로 말한다.
     주변 파일의 결을 따른다.
   - 픽스처에 사내 원문을 쓰지 않는다(§0). 고장을 낸 *모양*만 남긴다.
2. 고친다. 같은 원인의 다른 묶음까지 함께 고쳐지는지 본다.
3. **왜 이렇게 고쳤는지**를 코드 옆에 남긴다. 이 저장소는 그 이유를 주석에 적는
   관례가 있다 — 다음 사람이 같은 함정에 다시 빠지지 않게.
4. 이 고장이 **조용히** 났다면, 다음번엔 소리가 나게 한다. 오류 문구에 원인과
   고칠 자리를 적거나, 헬스 체크에 줄을 더하거나, 로그에 판정 근거를 남긴다.
   패킷에 올라왔다는 것 자체가 「아무도 몰랐다」 는 뜻이다.

## 6. 확인하고 보고한다

```bash
python -m pytest -q
python -m ruff check src tests scripts
```

둘 다 통과해야 끝이다. 실패하면 실패했다고 출력과 함께 말한다.

보고에 넣을 것:

- 묶음별로 **고쳤다 / 안 고쳤다 / 코드 문제가 아니었다** 중 하나. 셋째가 제일
  중요하다 — 운영 설정이나 자료 문제였다면 코드를 고칠 일이 아니고, 사용자가 할
  일이 따로 있다
- 각 묶음에 **어느 QA ID 가 덮이는지**. 다음 회차에 같은 ID 가 또 오면 안 고쳐진 것이다
- 이번에 손대지 않은 묶음과 그 이유

여러 건이면 `docs/verification/<날짜>-answer-issue-fixes.md` 에 인계 노트를 남긴다.
**QA ID 와 판정, 고친 곳만 적고 원문은 적지 않는다.** 이 문서는 커밋된다.

## 7. 피드백 되돌려 주기

패킷의 피드백 항목에는 처리 상태(`처리됨`/`미처리`)가 있다. 고친 뒤에는 콘솔에서
그 피드백에 처리 메모를 남기도록 사용자에게 알린다 — 커밋 해시와 확인 방법까지.
👎 를 누른 사람이 그 뒤를 못 보면 다음부터 안 누른다. 그러면 이 패킷이 비어 간다.
