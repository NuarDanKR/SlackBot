# Hermes

> 팀 슬랙 에이전트. 대화 아카이브를 근거로 질문에 답하고, 매일·매주 대화를 정리해 보냅니다.

## 처음 받으셨다면

이 저장소만으로는 아직 안 돕니다 — **자료 저장소를 따로 만들고 채워야** 합니다.
그 과정을 `hermes-install` 스킬이 0~8단계로 안내합니다.

이 폴더에서 Claude Code 를 열고 **"헤르메스 설치"** 라고 하세요.
설치는 며칠에 걸쳐도 됩니다 — 어디까지 갔는지 기억하고 이어서 합니다.

> 이미 돌고 있는 인스턴스를 손보시는 것이라면 이 절은 건너뛰세요.
> 매일 하는 일은 `archive-run`(「아카이브 한 바퀴」) 입니다.

## 하는 일

| | 언제 | 어디로 |
|---|---|---|
| **질문 답변** | `@Hermes` 멘션 또는 DM | 물어본 자리(스레드) |
| **일일 요약** | 매일 17:30 | `config.json` 의 전달처 |
| **주간 정리** | 금요일 16:00 | `config.json` 의 전달처 |
| **대화 로그** | 답할 때마다 | 자료 저장소의 `hermes-log/` (매일 07:00 반영) |

> **전달처가 채널이면 `#비공개가` 내용은 요약에서 자동으로 빠집니다.** 그 채널 전원이 보기 때문입니다.
> 본인 DM 으로 받을 때만 포함됩니다. 요약 하단에 `비공개 제외` 표시가 붙습니다.

답변의 근거는 두 곳입니다. 둘 다 **자료 저장소** 안에 있습니다 — **사람이 한 말**은 `slack-export/` 아카이브(채널별 md), **문서에 적힌 것**은 `documents/` 문서 아카이브입니다. 각각 몇 개인지는 여기 적지 않습니다 — 늘어나는 값이라 낡습니다. `npm run check` 의 `[3/6]`·`[4/6]` 이 그때그때 세어 줍니다. **검색은 `search` 하나로 두 곳을 한 번에 훑고**(2026-08-18 부터 — 그전에는 도구가 둘이라 봇이 같은 것을 두 번 물었습니다), **결과는 `## 대화` / `## 문서` 두 구역으로 갈라 돌려줍니다** — 발언과 확정 자료를 섞지 않기 위함입니다. 요약은 슬랙에서 그날/그주 대화를 스레드 답글까지 직접 읽어 만듭니다.

**질의에 사업장 이름이 들어 있으면 검색이 스스로 그 자리로 좁힙니다** (2026-09-03 부터). 봇이 자리를 지정하지 않고 물어도 그렇습니다 — 안 좁히면 결과 상한을 자리들이 나눠 가져서 정작 물어본 자리가 한 칸밖에 못 받습니다. 실측으로 돌아온 히트 중 물어본 자리 것이 대화 22%·문서 13% 였는데, 좁히면 둘 다 83% 가 되고 결과 자수가 25% 줍니다. **이름은 그 질문에서 볼 수 있는 자리 안에서만 풉니다** — 전체 목록으로 풀면 못 보는 비공개 채널로 좁혀져 그런 자리가 있다는 것이 드러납니다. 서로 다른 자리가 둘 이상 걸리면 안 좁히고, 좁혀서 빈손이면 안 좁힌 결과로 되돌아갑니다. 되돌리기는 `config.json` 한 줄입니다 — `limits.autoNarrow` 를 `false` 로 두면 꺼집니다(줄이 없으면 켜진 것으로 봅니다).

**낱말을 다 맞춘 것이 없어도 빈손으로 돌려주지 않습니다.** 그때는 일부만 맞은 것을 겹친 개수 순으로 함께 주고(제목 줄에 `(2/3 낱말)`), **사업장을 지정해 좁혔는데 그 안에 다 맞춘 것이 하나도 없으면 좁히지 않고 한 번 더 찾아 밖의 상위 3건을 `## 다른 사업장에서도` 구역으로 따로 붙입니다**(2026-08-20 부터). 구역을 뗀 것은 봇이 밖의 자료를 그 사업장 것으로 섞어 쓰지 않게 하려는 것이고, 밖의 것이 전부 일부만 맞은 것이면 구역 머리에 그렇게 적힙니다. 되돌리기는 `config.json` 한 줄입니다 — `limits.outsideWhenNarrowedMaxHits` 를 `0` 으로 두면 그대로 꺼집니다. **다만 그 한 줄은 아래 「전사 종합 문서」 카드도 함께 반쯤 끕니다** — 봇이 자리를 안 짚어 검색이 스스로 좁힌 경로에서는 카드가 버려집니다(`npm run check` 가 그때 화면에 알려 줍니다).

**여러 사업장을 한 문서에 담은 종합 보고서는 사업장으로 좁히면 구조적으로 범위 밖입니다.** 그래서 답이 그 안에 있는데도 봇이 「자료가 없습니다」로 닫는 일이 있었습니다(2026-09-11 실측: 같은 질문 8회 중 4회). 이제 **좁힌 검색이 「닫을 자리」일 때만** 그런 문서를 `## 전사 종합 문서` 구역에 **최대 2건, 발췌 없이** 가리킵니다 — 문서 이름·날짜·글자 수·절 개수뿐입니다. 발췌를 일부러 안 싣습니다: 그 문서들의 앞부분에는 답이 없고, 앞부분은 **엉뚱한 사업장 구간**이라 남의 숫자가 흘러듭니다. 봇은 카드를 보고 `read_document` 로 **그 사업장 절만** 엽니다. 「닫을 자리」는 낱말을 다 맞춘 것이 0건이고, 그 위에 일부만 맞은 것도 거의 없거나 **질의 낱말 중 그 사업장 자료에 아예 없는 것이 있을 때**입니다 — 답이 잘 나오던 질문에는 안 붙습니다. 어느 폴더가 전사 종합인지는 자료 저장소 `config.json` 의 `search.companyWideDocProjects` 가 원본이고, **그 목록을 비우면 통째로 꺼집니다.**

**일일 요약은 그날 올라온 첨부 문서의 내용까지 싣습니다** (2026-08-06 부터). 실시간 조회가 주는 것은 파일 이름뿐이라, 그것만으로는 "무슨 파일이 올라왔다"까지밖에 못 씁니다. 그래서 기간 안에 올라온 문서는 변환된 md 에서 본문을 꺼내 재료에 함께 넣습니다 — 요약이 아카이브에 기대는 곳은 여기 하나뿐입니다. 변환은 사람이 `doc-archive` 로 하는 일이라 **요약 전에 끝나 있어야 하고**, 그래서 16:00 에 마감 알림이 오고 17:00 에 자동 반영이 한 번 더 돕니다(아래 「요약 전 마감」). 아직 변환 안 된 첨부는 요약 하단에 `미반영 N건` 으로만 적힙니다 — 파일 이름·채널 이름은 적지 않습니다(팀 전원이 보는 자리).

## 처음 설치 (한 번만)

> 이 절은 **절차**입니다. 어디까지 했는지 기억하고 순서대로 밀어 주는 것은
> `hermes-install` 스킬("헤르메스 설치")이고, 그 스킬이 각 단계에서 여는 것이 이 절입니다.

### 0. 준비물 — `npm run doctor`

```
npm install
npm run doctor
```

이 기계에 있어야 할 것(node·git·python·LibreOffice 등)을 재고, **커밋·push 관문이
켜져 있는지**를 함께 봅니다. 기호는 넷입니다 — `✓` · `✗`(지금 막힘) · `⚠`(나중 단계에서
막힘) · `?`(못 쟀음). **`✗` 와 `?` 만 먼저 닫으면 됩니다.** `⚠` 는 대부분 문서 변환 도구라
1단계를 막지 않습니다. 고치는 명령은 `고치기:` 줄에 그대로 나옵니다.

**관문은 여기서 켭니다.** 훅은 저장소 안(`.githooks/`)에 있지만 git 은 훅을 복제하지
않으므로 clone 직후에는 꺼져 있고, **꺼져 있다는 신호가 어디에도 안 납니다** — 그대로 두면
승인 관문이 도는 줄 알고 일하게 됩니다. `고치기:` 줄을 실행한 뒤
`git config --get core.hooksPath` 를 다시 읽어 값이 들어갔는지 눈으로 확인하세요.
**값은 이 코드 저장소의 절대경로**여야 합니다 — 상대경로 `.githooks` 로 걸면 나중에 자료
저장소(별도 저장소·별도 설정)에 같은 함정으로 걸립니다.

### 1. Slack 앱 만들기

1. <https://api.slack.com/apps> → **Create New App** → **From a manifest**
2. 워크스페이스: **자기 팀 슬랙 워크스페이스** 선택
3. YAML 탭에 이 폴더의 `slack-app-manifest.yaml` 내용을 통째로 붙여넣기 → **Create**
4. **Install to Workspace** → 승인
5. **OAuth & Permissions** → *Bot User OAuth Token* (`xoxb-…`) 복사
6. **Basic Information** → *App-Level Tokens* → **Generate Token and Scopes**
   - 이름 `hermes-socket`, 스코프 `connections:write` → 생성 → 토큰(`xapp-…`) 복사

### 2. Anthropic API 키

<https://console.anthropic.com> → **API Keys** → 새 키 발급 (`sk-ant-…`)

### 3. 자료 저장소 만들기

**코드와 자료는 저장소가 둘입니다.** 코드(`hermes`)는 팀끼리 나눠 쓰고,
자료는 **팀마다 따로** 만듭니다 — 남의 자료 저장소를 받는 것이 아닙니다.

1. GitHub 에서 **private** 저장소를 하나 만듭니다 (예: `hermes-archive-<팀>`).
   비워 둡니다 — README 도 만들지 마세요.
2. 아무 폴더에나 clone 합니다.
   ```
   git clone https://github.com/<계정>/<자료저장소>.git
   ```
3. **코드 저장소 폴더에서** 씨앗을 넣습니다.
   ```
   npm run init-archive -- <clone 한 폴더>
   ```
   `.gitignore` 와 아카이브 틀이 만들어집니다. **`.gitignore` 가 특히 중요합니다** —
   없으면 나중에 첨부 원본 pdf·hwp 가 커밋에 섞여 들어갑니다.
4. 설정을 복사하고 자기 값으로 채웁니다.
   ```
   copy config.example.json <clone 한 폴더>\config.json     # 윈도우
   cp   config.example.json <clone 한 폴더>/config.json     # 맥·리눅스
   ```
5. 그 폴더에서 커밋하고 push 합니다.
   ```
   git add . && git commit -m "아카이브 틀" && git push
   ```

**대화·문서는 아직 비어 있습니다.** 봇은 뜨지만 "아직 안 채웠다"고 답합니다.
채우는 것은 **7단계**입니다 — 그전에 6단계(채널 초대)를 끝내야 합니다. 백필은 봇 토큰으로
읽으므로 **봇이 안 든 채널은 통째로 건너뜁니다.**

### 4. .env 파일 만들기

이 폴더에서 명령 프롬프트를 열고:

```
copy .env.example .env
notepad .env
```

세 줄에 위에서 복사한 값을 붙여넣고 저장합니다.

`HERMES_DATA_ROOT` 에는 **3단계에서 clone 한 폴더의 절대경로**를 적습니다.

### 5. 점검

검사 목적에 따라 실행 범위를 고를 수 있습니다.

| 명령 | 검사 범위 |
|---|---|
| npm run check:offline | 설정·토큰 없이 등록된 합성 입력·소스 검사만 실행 |
| npm run check:archive | 실제 자료·로컬 환경 의존 검사와 Python·셸 fixture 시험 |
| npm run check:live | 실제 Anthropic 모델 조회·유료 샘플 호출, Slack 인증·채널·히스토리 조회 |
| npm run check | 위 범위를 포함한 기존 전체 운영 준비 점검 |

**`check:live` 는 단가표를 그날 다시 확인해야 통과합니다.** `scripts/check-live-llm.js` 의
`VERIFIED_RATES` 는 사람이 공시 가격을 보고 손으로 적는 자리이고, 같은 파일의 `DAY` 가
**오늘 날짜와 다르면 멈춥니다**(`Stale price table`). 그 표가 `src/format.js` 의 `RATES` 와
갈려도 멈춥니다 — 유료 호출 한도를 재는 자리라 옛 단가로 통과시키지 않습니다. 돌리기 전에
공시 가격(`PRICE_SOURCE` 의 주소)을 보고 두 표를 맞춘 뒤 `DAY` 를 그날로 올립니다.

어떤 파일이 실행되는지는 `npm run check:offline -- --list` 등으로 확인합니다.
분류 원본은 `scripts/check-catalog.js`입니다. Python·셸 자동발견은 유지하며,
새 시험의 분류가 빠졌거나 등록된 파일이 없으면 실패합니다. 환경 의존성이 남은 기존
검사는 보수적으로 archive에 두었습니다. archive는 합성 시험만 실행하는 모드가 아니며,
일부 시험은 임시 파일·임시 Git 저장소를 만듭니다.

offline은 자식에게 운영 토큰·자료 경로와 시작 옵션을 넘기지 않습니다. 등록된 기본 실행을
검토한 범위의 계약이며 OS의 네트워크·파일 접근 차단을 제공하는 샌드박스는 아닙니다.
offline 종료코드는 통과 0, 실패 1, 미실행 포함 2입니다. archive/live의 성공은 선택한
범위만의 결과이며 전체 운영 준비 완료를 뜻하지 않습니다. 기본 check의 기존 종료코드와
선택 의존성 미설치 표시를 유지합니다.


```
npm install
npm run check
```

토큰 3종·아카이브·모델을 확인하고, **봇이 아직 초대되지 않은 채널 목록**을 보여줍니다.
그 목록은 **슬랙에 직접 물어본 채널**과 아카이브가 아는 채널을 합쳐서 냅니다 (2026-08-15 부터) —
예전에는 `.sync-state.json` 만 봐서 **한 번도 수집한 적 없는 새 채널이 원리상 안 떴습니다.**
`digest.skipChannels` 에 적힌 「안 다루기로 한 채널」은 초대 목록에서 빼고 그 아래 따로 적습니다.

**코드를 손봤을 때는 먼저 check:offline으로 회귀를 확인하고, 운영 준비는 전체 check로 확인합니다.** 맨 앞 `[1/6] 코드 일관성` 이 검사들을 함께 돌립니다
(개수는 여기 적지 않습니다 — 늘 때마다 낡습니다. 목록은 `scripts/check-catalog.js`가 원본입니다).
성격이 넷입니다 —

- **두 곳에 나뉜 같은 판정이 갈렸는지** (봇 판정(JS·파이썬) · 상황판 투영의 필드 ·
  색인 공통분의 해시 · 아침 목록 합치기 · 검색 낱말 쪼개기 · 위생 점검 DM 의 기준 줄)
- **검색이 실제로 그렇게 도는지** — 미초대 목록의 모집단 · 부분 일치 되돌림 ·
  첨부 「본문 수록」 표시 · 좁혔을 때 밖도 보는 안전망 · 엑셀 시트를 회차로 세지 않나.
  이 중 여럿은 **실제 아카이브를 상대로**
  돌아서, 아카이브가 자라 전제가 깨지면 「아카이브가 예상과 다릅니다」로 떨어집니다
  (몇 개인지는 여기 적지 않습니다 — 검사가 늘 때마다 낡습니다. 조용히 통과시키지도
  않습니다 — 통과와 못 잰 것은 다릅니다)
- **색인의 바닥이 자라지 않는 성질을 지키나** (2026-08-25 부터) — 접힘 줄이 종류 개수에
  안 비례하나 · 바닥의 다섯 조각이 원문 길이와 정확히 맞고 서로 독립인가. 둘 다
  순수 함수에 합성 입력을 먹여서 **파일도 네트워크도 안 씁니다**

- **손으로 적은 설정이 실물과 갈렸나** (2026-08-31 부터) — 채널을 이름으로 가리키는 설정
  줄이 개명으로 죽었는지. 죽은 줄은 **막으라고 적어 둔 것을 안 막는데** 에러가 안 나서,
  실제로 21일간 아무도 몰랐습니다

어느 쪽이든 **에러가 안 나고 숫자만 달라지는** 것들이라 사람이 알아채는 자리가
여기뿐입니다. 전부 네트워크가 필요 없어서 토큰이 없는 곳에서도 돌고,
하나가 실패해도 나머지는 계속 돌립니다. 목록은 `scripts/check-catalog.js` 한 곳에 있습니다.

### 6. 채널에 초대

**공개 채널은 한 번에 넣을 수 있습니다.**

```
python .claude/skills/doc-archive/scripts/join_channels.py            # 목록만 (기본)
python .claude/skills/doc-archive/scripts/join_channels.py --confirm  # 실제 참여
```

**`--confirm` 은 슬랙에 흔적을 남기는 쓰기 작업입니다** — 채널마다 "Hermes님이 채널에
참여함" 이 팀원 눈에 뜨고, 되돌리려면 채널마다 나가야 합니다. 그래서 기본은 목록만
보여주는 것이고, **목록을 사람이 보고 나서** `--confirm` 을 붙입니다.

**비공개 채널은 봇이 스스로 못 들어갑니다** — 그 채널에서 사람이 `/invite @Hermes` 를
입력해야 합니다. 초대되지 않은 채널은 요약과 최신 조회에서 빠집니다(아카이브 md 는
그대로 읽으므로 Q&A 는 계속 동작합니다).

초대가 끝나면 `npm run check` 를 다시 돌려 목록이 비었는지 확인하세요.

### 7. 과거 대화 채우기 — `npm run backfill`

여기까지 하면 봇은 뜨지만 아카이브가 비어 있어 "아직 안 채웠다"고 답합니다.

```

npm run backfill -- --channel <채널이름>          한 채널만

```

**인자 없이 부르면 막힙니다.** 인자 없는 실행이 전 채널 백필을 시작한 적이 있어서
`--all-channels` 를 명시해야 돌게 해 두었습니다. **채널 하나로 먼저 해 보고**
결과를 확인한 뒤 전체로 넘어가세요.

**5단계에서 짚은 미초대 채널이 여기서 물립니다** — 백필은 봇 토큰으로 읽으므로 봇이 안 든
채널은 통째로 건너뛰고, 그래도 **정상 종료합니다.** 끝에 `not_in_channel` 로 이름이 나오면
「0건」이 아니라 「못 읽었다」로 읽으세요.

**끝나면 채널별 「가장 오래된 날짜」 표가 나옵니다.** 슬랙 요금제에 따라 과거가 90일치만
남기도 하는데 그때도 백필은 정상으로 끝납니다 — 이 표를 보고 「여기까지가 전부다」를
확인하세요. 안 보면 그 상태가 「과거를 다 채웠다」로 잘못 읽힙니다.

**첨부 문서는 `doc-archive` 스킬이 따로 채웁니다.**

## 실행 — GCP VM 에서 상시 운영

봇은 **Google Cloud 의 `hermes` VM** 에서 systemd 로 24시간 돕니다. 노트북과 무관합니다 (절전·재부팅·세션 종료 어느 것도 영향 없음).

접속은 이 윈도우 PC 에서도 브라우저 [Cloud Shell](https://console.cloud.google.com) 에서도 같은 한 줄입니다:

```
gcloud compute ssh hermes --project=whk-hermes --zone=us-west1-b --tunnel-through-iap
```

> **`hermes`·`whk-hermes`·`us-west1-b` 는 TEC 프로젝트금융 팀의 VM 이름·프로젝트 ID·존입니다**
> — 다른 팀은 자기 값으로 바꾸세요. 무엇을 바꿔야 하는지는 `deploy/README.md` 「먼저」 절에
> 표로 있습니다. 봇 소스와 `config.json` 에는 이 값들이 없습니다.

> **`--tunnel-through-iap` 를 빼지 마세요.** 22번 포트는 방화벽 `allow-iap-ssh-hermes` 로 IAP
> 대역(`35.235.240.0/20`)만 열려 있어 **직접 SSH 는 원래 안 됩니다** — 터널이 정상 경로입니다.
> 빼고 돌리면 `FATAL ERROR: Network error: Connection timed out` 이 납니다(2026-08-29 실측).
> 사용자는 `wkimclementia` 가 아니라 **`TY`** 입니다(프로젝트 메타데이터에 키 2개가 있고 이 PC 의
> `~/.ssh/google_compute_engine` 과 맞는 쪽이 `TY`).

> **2026-08-12 에 적어 둔 우회는 걷어냈습니다 (2026-08-29).** 그때는 이 PC 에서 위 명령이
> `plink.exe exited with return code [1]` · `Remote side unexpectedly closed network connection` 으로
> 실패해, 터널을 따로 열고(`start-iap-tunnel … localhost:2222`) OpenSSH 로 붙으라고 적어 두었습니다.
> **8/29 에 이 PC 에서 위 한 줄이 그대로 됐습니다** — `--command="hostname; uptime; systemctl is-active hermes"`
> 로 exit 0, 터널을 따로 열지 않았습니다. **다만 「고쳤다」가 아닙니다** — 8/12 의 그 메시지가
> 무엇이었는지는 못 찾았고, SSH 에 닿는 유일한 경로가 지금 멀쩡해서 **재현할 방법도 없습니다.**
> 같은 메시지가 또 나오면 그때 봅니다. 백로그는 워크스페이스 할 일 파일에 있습니다.
>
> 손으로 터널을 열 일이 생기면 쓰고 나서 **닫으세요** — 2222 를 계속 잡고 있습니다.

| 하고 싶은 것 | 명령 |
|---|---|
| 실시간 로그 | `journalctl -u hermes -f` |
| 상태 확인 | `systemctl status hermes` |
| 재시작 | `sudo systemctl restart hermes` |
| 아카이브 즉시 동기화 | `sudo systemctl start hermes-archive-pull` |

구축·운영 전체는 [`deploy/README.md`](deploy/README.md) 참조.

### 고쳤을 때 — 갈래가 셋

**무엇을 고쳤느냐로 갈립니다.** 셋 다 커밋·push 는 사람 승인입니다.

설정이 계속 돕니다.

**끝나면 `npm run deployed`.** VM 이 도는 것이 지금 원격과 같은지, **받아만 놓고 재시작을
안 했는지**를 봅니다 — 그 경우는 해시가 맞아서 `git log` 로는 안 보입니다.
**읽기만 하고 아무것도 안 바꿉니다**(pull 도 restart 도 사람이 합니다).
`.env` 에 `GCP_VM`·`GCP_PROJECT`·`GCP_ZONE` 이 없으면 그 검사는 「못 쟀습니다」로 건너뜁니다.

> **✗ 가 늘 고장은 아닙니다.** 검사·문서만 고친 커밋은 봇 동작을 안 바꾸므로 일부러 VM 에
> 안 붙이기도 합니다. 그때도 「VM 이 옛 코드로 돕니다」가 뜹니다 — 검사는 사실을 말할 뿐이고,
> 붙일지는 사람이 정합니다.

> **노트북에서 `npm start` 를 돌리지 마세요.** 같은 토큰으로 둘이 붙으면 질문마다 두 번 답하고 요약도 두 번 나갑니다. 프롬프트를 시험할 때는 `--dry` 옵션을 쓰세요(아래 "요약을 지금 바로 돌려보기").

```
@Hermes 사업장나 PF 잔액 얼마야?
  → (답변)
@Hermes 그럼 만기는?
```

**단, 봇이 쓴 앞 발언은 안 봅니다** (Hermes 자신이든 다른 봇이든, 2026-08-12 부터). 아카이브에 봇 글을 넣지 않는 것과 같은 규칙입니다 — Hermes 답변은 2차 가공물이라, 맥락으로 넣으면 한 번 잘못 요약한 숫자가 다음 답변에 그대로 이어집니다. 사람의 앞 질문은 남으므로 위 예처럼 「무엇의 만기인지」는 그대로 풀립니다. 다만 **답변에서만 나온 이름**(`"거기 잔액은?"` 의 '거기')은 봇이 도구로 다시 찾으므로 조금 느리고, 못 찾으면 되물을 수 있습니다. 그럴 때는 이름을 적어 물으세요.

봇이 낀 적 없는 스레드(사람들끼리의 업무 논의)에서 부르면 그 대화가 그대로 맥락이 됩니다. 앞 대화는 최근 20건·4,000자까지 싣고 넘치면 **앞을 자릅니다**(`limits.threadContextMaxMessages` · `threadContextMaxChars`). 앞 대화에도 **비공개 가리기가 걸립니다** — 공개 채널 스레드에 누가 `#비공개가` 이야기를 적어 두었으면 그 발언은 맥락에서 통째로 빠집니다.

**DM 에서도 답이 스레드로 옵니다** (2026-08-06 부터). 물어보신 그 메시지 밑에 답이 달리니, 이어 물을 것은 그 스레드에 쓰시면 됩니다. DM 평문(그냥 연달아 보낸 메시지)끼리는 여전히 안 이어집니다 — 어디부터 어디까지가 한 대화인지 정할 방법이 없어서입니다.

> 그전까지 DM 은 평문으로 답했습니다. 그러면 이어 물으려고 스레드를 열 자리가 **봇 답변 밑뿐**이라 스레드 뿌리가 봇 자기 글이 되는데, 봇 답변은 맥락에 안 싣기로 했으므로 **DM 첫 후속 질문은 앞 대화가 늘 0건**이었고 원래 질문은 스레드 밖이라 영영 안 보였습니다. 2026-08-06 실측(`logs/qa-*.jsonl` 의 `threadContext` 가 0)으로 확인하고 채널과 같게 맞췄습니다.

**답변 끝에 `— 출처: #채널명` 이 붙습니다.** 출처가 없으면 근거를 찾지 못하고 색인만 보고 답한 것이니 그대로 믿지 마세요.

## 자주 바꾸는 설정 — `config.json`

**요약 시각**

```json
"daily":  { "enabled": true, "cron": "30 17 * * *" },
"weekly": { "enabled": true, "cron": "0 16 * * 5" }
```

`분 시 일 월 요일` 순서입니다. 요일은 0=일요일 … 5=금요일.
예) 매일 오후 6시 → `"0 18 * * *"` · 요약 끄기 → `"enabled": false`

일일 요약이 **평일만이 아닌 것은 의도입니다** — 주말만 빼면 그 대화가 어떤 요약에도 안 들어갑니다.

**요약 전 마감** — 일일 요약이 그날 첨부 문서까지 싣게 하는 두 시각입니다.

```json
"healthPre": { "enabled": true, "cron": "0 16 * * *", "scanDays": 2 },
"ingestPre": { "enabled": true, "cron": "0 17 * * *" }
```

- **16:00 마감 점검** — 최근 `scanDays` 일 안에 올라온 첨부 중 아직 md 로 안 들어간 것을 본인 DM 으로. **첨부만 봅니다** (동기화 밀림은 09:00 회차 담당 — 같은 경고를 하루 두 번 보내면 곧 안 읽게 됩니다). 이상 없으면 안 보냅니다
- **17:00 자동 반영** — `git pull` 로 그 사이에 사람이 push 한 문서 커밋을 VM 에 들이고, 대화 원문도 요약 시각에 붙입니다. 요약 대조와 수정·삭제 대조는 **끕니다**(07:00 회차 담당). 모델 비용이 두 배가 되고 같은 후보를 하루 두 번 받게 되기 때문입니다
- 사람이 할 일은 그 사이입니다 — 16:00 DM 을 받으면 `doc-archive` 를 돌리고 **커밋·push 승인**까지 마쳐야 17:00 회차가 그것을 가져갑니다. 안 해도 요약은 정상적으로 나가고, 하단에 `미반영 N건` 이 붙습니다
- 시각을 바꿀 때는 **순서를 지키세요**: 마감 점검 → (사람) → 자동 반영 → 일일 요약. 마감 점검이 요약에 너무 붙으면 돌릴 시간이 없고, 자동 반영이 요약보다 뒤면 그날 문서가 안 실립니다

**일일 요약에 싣는 문서 분량** — `limits` 아래에 있습니다.

```json
"digestDocMaxChars": 15000, "digestDocPerDocChars": 3000
```

총 상한을 넘긴 문서는 **빠지지 않고 요지만** 실립니다. `perDoc` 은 문서 하나가 총 상한을 다 먹지 못하게 하는 몫입니다. 문서는 **올라온 시각이 늦은 것부터** 채우므로, 상한에 걸리면 그날 가장 일찍 올라온 것이 밀립니다.

두 값 다 2026-08-10 에 올렸습니다(8,000/2,500 → 15,000/3,000). 그날 문서 5건이 8,000자를 다 먹어 어느 사업장 일일업무일지가 제목만 실렸고, `perDoc` 2,500자는 그 문서의 분양현황 표에서 **합계 행(2,571자 지점) 앞을 끊어** 요약이 아파트 소계만 쓰게 만들었습니다. 모델이 볼 수 없는 값을 쓰라고 하면 지어내므로, 프롬프트보다 이 몫을 먼저 봐야 합니다.

**아카이브 위생 점검** — 아카이브가 얼마나 밀렸는지 알려주는 알림입니다.

```json
"health": { "enabled": true, "cron": "0 9 * * *", "scanDays": 60, "syncWarnDays": 7, "docWarnCount": 1 }
```

봇은 아카이브를 읽기만 하고, 새 내용을 넣는 일(`slack-sync`·`doc-archive`)은 사람 손입니다.
며칠 안 돌리면 봇의 근거가 낡는데 **그 사실이 아무 데도 드러나지 않습니다** — 봇은
"아카이브에 없습니다"라고 정상적으로 답합니다. 이 알림이 그걸 대신 말해줍니다.

- 대화 동기화가 `syncWarnDays` 넘게 밀렸으면 알리고, `liveFetchMaxDays - 2`(현재 12일)를
  넘으면 경고합니다. **14일을 넘긴 구간은 실시간 조회로도 안 메워져 봇이 아예 못 봅니다**
- 미변환 첨부를 `scanDays` 범위에서 세어 채널별로 알려줍니다
- **사람이 「이번엔 아니다」로 정한 것은 빼고 셉니다** (2026-08-09 부터). `doc-archive` 의
  `decide.py --later` 가 `.doc-state.json` 의 `deferred` 에 적고, 위 두 숫자에서 빠집니다.
  안 빼면 줄지 않는 숫자가 매일 와서 곧 알림 전체를 안 읽게 됩니다. **대신 만기(`until`)가
  지나면 저절로 다시 세어집니다** — 미뤄 둔 것을 잊을 수 없게. 보류가 있으면
  `⏸ 보류 N건 (가장 이른 만기 M/D)` 한 줄이 붙는데, **보류만 있고 다른 이상이 없으면
  DM 을 만들지 않습니다**(보류는 어긋남이 아니라 정한 상태입니다).
  판정은 `src/ingest/util.js` 의 `activeDeferred` 와 `scripts/fetch_slack_files.py` 의
  `active_deferred` 가 **같아야 합니다** — 갈리면 한쪽은 「N건 남음」, 한쪽은 「0건」입니다.
  JS 쪽은 **`util.js` 한 곳뿐입니다**(2026-08-10 부터) — 09:00 위생 점검과 07:00 자동 반영
  보고가 그 함수를 함께 부릅니다. 전에는 `archive-health.js` 에만 있어서 07:00 보고가 안
  걸렀고, 「미뤄 두면 만기까지 조용합니다」라고 안내해 놓고 다음 날 아침에 그 건의 이름을
  다시 불렀습니다
- **팀이 `[공개]` 로 승인했는데 봇은 아직 막고 있는 자료**를 알려줍니다 (2026-08-07 부터).
  승인은 문서가 아카이브에 들어간 **뒤에** 나오는데, 그때는 `doc-archive` 수집이 그 파일을
  이미 다룬 것으로 보고 태그를 읽기 전에 건너뜁니다 — 스킬을 다시 돌려도 안 뜹니다.
  받으면 **`doc-archive` 의 「승인 반영」**(`scripts/apply_approvals.py --apply`)을 돌리세요 —
  그 md 의 메타 두 줄(`열람: 공개` + `공개승인`)을 고칩니다. 재변환하면 같은 문서가 두 벌
  쌓입니다. **건별로 고르되 번호가 아니라 이름으로 고릅니다** — `--only "채널/파일명"`.
  번호는 실행할 때마다 다시 매겨져, 목록을 본 뒤 명령을 치는 사이에 승인이 하나 늘면 다른
  문서를 엽니다(2026-08-10 수정). 조각이 둘 이상 걸리면 아무것도 안 열고 멈춥니다.
  `--apply` 만
  주면 걸린 승인을 전부 여는데, 그 순간 그 문서들이 팀 전원의 답변 근거가 됩니다. 첨부를 세느라 어차피 매일 스레드를 훑으므로 슬랙 호출은 안 늡니다.
  `scanDays`(60일) 밖의 옛 파일에 달린 승인은 못 봅니다
- **재기 전에 `git pull` 로 맞춰봅니다** (2026-08-20 부터, `syncForRead()`). 로컬 저장소는
  최대 15분 밀린 상태로 있을 수 있어(자동 반영이 15분 간격), 그대로 재면 이미 처리된 것을
  다시 밀렸다고 알릴 수 있습니다. DM 꼬리에 붙는 `기준: HEAD <해시> · HH:MM:SS 최신화` 가
  그때 무엇을 보고 셌는지입니다. **최신화가 안 되면 다른 이상이 0건이어도 DM 이 옵니다** —
  `⚠️ 최신화 실패 … origin 에 안 받은 커밋이 N개 있습니다` 로 시작합니다. 손잡이는
  `digest.health.syncBeforeCheck`(기본 `true`) — 끄면 **pull 만 멈추고 낡음 표시는 그대로
  돕니다**(끄면 알림 전체가 조용해지는 것을 막으려는 것입니다). **손 실행(`npm run health`)은
  pull 을 하지 않습니다** — 사람 PC 에서도 도는 명령이라 남의 작업 트리를 안 건드립니다.
  다만 **`git fetch` 는 pull 없이도 돕니다** — 뒤처짐을 재려고 원격에 한 번은 닿아 보는
  것이라, 작업 트리는 그대로여도 로컬의 `origin/main` 참조는 갱신됩니다.
  **원격이 반쯤 끊겨 응답이 없으면 60초에 끊습니다** (`git pull`·`git fetch` 각각).
  그때 DM 은 `⚠️ 최신화 실패 (60초 안에 응답 없음 · git pull)` 로 옵니다 — 상한에 걸리면
  git 이 stderr 를 안 남겨서, 이 문구가 없으면 잠금·인증 실패와 글자가 같아집니다
  (2026-09-07 부터). 예약 회차는 pull 이 먼저 서고 fetch 가 한 번 더 서므로 **최대 120초**
  기다립니다.
- **이상이 없으면 보내지 않습니다.** 매일 "이상 없음"이 오면 곧 안 읽게 되고,
  그때부터는 진짜 경고도 같이 안 읽힙니다
- 요약과 달리 **항상 본인 DM 으로** 갑니다 (`deliverTo` 와 무관). 내부 운영 상태라
  요약 채널(`digest.channelId`)에 올리면 팀 전원에게 보입니다

**전달처를 DM 에서 채널로**

```json
"deliverTo": "channel",
"channelId": "C0EXAMPLE03"
```

채널 ID 는 슬랙에서 채널 → 우클릭 → 링크 복사 → 주소 끝의 `C…` 부분입니다.

**대화 로그** — Hermes 와 오간 것을 전부 남길지. 자세한 것은 아래 「대화 로그」 절에.

```json
"log": { "enabled": true, "path": "hermes-log", "rawPath": "logs" }
```

**두 값의 기준이 다릅니다** — `path`(사람이 읽는 md)는 **자료 저장소** 기준이고,
`rawPath`(원본 jsonl)는 **코드 저장소** 기준입니다(`src/config.js` 의 `LOG_DIR`·`LOG_RAW_DIR`).
`path` 에 `../` 로 시작하는 값을 넣으면 로그가 **저장소 밖**에 쌓이는데 **에러가 안 납니다.**
2026-08-31 이사 전에는 이 예시가 두 단계 위로 올라가는 값이었고, 그대로 넣으면 홈 폴더
아래에 쌓입니다(실측으로 확인했습니다). **저장소 안의 폴더 이름만 적으세요.**

`enabled: false` 로 두면 기록이 통째로 꺼집니다 (이미 쌓인 원본은 그대로 남습니다).

**비용을 줄이려면** — Q&A 만 낮춥니다. 요약은 그대로 두는 편이 낫습니다. 두 달 로그에서
정기 발송·점검이 쓴 돈은 전체의 5%뿐이라 거기서 아낄 것이 거의 없습니다.

손잡이가 둘입니다. **모델을 바꾸거나, 같은 모델에서 생각 깊이(`effort`)를 낮추거나.**

```json
"qa": { "id": "claude-sonnet-5", "effort": "high", "maxTokens": 8000 }
"qa": { "id": "claude-opus-5-5", "effort": "medium", "maxTokens": 16000 }
```

`effort` 쪽은 2026-09-08 에 (Opus 5 기준 — 2026-09-28 부터는 Opus 5.5) 같은 질문 7개를 `high`·`medium` 으로 번갈아 돌려 쟀습니다 —
핵심 숫자는 6개에서 같았고 시간 40%·출력 토큰 43%가 줄었습니다. **갈린 자리가 하나
있었습니다**: 여러 판이 쌓인 자리에서 옛 회차 값을 결론으로 쓰는 것이라, 색인 줄의
기준일 표기와 `qa.md` 「여러 판이 있을 때」 절로 함께 막았습니다(`8736372`). 그 뒤로는
`medium` 도 최신 판을 골랐지만 도구를 한 번 더 불러 **절감폭이 출력 토큰 −43% 에서
−22% 로 줄었습니다.** 낮추기 전후를 재려면 `npm run ask` 로 같은 질문을 양쪽에서
돌려 답 끝의 `logUsage` 줄을 대봅니다.

요약 쪽을 내리는 것은 권하지 않습니다 — 일일 요약을 `medium` 으로 돌린 회차가
`daily.md` 가 제목까지 고정해 둔 「올라온 문서」 절을 통째로 빼먹었습니다.

바꾼 뒤에는 **커밋·push 하고 VM 에서** 받아 재시작해야 반영됩니다.

```
sudo systemctl start hermes-archive-pull    # 바뀐 설정을 받아오고
sudo systemctl restart hermes               # 재시작
```

**소스(`src/`)를 고쳤으면 위 첫 줄로는 안 옵니다.** 자동 pull 은 **자료 저장소만** 받습니다 —
`config.json` 은 거기 있어 따라오지만 코드는 사람이 받아야 합니다.

```
sudo -u hermes git -C /opt/hermes/code pull   # 코드를 받아오고
sudo systemctl restart hermes                 # 재시작
```

(아카이브 md 는 재시작 없이 반영됩니다. 소스와 `config.json` 만 재시작이 필요합니다.)

## 요약이 안 왔을 때

**DM 을 먼저 보세요.** 실패하면 본인 DM 으로 알림이 갑니다 (2026-08-06 부터).

- **DM 이 있으면** — 실패한 것입니다. 사유·시각·요청 ID 와 다시 보내는 명령이 함께 적혀 있습니다
- **DM 이 없으면** — 그날 대화가 0건이라 안 보낸 정상입니다 (`minMessages`)

이 구분이 없던 동안은 「조용한 것」이 두 가지 뜻이라 VM 로그를 열기 전에는 알 수 없었습니다.

실패한 회차는 **다시 보내지 않습니다 — 사람이 돌립니다.** 다만 **못 보낸 구간은 안 없어집니다**:
일일 요약의 구간은 "직전에 **실제로 나간** 회차 이후 ~ 지금" 이라(`slack-live.js` 의
`dailyWindow`), 손으로 돌리든 다음 날 회차가 돌든 못 보낸 데부터 함께 실립니다.
명령은 아래 「요약을 지금 바로 돌려보기」와 같습니다.

> 2026-09-03 까지는 구간이 "지금부터 24시간 전"이라, 한 회차가 죽으면 **그 24시간이 어떤
> 요약에도 안 들어갔습니다.** 다음 날 회차는 자기 몫만 싣고 팀에게는 끊김 없이 이어진 것처럼
> 보입니다 — 2026-09-01 17:30 회차(`authentication_error`)가 그랬고, 08-31 17:30 ~ 09-01 17:30
> 은 지금도 비어 있습니다. **상한은 48시간입니다** (`digest.daily.maxHours`, WHK 결정
> 2026-09-03) — 「평소는 24시간 그대로, 한 회차 실패했을 때만 메운다」는 뜻입니다. 정상이면
> 창은 정확히 24시간이고, 한 회차가 죽으면 48시간이 되어 빠진 하루를 함께 싣습니다.
> **두 회차 연속으로 죽으면 가장 오래된 24시간은 잘려 잃습니다** — 그 대신 한 요약이
> 며칠치로 부풀어 그 회차마저 죽는 것을 막습니다. 잘린 구간은 VM 로그에 한 줄 남깁니다.

**과부하는 자동으로 넘깁니다.** 요약 생성 호출이 `overloaded_error` 를 만나면 **즉시 · 1분 뒤 ·
3분 뒤** 다시 걸고, 그래도 안 되면 **대체 모델**(`models.fallback`)로 한 번 더 갑니다. 그래서
요약이 최대 4분 늦게 올라올 수 있습니다 — 늦는 것보다 아예 안 나가는 쪽이 나쁘다고 봤습니다.
Q&A 는 사람이 앞에서 기다리는 자리라 이 대기를 쓰지 않습니다. 대기 간격은 `claude.js` 의
`DIGEST_RETRY_WAITS_MS` 입니다.

> 2026-08-06 17:30 회차가 이것 하나로 통째로 안 나갔습니다. 재료 수집은 3초 만에 정상으로
> 끝났고 요약문을 쓰는 호출에서만 걸렸는데, 그때는 **재시도가 한 번도 걸리지 않았습니다.**
> SDK 기본 재시도는 HTTP 응답의 상태코드를 보고 정하는데, 과부하가 응답이 아니라 **이미 열린
> 스트림 안의 `event: error`** 로 왔기 때문입니다. 13분 뒤 손으로 돌린 회차는 첫 시도에
> 성공했습니다.

`4xx`(잘못된 요청)는 다시 걸어도 같으므로 기다리지 않고 즉시 실패합니다.

## 아카이브 자동 반영 (ingest)

> **켜져 있습니다 — 매일 07:00** (`config.json` 의 `digest.ingest.enabled: true`, 2026-08-04 부터).
> **하루 두 번입니다** — 17:00 에 한 번 더 돕니다 (2026-08-06 부터, 위 「요약 전 마감」).
> 17:00 회차는 요약 대조와 수정·삭제 대조를 끄고 원문만 넣습니다.
> 설정을 바꿨으면 **반드시 `sudo systemctl restart hermes`** 하세요. `config.json` 은 기동할 때만
> 읽으므로, 재시작 전에는 파일만 바뀌고 예약은 그대로입니다 (기동 로그의 예약 목록으로 확인).

`slack-sync` 스킬이 하던 **원문 반영**을 봇 토큰으로 무인 수행합니다. 스킬은 Slack MCP
커넥터(개인 인증)를 써서 사람이 붙어 있어야 돌지만, 같은 일이 봇 토큰으로 전부 됩니다.

```
npm run ingest -- --dry --skip-summary   파일·git·모델 전부 안 건드리고 화면에만
npm run ingest -- --dry                  요약 대조까지 (모델 호출 있음, 채널당 약 $0.05)
npm run ingest -- --dry --skip-summary --no-edit-scan   17:00 회차와 같은 조합
npm run ingest                           실제 반영 + 커밋 + push + DM
```

**원문만 넣습니다.** 채널 md 첫머리의 요약(`핵심 쟁점` 줄, `## 자금 구조 요약` 표)은
건드리지 않고, 요약과 어긋나는 곳을 찾아 **DM 으로 보고만** 합니다. 원문은 슬랙을 그대로
옮기는 것이라 틀릴 여지가 없지만, 요약은 틀리면 봇이 그 숫자를 근거로 답합니다.

### 슬랙에서 고쳐지거나 지워진 것 (2026-08-05 부터)

증분 조회는 **작성 시각**으로 거릅니다. 본문을 고쳐도 작성 시각은 안 변하므로, 이미 반영된
메시지는 두 번 다시 조회 범위에 안 들어옵니다. 삭제는 "사라졌다"는 신호를 볼 자리가 없습니다.
그래서 전에는 슬랙 화면과 아카이브가 조용히 갈라졌습니다.

이제 같은 30일 구간(`limits.threadLookbackDays`)에서 **md 와 슬랙을 대조해** 찾아냅니다
(`ingest/slack-archive.js` 의 `detectChanges`). 끄려면 `digest.ingest.reportEdits: false`.

- **찾아서 알리기만 하고 고치지 않습니다.** 원문을 무인으로 바꾸면 되돌릴 자리가 없고,
  슬랙 원문을 따라가는 것과 사람 판단으로 정정하는 것을 기계가 못 가릅니다
- 기록을 남기지 않고 그때그때 맞춰 보므로 **안 고치면 다음 날도 계속 잡히고, 고치면 저절로
  조용해집니다.** 밀린 것은 「미반영 N건」 한 줄로 계속 알립니다
- **대조에 작성자 이름을 안 씁니다** — 슬랙 표시 이름은 바뀌는데 md 에는 기록 당시 이름이
  박혀 있어, 이름으로 맞추면 이름 한 번 바꾼 사람의 30일치가 전부 "지워졌다"로 잡힙니다.
  대신 같은 1분 안에 메시지가 둘 이상이면 대조에서 빠집니다
  (2026-09-16 실측 1,842건 중 188건, 10.2%. **잰 날짜를 같이 적습니다** — 아카이브가
  커지면 이 값이 바뀌는데, 날짜가 없으면 낡은 줄 모르고 계속 인용됩니다)
- 한 채널에서 `limits.editScanMaxFindings`(10건)를 넘게 잡히면 목록 대신 경고만 냅니다 —
  하나씩 지워진 것이 아니라 보존 기간이 짧아졌거나 포맷이 어긋난 경우입니다
- 감지가 터져도 **아카이브 반영은 계속합니다.** 부수 기능이 본업을 막지 않게
- 반영할 목록은 `slack-export/.pending-edits.json` 에 쌓입니다. **봇은 이 파일을 안 읽습니다**

### 순서

```
git pull → 대화 수집·삽입 → 요약 대조 → 관문 → commit·push → DM
              │                            └ 실패하면 reset --hard 후 DM
              └ 어느 단계에서 멈춰도 🚨 DM (git pull 이 막힌 경우 포함)
```

**새 대화가 0건이어도 커밋합니다.** `.sync-state.json` 의 `last_sync` 는 새 메시지가 없어도
매번 새로 쓰이므로, 그날 커밋을 안 남기면 작업 트리가 더러운 채로 남고 **다음 날 `git pull`
단계에서 멈춥니다.** 그 커밋은 `동기화 시각만 갱신 (새 대화 없음)` 으로 남고 **DM 은 안 갑니다** —
매일 "이상 없음"이 오면 곧 진짜 경고도 같이 안 읽힙니다. 그래서 **돌았는지를 DM 유무로
판정하면 안 되고**, `git log --author=Hermes` 나 VM 로그로 봐야 합니다.

### 관문 — 통과해야만 커밋합니다

포맷 계약이 깨져도 **에러가 나지 않습니다.** 검색이 조용히 0건이 되고 봇은 "아카이브에
없습니다"라고 정상적으로 답합니다. 그래서 "넣었다"가 아니라 **"봇에게 보인다"**까지 봅니다.

| 검사 | 무엇을 막나 |
|---|---|
| 요약이 메시지 블록에 섞임 | 2026-08-02 사고 — 요약표가 사람 발언으로 인용됨 |
| 봇이 쓴 글이 아카이브에 들어감 | `checkNoSelfAuthored` — 봇이 자기 요약을 원본 근거로 삼게 됨 (다른 봇의 글도 함께 막음, WHK 결정 2026-08-12) |
| 문서 트리에 원본 혼입 | 저장소에 바이너리가 영구 기록됨 |
| 슬랙 아닌 출처가 섞임 | `checkNonSlackSources`(`.doc-state.json` 의 `local_files`) — 근거가 슬랙이 아니게 됨 (WHK 결정 2026-08-03) |
| `verify_format.py --all` | 문서 md 포맷 계약 + **회차 헤더 없이 놓인 본문** (2026-08-04 추가) |
| 넣은 메시지가 한 건으로 잘리나 | `splitMessages` 가 못 자르면 봇이 못 찾음 |

「문서 트리에 원본 혼입」은 **2차 방어선입니다.** 자료 저장소 `.gitignore` 의 `documents/**`
네 줄이 이미 그 아래를 `.md` 와 `.doc-state.json` 만 추적하게 막고 있어서,
이 검사는 `git add -f` 로 강제 추가한 경우에만 발동합니다. 검사가 안 걸린다고
"원본이 없다"가 아니라 **"gitignore 가 먼저 막았다"** 일 수 있습니다.

관문이 실패하면 `rollback()` 이 시작 커밋으로 되돌립니다. `reset --hard` 는 트리
전체에 걸리지만 `git clean` 은 **아카이브 경로에만** 겁니다 — 경로 밖의 작업물은
남습니다(2026-08-04 실측 확인).

볼 수 없습니다.

> **검색이 스스로 좁혔으면 도구 줄 꼬리에 `[좁힘: …]` 이 붙습니다**(좁혔다가 빈손이라
> 되돌렸으면 `[넓힘: …]`). 값이 있을 때만 붙으므로 옛 기록의 렌더는 안 바뀝니다.
> 이것이 없으면 로그만 보고 **「좁혀서 못 찾은 것인지 원래 없는 것인지」를 못 가릅니다** —
> 자동 좁히기는 모델이 보낸 인자가 아니라 도구 함수 **안에서** 일어나기 때문입니다
> (2026-09-12).

**왜 필요했나.** 봇 답변은 대화 아카이브에 **일부러** 넣지 않고(자기 요약을 원본 근거로
삼는 것을 막는 규칙), DM 은 아카이브 수집 대상 자체가 아닙니다. 그래서 지금까지 Hermes 와
오간 대화는 journal 에 잘린 한 줄로만 남고 답변 본문은 어디에도 없었습니다.

### 자리가 둘입니다

| | 자리 | 언제 | git |
|---|---|---|---|
| **원본** | 코드 저장소의 `logs/qa-YYYY-MM.jsonl` | 답변 직후 즉시 | 추적 안 함 |
| **읽는 자리** | 자료 저장소의 `hermes-log/YYYY-MM.md` + `index.md` | 매일 07:00 자동 반영이 렌더 | 커밋·push |

나눈 이유: 답변 직후 저장소 안에 바로 쓰면 작업 트리가 더러워지고, 다음 자동 반영의
`syncBeforeWork()` 가 거기서 멈춰 **대화 반영이 통째로 죽습니다.** 렌더를 자동 반영 **안**
(`git pull` 이후)에 두면 그 검사를 이미 지난 뒤라 안전합니다.

그래서 **저장소에 보이는 것은 하루 지연**입니다. 당일 것을 보려면 VM 의 jsonl 을 보세요.

```
tail -1 /opt/hermes/code/logs/qa-$(date +%Y-%m).jsonl
npm run log:render               # 무엇이 바뀌는지만 (파일 안 씀)
npm run log:render -- --print    # 렌더 결과 전문
```

> `npm run log:render -- --write` 는 md 를 실제로 씁니다. **쓴 뒤 커밋하지 않으면 다음
> 자동 반영이 멈춥니다.** 평상시에는 손으로 돌릴 일이 없습니다.

### 이 트리는 봇의 근거가 아닙니다

`archive.js` 는 `CHANNELS_DIR`, `documents.js` 는 `DOCS_DIR` 만 읽습니다.
자료 저장소의 `hermes-log/` 를 읽는 코드는 없고, 앞으로도 넣으면 안 됩니다 — 넣는 순간
봇이 자기 답변을 원본 근거로 삼고, 한 번 잘못 요약한 숫자가 원문처럼 굳습니다.

렌더는 **멱등**입니다. 같은 jsonl 이면 몇 번을 돌려도 같은 md 가 나오고, 바뀐 것이 없으면
파일을 건드리지 않아 헛커밋이 생기지 않습니다. md 를 손으로 고쳐도 다음 렌더가 덮어씁니다 —
고칠 것이 있으면 원본 jsonl 을 고치세요.

뒤가 5분(도구 결과)** 입니다. 캐시가 안 맞은 회차에는 사유도 함께 찍힙니다
(`· 캐시 미스: system_changed (27000 토큰)`) — `cache-diagnosis` 베타로 API 가 알려주는 값입니다.

**그 사유는 대화 로그에도 실립니다** (2026-08-11 부터). 건별로는 자료 저장소의 `hermes-log/YYYY-MM.md`

**맞은 회차에는 줄을 안 씁니다** — 대부분이 맞아야 정상이라, 0을 매 건 적으면 정작 미스가 난 건이
눈에 안 들어옵니다. 전에는 이 값이 VM 콘솔에만 있어서 판정하려면 `journalctl` 을 뒤져야 했고,
클라우드 예약 실행에서는 VM 에 못 붙어 사실상 사람이 그 자리에 앉아 있을 때만 볼 수 있었습니다.

**대조 기준은 「앞 질문의 마지막 응답」입니다** (`claude.js` 의 `previousMessageId`). API 는
`diagnostics.previous_message_id` 로 준 요청과 이번 요청을 견줘 사유를 내는데, 예전에는 첫 회차에
`null` 을 줬습니다. **색인을 다시 쓰는 것이 바로 그 첫 회차라, 정작 알고 싶은 자리에 사유가 한 번도
안 붙었습니다** — 2026-08-11 실측으로 도구를 8회 도는 질문도 사유가 빈 배열이었습니다. 앞 질문의
응답 ID 를 주도록 바꾸니 그 자리에서 사유가 나옵니다 (색인을 실제로 바꾼 뒤 물어
`system_changed` 21,577토큰을 확인).

읽는 법 — 사유는 둘인데 **성격이 다릅니다.** `system_changed` 는 **색인이 실제로 바뀐 것**(커밋이
들어왔다)이라 진짜 미스이고 배치·주기로 줄일 여지가 있습니다. `previous_message_not_found` 는
**미스가 아니라 진단 실패**입니다 — 대조할 앞 요청을 못 찾았다는 뜻이라 그 회차는 캐시가 맞았는지
안 맞았는지를 **모릅니다**. 그래서 `cache_missed_input_tokens` 도 0으로 오는데, 그 0은 손해가
0이라는 뜻이 아니라 **못 쟀다**는 뜻입니다. 뒤엣것은 1시간 만료·축출뿐 아니라 **봇이 재시작해 기준이
없는 경우**에도 납니다(기준은 프로세스 메모리에만 있습니다). 넘기는 값은 실제로 받은 `msg_…` id
뿐입니다 — 모양이 틀린 값은 400 이고, 모양이 맞는데 없는 id 는 정상 응답에
`previous_message_not_found` 로 돌아옵니다(둘 다 실측).

**표는 그 둘을 갈라 셉니다** (2026-08-28 부터, `convo-log.js` 의 `cacheStats`). 그전에는 한 칸에
세어서 **줄일 수 있는 몫이 다섯 배로 부풀어 보였습니다** — 8월 표가 「문답 129건 중 16건」으로
읽혔는데, 실제 미스는 3건(75,271토큰 ≈ $0.72, 그 달 $90.77의 0.8%)이었습니다. 어긋난 곳이 둘입니다.
**① 분모** — `cacheMiss` 필드는 커밋 `8468500`(배포 2026-08-12 09:09) 부터 붙었고 그 전 회차에는
필드 자체가 없는데, 그것들이 「맞았다」쪽에 세어졌습니다. 이제 **필드가 있는 회차만** 분모입니다
(빈 질문·모델을 못 부르고 죽은 회차도 같이 빠집니다 — 잴 것이 없는 자리입니다).
**② 판정** — `previous_message_not_found` 를 「진단 실패」 칸으로 옮겼습니다. **새 사유는 기본이
「미스」입니다** — 모르는 것을 「못 쟀다」에 넣으면 표 아래로 밀려 조용히 묻힙니다.

**봇을 다시 켠 뒤 첫 질문은 진단이 아예 안 옵니다**(기준이 프로세스 메모리에만 있어 사라지고,
기준이 없으면 API 가 사유 자체를 안 보냅니다). 색인을 다시 쓰는 자리인데 **사유 줄이 비어서 오기
때문에 예전에는 맞은 쪽에 세어졌습니다** — 8월 실측으로 직전 문답이 1시간을 넘겼는데 사유 줄이 없는
회차가 14건 있었고, 그중 몇이 이 경우인지 가릴 수가 없었습니다.

**이제 기준이 있었는지를 함께 남깁니다** (2026-09-02 부터, `claude.js` 의 `cacheBaseline`). 기준이
없던 회차는 대화 로그에 `> **캐시** 대조 기준 없음 …` 으로 찍히고, `index.md` 표에서는
`(대조 기준 없음)` 행으로 **「진단 실패」쪽에** 섭니다. 괄호는 **API 사유가 아니라 우리가 붙인
이름**이라는 표시입니다. 옛 기록에는 이 필드가 없는데(`undefined`), 그것을 「기준이 없었다」로 읽지
않습니다 — 우리가 아는 것은 「모른다」입니다. **첫 회차만 기준이 없고 2회차부터는 그 질문 안에서
대조되므로**, 한 질문이 「기준 없음」과 실제 미스를 동시에 가질 수 있고 그때는 양쪽에 다 셉니다.

이것으로 **재는 자리는 메워졌지만 첫 회차 자체는 여전히 못 잽니다** — 「몇 건이 안 재졌나」가 보일
뿐, 그 회차에 캐시가 맞았는지는 모릅니다. 재려면 응답 id 를 재시작 너머로 들고 가야 하는데(지금은
메모리에만 둡니다), 낡은 id 는 `previous_message_not_found` 로 돌아와 결국 같은 「못 쟀다」칸입니다.

검사는 `node scripts/check-cache-stats.js` (`npm run check` 의 `[1/6]` 이 함께 돌립니다). 여기가
깨지면 **에러가 안 나고 숫자만 조용히 틀립니다** — 그리고 그 숫자를 보고 줄일 것이 있다고 판단하게
됩니다. 그래서 검사가 필요했습니다.

**슬랙에 쓰지 않고 질문 하나를 시험**하려면 `node scripts/run-ask.js "질문"` 을 씁니다
(`--full` 전체 권한 · `--private <채널>` 그 채널만). npm 으로 부를 때는 **`--` 를 빼면 안 됩니다** —
`npm run ask -- "질문" --full`. 빼면 npm 이 `--full` 을 먹어서 공개 권한으로 돌면서도 화면에는
아무 말이 없습니다.

## 문제가 생기면

| 증상 | 확인할 것 |
|---|---|
| 아무 반응이 없다 | `systemctl status hermes` 가 `active (running)` 인지. 봇이 그 채널에 초대됐는지 |
| 계속 재시작된다 | `journalctl -u hermes -n 50` — 대개 `.env` 토큰 오류 |
| `not_in_channel` | 해당 채널에서 `/invite @Hermes` |
| `missing_scope` | 매니페스트 스코프 수정 후 앱 **재설치** 필요 |
| `invalid_auth` | `.env` 토큰 오타 |
| 요약이 안 온다 | 그날 대화가 없으면 보내지 않습니다. `journalctl -u hermes --since today` 로 확인 |
| 답이 오래된 자료다 | 노트북에서 **push** 를 했는지. `systemctl status hermes-archive-pull` |
| 답이 이상하다 | 출처 채널이 붙었는지 확인. 없으면 근거를 못 찾은 것 |
| 답이 두 번 온다 | 노트북에서 `npm start` 가 돌고 있음 |

무슨 일이 있어도 먼저: `journalctl -u hermes -n 50`
설정 자체를 의심할 때: `sudo -u hermes bash -c "cd /opt/hermes/code && npm run check"`
