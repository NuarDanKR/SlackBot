# issue-trim

채널 md 머리말의 `> **핵심 쟁점**:` 줄에서 **덮인 옛 기록만** 빼서 채널당 400자 상한
안으로 들인다. 이 줄들은 접기도 상한도 없이 봇 프롬프트에 매 답변마다 통째로 실리고
(`src/archive.js` 의 `channelBrief` → `buildArchiveBriefSplit`), 색인이 자라는 것의
93%가 이 줄이다(2026-09-20 실측). 2026-09-21 에 경고선을 실제로 넘어(30,645자) 처음
일괄로 줄였다 — 이 스킬은 그 회차에서 밟은 것을 절차로 만든 것이다.

**400자 규칙의 원본은 `slack-sync` SKILL.md 6.5 「상단 요약 대조」의 ★ 블록**이고,
`archive-inbox` 5단계에 같은 규칙이 있다. 거기는 「쟁점을 더할 때 넘으면 먼저 뺀다」를
말하고, 여기는 **빼는 일 자체의 절차**다 — 무엇이 「덮인 기록」인지, 뺀 것이 안전한지를
어떻게 증명하는지, 적용을 어떻게 하는지.

## 어디서 돌리나 — 저장소가 둘이다

명령은 코드 저장소 뿌리에서 친다. 채널 md 는 **자료 저장소**에 있고, 그 뿌리는
`.env` 의 `HERMES_DATA_ROOT` 다.

```bash
cd ~/hermes/code                     # 코드 저장소 (VM 은 /opt/hermes/code)
DATA=$(node -e "import('./src/config.js').then(m=>console.log(m.DATA_ROOT))")
```

자료를 다루는 git 은 `git -C "$DATA"` 로 친다 (이유는 `slack-sync` 「어디서 돌리나」).

## 언제 돌리나

- **평상시** — 그 채널의 `핵심 쟁점` 을 만지게 될 때(쟁점 추가·요약 반영) 그 채널만.
  이것이 원칙이다 (`slack-sync` 6.5 · `archive-inbox` 5단계 — 이미 넘는 채널을 일괄로
  줄이지 않는다)
- **일괄 회차** — WHK 가 따로 시킬 때만. 넘는 채널 목록은 `npm run check` 의 `[3/6]` 이
  채널마다 재서 ⚠ 로 보여준다(`scripts/check-setup.js` 의 `ISSUE_LINE_MAX`).
  채널이 많으면 몫을 나눠 병렬 에이전트로 돌리고 **회의적 검증을 따로 거친다**
  (WHK 지시 2026-09-20 방식 — 2026-09-21 회차는 14채널을 셋으로 나눴다).
  병렬로 만든 제안일수록 4단계 기계 검증을 건너뛰지 않는다

## ⚠️ 먼저 알아야 할 것 — 무엇을 빼고 무엇을 안 빼나

1. **앞머리 쟁점 목록은 불가침이다.** 그 첫 문장이 봇이 **어느 채널을 볼지 고르는
   근거**다. 거기서 낱말을 빼면 그 주제 질문에 채널을 못 찾고 「자료가 없습니다」로
   답한다. 빼는 것은 **뒤에 붙은 날짜별 경과 기록**이다.
2. **「덮였나」는 본문(`## YYYY-MM` 아래)을 열어 확인한다.** 줄 안에서만 보면 안 된다.
   사업장 A 의 8/10 「미납입 107→102실」이 덮였다고 말할 수 있는 것은 본문에서 9/10
   「94→93실」 갱신을 확인했기 때문이다. 그리고 **뺀 것이 본문에 남아 있는 것까지
   확인한다** — 이 작업은 줄이는 것이지 내용을 없애는 것이 아니다.
3. **진행 중인 것은 안 뺀다.** 「예정」·「진행중」·「검토 중」으로 끝나고 뒤에 결말이
   없으면 살아 있는 쟁점이다.
4. **문장을 새로 쓰지 않는다 · 숫자를 새로 만들지 않는다.** 남기는 것은 원문 표현
   그대로다. 이것은 다짐이 아니라 4단계의 부분수열 검증이 기계로 증명한다.
5. **400자에 못 맞으면 줄이지 말고 묻는다.** 2026-09-21 회차 14채널 중 **7개는 못
   맞췄다** — 살아 있는 협의가 많아 1,331→1,113 에서 멈춘 채널, 덮인 기록이 하나도
   없어 한 글자도 못 뺀 채널, 1자 초과인데 줄 전체가 최신 기록인 채널.
   **「못 줄인다」가 정답인 채널이 있다.** 검사도 그래서 막지 않고 보이기만 한다.
6. **금액이 든 줄은 따로 본다.** 그 채널이 워크스페이스 원장의 `1급` 미결(총액 미확정
   등)에 걸려 있으면 손대지 않고 보고만 한다 — 확정 전 숫자를 옮겨 적는 손이 늘수록
   틀릴 자리가 는다.
7. **덤으로 낡은 숫자가 드러난다 — 별건 정정이다.** 줄을 본문과 대조하다 보면 줄의
   숫자가 본문의 나중 기록(오기 수정·재산정)과 어긋난 것이 나온다. 봇이 질문마다 그
   줄을 읽으므로 그대로 두면 틀린 값을 인용한다. 정정은 **본문 근거를 대고 사람 승인을
   받아** 하고, 제안 JSON 의 `corrections` 에 선언한다 — 선언 없이 끼워 넣은 새 문장은
   4단계가 ★ 로 잡는다. 승인 절차는 `slack-sync` 6.5 의 보고 형식을 그대로 쓴다.

## 절차

### 1. 받아오기 + 대상 고르기

```bash
git -C "$DATA" pull        # 자료 저장소는 작업 중에도 봇이 커밋한다 (07:00 · 17:00 · 15분 pull)
npm run check              # [3/6] ⚠ 목록 = 넘는 채널과 글자 수
```

2026-09-21 회차에 VM 자동 반영이 같은 파일들을 건드려 base 가 밀렸다. 시작 전에 받고,
6단계 적용 직전에도 검산이 다시 잰다(어긋나면 apply 가 멈춘다).

### 2. 채널마다 본문 대조 — 「덮인 기록」 가려내기

위 「먼저 알아야 할 것」 1~3 이 판정 기준이다. 채널 md 를 열어 `핵심 쟁점` 줄의 기록
하나하나에 대해 ① 본문에 그것을 덮는 나중 기록이 있는가 ② 빼려는 내용이 본문에
남아 있는가를 확인한다. 어긋난 숫자(7번)가 나오면 별도 목록에 근거와 함께 적는다.

### 3. 제안 JSON 만들기

**커밋에 안 담기는 임시 자리**(세션 스크래치패드 등)에 쓴다 — 저장소 안에 두면 커밋에
딸려 들어간다. 모양은 `scripts/verify_trim.py` 첫머리 주석이 원본이다:

```json
{
  "채널가.md": "> **핵심 쟁점**: …(원문에서 빼기만 한 줄)…",
  "채널나.md": {
    "line": "> **핵심 쟁점**: …",
    "corrections": [{"old": "원래 표현", "new": "승인받은 정정 표현"}]
  }
}
```

### 4. 기계 검증 — 눈 대조는 증명이 아니다

```bash
python .claude/skills/issue-trim/scripts/verify_trim.py --proposals <제안.json>
```

핵심은 **부분수열 검사**다 — 제안 줄이 원본 줄에서 글자를 **빼기만** 한 것인지
두-포인터로 잰다. 이것이 「새 글자가 안 들어갔다」의 유일한 증명이다(2026-09-21 회차
11줄 전부 이 검사를 통과시킨 뒤에만 적용했다). 정정은 `old` 로 되돌린 뒤 잰다.
✗ 가 하나라도 있으면 적용하지 않는다. 상한 초과는 ⚠ 로만 나온다(위 5번).

### 5. 사람 승인 — 여기서 멈춘다

채널별 「전 → 후」와, 정정은 본문 근거(날짜·발언자·원문 인용)를 함께 보인다.
빼는 것도 정정도 요약 변경이므로 **`slack-sync` 6.5 의 승인 절차를 그대로 탄다** —
번호를 매겨 보이고, 답을 듣기 전에는 한 글자도 고치지 않는다.

### 6. 적용 — `sed -i` 금지, 바이트로

```bash
python .claude/skills/issue-trim/scripts/apply_trim.py --proposals <제안.json>
```

`sed -i` 는 CRLF 를 LF 로 바꾼다 — 2026-09-21 에 43개 파일에서 실제로 밟았고 그때
`git diff` 는 깨끗해 보였다. 이 저장소는 줄끝으로 요약 해시가 갈려 관문이 한 번도 안
걸렸던 사고를 겪었다. `apply_trim.py` 는 파일을 바이트로 읽어 그 줄만 갈아 끼우고 그
줄의 줄끝을 그대로 쓰며, **적용 직전에 검산을 스스로 한 번 더 돌린다** — 그 사이 봇
커밋으로 base 가 밀렸으면 여기서 멈춘다.

### 7. 도장 — 없으면 커밋이 막힌다

```bash
python .claude/skills/archive-inbox/scripts/decide_work.py --show
```

`>` 메타 블록 전체가 「요약 자리」다(`review_work.py` 의 `_summary_end` = `summary.js`
의 `extractSummary` 범위) — `핵심 쟁점` 줄 변경도 pre-commit 관문에 걸린다.
도장의 원본 절차는 **`archive-inbox` 6단계**다. 적용 뒤 또 고치면 해시가 달라져 다시
막힌다 — `--show` 를 다시 돌리면 된다.

### 8. 확인 + 커밋·push 는 따로 승인

```bash
npm run check                                # [3/6] 이 줄었는지
git -C "$DATA" status                        # 내가 만든 것만 들어 있나
```

**커밋도 push 도 WHK 승인을 각각 따로 받는다** (`archive-inbox` 7단계 · CLAUDE.md).
push 한 내용은 15분 안에 봇이 팀 앞에서 인용하는 근거가 된다.

## 이 스킬이 안 하는 것

- **새 쟁점을 더하는 것 · 요약 대조** → `slack-sync` 6.5 · `archive-inbox`
- **원문 메시지 블록 수정** — 아카이브는 슬랙 그대로다. 낡은 숫자의 정정도 고치는
  자리는 `핵심 쟁점` 줄뿐이고, 원문이 틀렸으면 슬랙 스레드 `[정정]` 댓글이다
- **요약 섹션(`## 자금 구조 요약` 표) 정리** — 봇 검색에 안 걸리는 사람 자리라
  프롬프트 비용과 무관하다
- **문장 재작성** — 남기는 것은 원문 표현 그대로. 더 좋은 문장이 필요하면 그건
  요약 재작성이고 사람이 따로 정한다

## 시험

```bash
python .claude/skills/issue-trim/scripts/test_trim.py
```

임시 폴더에서만 돌고 저장소를 안 건드린다. `npm run check` 가 `test_*.py` 이름 규칙으로
저절로 함께 돌린다. 결함(새 글자 유입·줄 위치 이탈·중복 줄·검산 없는 적용)을 넣어
빨개지는 것과, 정상 제안·상한 초과 경고가 오탐하지 않는 것을 함께 본다.
