# 요약 검토 — 검토자가 확인한 것만 남는다

> 결정: 2026-09-02 (오너). Hermes 흡수의 핵심. [`bot-hierarchy.md`](bot-hierarchy.md) 의 하위 문서.
> 구현 점검과 보완 조건: [`../verification/2026-09-07-hermes-summary-review.md`](../verification/2026-09-07-hermes-summary-review.md)

## 무엇을 바꾸는가

마스터 TYBot은 채팅 원문을 md로 수집하고, Hermes는 그 원문으로 요약 후보를 만든다.
채널별 자동 요약은 사람이 확인하기 전에는 확정하지 않는다.

Hermes 는 다르다. 요약은 사람이 유지하고, 봇은 **어긋난 곳을 후보로만** 올린다.
그 판단의 근거는 실물 사고다.

> 어느 채널의 요약표 금액이 원문에서 바뀐 것을 **두 달 뒤에야 손으로** 발견했다.
> 에러는 나지 않았다. (`ref/hermes/src/ingest/summary.js`)

자동 요약의 위험은 틀리는 것이 아니다. **틀린 채로 조용한 것**이다. 승인 요약은
사람이 읽는 파생 문서다. 검색·주제 탐색의 길잡이로는 사용할 수 있지만 사실 답변을
만들 때는 반드시 연결된 원문을 현재 권한으로 다시 열고 그 원문을 출처로 사용한다.

그래서 흐름을 바꾼다.

```
   원문 수집(자동)  →  요약 후보 생성(자동)  →  검토자 확인(사람)  →  승인 요약 반영
                                                    │
                                              틀렸다 → 반영 안 함
                                                       (봇은 그것을 학습하지 않는다)
```

## 검토자는 누구인가

**채널마다 검토자를 지정한다.** 채널 개설자가 정하고, 보낼 시각도 정한다.

| 값 | 정하는 사람 | 기본값 |
|---|---|---|
| 검토자 | 채널 개설자 | 개설자 자신 |
| 보낼 시각 | 채널 개설자 | 매일 08:00 (KST) |
| 보낼 곳 | — | 검토자 DM |
| 주기 | 채널 개설자 | 매일 |

검토자가 **없으면 요약을 반영하지 않는다.** 원문은 그대로 쌓인다.
"검토자를 안 정하면 자동으로 반영" 이 아니다 — 권한은 막는 쪽이 기본값이고,
요약 반영도 같다. 대신 **검토자가 없다는 사실을 콘솔 헬스 체크에 올린다.**
조용히 아무것도 안 하는 것이 지금 우리가 가장 자주 겪은 고장이다.

## 검토자가 받는 것

DM 은 **알림이고, 목록은 DB 에 있다.** Hermes 가 DM 본문만 보내다가 사람이 손으로
복사해 붙여야 했고, 붙인 뒤에는 건별로 멈출 자리가 없어 전부 한꺼번에 반영됐다.
우리는 처음부터 목록을 DB 에 둔다.

DM 에 담을 것.

- 채널 · 기간 · 후보 건수
- Canvas 링크: **그날 수집된 채팅·변환 완료 첨부의 핵심 요약과 출처**
- 건별로: **요약에 뭐라고 적혀 있는지 / 후보가 뭐라고 바꾸자는지 / 근거 원문**
- 버튼: `맞다` · `틀렸다` · `나중에`

근거 원문을 반드시 함께 보낸다. **요약하지 않고 그대로 보낸다.**
판정에 쓰이는 것은 원문의 표현이다. Hermes 는 DM 문구와 원문이 다른 건을 실제로 겪었다
(DM 은 「내부 승인 진행」, 원문은 「진행예정」).

## 후보를 만드는 규칙

Hermes 의 `summary-check.md` 프롬프트를 이식한다. 잡는 것은 세 가지뿐이다.

| 유형 | 뜻 |
|---|---|
| `숫자·일정` | 요약에 적힌 금액·비율·날짜가 새 메시지에서 달라졌다 |
| `새 쟁점` | 핵심 쟁점에 없던 논의가 시작됐다 |
| `끝난 쟁점` | 핵심 쟁점에 있던 항목이 종결·철회됐다 |

반드시 지킬 것 — 이 넷이 프롬프트의 뼈대다.

1. **값은 원문에서 그대로 옮긴다.** 반올림·환산·추론 금지
2. **다른 현장 숫자를 끌어오지 않는다.** 사업장이 30개가 넘고 금액 단위가 비슷하다.
   다른 현장 숫자가 흘러드는 것이 가장 흔한 사고다
3. **근거를 반드시 댄다.** 날짜·시각·작성자와 그 문구를 그대로 인용한다.
   근거를 댈 수 없으면 **후보로 올리지 않는다**
4. **확실하지 않으면 넣지 않는다.** 잘못된 후보는 사람의 시간을 뺏고, 잘못 반영되면
   봇이 그 숫자를 근거로 답한다

## 근거 대조 — 후보가 화면에 오기 전에

모델이 댄 인용을 **원문에서 실제로 찾는다.** 못 찾으면 후보에서 뺀다.
이것이 우리 `hallucination-guard` 를 한 겹 더 두껍게 만든다 — 지금은 출처를
표기하지만, 그 출처가 실재하는지는 확인하지 않는다.

찾을 때는 정규화해서 비교한다(공백·따옴표·강조·글머리표). 그런데 여기에
**Hermes 가 다섯 번 발이 걸린 함정**이 있다.

| 놓친 것 | 결과 |
|---|---|
| 백틱 · 별표 · 따옴표 | 관문은 통과시킨 근거를 화면이 못 찾았다(전량 실측 440·141·25건) |
| 여러 줄에 걸친 인용 | 못 찾음 |
| 모델이 인용 가운데를 `...` 로 건너뛴 것 | 못 찾음 |
| 글머리표 `•`·`◦`·`∙` | 원문에 있는 근거가 「뺀 후보」로 밀렸다(2,053건 중 120건) |
| 백슬래시로 이스케이프된 따옴표 | **양쪽이 함께 틀려** 갈림 검사가 못 잡았다 |

우리가 배울 것 두 가지.

- **정규화는 한 곳에만 적는다.** 후보를 만드는 쪽과 화면에 보여 주는 쪽이 같은 함수를
  부른다. 두 곳에 적으면 갈려도 에러가 안 나고, **관문은 통과했는데 화면은 "원문에서
  찾지 못했습니다"** 가 된다. 그 문구는 검토자에게 「빼」로 읽힌다
- **`·`(U+00B7)와 `-` 는 지우지 않는다.** 글머리표가 아니라 문장 구분자다.
  지우면 서로 다른 문장이 같은 값으로 접혀 **엉뚱한 원문을 보여준다.**
  「못 찾음」보다 나쁘다

## `/피드백` 과 합치기

검토 결과와 피드백은 **같은 것**이다. 둘 다 "봇이 틀렸다" 를 사람이 알려 주는 자리다.
이미 만든 것을 쓴다.

| 검토자 행동 | 피드백 기록 |
|---|---|
| `맞다` | `kind=positive`, 요약 반영 |
| `틀렸다` | `kind=negative` + **정정 사항 필수**, 요약 반영 안 함 |
| 근거를 못 찾음 | `kind=missing` + 정정 사항 필수 |
| `나중에` | 다음 날 한 번 더 표시. 그날도 결정하지 않으면 폐기 |

아무 버튼도 누르지 않은 후보는 다음 검토일에 `expired`로 폐기한다. 미응답을 암묵적
승인으로 취급하지 않으며, 폐기 후보는 승인 요약에 들어가지 않는다.

`REQUIRES_CORRECTION` 이 이미 `negative`·`missing` 에 정정 사항을 강제한다.
검토자 흐름이 그 위에 그대로 올라간다 — **"틀렸다" 만 누르고 끝나면 무엇이 틀렸는지
아무도 모른다.**

콘솔의 **접수된 신고** 화면과 **기여도** 도 그대로 쓴다. 검토자가 실제로 고칠 거리를
준 사람으로 순위에 올라간다.

## 학습하지 않는다는 것의 뜻

"틀렸으면 봇이 학습하지 않는다" 를 코드로 옮기면 이렇다.

- 틀린 후보는 **아카이브에 반영하지 않는다.** 요약이 옛 값 그대로 남는다
- 틀린 후보와 정정 사항은 **피드백 로그에만** 남는다. 아카이브가 아니다
- 정정 사항을 **답변 근거로 쓰지 않는다.** 사람이 쓴 문장이지만 원문이 아니다
  (원칙 7 — 사람 발언 ↔ 문서 분리)
- 다음 회차에 같은 자리가 또 어긋나면 **다시 올라온다.** 「틀렸다」 는 그 후보를
  버리는 것이고, 그 자리를 영구히 덮는 것이 아니다

마지막 항목이 중요하다. 「빼」 를 영구 무시로 만들면, 한 번 잘못 뺀 자리가
**두 번 다시 검토 대상이 되지 않는다.**

## 반영은 별도 승인 요약만

**원문 메시지 블록은 건드리지 않는다.** 아카이브는 Slack 그대로다.
틀린 내용을 고치는 것은 그 메시지 스레드의 정정 댓글이고, 그것도 원문으로 쌓인다.

승인된 결과는 `raw/` 밖의 파생 데이터(`approved_summary_item`)와 검토 Canvas로 저장한다.
레거시 채널 MD의 상단 요약을 직접 고치는 방식은 아카이브 v2와 맞지 않는다. 별도 MD를
만들더라도 `raw/`나 원문 색인에는 넣지 않는다. 승인 요약은 검색 후보를 좁히는 데만
쓰고, 답변 생성 전에는 후보가 가리키는 `evidence_locator`의 원문을 다시 읽는다. 이 선을
흐리면 원문 보존과 요약 재귀 차단이 함께 무너진다.

## 승인 요약을 검색 길잡이로 (B-56, 2026-09-17 구현)

구현: `src/tybot/summary_guide.py` · 호출: `answer.AnswerEngine._with_approved_guide()`

사람이 쓰는 말과 문서에 적힌 말은 자주 다르다(「미수금」 ↔ 「미회수 채권」).
검색은 그 둘을 잇지 못하고, 읽을 수 있는 문서를 옆에 두고 못 찾는다. 검토자가
승인한 요약은 그 둘을 이어 주는 **사람이 확인한 유일한 자료**다. 그래서 길잡이로만
쓴다 — 근거로는 쓰지 않는다.

```text
질문 ─▶ 승인 요약과 대조 ─▶ evidence_locator ─▶ 현재 ACL 로 원문 재개봉 ─▶ 원문 줄만 근거로
                                            └─ 못 열거나 어긋나면 버린다(재검토)
```

지키는 선:

| 무엇 | 어디서 판정하나 |
|---|---|
| 어떤 승인을 볼 수 있나 | `state='approved'` · `superseded_at IS NULL` · `stale_at IS NULL` |
| 질문과 맞나 | `search_index.score_line()` — **검색과 같은 함수** |
| 요청자가 그 원문을 볼 수 있나 | `ArchiveStore.resolve_refs()` — ACL 은 한 곳뿐 |
| 그 좌표에 아직 그 문장이 있나 | `summary_guide._line_of()` — 인용·시각·작성자 대조 |

- 반려·보류·미응답 폐기 후보와 **정정 모달 입력은 읽지 않는다.** 정정은 사람이 쓴
  문장이지 원문이 아니다(원칙 7).
- 승인 문장은 LLM 에 한 글자도 가지 않는다. 더해지는 것은 그 문장이 가리킨 원문
  줄이고, 출처도 그 줄의 문서·Slack 링크가 붙는다(원칙 2).
- 승인 당시 검토자의 권한은 지금 묻는 사람의 권한이 아니다. 질문자가 채널을 잃으면
  승인 요약이 있어도 그 내용을 볼 수 없다(원칙 3).
- 원문이 사라졌거나 좌표·전체 원문 지문이 어긋나면 **비슷한 줄로 갈아 끼우지 않는다.**
  `approved_summary_item.stale_at` 을 찍어 길잡이와 「기존 승인 요약」 에서 빼고,
  같은 사실이 새 원문으로 다시 수집된 경우에만 정상 후보 생성 경로로 다시 검토한다.
- DB 를 못 보면 길잡이는 **그냥 없다.** 검색 결과가 예전과 같아질 뿐 답이 막히지 않는다.

### 근거 메시지 좌표

Canvas 의 후보별 출처가 채널 맨 위를 열면 사람은 그날 대화를 처음부터 뒤져야 하고,
실제로는 확인하지 않은 채 승인한다. 그래서 수집 단계에서 Slack 메시지 `ts` 를
보존한다.

```text
> [2026-09-16 10:00|1758012345.123456] 홍길동: 공정률은 62.5%입니다
```

좌표는 **시각 칸 안에** 적는다. 본문 뒤에 붙이면 우리가 덧붙인 글자가 원문 텍스트가
되고, 그 뒤로 검색·요약·인용이 전부 그 글자를 원문으로 읽는다(원칙 1). 좌표가 없는
옛 줄은 그대로 읽히고, 그때만 채널 링크로 내려간다. 중복 판정(`writer.dedupe_line`)은
좌표를 떼고 보므로 좌표를 남기기 전에 쌓인 줄이 다시 쌓이지 않는다.

## 재귀 차단을 관문으로

Hermes 는 커밋 전 관문에서 **아카이브에 봇이 쓴 줄이 있는지** 검사해 하나라도
있으면 커밋하지 않는다. 우리는 원칙으로만 두고 있다.

우리 `.githooks/pre-commit` 과 아카이브 쓰기 경로 양쪽에 넣는다.
봇 작성자 표시가 붙은 줄, 우리 봇 이름이 적힌 헤더가 원문 블록에 들어가면 실패다.

이유는 원칙 1 그대로다 — 봇 요약이 아카이브에 들어가면 다음번에 봇이 자기 요약을
원본 근거로 삼고, 한 번 잘못 요약한 숫자가 **원문처럼 굳는다.** 되돌릴 방법이 없다.

## 첨부 변환 상세는 DM으로 보내지 않는다 (2026-09-16 변경)

첨부 처리를 별도 명령으로만 열어 뒀더니 **대기 31건·처리 0건**이 됐다.
사람은 모르는 일을 하러 찾아오지 않는다.

> "첨부파일은 별도의 승인 없이 진행하는게 옳은 방향인듯한데. 차라리 확인을
> 받을거면 내가 이전에 얘기했듯 채널의 검토자에게 일정시간에 그날 하루치것을
> 확인받는게 옳을듯 해" — 오너

초기에는 변환 결과까지 같은 DM으로 보냈다. 실제 운영에서는 HWP/XML/표 변환 원문이
그대로 노출돼 검토자가 이해할 수 없었고, 요약 검토가 변환 진단에 묻혔다. 따라서
검토자에게는 **요약 후보만** 보낸다.

| 첨부 | 어떻게 |
|---|---|
| 변환본이 아카이브에 들어간 것 | **승인 없이 쓴다.** 그 텍스트가 수집 단계 PII 검사를 통과했다 |
| 변환 실패·지원 불가 | 원본을 외부 LLM에 보내지 않는다. 관리 콘솔의 아카이브 진단에만 사유·원본 링크를 보인다 |

발송기(`src/tybot/daily_review.py`, `tybot-review-dm.timer`)는 요약 후보만 보낸다.
과거 첨부 발송 이력은 호환을 위해 남기되 새 `kind='attachment'` 이력은 만들지 않는다.

숫자·금액·비율·날짜 후보를 먼저 배치하고, 후보 문장에 포함된 값을 별도 줄로 표시해
검토자가 근거 원문과 한 자리씩 비교할 수 있게 한다.

## 요약 검토 Canvas 검토 결과 (2026-09-16)

Canvas는 장문의 통합 요약과 표를 읽기에 적합하지만 `맞다`·`틀렸다`·`나중에` 같은
Block Kit 동작 버튼을 문서 안에 넣을 수 없다. 따라서 Canvas가 DM을 완전히 대체하면
승인 동선이 끊긴다.

권장 구조는 **Canvas는 읽기 화면, DM은 승인 화면**인 혼합형이다.

1. 채널·검토일별 Canvas를 하나만 생성한다.
2. Canvas에는 AI 생성 문서 고지, **그날 수집 내용 요약**, 숫자 확인표, 근거 좌표와
   Slack 채널 원문 링크를 넣는다.
3. 검토자 DM에는 Canvas 링크와 후보별 승인 버튼만 둔다.
4. 여러 검토자가 있어도 Canvas는 공유하고 사용자별 발송·결정 권한은 기존 DB로 유지한다.
5. Canvas ID를 DB에 저장해 타이머 재실행 시 중복 문서를 만들지 않는다.

이 구조는 Canvas ID와 생성 상태를 저장할 스키마, 일부 수신자 실패 후 재시도 정책,
검토자 접근권한 회수가 함께 필요하다. 이 조건 없이 즉시 생성하면 같은 날 Canvas가
여러 개 생기므로 B-50에서 구현한다. 구현 계약은
[요약 검토 Canvas + DM 승인 설계](summary-review-canvas.md)를 따른다.

## 소급 검토 — 수집됐지만 한 번도 검토되지 않은 과거 (B-58, 2026-09-17)

봇이 들어오기 전의 자료를 나중에 넣으면 검토 후보가 **한 건도** 만들어지지 않았다.
후보 생성이 세 겹으로 좁혀져 있기 때문이다.

1. `start_at` — 최초 회차는 검토자를 지정한 시각 이후의 원문만 본다
2. 24시간 클램프 — 커서가 없으면 그 위에 다시 「최근 하루」를 씌운다
3. watermark — 한 번 돌면 커서는 앞으로만 간다

셋 다 **매일 새로 올라온 것만 본다**를 위한 장치고, 그 목적에는 맞다. 다루지 않은
것은 「과거를 나중에 넣는 경우」다. 과거 전체 수집으로 몇 달치를 넣어도 화면은
`오늘 검토할 새 후보가 없습니다`만 돌려준다 — 수집은 됐는데 검토 대상이 아니다.

### 무엇을 하는가

커서를 되돌려 **같은 생성 경로를 다시 태운다.** 소급 전용 생성 경로를 만들지
않는다 — 후보 계약·원문 대조·승인 절차가 갈라지면 어느 쪽이 맞는지 아무도 모른다.

- 시작점은 커서 값으로 표현한다(`backfill_watermark`). 시작일은 **그날을 포함**한다.
  비우면 아카이브 처음부터다.
- 한 회차는 `MAX_NEW_SOURCE_CHARS` 만큼 읽는다. 커서가 회차마다 전진하고, 안 움직이면
  읽을 원문이 없다는 뜻이라 거기서 멈춘다.
- 회차마다 LLM 을 한 번 부른다. 상한(기본 10, 최대 50)에 걸리면 커서가 남으므로
  다시 실행할 때 **멈춘 지점부터 이어 간다**.
- 실행 전에 LLM 없이 분량을 센다(`backfill_estimate`). 비용을 보고 누르라고 있다.

후보는 `(워크스페이스, 채널, 원문 지문, 종류, 제안 문장)` 으로 유일하므로 같은 구간을
다시 읽어도 같은 후보가 두 번 생기지 않는다.

### 보여 준 적 없는 후보는 폐기하지 않는다

한 회차 DM 은 후보를 **10건만** 싣는다. 소급으로 200건이 쌓이면 190건은 사람 앞에
나온 적이 없다. 예전 폐기 규칙은 `run_date < 오늘` 인 미결정 후보를 전부 버렸으니,
소급은 시작한 다음 날 통째로 사라졌을 것이다.

「확인하지 않았다」 는 **보여 준 뒤에만** 할 수 있는 말이다. 그래서 후보에
`delivered_at` 을 남기고, 폐기는 그 값이 있는 것만 본다. 소급 없이도 이건 버그였다 —
하루 후보가 11건이면 11번째는 한 번도 안 보이고 다음 날 폐기됐다.

## 쓴 돈을 버리지 않는다 (B-59, 2026-09-17)

소급이 LLM 을 열 번 넘게 부르고도 DM 은 한 건도 안 갔다. 후보는 DB 에 남으니 산출물이
사라진 것은 아니다 — DM 실패는 5분 타이머가 알아서 재시도한다(`pending()` 이 다시
뽑고, 실패한 delivery 는 `state='sent'` 가 아니므로 다시 보낸다).

문제는 재시도가 아니라 **사람이 그 사실을 모른다는 것**이었다. 안 갔으니 다시 누르고,
다시 누르면 소급이 커서를 되돌려 같은 원문을 또 LLM 에 보낸다. 산출물은 중복 차단에
막히고 **돈만 두 번 나간다.**

### 같은 원문을 두 번 요약하지 않는다

`summary_review_source_run` 에 `(워크스페이스, 채널, 원문 지문)` 을 남긴다.
`generate_channel` 은 모델을 부르기 전에 이걸 보고, 이미 돌린 구간이면 **커서만 옮기고
지나간다.** 두 번째 소급은 LLM 0회로 끝까지 걸어간다.

후보가 0건이었던 구간도 남긴다. 행이 없으면 「안 돌렸다」 와 구별되지 않아, 잡담뿐인
구간을 누를 때마다 다시 요약하게 된다.

### 보내기만 다시 한다

`--deliver-only` 는 생성 단계를 통째로 건너뛰고 대기 후보만 민다. 요약은 됐는데 DM 만
실패한 회차를 **공짜로** 복구하는 경로다. 이 버튼이 없으면 사람은 보내려고 생성
버튼을 누르고, 그게 위의 낭비로 이어진다.

그리고 결과에 대기 후보 건수를 싣는다. `sent=0` 인데 `pending>0` 이면 화면이
「만들어 둔 후보 N건이 대기 중 — 다시 보내기로 보냅니다(LLM 호출 없음)」 라고 말한다.
쓸 수 있는 복구 수단을 사람이 보게 하는 것이 이 수치의 목적이다.

## 검토자 지정을 기다리지 않는다 (B-62, 2026-09-18)

채널 목록은 `channel_reviewer` 가 안다. 보낼 사람이 있는 채널만 도는 것이 맞기
때문이다. 그런데 검토자 지정은 **채널마다 업무 협의**라 몇 주가 걸리고, 채널이 100개를
넘으면 그 협의가 끝나기를 기다리는 동안 수집만 계속 쌓인다.

`run()` 안을 보면 생성은 검토자 확인보다 **먼저** 끝난다. 검토자 유무는 DM 단계에서만
걸린다. 즉 막고 있던 것은 생성 로직이 아니라 **채널 목록** 하나였다.

`--generate-only` 는 아카이브에 원문이 있는 모든 채널을 돌아 후보만 만들고 멈춘다.
사람에게 아무것도 보내지 않는다. 뒤에 쌓아 둔 장치들이 이걸 안전하게 만든다.

- 후보는 보여 준 적이 없으므로 **폐기되지 않는다**(B-58 `delivered_at`)
- 같은 구간을 다시 읽어도 **모델을 부르지 않는다**(B-59 `summary_review_source_run`)
- 검토자가 지정되면 5분 타이머가 `pending()` 으로 집어 그대로 보낸다

그래서 검토자 협의와 요약 생성이 직렬이 아니게 된다. 비용은 한 번만 든다.

**소급과 함께 쓸 때는 채널을 명시하게 한다.** 소급은 회차마다 LLM 을 한 번 부르므로,
채널 수십 개를 암묵적으로 도는 것은 일일 비용 한도를 한 번에 쓰는 일이다.

**콘솔에서 한다.** 수집 > 채널 관리 > 요약 검토 DM 에 버튼 둘이 있다 — 「검토자 없이
후보만 만들기」 와 「검토자 없이 소급해서 후보만 만들기」. 채널을 고르면 검토자 유무를
묻지 않고 그 채널들이 대상이 된다(운영 기능은 콘솔에 둔다, CLAUDE.md).

CLI 는 자동화·복구용으로 남는다.

```bash
# 오늘 새 원문만, 검토자 없는 채널까지
--generate-only

# 과거 소급 — 채널을 골라야 한다
--generate-only --backfill --target tyit:C1 --since 2026-06-01
```

## 만들 순서

1. 채널별 검토자·시각 설정 (`/채널` 에 붙인다. DB: `channel_reviewer`)
2. 후보 생성 (프롬프트 이식 + 근거 대조 함수 **한 곳에**)
3. 검토 DM (Block Kit. 버튼 `value` 를 비우지 않는다 — 비우면 메시지가 통째로 사라진다)
4. 검토 결과를 피드백으로 기록 + 요약 반영
5. 검토자 없는 채널을 헬스 체크에 올린다
6. 재귀 차단 관문
