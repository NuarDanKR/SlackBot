# 콘솔 답변 추적·원본 열람 설계

_상태: 오너 확인·구현 반영_
_작성: 2026-09-11_

## 1. 요청을 이렇게 이해했다

관리자가 답변 통계만 보는 데서 끝나지 않고, 한 건의 질문이 어떻게 처리되어 어떤 답변으로
나갔는지 끝까지 추적할 수 있어야 한다.

1. `수집 > 원문 문서`처럼 `답변`에도 질문·답변 원본을 모아 보는 별도 메뉴를 만든다.
2. `질문 처리 기록`의 행을 선택하면 그 질문의 질문자, 질문 원문, 봇 답변 원문을 연다.
3. `답변 품질`의 문제 건과 `피드백`의 신고 건도 같은 질문·답변 원본으로 연결한다.
4. 성격이 겹치는 `답변 개요`, `질문 처리 기록`, `답변 품질`은 기능을 버리지 않고 하나의
   `답변 현황` 화면으로 통합한다.
5. 기존 나머지 메뉴와 기능은 없애지 않고 실제 답변 처리 흐름에 맞춰 순서를 조정한다.
6. 질문·답변 원본은 운영 감사 자료일 뿐, 아카이브나 다음 답변의 근거로 재사용하지 않는다.
7. `봇 분류 상태`의 호출 행에서도 동일 처리 건의 질문·답변 원본으로 이동할 수 있게 한다.

## 2. 현재 콘솔과 데이터 상태

현재 `답변` 메뉴는 다음 순서다.

```text
답변 개요
질문 처리 기록
사용량 및 비용
전문 봇 분석
답변 품질
피드백
답변 규칙
```

- `질문 처리 기록`은 시각, 워크스페이스, 의도, 결과, 근거 수, 모델, 비용, 시간만 보여 준다.
  API가 질문·답변 본문과 QA 레코드 ID를 내려주지 않으므로 행에서 원본을 열 수 없다.
- `답변 품질`은 최근 7일 집계와 관리자용 문제 질문 문장을 같은 화면에 펼친다. 답변 본문은
  없고 다른 기간·정상 답변을 탐색하기 어렵다.
- `피드백`은 이미 `qaRecordId`를 보유하지만 화면에서 QA 레코드로 이동하지 않는다.
- QA JSONL에는 `record_id`, 질문자 ID·표시명, 채널, 질문, 전달한 답변, 출처, 모델, 비용,
  소요 시간과 Slack 요청·응답 시각이 있다. 따라서 원본 화면의 기초 데이터는 존재한다.
- 복합 질문은 현재 QA 한 줄에 합쳐 기록하면서 모델·근거·결과는 마지막 하위 답변의 값만
  대표값으로 남긴다. 단계별 화면을 정확히 만들려면 이 부분은 구조화 기록으로 보완해야 한다.
- 기존 전문 봇 호출 기록과 QA 기록 사이에는 공통 추적 ID가 없었다. 구현 이후 생성되는 기록은
  QA `record_id`를 함께 저장해 한 질문의 분류 결과와 원본을 정확히 연결한다.
- 작업 트리에는 후속 질문용 원문 참조(`EvidenceRef`) 구현이 진행 중이다. 이 참조는 다음 질문의
  근거 재검증용이며, 콘솔의 질문·답변 원본 열람과 목적이 다르다. 구현 시 사용자 작업을 덮어쓰지
  않고 QA 레코드 ID만 공통 축으로 사용한다.

## 3. 실제 답변 처리 순서 검증

현재 코드의 실제 순서는 다음과 같다.

```text
Slack 이벤트 접수·중복 제거
  → 명시 명령 판정 또는 LLM 의도 분해·처리 계획
  → 요청자·질문 위치 기반 권한 컨텍스트 생성
  → 권한 필터를 먼저 적용한 원문 검색
  → 전문 봇 후보 라우팅
  → 전문 봇 호출 또는 기본 LLM 호출
  → 출처 부착·Slack 메시지 구성
  → Slack 전송
  → 질문·답변 QA 기록
```

사용자가 제시한 `접수 → 라우팅 → 권한체크 → LLM/subbot → 답변확인(검증) → 답변`과 큰
방향은 같다. 다만 현재 구현에는 두 가지 차이가 있다.

1. 의도 분해·처리 계획이 권한 컨텍스트 생성보다 먼저다. 이 단계에는 질문만 전달되고 원문은
   전달되지 않는다. 실제 원문 검색과 전문 봇 호출은 권한 필터 뒤에 있다.
2. 기본 LLM 답변 뒤에 독립적인 의미 검증 단계는 없다. 전문 봇에는 빈 응답·출처 임의 생성·길이
   등을 막는 출력 계약 검사가 있고, 기본 답변에는 출처 부착과 회귀 불변식이 있지만 이를
   `답변 검증 완료`라고 표시하면 실제보다 강한 보장을 주장하게 된다.

운영자가 보는 전체 흐름은 다음과 같이 구분한다.

```text
접수 → 분류·라우팅 → 권한·근거 → 모델·전문 봇 실행 → 전달 → 사람 검토·피드백
```

별도 기계 검증 단계는 추가하지 않는다. 기존 전문 봇 출력 계약과 권한·출처 불변식은 안전장치로
계속 유지하지만 이를 독립적인 `답변 검증` 단계나 메뉴로 표현하지 않는다. 답변 내용의 적절성은
전달 후 사람이 질문·답변 원본과 출처를 확인하고 피드백·처리 기록을 남기는 방식으로 검토한다.

현재 Slack 답변은 사람 승인 전에 즉시 전달된다. 따라서 이 문서의 `사람 검토`는 **전달 후 검토**를
뜻한다. 전달 전 승인 큐를 의미한다면 봇의 응답 방식 자체가 달라지는 별도 설계가 필요하다.

## 4. 제안 메뉴 구성

```text
답변
  1. 답변 현황                 통합 — 개요 + 품질 지표 + 질문 처리 기록
  2. 봇 분류 상태              분류·전문 봇 호출과 질문·답변 원본 연결
  3. 질문·답변 원본            신규 — 실제 질문과 전달 답변 열람
  4. 피드백                    기존 유지 — 전달 이후 사람 검토·사용자 반응
  5. 사용량 및 비용            기존 메뉴 이동 — 전체 흐름의 횡단 지표
  6. 답변 규칙                 기존 유지 — 운영 설정
```

세 화면은 같은 QA 기록을 집계 수준만 달리해 보여 주므로 분리 이점보다 왕복 비용이 크다.

- `답변 개요`: 품질 숫자와 다른 두 화면으로 가는 링크가 대부분이다.
- `답변 품질`: 같은 질문의 근거·오류·지연을 기간 집계한다.
- `질문 처리 기록`: 위 집계의 원인이 된 개별 질문 행이다.

따라서 하나의 화면에서 `상단 요약 → 품질 분포 → 검토할 질문 목록` 순으로 내려가게 한다.
권한 체크와 모델 실행은 서로 다른 문서가 아니라 질문 한 건의 처리 단계이므로 목록 행의 상세
패널에 표시한다. 라우팅은 여러 질문과 전문 봇을 비교하는 독립 분석 수요가 있어 별도 메뉴를
유지한다.

`봇 분류 상태`의 각 호출 행에는 `원본 보기`를 둔다. 호출 기록에 질문·답변 본문을 다시
복제하지 않고 QA `record_id`만 저장하며, 원본 상세 API가 사용자·채널 검토 권한을 다시
검사한다. 연결 기능 도입 전 기록은 시각이 가깝다는 이유로 추측해 연결하지 않고
`연결 전 기록`으로 표시한다.

기존 주소와 북마크는 깨뜨리지 않는다.

```text
#/answer           → 통합 답변 현황
#/answer/questions → 통합 화면의 처리 기록 위치
#/answer/quality   → 통합 화면의 품질 위치
```

## 5. 통합 답변 현황과 처리 기록 상세

통합 화면은 네 구역으로 구성한다.

1. **기간·범위 필터** — 기간, 워크스페이스, 채널
2. **답변 요약** — 질문 수, 근거 확보율, 오류, 지연, 피드백, 비용
3. **품질 분포** — 근거 있음/없음, 오류, 15초 초과와 판정 기준
4. **질문 처리 기록** — 필터 결과를 만든 개별 QA 레코드

세 구역이 반드시 같은 기간과 워크스페이스 필터를 공유해야 한다. 현재처럼 개요의 선택 기간과
품질의 고정 7일, 질문 기록의 별도 필터가 섞이면 같은 화면의 숫자끼리도 일치하지 않는다.

목록 행 전체를 선택할 수 있게 하고 `#/answer/questions?record=<record-id>`로 깊은 링크를 만든다.
상세 패널은 다음 순서로 표시한다.

| 단계 | 표시 내용 | 현재 기록 여부 |
|---|---|---|
| 접수 | 접수 시각, 워크스페이스, 채널, 질문자, 질문 종류 | 일부 있음 |
| 분류·라우팅 | 하위 의도, 분류 출처, 선택 전문 봇, 선택 이유·신뢰도 | 전문 봇과 QA 연결 필요 |
| 권한·근거 | 채널/DM 범위, 허용 근거 수, 제외 수·비민감 사유 코드 | 구조화 보완 필요 |
| 모델·전문 봇 | 기본/전문 봇, 모델, 실행 결과, 비용·시간 | 일부 있음 |
| 전달 | Slack 전달 성공 여부, 응답 시각, 메시지 링크 | 시각 있음, 링크 조합 필요 |
| 사람 검토 | 연결된 피드백, 처리 상태와 처리 메모 | 피드백 연결 있음 |

목록 화면에는 본문을 넣지 않는다. 행을 선택한 경우에만 아래 원본 API를 호출해 질문과 답변을
표시한다. 긴 질문·답변은 접힌 상태로 시작하지 않고 읽을 수 있는 본문 영역에 그대로 표시하되,
코드 블록·표·Slack 마크업이 레이아웃을 깨지 않도록 안전하게 렌더링한다.

## 6. 질문·답변 원본 화면

`수집 > 원문 문서`와 같은 좌측 목록 + 우측 본문 구조를 사용한다.

### 목록과 필터

- 기간, 워크스페이스, 채널, 질문자, 처리 결과, 모델, 전문 봇, 품질 판정, 피드백 유무
- 기본 기간은 최근 7일, 서버 상한은 한 번에 200건
- 목록에는 시각, 질문자, 채널, 결과와 질문 앞부분만 표시
- 서버가 발급한 `recordKey`로 선택하며 파일 경로나 JSONL 줄 번호를 URL에 노출하지 않음

### 본문

- 질문자 표시명과 Slack 사용자 ID
- 질문 원문과 Slack 질문 시각
- 실제 전달된 봇 답변 원문과 응답 시각
- 모델·전문 봇·비용·소요 시간
- 출처 목록과 근거 참조 상태
- 연결된 품질 판정과 피드백·처리 상태
- 가능한 경우 `Slack에서 질문 보기` 링크

화면 제목은 `답변 원문`보다 `질문·답변 원본`으로 한다. `원문`은 현재 프로젝트에서 사람이
작성한 수집 근거를 뜻하므로, 봇 답변까지 원문이라고 부르면 답변이 검색 근거라는 오해가 생긴다.

## 7. 품질·피드백 연결

### 답변 품질

- 별도 메뉴는 없애되 품질 지표·그래프·산정 근거는 통합 `답변 현황`에 그대로 유지한다.
- 현재 화면 안의 `판정 근거 문장` 펼치기는 새 원본 화면으로 가는 링크로 대체한다.
- `근거 없음`, `오류`, `15초 초과` 그래프나 문제 목록을 누르면 해당 조건이 적용된
  `질문·답변 원본` 목록을 연다.
- 개별 문제 행의 `원본 보기`는 정확한 `recordKey` 한 건을 연다.
- 품질 판정 이유와 임계값은 원본 상세의 `품질 판정` 영역에도 함께 표시한다.

### 피드백

- 각 피드백 행에 `질문·답변 보기`를 추가하고 기존 `qaRecordId`로 원본 한 건을 연다.
- 원본 상세에서 피드백 종류, 작성자, 피드백 본문, 처리자·처리 메모를 함께 표시한다.
- QA 레코드가 삭제·보존기간 만료되었으면 다른 레코드를 추측해 연결하지 않고
  `연결된 질문·답변 기록 없음`으로 표시한다.

## 8. API와 기록 변경

### 읽기 API

```text
GET /api/answer-records
GET /api/answer-records/{recordKey}
```

- 목록 API는 본문을 반환하지 않는다.
- 상세 API만 질문·답변·질문자·피드백을 반환하고 매 열람을 감사 기록에 남긴다.
- 기존 `/api/questions`에는 `recordKey`를 추가해 상세 링크를 만든다.
- 품질 집계의 문제 레코드에도 `recordKey`를 포함한다.
- 기존 `/api/diagnostics/answers/evidence`는 호환 기간 동안 유지하되 화면에서는 새 상세 API를
  사용한다.

### 구조화 추적

새 요청은 Slack 이벤트를 받은 즉시 QA `record_id`를 만들고 다음 기록에 공통으로 넣는다.

- QA 레코드
- 전문 봇 라우팅·호출 기록
- 질문·답변 QA 기록과 피드백 연결

복합 질문의 하위 작업별 `stages/subresults` 구조화는 후속 개선으로 남긴다. 업무 본문은 기존
`question`과 `answer` 외의 단계 기록에 복제하지 않는다.

## 9. 권한과 안전 기본안

수집 원문 열람과 같은 정책을 적용한다.

- 질문·답변 **목록과 본문**: admin은 전체, 그 외 사용자는 본인의 Slack 질문과 자신이
  검토자로 지정된 채널 기록만 서버에서 선별
- 질문·답변 **본문**: 한 건을 명시적으로 선택했을 때만 반환하며 목록과 같은 권한을 재검사
- 본문 열람마다 actor, record ID, workspace, 시각, 성공/실패를 통합 감사 기록에 저장
- 감사 로그에는 질문·답변 본문을 복제하지 않음
- `Cache-Control: no-store, private`, 브라우저 캐시 금지
- 일괄 다운로드, 내보내기, 전체 펼치기, 원본 수정 기능은 제공하지 않음
- 콘솔 사용자에게 Slack 채널 멤버십을 실시간 검증할 수 없으므로 워크스페이스 담당자라는 이유만으로
  비공개 채널 질문·답변 본문을 보여 주지 않음
- QA 기록과 봇 답변은 `ArchiveStore` 검색 대상에 넣지 않으며 후속 답변의 사실 근거로 사용하지 않음

## 10. 사람 검토

기계 검증이나 별도 LLM 심판은 추가하지 않는다. 관리자는 통합 `답변 현황`에서 오류·근거 없음·
부정 피드백 등 우선순위가 높은 건을 찾고, `질문·답변 원본`에서 실제 질문, 답변, 출처를 확인한다.
검토 후 조치 내용은 기존 피드백 처리 기록에 남긴다.

기존 안전장치인 권한 선필터, 출처 강제, 전문 봇 출력 계약은 제거하지 않는다. 이것들은 답변의
정답 여부를 평가하는 검증이 아니라 정보 누출과 출처 불일치를 막는 실행 제약이다.

## 11. 구현 순서

다음 순서로 구현했다.

1. QA 상세 조회 저장소와 역할·검토 범위 제한 상세 API, 열람 감사 테스트
2. `/answer/records` 질문·답변 원본 화면
3. 답변 개요·품질·질문 처리 기록을 공통 기간 필터의 `답변 현황`으로 통합
4. 피드백 `qaRecordId` 연결
5. 품질 문제 목록을 원본 화면 링크로 교체
6. QA·전문 봇·권한·전달 기록에 공통 `trace_id` 추가
7. 메뉴 순서·명칭 변경, 구 주소 호환
8. 권한 누출·본문 미포함 목록·감사·구형 QA·복합 질문 회귀 테스트

## 12. 오너 확인이 필요한 결정

아래 두 항목을 기본안으로 구현해도 되는지 확인이 필요하다.

1. 질문·답변 본문은 수집 원문과 동일하게 **admin만** 열람하고 developer는 담당
   워크스페이스의 목록·메타데이터까지만 본다.
2. 사람 검토는 Slack 답변을 막는 사전 승인이 아니라, 현재 동작을 유지한 **전달 후 검토**로 한다.
