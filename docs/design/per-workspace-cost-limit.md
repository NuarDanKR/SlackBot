# 워크스페이스별 비용 상한 — 지갑 하나, 칸 여럿

> 작성: 2026-09-15
> 상태: 구현 완료·운영 반영 대기

## 1. 무슨 일이 있었나

경영본부(`mgmt`) 워크스페이스가 답을 못 했다.

```
WARNING tybot.answer 전문 봇 답변 불가 status=unavailable code=cost-limit attempted=['hermes']
WARNING tybot.specialist_contract 전문가 호출 실패 code=cost-limit CostLimitExceeded
        msg=일별 비용 상한 초과: 사용 $4.92 + 예상 $0.15 > 한도 $5.00
```

오너가 콘솔 > 운영 > 워크스페이스 관리에서 그 워크스페이스 상한을 **$2 → $5 → $10**
으로 올렸다. 화면에는 $10 이 그대로 보였다. **봇은 계속 막았다.**

이유가 셋이었고, 셋 다 화면에는 안 보였다.

| # | 무엇이 | 어떻게 보였나 |
|---|---|---|
| 1 | 봇이 `workspace.limit_usd` 를 **읽지 않는다** | 콘솔은 저장에 성공했다고 답한다 |
| 2 | 누적이 **워크스페이스별로 안 세어진다** | 다른 곳이 쓴 $4.92 가 여기를 막는다 |
| 3 | 오류가 **어느 상한인지 말하지 않는다** | 엉뚱한 쪽(워크스페이스)을 올리게 된다 |

`$5.00` 은 `/etc/tybot/tybot.env` 의 `DAILY_COST_LIMIT_USD` 였다. 콘솔에서 올린 $10 은
그 숫자와 아무 관계가 없었다.

이 세 가지는 각각의 버그가 아니라 **같은 고장의 세 면**이다. 상한이라는 개념이 두
곳(환경변수·DB)에 나뉘어 있는데, 둘을 잇는 코드가 없었고, 어느 쪽이 실제로 작동하는지
말해 주는 자리도 없었다.

## 2. 왜 지갑은 하나인가

오너 결정(2026-09-15): **API 키는 하나, 결제도 한 계정에서 나간다.**

그러면 전체 상한은 없앨 수 없다 — 그게 실제로 청구되는 금액의 뚜껑이다.
그렇다고 전체 상한만 두면 **먼저 쓰는 쪽이 다 가져간다.** 그날 일어난 일이 그것이다.

그래서 두 겹으로 둔다.

```
┌─ 전체 상한 (DAILY_COST_LIMIT_USD) ─── 결제 계정의 뚜껑. 환경변수, 재시작 필요 ─┐
│  ┌─ mgmt $10 ─┐  ┌─ tyit $10 ─┐  ┌─ pilot $2 ─┐                              │
│  └────────────┘  └────────────┘  └────────────┘   ← workspace.limit_usd, DB  │
└──────────────────────────────────────────────────────────────────────────────┘
```

**먼저 닿는 쪽이 막는다.** 그리고 오류는 어느 쪽인지 말한다.

> **전체 상한은 워크스페이스 상한들의 합 이상이어야 한다.** 작으면 안쪽 칸은
> 장식이 된다 — 올려도 안 먹고, 그 이유는 오류 문구에만 나온다. 헬스 화면이
> 이 어긋남을 먼저 말한다(§6).

## 3. 어디에 무엇을 두었나

| 것 | 자리 | 왜 거기인가 |
|---|---|---|
| 상한 판정·누적 | `gateway/cost.py` `CostGuard` | 순수 계산. **DB 를 모른다** — 그래야 DB 없이 시험된다 |
| 상한 값 공급 | `gateway/budget.py` `WorkspaceLimits` | 정책. TTL 캐시로 DB 를 감싼다 |
| 비용의 주인 | `gateway/cost.py` `attribute_to()` | 요청 단위 ContextVar |
| 주인을 세우는 곳 | `slack/pilot.py` Bolt 미들웨어 | 워크스페이스당 `App` 이 하나다 |
| 보여 주는 곳 | 상태 파일 → `console/reader.py` | **막는 숫자와 보이는 숫자가 같아야 한다** |

## 4. 왜 인자가 아니라 ContextVar 인가

답변 한 건 안에서 LLM 은 여러 겹으로 불린다 — 의도 분류, 전문 봇 라우팅, 본 답변,
문장 다듬기. `Router.complete()` 호출 자리가 코드베이스에 **열 곳이 넘고**,
`intent.py` · `compose.py` · `specialist_adapters.py` 는 워크스페이스라는 개념을
아예 들고 다니지 않는다.

거기에 인자를 끼우려면 그 함수들의 호출자, 또 그 호출자까지 서명을 고쳐야 한다.
그리고 **한 군데만 빠지면 그 경로의 비용은 아무에게도 안 달린다** — 예외도 안 나고,
화면에는 「사용 $0」 으로 정상적으로 보인다. 조용히 틀린다.

요청 ID 와 같은 성격의 값이다. 그래서 요청 단위로 한 번 세우고 안쪽은 읽기만 한다.

```python
@self.app.middleware
def attribute_cost(next):
    with cost.attribute_to(self.workspace):
        next()
```

**반드시 되돌린다.** Slack 이벤트는 스레드 풀에서 돌고 스레드는 재사용된다 —
안 되돌리면 다음 이벤트가 앞 이벤트의 워크스페이스를 물려받아 엉뚱한 칸을 깎는다.
`attribute_to` 는 `finally` 에서 토큰을 되돌리고, 시험이 그것을 고정한다.

미들웨어는 **핸들러마다가 아니라 한 곳에** 건다. 핸들러는 서른 개가 넘고 계속 늘어난다.
LLM 을 부르는 경로는 전부 Bolt 핸들러에서 시작하므로(배치 모듈 `collect`·
`attachment_review`·`daily_review`·`schedule_dm` 은 라우터를 부르지 않는다) 이 한 곳이
전부를 덮는다.

## 5. 왜 TTL 캐시인가

- **기동 시 한 번만 읽으면** 콘솔에서 바꾼 값이 재시작 전까지 안 먹는다. 그게 그날
  일어난 일이다. 사람은 자기가 한 조작이 먹혔다고 믿는다.
- **매번 읽으면** 답변 경로에 DB 왕복이 하나 늘고, DB 가 느린 순간이 곧 답변이 느린
  순간이 된다.

그래서 60초. 「바꾸고 1분 안에 먹는다」 는 사람이 기다릴 수 있는 시간이고, 초당 수십
호출이 와도 DB 는 분당 한 번만 읽힌다.

**못 읽으면 막지 않는다.** 직전 값을 쓰고, 그것도 없으면 전체 상한만 적용한다.
DB 가 잠깐 죽었다고 전 워크스페이스가 답을 못 하는 쪽이 예산 초과보다 나쁘다.
대신 경고를 남긴다 — 조용히 무한대가 되면 안 된다.

## 6. 보이는 숫자 = 막는 숫자

전에는 봇이 상태 파일에 **전체 누적**과 **전체 환경변수**를 워크스페이스 칸에 그대로
넣었다. 화면은 "경영본부 $4.92 / $10" 처럼 보였지만 $4.92 는 전 워크스페이스 합계였고
$10 은 아무도 안 보는 숫자였다. **두 숫자 모두 그 워크스페이스에 관한 것이 아니었다.**

지금은 `heartbeat` 가 그 워크스페이스의 누적과 그 워크스페이스에 실제로 걸리는 상한을
쓴다. 워크스페이스 상한이 없으면 걸리는 것은 전체 상한이므로 **그것을 보여 준다** —
빈 칸으로 두면 「상한 없음」 으로 읽힌다.

콘솔의 워크스페이스별 사용액도 상태 파일을 먼저 본다. 감사기록(JSONL)에는 **답변 한
건의 비용만** 남고 의도 분류·라우팅 호출은 안 남는다. 상한을 거는 쪽은 그 전부를
센다 — 화면이 JSONL 만 보면 사람이 보는 사용액보다 실제로 깎이는 쪽이 항상 크고,
"아직 여유 있는데 왜 막히나" 가 된다. 둘 다 있으면 **큰 쪽**을 쓴다(작은 쪽을 보여
주면 실제 사용액을 낮춰 말하게 된다).

### 워크스페이스 관리 화면
상한을 **고치는 자리**에 두 겹을 같이 둔다. 그날 이 화면에는 워크스페이스 상한만
있었고 실제로 막은 전체 상한은 어디에도 없었다 — 사람이 볼 수 있는 정보만으로는
원인에 닿을 수 없었고, 그래서 안 먹는 숫자를 세 번 올렸다.

- 표 위에 **전체 상한 · 워크스페이스 상한 합계 · 오늘 사용 · 상한 미설정 수**
- 합계가 전체를 넘으면 그 자리에서 말한다 — 「아래에서 올려도 전체 상한에서 먼저
  막힙니다. `DAILY_COST_LIMIT_USD` 를 올리고 재시작해야 합니다」
- 상한 입력란 아래에, 지금 입력한 값이 전체 상한 안에 들어가는지 **저장하기 전에**
- 표의 상한 칸에 그 워크스페이스의 오늘 사용액(80% 부터 눈에 띄게)

**상한만 바꾼 저장은 봇을 재시작하지 않는다.** 60초 TTL 로 다시 읽기 때문이다.
매번 재시작을 걸면 상한 한 칸 고치자고 답변이 끊기고, 사람은 그걸 알기 때문에
상한을 아예 안 고친다. 토큰·등급·상태·표시 이름·열람 대상이 바뀌면 그대로 재시작한다.
바뀐 것을 알 수 없으면(저장 전 행을 못 읽으면) 재시작하는 쪽으로 친다 — 안 해도 될
재시작보다 안 먹는 설정이 나쁘다.

### 헬스 화면
그리고 헬스 화면이 **닿기 전에** 말한다.

- 워크스페이스 상한이 전체 상한보다 큼 → `warn` 「먼저 전체 상한에서 막힙니다」
- 상한의 80% 사용 → `warn`
- 상한 소진 → `bad` 「이 워크스페이스는 더 답하지 못합니다」

## 7. 하지 않은 것

- **`usage_call` 표에 호출마다 한 줄 넣기.** 스키마 주석대로 그 표는 *감사기록에서
  옮겨 담는* 배치용이다. 답변 경로에서 직접 INSERT 하면 LLM 호출마다 DB 왕복이
  하나 늘어난다. 지금 필요한 것(상한을 실제로 걸기, 오늘 누가 얼마 썼는지 보기)은
  상태 파일로 충족된다. **남은 구멍은 「어제 mgmt 가 분류 호출까지 합쳐 얼마 썼나」**
  — 그 답은 아직 어디에도 없다. JSONL 임포터를 따로 만드는 일로 남긴다.
- **급증 시 자동 차단.** 기준선 대비 배수로 멈추는 것(`anomaly.kind = 'spike'`)은
  별개 일이다.
- **워크스페이스별 키/결제 분리.** 오너 결정으로 지갑은 하나다.

## 8. 운영 반영

1. 배포 후 `/etc/tybot/tybot.env` 의 `DAILY_COST_LIMIT_USD` 를 **워크스페이스 상한
   합계 이상**으로 올린다. 지금 값은 `5` 이고 이것이 그날 실제로 막은 숫자다.
2. `sudo systemctl restart tybot`
3. 콘솔 > 운영 > 워크스페이스 관리에서 워크스페이스별 상한을 확인한다. 이후 그
   값 변경은 **재시작이 필요 없다**(60초 내 반영).
4. 헬스 화면에 「전체 상한보다 큽니다」 경고가 남아 있으면 1번이 덜 된 것이다.

재시작 직후 워크스페이스 누적은 0에서 시작한다(옛 상태 파일에는 칸이 없다).
전체 누적은 그대로 유지되므로 지갑의 뚜껑은 그날 안에도 지켜진다.
