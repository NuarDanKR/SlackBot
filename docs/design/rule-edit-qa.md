# 규칙 편집 QA

_B-17 · 2026-09-17 구현_

전문 봇 규칙을 반영하기 전에 같은 질문을 현재 규칙과 편집 중 규칙에 각각 보내고,
답변·근거·비용을 콘솔에서 나란히 비교한다.

## 실행 경로

1. 개발자가 등록된 전문 봇과 시험 워크스페이스를 선택한다.
2. 콘솔은 개발자의 회사 이메일을 해당 워크스페이스 Slack 사용자로 해석한다.
3. `users.conversations`로 그 사용자가 실제 참여한 공개·비공개 채널을 구한다.
4. 같은 질문과 같은 전문 봇을 현재 규칙, 편집 중 규칙으로 한 번씩 실행한다.
5. 비교 결과를 30일 동안 `specialist_rule_test`에 보관한다.
6. 변경 요청에 시험 ID가 붙으면 승인 화면에도 같은 비교 결과를 표시한다.

라우팅은 다시 하지 않는다. 두 실행이 서로 다른 전문 봇으로 가면 규칙 비교가 아니기
때문이다. 다만 전문 봇의 계약 검사, 게이트웨이 모델 호출, 비용 가드, 도구 권한 검사는
실제 답변과 같은 경로를 사용한다.

## 보안과 데이터 경계

- 시험 근거는 콘솔 역할의 워크스페이스 범위와 Slack 실제 채널 멤버십을 모두 통과해야 한다.
- Slack 사용자나 채널 멤버십을 확인하지 못하면 권한을 넓히지 않고 시험을 중단한다.
- 시험 질문과 답변은 중앙 아카이브, `qa_record`, 검색 색인에 쓰지 않는다.
- 감사 기록에는 `reason=rule_test`, 시험 ID, 성공·실패 상태만 남긴다. 질문과 답변 본문은 남기지 않는다.
- 비교 결과는 승인 검토용 파생 데이터이며 30일 뒤 API 조회에서 제외되고 다음 저장 때 삭제된다.
- 변경 요청을 저장할 때 요청자·전문 봇·워크스페이스와 현재/편집 규칙 해시를 다시 대조한다.
  시험 뒤 규칙이 달라졌으면 다시 시험해야 한다.

## 비용

두 실행 모두 공용 `Router`와 `cost.attribute_to(workspace)`를 사용한다. 따라서 실제 모델
비용으로 당일 전체 상한과 DB의 워크스페이스별 상한을 소모한다. 전문 봇 호출 기록에는
`task_kind=rule_test_current` 또는 `rule_test_draft`로 구분한다.

## 운영 반영

`specialist_rule_test` 테이블이 추가되므로 코드 배포 뒤 다음 명령으로 전체 스키마를 적용한다.

```bash
sudo /opt/tybot/deploy/apply-schema.sh
sudo systemctl restart tybot-console
```

실환경 확인은 개발자 계정으로 전문 봇 변경 화면에서 수행한다. 현재 규칙과 편집 규칙의
답변·출처·비용이 보이고, 시험한 변경 요청을 올린 뒤 관리자 승인 화면에서도 같은 결과가
보이면 된다.
