# 에이전트 구조 — 마스터 봇 / 정리 봇 검토

_결정 문서 · 2026-08-19 · "수집봇 + 정리봇 + 마스터봇" 구상에 대한 평가와 대안_

---

## 0. 결론 요약

| 구상 | 평가 |
|---|---|
| 워크스페이스마다 수집 봇 | **부분 채택.** Slack **앱**은 워크스페이스마다 필요하지만 **프로세스는 하나**다. 프로세스를 쪼개면 단일 인스턴스 보장이 깨지고 파일 경쟁이 생긴다 |
| 정리 봇이 raw MD 를 **수정** | **채택 불가.** 원칙 1(원문 보존)을 정면으로 깬다. 의도는 맞지만 기법을 바꿔야 한다 → 2절 |
| 정리 봇이 **파생물**을 만든다 | **채택.** 정정·색인·분류·품질 리포트를 별도 레이어에 쌓는다 → 3절 |
| LLM 마스터 봇이 다른 봇을 **지휘** | **채택 불가(현 단계).** 오케스트레이션은 결정론적 스케줄러가 맞다 → 4절 |
| 마스터 봇 = **운영 콘솔** | **채택.** 사람에게 보고하고 승인을 받는 창구로서는 가치가 크다 → 5절 |

## 1. 왜 프로세스는 하나인가

```
      워크스페이스 A 앱          워크스페이스 B 앱          워크스페이스 C 앱
      (xoxb + xapp)             (xoxb + xapp)             (xoxb + xapp)
            │                         │                         │
            └──── Socket Mode 연결 ───┼──── Socket Mode 연결 ───┘
                                      ▼
                    ┌─────────────────────────────────┐
                    │   tybot.service  (프로세스 1개)  │
                    │   - WorkspaceBot × N            │
                    │   - ArchiveStore (공유)          │
                    │   - LLM 게이트웨이 (공유, 비용상한) │
                    └─────────────────────────────────┘
```

프로세스를 워크스페이스별로 쪼개면 생기는 문제:

| 문제 | 내용 |
|---|---|
| 파일 경쟁 | 여러 프로세스가 같은 MD 를 append → 라인 유실·프론트매터 충돌 |
| 비용 상한 무력화 | `DAILY_COST_LIMIT_USD` 는 프로세스 내 카운터다. N개면 상한이 N배 |
| 중복 답변 | 같은 토큰이 두 프로세스에 붙으면 Slack 이 양쪽에 이벤트를 보낸다 |
| 운영 복잡도 | systemd 유닛 N개, 로그 N곳, 재시작 순서 문제 |

→ **단일 작성자 원칙**: 원문 MD 를 쓰는 주체는 항상 하나여야 한다.

---

## 2. "정리 봇이 raw MD 를 수정" 이 위험한 이유

의도("context 오염 방지")는 정확하다. 하지만 **원문을 고쳐서** 달성하면 자산 자체가 무너진다.

| 위험 | 구체적으로 |
|---|---|
| 감사 추적 소실 | "봇이 왜 이렇게 답했나"를 역추적할 수 없다. 근거였던 원문이 이미 바뀌어 있다 |
| 요약 재귀 | 정리 봇이 LLM 으로 문장을 다듬으면, 그 결과가 다음 답변의 근거가 된다. 몇 세대 지나면 원문에 없던 숫자가 사실처럼 굳는다 |
| 재현 불가 | 같은 질문에 어제와 오늘 다른 답이 나오는데 원인을 특정할 수 없다 |
| 복구 불가 | Slack 원본은 rate limit 때문에 다시 긁을 수 없다(분당 1요청/15건). 지운 원문은 사실상 영구 소실 |
| 조용한 왜곡 | "3억 2천만원" → "약 3억" 같은 정리는 사람 눈에 개선처럼 보이지만, 금액 질의에 오답을 만든다 |

특히 마지막 항목이 결정적이다. **다듬기와 왜곡은 코드로 구별할 수 없다.**

### 그럼 오염은 어떻게 막나 — 레이어 분리

```
archive/workspaces/<ws>/channels/<channel-id>__<name>/raw/YYYY-MM-DD.md
├── 프론트매터        ← 메타데이터. 정리 봇이 갱신 가능(visibility, 조직코드, 색인 상태)
├── ## 요약           ← 사람이 관리. 봇은 읽지도 쓰지도 않음
└── ## 원문           ← 불변, append only. 어떤 봇도 기존 라인을 수정·삭제하지 않음
                        틀린 내용은 [정정] 라인을 옆에 덧붙인다

archive/derived/<ws>/<channel>.index.md   ← 정리 봇 산출물 (색인·분류·품질 리포트)
qa-log/                                    ← 감사 기록 (이미 분리됨)
```

**답변 경로의 근거는 `## 원문` 뿐이다.** 파생 레이어는 "어디를 볼지" 힌트로만 쓰고 인용하지 않는다.
이 규칙은 이미 코드에 있다(`store._raw_section` 이 요약 섹션을 근거에서 제외).

## 3. 정리 봇이 실제로 해야 하는 일

원문을 건드리지 않고도 오염 방지에 기여하는 작업들. **전부 결정론적이고, 대부분 LLM 이 필요 없다.**

| 작업 | 쓰는 대상 | LLM | 트리거 |
|---|---|---|---|
| 스키마 검사 (프론트매터·구조 위반) | 리포트만 | ✗ | 15분 |
| 중복·깨진 라인 탐지 | 리포트만 | ✗ | 15분 |
| **PII 사후 스캔** (수집 시 놓친 주민번호·계좌) | 격리 + 승인 요청 | ✗ | 15분 |
| 채널→조직 매핑 (본부/팀/현장 코드 부여) | 프론트매터 | ✗ | 조직 동기화 후 |
| 색인 생성 (제목·기간·발화자·키워드) | `derived/*.index.md` | ✗ | 1시간 |
| 미변환 자료 목록 (엑셀·이미지·도면) | `derived/*.index.md` | ✗ | 1시간 |
| 임베딩 생성 | DB | 임베딩만 | 1시간 |
| 채널 활동 리포트 (수집 밀림 경보) | Slack 관리 채널 | ✗ | 09:00 / 16:00 |
| 일일·주간 요약 초안 | `derived/` + 관리 채널 | ✓ | 17:30 / 금 16:00 |

**PII 격리만 예외적으로 원문에 손을 댄다.** 법적으로 지워야 하는 자료라 불가피한데, 방식이 중요하다:
1. 정리 봇은 **삭제하지 않는다.** 후보를 찾아 관리 채널에 승인 요청만 올린다
2. 사람이 승인하면 해당 라인을 `[삭제됨: PII, 승인자, 일시]` **묘비(tombstone)** 로 대체
3. 삭제 이력은 감사 로그에 남긴다 → "왜 이 원문이 없나"에 답할 수 있다

## 4. LLM 마스터 봇이 "지휘"하면 안 되는 이유

오케스트레이션(무엇을 언제 돌릴지)에 LLM 을 쓰면:

| 문제 | 내용 |
|---|---|
| 비결정성 | 같은 상태에서 다른 판단을 한다. 데이터 자산에 대한 쓰기 작업에서 이건 결함이다 |
| 디버깅 불가 | "왜 어제 취합이 안 돌았나"에 "모델이 그렇게 판단했다"는 답만 남는다 |
| 비용 | 감독을 위해 상시 토큰을 태운다. 산출물은 0 |
| 권한 확대 | 지휘하려면 모든 봇의 권한을 갖는다. 프롬프트 인젝션 한 번이 전체 아카이브 쓰기 권한이 된다 |

특히 마지막 항목: 아카이브에는 **외부에서 들어온 텍스트**(Slack 메시지)가 쌓인다. 그걸 읽고 행동을
결정하는 LLM 에게 쓰기 권한을 주면, 메시지에 심은 지시문이 그대로 실행될 수 있다.

**대안: systemd 타이머 + 단일 목적 잡.**
```
tybot.service              봇 (Slack 이벤트 응답 + 실시간 수집)
tybot-tidy.timer           정리 잡 (15분) - 검사·색인·PII 스캔
tybot-report.timer         리포트 잡 (09:00/16:00/17:30/금16:00)
tybot-update.timer         자동 배포 (이미 있음)
```
LLM 은 **언어 작업**에만 쓴다: 의도 분류, 요약, 판단(advice). 스케줄·분기·쓰기 결정은 코드가 한다.

## 5. 마스터 봇의 정당한 역할 — 운영 콘솔

"총괄 관리"를 **자율 지휘자**가 아니라 **사람을 위한 창구**로 정의하면 가치가 크다.

전용 관리 채널(`#운영_tybot`)에 봇이 올리는 것:

| 종류 | 예시 |
|---|---|
| 헬스 | 워크스페이스별 연결 상태, 수집 건수, 오늘 LLM 비용, 상한 대비 |
| 경보 | 스키마 위반 N건 / 수집 밀림(채널 X 마지막 수집 3일 전) / 아카이브 쓰기 실패 |
| **승인 큐** | PII 삭제 승인 / `visibility: public` 전환 요청 / 크로스 워크스페이스 열람 요청 |
| 품질 | 근거 못 찾은 질문 Top 10 (검색 품질 개선 입력) |
| 배포 | 자동 배포 결과, 테스트 실패 알림 |

승인 큐가 핵심이다. **자료를 워크스페이스 밖으로 내보내는 결정은 사람이 한다**는 원칙(관문 ②)을
Slack 버튼 한 번으로 처리할 수 있게 만드는 것이 마스터 봇의 실질적 가치다.

## 6. 최종 구조

```
[워크스페이스 A 앱] ┐
[워크스페이스 B 앱] ┼── Socket Mode ──► tybot.service ──► archive/workspaces/  (원문, 일자별 append only)
[워크스페이스 C 앱] ┘                    (수집 + 응답)          │
                                                              │ 읽기만
                          tybot-tidy.timer  ────────────────────┤
                          (검사·색인·PII스캔)                    ├──► archive/derived/  (파생물)
                                                              │
                          tybot-report.timer ──────────────────┴──► #운영_tybot (헬스·경보·승인큐)
                          (리포트·요약초안)
```

규칙 세 줄:
1. **원문을 쓰는 주체는 `tybot.service` 하나.** 정리·리포트 잡은 원문을 **읽기만** 한다.
2. **파생물은 근거가 아니다.** 답변의 근거는 `## 원문` 라인뿐.
3. **자료를 내보내는 결정은 사람이 한다.** 봇은 요청을 올리고 결과를 집행한다.

## 7. 도입 순서 제안

| 단계 | 내용 | 왜 이 순서인가 |
|---|---|---|
| 1 | 조직 매핑 + 본부→산하 하향 조회 (`CROSS_WS_READ`) | 지금 필요한 기능. 코드 이미 있음, 설정만 |
| 2 | `tybot-tidy` 잡 — 스키마 검사 + 수집 밀림 경보 | LLM 불필요. 조용한 고장을 드러내는 게 최우선 |
| 3 | `#운영_tybot` 관리 채널 리포트 | 2단계 결과를 사람이 보는 곳 |
| 4 | PII 사후 스캔 + 승인 큐(묘비 방식) | 법적 리스크 대응. 승인 흐름이 3단계에 의존 |
| 5 | 색인 생성 → PostgreSQL 인덱서 | 원문이 쌓인 뒤에 의미가 생긴다 |
| 6 | 일일·주간 요약 초안 | 위가 안정된 뒤 |

**하지 말아야 할 것으로 남겨두는 것**: 원문 자동 편집, LLM 자율 오케스트레이션, 봇이 스스로
`visibility` 를 `public` 으로 바꾸는 기능.
