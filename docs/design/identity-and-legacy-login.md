# 사용자 이름 변경 · 그룹웨어 연동 인증 — 검토

_결정 문서 · 2026-08-21_

목표(제기된 요구): 사용자가 Slack에서 봇에게 **그룹웨어 ID/PW를 입력**하면 로그인되고,
Slack 표시 이름이 `이름(사번)` 형식으로 바뀐다.

---

## 0. 결론

| 항목 | 가능? |
|---|---|
| 봇 토큰으로 **다른 사람**의 표시 이름 변경 | **불가.** Slack API가 허용하지 않는다 |
| 관리자 사용자 토큰으로 변경 | 조건부 가능 (유료 플랜 + 관리자 토큰 + 높은 위험) |
| Slack에 **ID/PW를 입력받아** 그룹웨어 로그인 | **하지 말아야 한다.** 대안이 있고 위험이 크다 |
| 사번 확인 후 이름 표기 | 가능 — 단 **Slack 프로필을 바꾸는 대신** 봇이 매핑을 관리 |

---

## 1. 표시 이름 변경 — Slack 제약

| 방법 | 필요 조건 | 판단 |
|---|---|---|
| `users.profile.set` (자기 자신) | 사용자 토큰(`users.profile:write`), 본인만 | 봇이 대신 못 한다 |
| `users.profile.set` (타인) | **관리자 사용자 토큰** + 유료 플랜 | 가능하지만 아래 위험 |
| SCIM / `admin.users.*` | **Enterprise Grid** | 현재 플랜 밖 |

**봇 토큰(`xoxb-`)으로는 어떤 경우에도 타인의 프로필을 바꿀 수 없다.** 표시 이름 변경을 하려면
관리자 개인 계정의 사용자 토큰(`xoxp-`)을 서버에 보관해야 하는데, 그건:

- 그 토큰 하나로 **워크스페이스 전체 관리 권한**이 열린다. 봇 토큰보다 훨씬 위험한 자산이다.
- 우리 봇은 외부에서 들어온 텍스트(Slack 메시지)를 읽는다. 그 프로세스가 관리자 토큰을
  들고 있으면, 프롬프트 인젝션 한 번이 워크스페이스 관리 권한이 된다.

→ **권고: 관리자 토큰을 봇 프로세스에 두지 않는다.**

---

## 2. ID/PW를 Slack으로 받는 것 — 하지 말아야 하는 이유

1. **비밀번호가 평문으로 Slack에 남는다.** DM도 Slack 서버에 저장되고, 워크스페이스 관리자·
   법적 보존(eDiscovery)·백업에서 열람 가능하다. 사용자가 메시지를 지워도 사본은 남는다.
2. **우리 아카이브가 그것을 수집한다.** 봇은 초대된 채널·DM의 원문을 저장한다.
   비밀번호가 MD 파일에 들어가면 되돌릴 수 없다(원문 불변 원칙과 정면충돌).
3. **사고 시 피해 범위가 그룹웨어 전체다.** 봇 서버가 털리면 사번이 아니라 계정이 털린다.
4. 사용자에게 "채팅으로 비밀번호를 입력해도 된다"는 습관을 학습시킨다. 피싱에 그대로 이용된다.

> 이건 구현 난이도 문제가 아니라 **설계상 하지 않는 쪽이 맞는** 사안이다.
> (수집기가 주민번호 패턴을 거르듯, 비밀번호도 애초에 들어오지 않게 해야 한다.)

---

## 3. 대안 — 같은 목표를 안전하게

### 방안 A. 이메일 기반 자동 매핑 (권장, 인증 없음)
Slack 프로필의 회사 이메일 ↔ 그룹웨어 사용자 테이블을 조인한다.

> **구현됨 (2026-09-01)** — `/일정`과 `/채널`을 처음 사용할 때 `users.info`의
> 이메일을 활성 `employee.email` 한 명과 정확히 대조해 `user_identity`에
> `verified_by=email_match`로 저장한다. 이후 권한 조회는 저장된 사번만 사용한다.
> 이메일은 매핑 테이블과 로그에 복제하지 않는다.

```
Slack users.info → profile.email → (레거시 DB 읽기전용 조회) → 이름·사번·소속
```
- 사용자가 아무것도 입력하지 않는다. 비밀번호도, 클릭도 없다.
- 사내 이메일은 이미 신뢰된 식별자다(SSO로 발급).
- 봇은 **자체 매핑 테이블**만 갖고, Slack 프로필은 건드리지 않는다.
- 답변·감사 기록에 `홍길동(12345)` 로 표기하면 요구사항의 실질이 충족된다.

**한계**: Slack 프로필에 이메일이 없거나 개인 이메일인 사용자는 매핑 실패 → 4절 폴백.

### 방안 B. 일회용 코드 (인증이 꼭 필요할 때)
1. 사용자가 봇에게 `인증 hong@taeyoung.com` 처럼 **사번/이메일만** 보낸다(비밀번호 없음).
2. 봇이 그 주소로 6자리 코드를 메일 발송.
3. 사용자가 코드를 DM으로 회신 → 매핑 확정.

비밀번호가 어디에도 흐르지 않는다. 코드는 5분 만료·1회용·시도 5회 제한.

### 방안 C. 그룹웨어 SSO 링크 (가장 정석)
봇이 **일회용 링크**를 DM으로 보내고, 사용자는 사내 그룹웨어 로그인 페이지에서 인증한다.
그룹웨어가 콜백으로 `state → slack_user_id` 매핑을 서버에 전달한다.

- 비밀번호는 그룹웨어에만 입력된다(원래 있어야 할 곳).
- 단점: 콜백을 받을 **인바운드 엔드포인트**가 필요하다 → 현재 "인바운드 포트 0개" 경계를 깬다.
  내부망에 작은 수신 서비스를 두고 DMZ 봇이 폴링하는 형태면 경계를 유지할 수 있다.

## 4. 매핑을 어디에 두나

Slack 프로필을 바꾸지 않고 **봇이 표기를 담당**한다.

```sql
CREATE TABLE user_identity (
  workspace   TEXT NOT NULL,
  slack_user  TEXT NOT NULL,          -- U0BNJ...
  emp_no      TEXT,                   -- 사번
  name        TEXT,                   -- 이름
  org_code    TEXT,                   -- 소속(조직 트리 연결)
  verified_by TEXT NOT NULL,          -- email_match | otp | sso
  verified_at TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (workspace, slack_user)
);
```
- 수집된 원문의 발화자 표기는 **바꾸지 않는다**(원문 불변). 매핑은 답변·요약·감사에서 표시할 때 쓴다.
- 매핑 실패한 사용자는 Slack 표시 이름 그대로 둔다. 추정하지 않는다.
- 이 테이블은 조직 트리(`org_unit`)와 함께 [db-and-acl.md](db-and-acl.md) 2단계에서 만든다.

**부수 효과가 크다**: `slack_user → org_code` 가 확보되면 권한 판정이 채널 멤버십에서
**조직 기반**으로 올라갈 수 있다(본부/팀/현장 상속). 지금 요구의 진짜 가치는 이름 표기가 아니라
이 매핑 자체다.

---

## 5. 그래도 Slack 표시 이름을 바꿔야 한다면

정책적으로 필요하다면 **봇과 분리된 별도 도구**로 한다.

- 관리자가 자기 PC에서 실행하는 **일회성 스크립트**(관리자 토큰은 실행 시 입력, 저장 안 함)
- 대상·변경 전후를 CSV로 남기고, 관리자 승인 후 일괄 적용
- 봇 프로세스는 이 토큰을 절대 보지 않는다

이 방식이면 워크스페이스 관리 권한이 상시 온라인 프로세스에 놓이지 않는다.

## 6. 권고 순서

| 단계 | 내용 |
|---|---|
| 1 | 방안 A(이메일 매핑) — 레거시 DB 읽기전용 조회로 `user_identity` 채움. 사용자 조작 0 |
| 2 | 매핑을 답변·요약·감사 기록의 발화자 표기에 적용 |
| 3 | 매핑 실패자만 방안 B(일회용 코드)로 보완 |
| 4 | Slack 표시 이름 일괄 변경이 필요하면 5절의 분리된 도구로 |

**하지 않을 것**: 봇이 비밀번호를 받는 흐름, 봇 프로세스가 관리자 토큰을 보관하는 구성.
