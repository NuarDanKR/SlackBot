# PostgreSQL vs MariaDB — TYBot 인덱스 DB 선택 근거

_서버 관리자 검토용 · 2026-08-19_

## 0. 결론 3줄

1. **한국어 부분일치 검색**: PostgreSQL 은 `pg_bigm` 확장으로 색인 검색이 되고, MariaDB 는
   MySQL 의 `ngram` 파서가 없어 **한국어 부분일치를 색인으로 못 한다** → `LIKE '%기성금%'` 풀스캔.
2. **벡터 검색**(2단계 임베딩): `pgvector` 는 성숙·표준. MariaDB 는 `VECTOR` 타입이 11.8 에서야 GA 라
   Rocky 8 기본 제공 버전(10.3/10.5/10.11)으로는 못 쓴다.
3. 나머지(재귀 CTE·트랜잭션·복제·백업)는 **실질 차이 없음**. 관리자가 MariaDB 에 훨씬 익숙하다면
   그건 무시할 수 없는 이점이므로, 아래 4절의 대안(Plan B)을 검토한다.

## 1. 우리 워크로드가 DB에 요구하는 것

| 요구 | 왜 필요한가 |
|---|---|
| A. 한국어 **부분일치** 검색 | "기성금" 을 찾을 때 원문은 "기성금을", "기성금이" 로 저장돼 있다. 어절 단위 색인으로는 안 잡힌다 |
| B. 조직 트리(본부>팀>현장) 상향/하향 조회 | 채널 권한 상속 판정 |
| C. 임베딩 유사도 검색 (2단계) | 키워드로 못 찾는 질문 대응 |
| D. JSON 감사 로그 | 질문·근거·권한판정 스냅샷 저장 |

## 2. 항목별 비교

### A. 한국어 전문검색 — **결정적 차이**
한국어는 교착어라 조사가 붙는다(`기성금` → `기성금을/기성금이/기성금은`).
따라서 **부분일치(substring) 색인**이 필요하다.

| | PostgreSQL | MariaDB |
|---|---|---|
| 기본 전문검색 | `tsvector` — 한국어 형태소 분석기 없음(단독으로는 부적합) | `FULLTEXT` — 공백·구두점 기준 어절 분리 |
| 부분일치 색인 | **`pg_bigm`** (2-gram GIN 색인) 또는 `PGroonga` | **없음.** MySQL 8 의 `ngram`/`MeCab` 파서는 MariaDB 에 이식되지 않았다 |
| 대안 | — | `LIKE '%…%'` 풀스캔, 또는 **bigram 테이블을 직접 만들어 관리** |

원문 라인이 수십만 줄로 늘면 `LIKE '%…%'` 풀스캔은 질문마다 전체 테이블을 읽는다.
직접 bigram 테이블을 만들면 되지만, 그건 `pg_bigm` 이 공짜로 주는 것을 손으로 짓고 평생 유지하는 일이다.

### B. 조직 트리 — **차이 없음**
재귀 CTE(`WITH RECURSIVE`)는 MariaDB 10.2+ 도 지원한다. 이 항목은 PostgreSQL 의 근거가 아니다.

### C. 벡터 검색 — 시점 차이
| | PostgreSQL | MariaDB |
|---|---|---|
| 확장/기능 | `pgvector` (HNSW·IVFFlat, 사실상 표준) | `VECTOR` 타입 — 11.7 프리뷰, **11.8 GA** |
| Rocky 8 에서 | PGDG 저장소로 `pgvector_16` 설치 | AppStream 모듈은 10.3/10.5/10.11 → **벡터 불가**. 별도 저장소로 11.8 도입 필요 |

임베딩은 4단계(키워드 검색이 부족할 때)라 당장 필요하진 않다. 다만 그때 DB를 갈아엎게 된다.

### D. JSON 감사 로그 — PostgreSQL 우세
- PG: `jsonb` 바이너리 저장 + GIN 색인 → `sources` 안의 문서 경로로 바로 검색 가능
- MariaDB: `JSON` 은 `LONGTEXT` 별칭 + CHECK 제약. 색인은 가상컬럼을 만들어 우회

### E. 운영 — MariaDB 우세할 수 있음
| 항목 | 판단 |
|---|---|
| 관리자 숙련도 | **사내에 MariaDB 운영 경험이 쌓여 있으면 그게 최대 이점.** 장애 대응 속도가 곧 가용성 |
| 백업 | `mariabackup` vs `pg_basebackup`/`pgBackRest` — 둘 다 성숙 |
| Rocky 8 패키징 | 둘 다 AppStream 모듈 존재. 최신 버전은 어느 쪽이든 벤더 저장소 추가 필요 (`dnf module list postgresql mariadb` 로 확인) |
| 파티셔닝·복제 | 이 규모(원문 수백만 줄 이하)에서는 둘 다 충분 |

## 3. 왜 이 선택이 "되돌릴 수 있는" 결정인가

**DB는 진실이 아니라 인덱스다.** 원문의 진실은 MD 파일(`/var/lib/tybot/archive`)이고,
DB는 언제든 MD 에서 재빌드된다. 따라서:

- 잘못 골라도 **재구축 비용이 스키마 재생성 + 재색인 시간**뿐이다. 데이터 유실 위험이 없다.
- 단, 감사 로그(`audit_query`)는 재빌드 불가 → 이건 백업 대상.

이 성질 때문에 "일단 익숙한 걸로 시작"도 합리적인 선택지다.

## 4. Plan B — MariaDB 로 가야 한다면

관리자 판단이 MariaDB 라면 다음을 감수하는 조건에서 진행 가능하다.

| 항목 | MariaDB 에서의 처리 |
|---|---|
| 한국어 검색 | `raw_line_bigram(line_id, gram CHAR(2))` 테이블을 직접 만들어 색인. 색인 삽입 로직·재빌드 배치를 우리가 관리 |
| 임베딩 | 4단계로 미루고, 필요해지면 별도 벡터 저장소(Qdrant 등) 추가 — **DB 2개 운영** |
| 감사 로그 JSON | 검색이 필요한 필드는 별도 컬럼으로 평탄화 |
| 최소 버전 | **10.11 이상** 권장 (10.3 은 2023-05 EOL) |

즉 비용은 "직접 만들 코드 + 나중에 벡터 저장소 하나 더". 기능이 불가능한 건 아니다.

## 5. 권고

- **1순위: PostgreSQL 16 + pg_bigm** — 한국어 검색이 이 시스템의 핵심 기능이고, 그걸 확장 하나로 해결한다.
- **차선: MariaDB 10.11+** — 사내 운영 표준이 MariaDB 이고 관리 인력이 그쪽에 있다면, 4절 조건으로 수용.
  이 경우 bigram 색인 구현·유지 공수를 일정에 반영해야 한다.
- 어느 쪽이든 **접속은 localhost 만**, 앱 계정은 최소권한(스키마 CRUD, SUPERUSER 금지).
