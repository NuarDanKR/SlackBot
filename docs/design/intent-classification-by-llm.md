# 의도 분류를 LLM 이 한다 — 규칙은 검증과 폴백만

> 작성: 2026-09-15
> 발단: 오너 질문 — "`intent.py` 같은 단순 파이썬 파일보다 LLM 이 직접 분류를
> 판단하게 하는 게 우리 마스터봇의 목적 아닌가. 기계적으로 분류해서 의도와 맞지
> 않는 케이스가 너무 많이 생길 것 같다."
> 구현 담당: Codex · 검증: Claude
> 연결: [B-47](../../BACKLOG.md#b-47) ·
> [`master-specialist-orchestration.md`](master-specialist-orchestration.md)

## 1. 진단 — 질문은 옳고, 원인은 조금 다르다

**`intent.plan()` 은 이미 LLM 을 먼저 부른다.** 정규식은 LLM 장애 시 폴백이다.
그래서 "LLM 을 안 써서 기계적" 은 아니다.

실제로 겪은 실패 셋을 좇으면 원인이 한곳으로 모인다 — **LLM 판정 위에 덧댄 규칙.**

| 사고(2026-09-14 운영) | 무엇이 틀렸나 |
|---|---|
| 스레드 안에서 "…뭔지 **찾고** 제대로된 답을 얘기해봐" → "저는 이전 대화를 기억하지 못해요" | `ACTION_RE` 에 `찾아` 는 있고 `찾고` 가 없었다. LLM 이 고른 `memory` 를 **되돌리려던 규칙**이 못 걸렸다 |
| "그럼 채널에 있는 **폴더**는?" → 전체 사용법 | `CANVAS_CAPABILITY_RE` 가 LLM **앞에서 가로채는데** 폴더를 몰랐다 |
| "여태까지 수집된 주간 보고" → `status` | `STATUS_RE` 의 `수집된` 이 관형형까지 삼켰다(이미 고침) |

셋 다 LLM 이 아니라 **규칙이 LLM 을 덮어쓰거나 가로챈** 자리다.

> 한국어는 활용형이 많다. 표면형 목록은 **반드시** 샌다. 어간으로 바꿔도 새는
> 속도가 느려질 뿐이다 — 어미를 세려 들면 같은 실수를 활용형 수만큼 반복한다.

## 2. 그래서 무엇을 바꾸나

`intent.py` 를 **없애는 것이 아니라 역할을 다시 가른다.**

| 판단 | 누가 | 왜 |
|---|---|---|
| 무엇을 묻는가(kind) | LLM | 의미 판단이다 |
| 지칭 해석(`standalone_question`) | LLM | 스레드 맥락을 읽어야 한다 |
| 후속 질문인가(`reference_mode`) | **LLM** ← 지금은 정규식 | 「방금 그거」 가 지칭인지 아닌지는 의미다 |
| 우리 범위를 묻는가 | **LLM** ← 지금은 정규식 | 자료 종류마다 정규식을 두면 샌다 |
| 필요한 전문 능력 | LLM(제안) + 코드(검증) | 이름은 열거형에서만 |
| 기간·범위(`여태까지`→전체) | **코드** | LLM 이 바꾸면 조회 범위가 조용히 달라진다 |
| 채널·DM 범위, 권한, 출처 | **코드** | 원칙 3·4. 모델 출력이 권한 입력이 되면 안 된다 |
| 쓰기 명령(수집) | **코드** | 무엇을 실행하는지 모호하면 실행하지 않는다 |

### 핵심 규칙 하나

> **규칙은 LLM 판정을 덮어쓰지 않는다.** 규칙이 할 수 있는 것은 셋뿐이다 —
> (a) LLM 이 없을 때의 폴백, (b) 안전 게이트(쓰기·권한), (c) LLM 출력의 **검증**.

지금은 (d) 「LLM 이 틀렸을 것 같으니 고쳐 준다」 가 섞여 있다. 그 자리가 전부
사고의 출처였다.

## 3. 바뀌는 계약

`intent.plan()` 이 LLM 에게 요구하는 JSON 에 두 필드를 더한다. **호출 횟수는
늘지 않는다** — 이미 분해 때 한 번 부른다.

```json
{"tasks": [{
  "kind": "search",
  "question": "원문 조각",
  "standalone_question": "지칭을 푼 문장",
  "reference_mode": "none|prior_turn|prior_topic|prior_attachments",
  "asks_about_our_sources": false,
  "capability": "internal_document_qa",
  "specialist": "hermes",
  "confidence": 0.9,
  "terms": ["..."]
}]}
```

- `reference_mode` — 이전 결과를 이어 가는가. **`<이전_스레드>` 가 있을 때만
  받는다**(코드가 확인). 없으면 강제로 `none`.
- `asks_about_our_sources` — 「캔버스도 읽어?」 「폴더는?」 처럼 **업무가 아니라
  우리 범위**를 묻는가. 참이면 결정적 안내(`SOURCE_SCOPE_ANSWER`)로 답한다.

### 코드가 검증하는 것 (그대로 유지)

- `kind` 는 `KINDS` 안에서만
- `capability` 는 `master_planner.CAPABILITIES` 안에서만
- `specialist` 는 **지금 활성인 후보** 안에서만
- `parent_record_ids` 는 이 스레드에 실제로 있는 ID 만
- `days`/`time_scope`/`document_query` 는 **코드가 원문에서 계산**한다. LLM 값을 안 쓴다

## 4. 지우는 것

| 지울 것 | 대신 |
|---|---|
| `followup_hint()` 의 `REFERENCE_RE`·`ACTION_RE` 판정 | LLM 의 `reference_mode` |
| `apply_followup()` 이 LLM task 를 **덮어쓰는** 부분 | LLM 이 준 값을 그대로 쓰고, 코드는 범위만 좁힌다 |
| `CANVAS_CAPABILITY_RE`·`SOURCE_CAPABILITY_RE` 의 **가로채기** | LLM 의 `asks_about_our_sources` |
| `MEMORY_ONLY_RE` | LLM 의 `kind: memory` |

**남기는 것**: `STATUS_RE`·`INGEST_RE`·`INGEST_ALL_RE`·`HELP_RE` 와
`classify_by_rule()`·`plan_by_rule()`. 이것들은 **폴백**이고, 하필 LLM 이 죽었을 때
가장 필요한 질문("상태 어때?")에 답하는 길이다.

## 5. LLM 이 죽었을 때

폴백은 **정상 경로를 흉내내려 하지 않는다.**

| 질문 | 폴백 동작 |
|---|---|
| `상태`·`도움말`·`수집` 같은 **명확한 명령** | 규칙으로 처리. 지금과 같다 |
| 업무 질문 | **범위를 좁히지 않고** 일반 검색. 후속 질문 해석은 하지 않는다 |
| 지칭만 있는 질문("그건?") | 되묻는다 — 추측해서 좁히지 않는다 |

**후속 질문 해석을 규칙으로 흉내내지 않는 것**이 이 절의 요점이다. 한 번
해 봤고(2026-09-14, 생략형 규칙), `topic_terms_of()` 가 "그럼"·"채널"·"있는" 을
주제로 돌려줘서 판정이 거의 항상 빗나갔다. **반쯤 맞는 규칙은 안 맞는 규칙보다
나쁘다** — 언제 걸리는지 사람이 예측할 수 없다.

## 6. 대가와 완화

| 대가 | 완화 |
|---|---|
| 같은 질문에 다른 분류(비결정성) | 골든셋으로 **측정**한다(§7). 없애지는 못한다 |
| 프롬프트가 길어져 분류 비용 증가 | 목록·지시는 **질문보다 앞**에 둔다 — 프롬프트 캐시는 접두사 일치다 |
| LLM 이 `reference_mode` 를 남발해 범위를 과하게 좁힘 | 근거 0건이면 **넓히지 말고** 「다시 확인하지 못했다」 로 답한다(현행 유지) |
| 프롬프트 인젝션으로 분류를 흔듦 | 흔들 수 있는 것은 **라우팅뿐**이다. 권한·출처·기간은 코드가 소유하므로 최악이 「엉뚱한 전문가에게 물어 답이 부실한 것」 이고, 되돌릴 수 있다 |

## 7. 측정 — 이것 없이는 바꾸지 않는다

비결정성을 **없앨 수 없으므로 재야 한다.**

1. **골든셋**: `qa-log` 의 **실제 질문**에서 뽑는다. 지어낸 질문으로 만든 골든셋은
   우리 상상을 측정한다(`scripts/measure_specialist.py` 와 같은 규칙).
2. **같은 의미 · 다른 표현**을 3~5개씩 묶어 넣는다. 「주간 보고 정리해줘」 /
   「여태까지 수집된 주간 보고를 종합해줘」 / 「주간보고 취합」.
3. 재는 것: `kind` 일치율, `reference_mode` 일치율, **같은 묶음 안의 일관성**
   (다수결과 다른 비율), 분류 지연·비용.
4. **합격선을 먼저 정하고 시작한다.** 지금 규칙 기반의 값을 기준선으로 먼저 잰다 —
   "좋아졌다" 를 말하려면 이전 값이 있어야 한다.

## 8. 구현 순서

한 단계가 통과하기 전에 다음으로 가지 않는다.

1. **기준선 측정.** 지금 코드로 골든셋을 돌려 §7 의 수치를 남긴다.
   이 단계의 산출물은 숫자 하나가 아니라 **재현 가능한 스크립트**다.
2. `reference_mode`·`asks_about_our_sources` 를 planner 프롬프트와 파싱에 더한다.
   **아직 규칙을 지우지 않는다** — 두 값을 함께 기록해 얼마나 어긋나는지 본다.
3. 어긋남을 보고 프롬프트를 고친다. 규칙과 LLM 이 다를 때 **어느 쪽이 맞았는지**
   사람이 표본으로 확인한다.
4. 규칙 가로채기·덮어쓰기를 지운다(§4). 폴백만 남긴다.
5. 다시 측정해 §1 의 사고 셋이 재현되지 않는지 확인한다.
6. 골든셋을 CI 가 아니라 **운영 리포트**로 돌린다 — 실사용 질문이 계속 들어오므로
   한 번 통과가 영원한 통과가 아니다.

## 9. 필수 테스트

- §1 의 사고 셋이 **분류 단계에서** 올바르게 갈린다(스레드 후속, 폴더 질문, 여태까지)
- LLM 이 `reference_mode` 를 줘도 **이전 문답이 없으면** `none` 으로 강제된다
- LLM 이 준 `days`·`time_scope` 는 **무시되고** 코드 계산값이 쓰인다
- LLM 이 지어낸 `capability`·`specialist`·`parent_record_id` 는 거부된다
- LLM 장애 시 `상태`·`도움말`·`수집` 이 규칙으로 처리된다
- LLM 장애 시 **후속 질문을 규칙으로 흉내내지 않는다**(되묻거나 일반 검색)
- 프롬프트의 전문 봇 목록·지시가 **질문보다 앞**에 온다(캐시)
- 분류 프롬프트에 근거 원문이 실리지 않는다

## 10. 하지 않을 것

- **분류를 위해 LLM 을 한 번 더 부르지 않는다.** 이미 부르는 호출에 필드를 더한다.
  호출을 늘리면 그게 바로 「두 번의 확률적 판정」 — 우리가 방금 없앤 구조다
  ([`master-specialist-orchestration.md`](master-specialist-orchestration.md) §2).
- 권한·기간·출처 판정을 LLM 에 넘기지 않는다.
- 규칙을 전부 지우지 않는다. LLM 이 죽었을 때 「상태 어때?」 에 답하지 못하면,
  하필 가장 필요한 순간에 봇이 침묵한다.
- 분류 정확도를 **답변 품질과 같은 것으로 취급하지 않는다.** 분류가 맞아도 근거가
  없으면 답은 못 한다. 둘을 한 숫자로 합치면 어느 쪽이 나빠졌는지 알 수 없다.
