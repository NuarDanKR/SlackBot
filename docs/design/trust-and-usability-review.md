# 신뢰·사용성 피드백 검토

_2026-09-01 · 사내 피드백 2건(신뢰·투명성 / 기능)에 대한 코드 기준 검증과 대응안_

이 문서는 "무엇을 하겠다"가 아니라 **"지금 코드가 실제로 무엇을 하고 있고, 무엇이 없고,
무엇은 기술적으로 불가능한가"** 를 먼저 못 박는다. 피드백을 준 쪽에 그대로 보여줄 수 있게
근거 파일을 함께 적는다.

| 피드백 | 판정 | 비고 |
|---|---|---|

## 1. A‑1 — 답변 근거·오류 대응·업무 효용

### 이미 있는 것 (코드 근거)

| 요구 | 구현 | 근거 |
|---|---|---|
| 근거만으로 답한다 | 권한 필터 → 원문 검색 → **0건이면 LLM 호출 자체를 안 함** → LLM → 출처 부착 → 로깅 | `answer.py` 상단 주석·`respond()` |
| 출처 강제 | 답변 끝에 `출처: #채널, 📄문서(날짜)` 를 **시스템이** 붙인다. 모델이 쓰지 않는다 | `Answer.to_slack()`, 프롬프트 5항 |
| 없으면 없다고 한다 | "원문을 찾지 못했습니다. 추측으로 답하지 않습니다" + 문서 목록 | `answer.py:400` |
| 사실과 판단 분리 | 판단 요청은 `💬 판단 요청으로 답합니다` 머리말 + 근거 건수 표기 | `advise()` |
| 오답 신고 | `/피드백`(모달) · 👎 리액션 · 스레드 `정정:` — **셋 다 같은 로그로** | `feedback.py`, `test_slash_feedback.py` |
| 전 요청 감사기록 | journald 1줄 + 일자별 MD + 월별 JSONL. 질문·의도·근거 건수·출처·모델·비용·소요시간 | `audit.py` |
| 답변 오류가 조용히 묻히지 않게 | 예외가 나면 사용자에게 원인과 조치를 알린다(401 등) | `failures.py` |

### 없는 것 — 이것이 피드백의 핵심이다

1. **"어떤 과정을 거쳤는지" 가 답변에 보이지 않는다.** 출처는 붙지만 *무엇으로 검색해
   몇 건 중 몇 건을 썼는지*는 사용자에게 안 보인다. 내부적으로는 다 있다
   (`Answer.reason`, `hit_count`, `intent_kind/source`) — **표시만 안 한다.**
2. **오답 신고 뒤 무슨 일이 일어나는지** 사용자에게 약속된 것이 없다. 누가 언제 보고
   어떻게 회신하는지가 없으면 신고는 한 번 하고 끝난다.
3. **업무 효용을 알려주는 온보딩이 없다.** `도움말` 은 명령 목록이고, "내 업무에 이게
   왜 쓸모 있나" 를 말하지 않는다. 처음 만나는 사람에게 필요한 건 명령어가 아니라 예시다.

### 대응안 (구현 가능, 크지 않음)

**(a) 근거 요약 한 줄을 답변에 붙인다.** 이미 가진 값을 쓰는 것뿐이다.

```
전산팀은 이번주 서버 이관을 진행했습니다. …

_근거: 「서버 이관」으로 검색 · 문서 3건 중 원문 12줄 사용 · claude-sonnet-5_
출처:
• #본사팀-전산_ABB110-회의, 📄2026-09.md(2026-09-01)
```

**(b) `/왜` (또는 답변의 `근거 보기` 버튼)** — 그 답변에 실제로 넣은 원문 줄을 ephemeral 로
보여준다. 감사기록에 이미 있으므로 새로 저장할 것이 없다. 사람이 직접 원문을 보고
판단할 수 있으면 "봇을 믿을 수 있나" 라는 질문이 "이 답이 맞나" 로 바뀐다 — 후자는
검증 가능한 질문이다.

**(c) 신고 처리 약속을 문구로 못 박는다.** 지금 `/피드백` 응답은 "검토에 반영하겠습니다"
까지다. *누가·언제·어떻게 회신하는지*를 넣고 그것을 운영 규칙으로 지킨다.

**(d) 첫 사용 안내 DM.** 봇이 워크스페이스에 들어오거나 사용자가 처음 멘션할 때, 명령
목록이 아니라 **직무별 예시 3개**를 보낸다.

## 2. A‑2 — 범위·제약·사람 감독

### 이미 있는 것

| 요구 | 구현 | 근거 |
|---|---|---|
| 어떤 콘텐츠 한도 | 채널 이름 규칙에 맞는 채널만 수집. 봇이 멤버인 곳만 | `channels.py`, `autojoin.py` |
| 그 범위를 사람이 확인 | `/수집상태` — 이 채널이 수집되는지, 아니면 **왜 아닌지와 조치** | `collection_status.py` |
| 권한 3축 | 채널 멤버십 / 문서 `share_with` / `ROOT_WORKSPACES`. **막는 쪽이 기본값** | `access/__init__.py` |
| 학습 제약 | 봇 답변·요약을 다시 근거로 저장하지 않는다(요약 재귀 금지). 근거는 사람이 쓴 원문뿐 | 원칙 1, `compose.py` 경계 표 |
| 제외 대상 | 주민번호 형식·등본류·개인 특정 목록은 수집 단계에서 거절 | `writer.ingest()` refused |
| 사후 감사 | 전 요청 감사기록 · 15분마다 아카이브 점검(원문 무편집) · 관리 콘솔 | `audit.py`, `tidy.py`, `console/` |
| 커밋 단계 방어 | 시크릿·주민번호 형식·원문 커밋을 도구와 무관하게 차단 | `.githooks/pre-commit` |

### 정직하게 말해야 하는 것

**사전 감독(답변 전 사람 검토)은 없다.** 지금 설계는 *사후 감사*다 — 답은 즉시 나가고,
전 요청이 기록되며, 틀리면 신고로 잡는다. 사전 검토를 넣으면 실시간성이 사라져 아무도
쓰지 않게 된다. 이건 **설계상 선택**이고, 그 선택을 문서로 밝히는 것이 "감독이 없다" 는
오해보다 낫다.

대신 사전 방어는 다른 층에 있다: 근거 0건이면 LLM 을 아예 호출하지 않고, 권한 필터가
LLM 이 내용을 보기 전에 걸러내고, PII 는 수집 단계에서 거절된다.

**벤더 학습**은 계약(DPA) 문제이고 코드로 보장하는 것이 아니다. 우리가 코드로 보장하는
것은 "우리가 파인튜닝하지 않는다"와 "봇 출력을 근거로 재사용하지 않는다" 두 가지다.
이 구분을 흐리면 안 된다.

### 없는 것

1. **"내가 볼 수 있는 범위" 를 사용자가 확인할 방법이 없다.** `/수집상태` 는 채널 단위다.
   사용자 단위로 "나는 어느 워크스페이스·어느 채널을 근거로 답을 받는가" 가 필요하다.
2. **미승인 상태의 가시화.** 지금 승인 데이터가 비면 기능이 조용히 0건이다
   (`schedule_folder_org` 가 그 예다). 사람은 고장과 구별하지 못한다.

### 대응안

**(e) `/권한`** — 내 워크스페이스, 내가 멤버인 수집 대상 채널 수, 크로스 열람 여부를
ephemeral 로. 조직 트리 연동 전에도 Slack 멤버십만으로 답할 수 있다.

**(f) 제약 고지 문서 1장** — 임직원용. "봇이 보는 것 / 못 보는 것 / 학습하지 않는 것 /
사람이 개입하는 지점" 을 표 한 장으로. 이 문서(§1·§2)가 그 초안이다.

## 3. B‑1 — 원본 파일을 그대로 Claude 에 보내기

> 피드백: "현장→본사 보고서는 PPT·Excel·이미지PDF 인데, 전처리하면 누락·왜곡이 생긴다.
> 원본을 그대로 보내면 Claude 의 문서 이해력을 100% 쓸 수 있지 않나?"

**절반은 맞고 절반은 API 가 허용하지 않는다.** Claude API 문서 입력은 형식별로 다르다.

| 형식 | 원본 그대로 전송 | 근거 |
|---|---|---|
| **PDF (스캔본 포함)** | **가능** | `document` 블록 + base64. 요청 32MB, 600페이지(200k 컨텍스트 모델은 100) |
| **이미지** (jpg/png 등) | **가능** | `image` 블록, base64 또는 URL |
| 일반 텍스트 | 가능 | `document` 블록 |
| **xlsx / pptx / docx / hwp** | **불가** | 문서 블록 타입이 아니다. Files API 도 블록 타입이 파일 MIME 과 맞아야 한다 |

### 그래서 이렇게 나눈다

**PDF·이미지 — 원본 전송으로 바꿀 값이 있다. 그것도 크게.**

스캔 PDF 는 지금 우리 전처리에서 **텍스트 레이어가 없어 `미변환`** 이다(`convert.py`).
즉 현장 보고서 상당수가 사실상 "제목만 아카이브"인 상태다. 원본을 그대로 보내면
Claude 가 이미지로 읽는다. 이건 개선이 아니라 **없던 기능이 생기는 것**이다.

게다가 Claude API 의 **citations 기능**이 있다. `document` 블록에 `citations: {enabled: true}`
를 켜면 응답이 인용 단위로 쪼개지고 각 조각에 `cited_text` 와 **페이지 번호**
(`page_location`)가 붙는다. 우리 원칙 2(출처 강제)를 **문서 페이지 단위까지** 끌어올릴 수
있다. 지금은 출처가 "문서·날짜" 까지인데, "그 문서 7페이지" 가 된다.

**xlsx·pptx — 원본 전송은 불가. 대안 셋.**

| 안 | 방법 | 대가 |
|---|---|---|
| A. 현행 유지 | openpyxl/python-pptx 로 텍스트 추출 | 표 구조·병합셀·차트·도형 위치가 사라진다(피드백이 지적한 그 문제) |
| B. PDF 로 변환해 전송 | LibreOffice headless | 서버에 LibreOffice 의존이 붙는다. 렌더 실패·글꼴 문제·변환 시간 |
| C. Claude 코드 실행에 파일을 준다 | `code_execution` + 컨테이너에서 Claude 가 직접 파싱 | 비용·지연 증가. 샌드박스에 `python-pptx`·`pypdf` 는 있고 **`openpyxl` 은 목록에 없어 확인 필요** |

**권고: PDF·이미지는 A안 즉시 전환, xlsx·pptx 는 B안을 파일럿으로 검증.**
xlsx 는 표가 핵심이므로 PDF 변환이 실제로 표를 보존하는지 실물로 확인해야 한다.

### 지금 구조가 이미 이걸 받쳐준다

다른 세션이 넣은 `stage_files()` 가 **원본 바이트를 `staging/objects` 에 격리 보관**한다
(`archive/files.py`). 원본 전송의 전제가 이미 있다 — 새로 저장 구조를 만들 필요가 없다.

### 그래도 전처리를 없애면 안 된다

원본 전송은 **답변 시점**의 이야기고, 전처리는 **검색 시점**을 위한 것이다. 둘은 목적이
다르다.

```
수집: 원본 보관(staging) + 텍스트 추출(검색·아카이브용)
답변: 텍스트로 후보 문서를 찾고 → 상위 N건의 **원본**을 Claude 에 넘긴다
```

전처리를 없애면 검색할 것이 없어져 "어느 파일을 볼지" 를 고를 수 없다. 하이브리드가
정답이다.

### 반드시 함께 결정할 것

1. **PII 노출 범위가 넓어진다.** 지금은 우리가 추출한 텍스트만 벤더로 간다. 원본을
   보내면 **우리가 못 읽어서 걸러내지 못한 것까지** 간다 — 스캔된 등본, 명단, 도면의
   개인정보. 수집 단계 PII 거절이 텍스트 기반이라 스캔본에는 작동하지 않는다.
   → 원본 전송 대상 문서에 **사람 승인 게이트**를 둘지 결정해야 한다(원칙 5).
2. **비용.** PDF 페이지는 토큰으로 환산돼 과금된다. 페이지 수가 많은 보고서는 텍스트
   추출보다 크게 비싸다. 실제 문서로 `count_tokens` 를 재고 일별 상한
   (`DAILY_COST_LIMIT_USD`)을 다시 잡아야 한다.
3. **답변 지연.** 32MB 업로드 + 페이지 처리로 Slack 3초 응답 한도를 넘는다.
   "찾는 중" 을 먼저 보내고 뒤에 답을 붙이는 형태가 필요하다.

## 4. B‑2 — 표·서식 렌더링

> 피드백: "제미나이는 md 로 표·굵기·크기가 렌더링되는데, 우리는 메시지라 표가 깨진다."

**Slack 메시지에서는 불가능하다.** Slack 의 `mrkdwn` 에는 표 문법이 없고 글꼴 크기 제어도
없다. 굵게·기울임·코드·인용·목록까지가 전부다. 이건 우리 코드 문제가 아니라 Slack 의
메시지 서식 한계다.

### 쓸 수 있는 것

| 방법 | 표 | 서식 | 비용 |
|---|---|---|---|
| 코드 블록 정렬 표 | 고정폭으로 **줄이 맞는다** | 없음 | 없음. 지금 당장 가능 |
| Block Kit 필드 | 2열까지 | 굵게 | 없음. 열 3개 이상은 안 됨 |
| **Slack 캔버스** | **진짜 표** | 제목·굵기·목록 | `canvases:write` 스코프 추가 + 앱 재설치 |
| 이미지로 렌더 | 원하는 대로 | 원하는 대로 | 무겁다. 복사·검색 불가 |

**권고: 짧은 표는 코드 블록, 긴 표·보고서형 답변은 캔버스에 쓰고 링크를 답변에 붙인다.**

### 캔버스로 갈 때 반드시 막아야 하는 것

**우리 캔버스 수집기가 봇이 쓴 캔버스를 다시 수집한다.** 그러면 봇 출력이 아카이브에
들어가 다음 답변의 근거가 된다 — 원칙 1(요약 재귀) 정면 위반이고, 이건 조용히 일어난다.

→ 캔버스 답변을 만들면 **그 캔버스를 수집 제외로 표시**해야 한다. 구현 전에 이걸
먼저 넣어야 한다. 순서를 바꾸면 오염된 아카이브를 되돌릴 방법이 없다(원문 불변).

또 하나: 캔버스는 채널에 남는다. 답변 내용이 채널 기록이 되므로 **권한 범위를 넘는
자료가 캔버스로 새어나갈 수 있다.** ephemeral 답변과 성질이 다르다 — 캔버스 답변은
"공유" 동작으로 취급하고 사용자가 명시적으로 누를 때만 만들어야 한다.

## 5. 구현 순서 제안

작은 것부터, 각각 독립적으로 되돌릴 수 있게.

| 순 | 항목 | 크기 | 값 |
|---|---|---|---|
| 1 | (a) 근거 요약 한 줄 | 작다 | 신뢰 체감이 가장 크게 바뀐다. 이미 가진 값만 쓴다 |
| 2 | (e) `/권한` · (c) 신고 처리 약속 문구 | 작다 | A‑2·A‑1 의 빈 칸을 메운다 |
| 3 | (b) `근거 보기` | 중간 | "믿을 수 있나" 를 "이 답이 맞나" 로 바꾼다 |
| 4 | 코드 블록 표 렌더 | 작다 | B‑2 의 즉시 완화 |
| 5 | **PDF·이미지 원본 전송 + citations** | 크다 | 스캔 보고서가 처음으로 읽힌다. **PII 게이트·비용 상한 먼저** |
| 6 | (f) 임직원용 제약 고지 1장 · (d) 첫 사용 안내 | 작다 | 피드백을 준 쪽에 내보일 산출물 |
| 7 | 캔버스 답변 | 중간 | **수집 제외 표시가 선행 조건** |
| 8 | xlsx·pptx → PDF 변환 파일럿 | 중간 | 표 보존이 실제로 되는지 실물 확인 후 판단 |

5번은 이 목록에서 유일하게 **보안 결정이 선행**되는 항목이다. 나머지는 우리가 판단해서
진행할 수 있다.
