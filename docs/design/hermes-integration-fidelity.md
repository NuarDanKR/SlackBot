# Hermes 연동 동작 복구와 품질 비교

작성: 2026-09-14

상태: 구현 완료 (2026-09-14) · Codex 검증 대기

인계: [`2026-09-14-master-specialist-orchestration-handover.md`](../verification/2026-09-14-master-specialist-orchestration-handover.md)

연결 작업: BACKLOG B-44. 이 문서는
[마스터 오케스트레이션 설계](master-specialist-orchestration.md)의 구현 우선순위와
도구·검색·출력 계약을 보완한다.

## 1. 판단의 근거와 한계

다른 부서 Hermes가 잘 작동한다는 사용자 관찰과 우리 실행 경로의 결함을 구분한다.
다른 부서의 실제 모델, 프롬프트, 검색 자료, 도구 실행 기록은 아직 비교하지 않았다.
마스터 존재 자체가 품질 저하의 원인이라고 단정하지 않는다.

현재 로컬 `subbots/hermes`에는 메타데이터와 프롬프트가 있다. 원본 Hermes 프로그램 전체를
실행하는 것과 다르다. 계약에는 원본 규칙을 TYBot 도구 위에서 실행한다고 적혀 있다.
서버의 실제 배포 파일과 DB 설정은 별도로 확인해야 한다.

확인한 결함과 제약:

- DB execution_mode를 읽고도 Specialist 생성자에 전달하지 않는다.
- tools 실행을 요청해도 ToolBox가 없으면 PromptSpecialist로 조용히 내려간다.
- prompt형 실행은 TYBot의 초기 근거 선택에 의존한다. 원본 Hermes의 탐색 루프와 다르다.
- 입력 근거는 40,000자에서 잘릴 수 있고 출력 규칙은 세 문장으로 제한한다.
- 프롬프트의 재검색 금지와 검색 횟수만으로 자료 없음을 판정하는 규칙은 검색 실패와
  실제 자료 부재를 혼동할 수 있다.
- DB rules가 파일 프롬프트보다 우선하므로 파일 변경만으로 운영 규칙이 바뀌지 않을 수 있다.

## 2. 역할 경계

| 주체 | 책임 |
|---|---|
| 마스터 LLM | 질문의 의도·지칭 대상·필요한 전문 능력 판단 |
| TYBot 코드 | 요청 범위, 권한, PII, 도구 실행, 출처 검증, 비용·시간 예산 |
| Hermes | 검색어와 읽을 자료 제안, 허용된 결과 해석, 업무 답변 작성 |

Hermes는 TYBot이 제공한 검색·읽기 도구를 반복 사용할 수 있다. 매 호출은 요청자의
RequestContext와 채널/DM 범위를 다시 검사한다. 자체 저장소 조회나 임의 URL 요청,
권한 변경, 아카이브 쓰기는 허용하지 않는다.

이전 답변에 언급된 특정 첨부를 다시 묻는 경우에는 해당 파일 ID 범위를 유지한다.
일반 주간 보고 종합은 현재 채널의 관련 문서 집합까지 탐색할 수 있다. 둘을 같은
검색 범위로 처리하지 않는다. DM도 사용자가 볼 수 없는 채널을 탐색하지 못한다.

## 3. Claude 구현 작업

### A. 실제 실행 모드 복구

- specialist_router.available의 DB 행 매핑을 수정한다.
- prompt/tools/http 모드별 실제 어댑터 선택을 테스트한다. 특히 http가 prompt로
  흘러가는 일반 분기가 없는지 현재 런타임 호출 경로를 확인한다.
- tools에 ToolBox가 없으면 `toolbox-unavailable`로 종료한다. prompt로 자동 강등하지 않는다.
- 콘솔은 선언 모드와 실제 모드, 도구 제공 여부, 규칙 출처(file/DB), 계약 버전과
  프롬프트 digest를 표시한다. 키와 프롬프트 본문은 실행 감사에 복제하지 않는다.
- 요청 단위의 모델·비용·근거 상태가 공유 어댑터에서 다른 요청과 섞이지 않는지 검사한다.

### B. 맥락과 전문 봇 입력

- 마스터가 해석한 독립형 질문을 검색과 Hermes에 동일하게 전달한다.
- 이전 사용자 질문과 근거 좌표를 연결하되 이전 봇 문장을 사실 근거로 전달하지 않는다.
- 문서명만 같고 file ID가 다르면 동일 문서로 합치지 않는다.
- 선행 설계의 ThreadFollowupResolver, EvidenceRef, 문서별 coverage를 재사용한다.
- 지칭 대상이 여러 개면 사용자에게 확인한다. 임의로 채널 전체 목록을 제공하지 않는다.

### C. 권한 내 탐색 복구

- 초기 검색 0건이라도 도구형 Hermes에는 실행 기회를 준다. 빈 seed를 명시적으로
  허용하고 “검색 결과 없음” 문자열을 가짜 AuthorizedEvidence로 만들지 않는다.
- search, read_document, read_channel, fetch_recent_slack이 실제 실행되는 통합 테스트를 둔다.
- 초기 검색에서 놓친 문서를 파일명 검색이나 문서 읽기로 발견하는 사례를 포함한다.
- 재검색은 허용된 범위 안에서만 한다. 검색어 변경은 가능하지만 무한 반복은 금지한다.
- 도구별 호출 수, 총 읽기량, 총 시간과 비용 예산을 코드가 제한한다. 예산 소진,
  도구 장애, 결과 없음은 별도 상태로 반환한다.
- 새 도구 결과의 실제 사용 source ID를 답변과 EvidenceRef에 연결한다. 초기 seed의
  출처만 붙여 새로 읽은 자료를 누락하지 않는다.
- 파일 존재, 변환 성공, 읽기 성공과 질문의 답을 찾았다는 사실을 별도로 취급한다.

### D. 작업별 출력과 입력 예산

- 세 문장 고정 규칙을 제거하고 짧은 질의응답, 다문서 종합, 비교, 보고서 모드를 구분한다.
- 보고서 종합은 핵심 현황, 공통 쟁점, 문서별 차이와 확인 범위를 표현할 수 있어야 한다.
- 길어진다고 정확하다고 판정하지 않는다. 금액·날짜 보존과 질문 항목 충족으로 평가한다.
- 입력을 40,000자에서 단순 절단하는 대신 문서별 배분·분할 읽기·coverage를 사용한다.
  모델 한도를 무제한으로 바꾸지 않는다. 누락된 자료는 명시한다.
- prompt와 DB rules의 실제 우선순위를 확인하고 적용된 규칙의 버전/digest를 비교한다.
  기존 DB 규칙을 자동 덮어쓰지 말고 변경 대상과 적용 절차를 인계한다.
- Canvas는 사용자의 명시 요청 때만 유지한다. 내용이 길다는 이유로 자동 전환하지 않는다.

### E. 불확실성과 장애 분리

| 상태 | 처리 |
|---|---|
| 질문 지칭/전문 능력 불확실 | clarification, 전문 봇을 임의 선택하지 않음 |
| planner 서비스 장애 | 허용 모델 재시도 후 unavailable |
| 검색 결과 없음 | 허용 탐색을 마친 뒤 확인 범위를 명시 |
| 검색 예산 소진 | search-budget-exhausted, 자료가 없다고 단정하지 않음 |
| 도구/전문 봇 실행 장애 | 제한된 다음 승인 후보 시도 후 unavailable |
| 출력 계약 위반 | 해당 출력 폐기, 예산 내 다음 승인 후보 또는 unavailable |

모든 경우 마스터가 업무 답변을 대신 작성하지 않는다. 후보 체인은 각 후보 한 번,
요청 전체 시간·비용 한도 내에서만 실행한다. 근거 부족을 다른 모델의 추측으로 채우지 않는다.

## 4. 품질 비교 방법

Claude는 로컬 합성·비식별 fixture로 재생 가능한 평가 도구와 결과 형식을 만든다.
다른 부서의 운영 자료나 자격을 자동으로 가져오거나 운영 Slack에 테스트 메시지를 보내지 않는다.
실제 부서 비교 자료가 확보되지 않으면 비교 미실시로 명시하고 구현 검증을 계속한다.

가능한 경우 세 경로를 비교한다.

1. 다른 부서의 검증된 Hermes 실행 경로
2. 같은 문맥과 허용 자료로 TYBot Hermes 어댑터를 직접 호출하는 경로
3. TYBot 마스터를 포함한 전체 경로

1과 2의 차이는 검색·어댑터·프롬프트 통합을, 2와 3의 차이는 맥락·라우팅·근거 전달을
우선 조사한다. 이는 원인 후보를 좁히는 실험이며 각 요소를 하나씩 고정해 확인한다.
모델 버전, 규칙 digest, 자료 snapshot, 권한 범위, 도구·시간·토큰 예산과 실행 횟수를
기록한다. 조건이 다르면 동일 조건 비교라고 표시하지 않는다.

최소 사례:

- 미수금 질문과 같은 스레드의 모호한 후속 질문
- 특정 변환 실패 첨부 한 건 재확인
- HWP/HWPX 주간 보고 여러 건 종합
- 초기 검색 결과 0건이지만 읽을 수 있는 관련 문서가 존재하는 사례
- 표의 금액·단위·기준일 비교, 이미지 근거 질의
- 실제 자료 없음, 도구 장애, 예산 소진
- 다른 채널 자료와 이전 봇 답변을 유혹 자료로 포함한 권한·재귀 차단 사례

평가 항목: 지칭 대상 정확성, 파일 ID 재현율, 실제 읽은 문서와 인용 일치,
질문 항목 충족, 숫자 보존, 관련 없는 자료 포함 여부, 실패 상태 정확성,
라우팅 일관성, 지연과 비용. 의미가 같은 질문은 여러 표현으로 반복해 분류 일관성을
측정한다. 문장 일치나 무조건 긴 답변을 합격 기준으로 사용하지 않는다.

## 5. Codex 인계와 완료 조건

Claude는 변경 커밋, 실행 명령, 테스트 결과, 실제 모드·규칙 출처 확인 결과,
DB 마이그레이션 필요 여부와 아직 하지 못한 운영 비교를 verification 문서에 기록한다.
업무 원문과 질문 본문은 저장소에 커밋하지 않고 합성 fixture와 비민감 집계만 남긴다.

Codex는 DB 행부터 실제 어댑터·도구 호출까지 연결된 테스트를 우선 확인한다.
SQL에 문자열이 존재하거나 dataclass를 직접 만든 테스트만으로 모드 복구를 인정하지 않는다.
초기 검색 0건에서 문서 발견, 단일 파일 후속 질문 범위 유지, 긴 종합의 coverage,
불확실성과 장애 구분, 마스터 업무 답변 호출 0건을 실행 검증한다.

필수 단계별 회귀가 통과한 뒤 pytest, Ruff, 프론트 빌드와 데스크톱 상세 추적을 확인한다.
Windows 셸 미설치 등 환경 실패를 숨기거나 모든 관련 테스트를 skip하지 않는다.
Linux 지원 환경 검증과 실제 부서 비교가 없으면 그 항목은 미검증으로 인계한다.
