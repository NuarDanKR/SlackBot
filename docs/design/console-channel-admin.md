# 콘솔 채널 관리 — 담당자를 일괄로 정한다

> 작성: 2026-09-15
> 상태: 구현 완료·운영 검증 대기

## 1. 왜 필요한가

옛날에 만든 채널이 `/채널 수정` 이 안 된다. **담당자가 없기 때문이다.**

`ChannelOwnerStore` 는 TYBot 이 채널을 만들 때 요청자를 기록한다. 그 전에 사람이 직접
만든 채널에는 그 기록이 없다. 기동 시 `record_if_missing()` 이 Slack 개설자로 메우지만,
TYBot 이 만든 채널은 Slack 상 개설자가 **봇 자신**이라 사람이 안 들어간다.

결과: 그 채널은 **아무도 고칠 수 없다.** 검토자도 못 정하고, 그러면 첨부 검수 DM 도
안 간다. 한 칸이 비어서 그 뒤 기능이 줄줄이 멈춘다.

Slack 에서 채널마다 명령을 치게 하면 수십 개를 하나씩 돌아야 한다. 그 일은 안 한다 —
그래서 지금까지 안 된 것이다. **한 화면에서 표로 보고 한 번에 정하는** 길이 필요하다.

## 2. 무엇을 보여 주나

한 줄 = 한 채널. 워크스페이스 안에서 채널 ID 로 식별한다(이름은 바뀐다).

| 칸 | 출처 | 왜 필요한가 |
|---|---|---|
| 워크스페이스 · 채널명 | 아카이브 원문 프론트매터 | 어느 채널인지 |
| 담당자 | `ChannelOwnerStore`(JSON) | **비어 있으면 아무도 못 고친다** |
| 검토자 · 발송 시각 | `channel_reviewer`(DB) | 비어 있으면 첨부 검수가 아무에게도 안 간다 |
| 문서 수 · 원문 줄 수 | 아카이브 | 실제로 쌓이고 있는가 |
| 첨부 줄 수 | 아카이브 | 문서가 근거로 쓰이는가 |
| 마지막 수집 | 아카이브 | **언제 멈췄나** — 목록에 있다고 살아 있는 게 아니다 |
| 답변 수 · 마지막 답변 | QA 기록(`qa-*.jsonl`) | 사람이 실제로 쓰는 채널인가 |

### 활성도를 왜 같이 보나
담당자를 정할 때 **어느 채널이 살아 있는지** 알아야 한다. 답변이 0건이고 수집도 멈춘
채널에 담당자를 붙이는 것은 일을 만드는 것이다. 반대로 답변이 많은데 담당자가 없는
채널이 가장 급하다 — 그 줄이 맨 위로 오게 정렬한다.

## 3. 무엇을 하지 않나

- **채널을 만들거나 지우지 않는다.** 이 화면은 이미 있는 채널의 메타데이터만 다룬다.
- **원문을 보여 주지 않는다.** 건수와 시각만. 본문 열람은 기존 경로(기록을 남긴다)로.
- **검토자를 여기서 바꾸지 않는다.** 검토자는 채널 소유자가 Slack 에서 정한다 —
  여기서 바꾸면 그 결정이 두 곳에서 나고, 누가 정했는지가 흐려진다. **보여만 준다.**
- 담당자가 아닌 사람을 담당자로 **추측하지 않는다.** 빈 칸은 빈 칸으로 둔다.

## 4. 담당자 저장 — 잠금이 필요하다

`ChannelOwnerStore` 는 JSON 파일이고 `threading.Lock` 으로만 감싸여 있다. 그건 **한
프로세스 안에서만** 유효하다. 콘솔(`tybot-console`)과 봇(`tybot`)은 다른 프로세스다.

지금은 봇만 쓰니 문제가 없었다. 콘솔이 쓰기 시작하면 이렇게 된다.

```
콘솔   읽기 ─────────── 쓰기(내 변경만 담긴 전체 파일)
봇          읽기 ── 쓰기(내 변경만 담긴 전체 파일)
                                    ↑ 콘솔 변경이 사라진다
```

원자적 교체(`tmp.replace`)는 **파일이 깨지는 것**을 막을 뿐, 읽고-고치고-쓰는 사이의
분실은 막지 못한다.

그래서 `lock.FileLock` 으로 **프로세스 간** 잠금을 건다. 이미 있는 것을 쓴다.

잠금을 못 잡으면 **실패로 답한다.** 기다리지 않고, 무시하지도 않는다 — 조용히 덮어쓰면
다른 쪽 변경이 사라지고, 그건 화면에 성공으로 보인다.

## 5. 일괄 지정

표에서 여러 줄을 고르고 담당자 한 명을 지정한다.

- **부분 성공을 부분 성공이라고 말한다.** 10건 중 3건이 실패하면 「3건 실패」 와 그
  사유를 돌려준다. 전부 성공으로 보이면 사람은 확인하지 않는다.
- 이미 담당자가 있는 채널은 **덮어쓰지 않는다**(`overwrite` 를 명시해야 바뀐다).
  기존 담당자는 그 채널을 만든 실제 요청자일 수 있다 — 덮으면 그 사람이 권한을 잃는다.
- 누가 언제 지정했는지 감사 기록에 남긴다.

## 6. 권한

관리자만 본다. 채널 목록 자체가 조직 구조를 드러내기 때문이다(원칙 3).

담당자로 지정할 사람은 **Slack 사용자 ID** 다. 콘솔은 Slack 을 모르므로, 이미 아는
사람 중에서 고른다 — `user_identity` 에 매핑된 재직자. 그 목록에 없는 ID 를 그대로
받으면 오타가 그대로 저장되고, 그 채널은 계속 아무도 못 고친다.

## 7. 구현 순서

1. `ChannelOwnerStore` 에 프로세스 간 잠금 + `set_owner`/`all()` 추가
2. `console/channel_admin.py` — 표 한 줄을 만드는 순수 함수와 일괄 지정
3. 콘솔 API — 조회·일괄 지정
4. 콘솔 화면 — 표, 다중 선택, 빈 담당자 우선 정렬

## 8. 채널 수집 작업

표에서 여러 채널을 선택해 다음 작업을 시작한다.

- **채널 파일 수집**: Slack 파일 탭의 미수집 파일을 기존 변환·PII·원문·색인 경로로 처리
- **과거 전체 수집**: 봇 초대 이전 메시지, 스레드 답글, 현재 Canvas와 파일을 체크포인트 방식으로 처리

수집과 변환은 오래 걸리므로 HTTP 요청에서 직접 실행하지 않는다. 콘솔은 고정된 두 작업
중 하나와 검증된 `(workspace, channel_id)`만 `collection_jobs` runner에 넘긴다. 임의
명령·스크립트 경로·환경변수는 입력받지 않는다. 작업은 한 번에 하나만 실행하고 상태 및
최근 로그는 `STATE_DIR/collection-jobs`에서 조회한다.

콘솔은 Slack API와 토큰을 직접 사용하지 않는다. 봇이 heartbeat에 참여 중인 수집 대상
채널의 ID와 이름만 기록하고, 콘솔은 이를 아카이브 통계와 합친다. 따라서 아직 원문이 없는
새 채널도 표에서 선택할 수 있으며 메시지·파일명·구성원 정보는 heartbeat에 저장하지 않는다.

### 2026-09-15 404 원인

`StaticFiles`의 `/` 마운트가 `/api/channels`보다 먼저 등록되어 운영 환경에서 정적 라우트가
API 요청을 가로챘다. 모든 API를 등록한 뒤 정적 프론트엔드를 마지막에 마운트하도록 고쳤다.
