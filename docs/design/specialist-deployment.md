# 전문 봇 배포 — 개발자와 저장소가 다를 때

> 질문(2026-09-07): 전문 봇은 팀마다 개발자가 다르고 **저장소도 다를 수 있다.**
> 지금 배포·업데이트는 마스터 봇 저장소 하나를 기준으로 돈다. 어떻게 해야 하나.
>
> 상위 설계: [`bot-hierarchy.md`](bot-hierarchy.md)

## 지금 구조로는 안 된다

전문가는 현재 **마스터 프로세스 안의 파이썬 코드**다.

```python
class SpecialistAdapter(Protocol):
    def complete(self, request: SpecialistRequest) -> str: ...
```

`ALLOWED_ADAPTERS` 는 우리 저장소의 키 목록이고, `specialist_contract.execute()` 는
그것을 우리 스레드에서 부른다. 즉 지금은 **팀 개발자가 우리 저장소에 코드를 넣어야**
하고, 배포도 우리 릴리스를 기다려야 한다.

이 구조가 무너지는 자리는 셋이다.

| | 무슨 일이 나는가 |
|---|---|
| 릴리스 결합 | 법률 봇 프롬프트 한 줄을 고치려고 **마스터 봇 전체 테스트를 통과**하고 봇을 재시작해야 한다 |
| 의존성 충돌 | 팀 A 의 라이브러리가 팀 B 의 것과 안 맞으면 `pip install` 한 번에 **마스터 봇이 안 뜬다** |
| 자격 노출 | 같은 프로세스라 남의 코드가 `DATABASE_URL`·Slack 토큰·아카이브 파일을 그대로 읽는다. 계약(`execute`)은 **출력만** 검사한다 |

셋째가 결정적이다. 계약이 막는 것은 "출처를 붙였는가·너무 길지 않은가" 뿐이다.
같은 프로세스 안에서는 **무엇을 읽었는지 막을 방법이 없다.**

## 어디서 돌릴 수 있는가

| | 어디서 도는가 | 저장소 | 실패 격리 | 자격 |
|---|---|---|---|---|
| 같은 프로세스 (지금 구조) | 마스터 안 | 우리 것 하나 | 없음 | 공유 |
| pip 패키지 | 마스터 안 | 팀별 | **없음** | 공유 |
| 별도 서비스 | 팀이 띄운 곳 | 팀별 | 있음 | 분리 |

**pip 패키지를 하지 않는다.** 저장소만 갈라지고 위 세 문제 중 두 개가 그대로 남는다.
"남의 배포에 우리 봇이 죽지 않는다" 는 계약을 pip 의존성 해석이 정면으로 깬다.
겉으로는 깔끔해 보여서 가장 고르기 쉬운 오답이다.

그런데 **이 표만으로는 답이 안 나온다.** 코드를 어디서 돌릴지 정하기 전에,
애초에 **코드를 받아야 하는지**를 물어야 한다. 다음 절이 그것이다.

## 권장 — 능력의 값이 어디 있는지로 갈린다

> **2026-09-07 고침.** 처음에는 「1단계: 같은 저장소 유지, 첫 전문가 Hermes 는 우리가
> 만든다」 로 썼다. **틀렸다.** Hermes 는 다른 팀이 만들었고 지금도 그 팀이 개발 중이다.
> 게다가 **Node.js** 다 — 파이썬 프로세스 안의 어댑터가 될 수 없다. 즉 Hermes 에게는
> 1단계가 애초에 없었다. 아래는 그 사실을 반영해 다시 쓴 것이다.

저장소가 다른 것은 정해진 조건이다. 정할 것은 **무엇을 주고받는가** 뿐이고, 그것은
그 능력의 값이 어디 있는지에 달렸다.

| | 값이 있는 곳 | 우리가 받는 것 | 런타임 결합 | 근거가 밖으로 나가나 |
|---|---|---|---|---|
| **A. 프롬프트 계약** | 프롬프트·판정 규칙 | 파일(버전) | **없음** | **아니다** |
| **B. HTTP 서비스** | 그쪽 코드·모델·색인 | 문장 | 있음 | 나간다 |
| **C. MCP 도구** | 조회 대상 | 도구 결과 | 있음 | 질의만 |

### Hermes 는 A 로 시작한다

소스를 읽어 보면 Hermes 의 값은 **모델이 아니라 판정 규칙**에 있다.

| 있는 것 | 무엇인가 |
|---|---|
| `src/prompts/*.md` 4개 | 요약 대조·질의 응답 지시문 |
| `ingest/summary.js` (233줄) | 요약에서 어긋난 곳을 후보로 뽑는 규칙 |
| `ingest/verify.js` (280줄) | 근거 인용을 원문에서 실제로 찾는 대조(fold) |

이것들은 **모델 가중치가 아니라 글과 규칙**이다. 우리 모델로 우리 근거에 대고 돌려도
같은 판정이 나온다. 그러면 얻는 것이 크다.

- **런타임 의존이 없다.** 그 팀이 배포하는 중이어도 우리 봇은 답한다
- **근거가 우리 밖으로 나가지 않는다.** 위험 하나가 통째로 사라진다
- 그 팀이 계속 개발하는 것이 문제가 아니라 **이득**이 된다 — 프롬프트 버전을 올려
  가져오면 된다. 코드 포팅은 움직이는 표적을 쫓는 일이지만, 프롬프트는 그렇지 않다

주고받을 것을 계약으로 고정한다.

```
hermes-rules/                 (그 팀 저장소의 태그 하나)
  prompts/summary-check.md
  prompts/qa.md
  rules/fold.md               ← 무엇을 지우고 무엇을 남기는지
  VERSION                     ← 우리가 무엇을 쓰고 있는지 콘솔에 보인다
```

`fold.md` 를 따로 두는 이유가 있다. Hermes 는 근거 정규화가 관문과 화면에서 갈려
**멀쩡한 근거가 「원문에서 못 찾음」 으로 버려지는** 사고를 다섯 번 겪었다. 우리가
그 규칙을 다시 구현하면 여섯 번째가 된다. 규칙을 글로 받아 **한 곳에** 옮긴다
([`summary-review.md`](summary-review.md) 참조).

### B 로 넘어가는 조건

세 가지 중 하나가 생기면 A 로는 안 된다.

1. 그 팀이 **자기 모델·자기 튜닝**으로 답하고 싶다
2. 판정이 프롬프트가 아니라 **그쪽 색인·상태**에 달려 있다
3. 우리가 프롬프트를 따라가지 못할 만큼 자주 바뀐다

그때는 그 팀이 엔드포인트를 만들어야 한다. **지금 Hermes 에는 HTTP 서버가 없다** —
Socket Mode 봇과 CLI 스크립트뿐이다. 그래서 이건 「설정을 바꾸는 일」 이 아니라
**그 팀의 개발 항목**이고, 그 사실을 먼저 서로 알아야 한다.

넘길 때 **반드시 받아야 하는 보장**이 하나 있다.

> **Hermes 가 자기 아카이브를 참조하지 않는다.**

없으면 그쪽 워크스페이스 원문 지식이 섞이고 거기에 **우리 출처가 붙는다.**
권한 유출인데 출처가 위장돼 추적조차 안 되는, 가장 위험한 실패 모드다.
A 에서는 우리가 돌리므로 이 조건이 아예 성립하지 않는다 — 그것도 A 를 먼저 두는 이유다.

### 도구만 필요하면 전문가가 아니라 MCP

팀이 원하는 것이 "우리 법령 조회를 봇이 쓸 수 있게" 뿐이면 **전문 봇을 만들 필요가
없다.** 그건 도구이고, `specialist_mcp` 허용 목록이 이미 그 자리다.

| | 전문 봇(HTTP) | MCP 서버 |
|---|---|---|
| 팀이 소유하는 것 | 프롬프트 · 모델 · 평가 루프 | 조회 도구 |
| 답을 만드는 주체 | 그쪽 모델 | 우리 모델(도구만 호출) |
| 언제 고르나 | 판단이 그 분야 지식에 달렸을 때 | 사실 조회만 필요할 때 |

**MCP 쪽이 훨씬 싸다.** 먼저 이걸로 되는지 묻는다.

## 배포·업데이트 — 무엇을 누가 하나

핵심은 하나다. **우리 배포와 그들 배포를 분리하고, 우리 쪽 레버는 「끄기」만 남긴다.**

| | 누가 | 어디서 |
|---|---|---|
| 전문가 코드 배포 | 팀 | 팀의 CI/서버. **우리 콘솔의 배포 버튼과 무관** |
| 전문가 등록·범위·모델 | 팀 개발자가 요청 → 우리 관리자 승인 | 콘솔(이미 있다) |
| 켜기/끄기 | 우리 관리자 | 콘솔 `state` |
| 되돌리기 | 우리 관리자 | **`state='disabled'`. 배포 없이 즉시** |

되돌리기가 배포를 타지 않는 것이 중요하다. 남의 코드가 이상하게 답할 때 우리가
기다릴 수 있는 시간은 몇 분이 아니라 몇 초다.

### 버전은 그쪽이 보고한다

우리가 그들 저장소를 pull 하지 않으므로 버전을 알 길이 없다. 응답에 담게 한다.

```
→ 200 {"text": "...", "version": "1.4.2"}
```

`specialist_bot.version` 을 **응답에서 갱신**한다. 그러면 콘솔에서 "지금 무엇이
돌고 있나" 가 보이고, 팀이 배포했는데 안 바뀌면 그것도 보인다.

### 켜기 전에 실제로 찔러 본다

승인만으로 켜지 않는다. `enabled` 로 넘어갈 때 마스터가 **정해진 요청 하나를 보내고**
응답이 계약을 지키는지 본다(출처를 붙이지 않았는가·시간 안에 오는가·형식이 맞는가).

스키마에 이미 자리가 있다 — `health`, `error_code`, `last_checked_at`.
문서로 계약을 알리고 사람이 리뷰로 잡는 방식은, 팀이 늘어나는 만큼 놓친다.

### 인증

- **HTTPS 만.** 근거 텍스트가 그 요청에 실린다
- **전문가별 시크릿** 하나. `llm_secret` 과 같은 방식으로 암호화 저장하고 콘솔에서 교체
- 네트워크에서도 좁힌다(출발지 제한). 시크릿 유출이 곧 접근이 되지 않게

전문가는 우리를 **호출하지 않는다.** 방향은 마스터 → 전문가 한쪽뿐이다.
그쪽이 우리에게 인바운드를 열면 아카이브를 직접 가져가는 통로가 생긴다.

### 비용은 갈라진다

전문가가 자기 키로 자기 모델을 부르면 그 비용은 그 팀 것이다. 예산이 갈라지는 것은
장점이지만, `specialist_call.cost_usd` 에 우리가 채울 값이 없어진다.
**그쪽이 보고한 값은 우리 상한의 근거로 쓰지 않는다** — 우리 상한은 우리가 쓴 것에만
걸린다. 라우팅 모델 호출은 우리 비용이라 그대로 잡힌다.

## 남는 위험 두 개

**하나 — 전문가가 근거를 밖으로 흘린다.** 우리가 보낸 근거를 그 팀이 로그에 남기거나
외부로 보내는 것을 기술로 막을 수 없다. 계약 문서와 **접근 범위**로 줄인다:
전문가는 `specialist_workspace` 로 묶인 워크스페이스의 근거만 받는다. 그리고
`authorization_id` 를 남겨 두어, 나중에 "무엇이 그쪽에 갔나" 를 되짚을 수 있게 한다.

**둘 — 서비스를 어디에 띄우나.** 팀마다 서버를 요구하면 시작이 안 된다.
사내 컨테이너 한 곳에 여러 전문가를 각각 올리고 마스터가 이름으로 부르는 쪽이 현실적이다.
그건 인프라 결정이라 여기서 정하지 않는다.
