# 아카이브 저장 구조 실측 — 개발 폴더와 변환·측정 계약

> 작성: 2026-09-23
> 상태: 실측 준비. **구조는 아직 정해지지 않았다.**
> 2026-09-23 정정: 실측의 성격이 「성능 비교」 에서 **「동등성 증명」** 으로 바뀌었다(§5).
> 근거: [Archiving Bot 분리](archiving-bot-separation-2026-09-23.md) §3(권고),
> 2026-09-23 PF·IT 협의
> 읽는 사람: 서버 폴더 구조를 정하는 쪽(Codex), 변환 스크립트를 만드는 쪽, 결정하는 사람

## 1. 무엇이 정해졌고 무엇이 안 정해졌나

**정해진 것**

| 항목 | 결정 |
|---|---|
| 첨부 파일 | 구조 1 처럼 **별도 보관**. raw 본문에 복제하지 않는다 |
| 채널 식별 | 파일이든 폴더든 **ID 를 붙인다** |
| 요약 | Hermes 몫. Archiving Bot 은 쓰지 않는다 |

**안 정해진 것** — 이 문서가 다루는 것

| 후보 | 모양 |
|---|---|
| 구조 1 (프금팀) | `channels/<slug>__<id>.md` — 채널당 파일 하나 |
| 구조 2 (전산팀) | `channels/<id>__<slug>/raw/YYYY-MM-DD.md` — 채널당 폴더, 날짜별 파일 |

두 줄의 `<id>`·`<slug>` 순서가 다른 것은 오타가 아니다. 구조 2 의 디렉터리 이름은
**이미 운영에 있는 것**이라(`writer.channel_dir`) 바꾸면 전부 옮겨야 한다. 새로
만드는 구조 1 만 읽기 좋은 순서로 둔다(§9, 2026-09-23 오너 결정).

분리 결정 문서 §3 은 구조 2 를 **권고**했지만 합의는 아니다. 실측으로 정한다.

## 2. 개발 아카이브는 운영의 **형제**여야 한다

```text
/var/lib/tybot/archive/          ← 운영. 답변 근거. 이 실측은 여기를 읽기만 한다
/var/lib/tybot/archive-lab/      ← 실측 전용
    snapshot/                    ← 운영 복사본(읽기 전용). 두 변환의 같은 입력
    layout-a/                    ← 구조 1 배치 결과
    layout-b/                    ← 구조 2 배치 결과
    reports/                     ← 측정 결과와 보고서
/var/lib/tybot/objects/          ← 첨부 원본. 실측 대상 아님(구조 무관)
```

### 왜 `archive/` 아래가 아닌가
`ArchiveStore._files()` 가 이렇게 훑는다.

```python
files = sorted(v2.glob("*/channels/*/raw/*.md"))     # ARCHIVE_DIR/workspaces/…
legacy_files = sorted(legacy.glob("*/*.md"))         # ARCHIVE_DIR/channels/…
```

`ARCHIVE_DIR` 아래에 실측용 사본을 두면 **그 모양에 걸리는 순간 답변 근거가 된다.**
`archive/lab/workspaces/…` 같은 경로는 첫 글롭에 안 걸리지만, `archive/lab/channels/x.md`
는 **두 번째 글롭(v1 레거시)에 걸린다.** 그러면 실측용 복제본이 답변 출처로 나가고,
사람이 그 출처를 눌러도 실물이 없다.

그래서 **형제 디렉터리**로 둔다. 경로를 안 겹치게 하는 것이 아니라 **뿌리를 다르게**
하는 것이 요점이다 — 글롭이 바뀌어도 안전하다.

> Codex 에게: `archive-lab` 의 소유자를 `tybot` 으로 두되 **봇 서비스의
> `ReadWritePaths` 에는 넣지 않는다.** 실측 스크립트는 사람이 돌리고, 봇은 이
> 경로를 몰라야 한다. 봇이 쓸 수 있으면 언젠가 쓴다.

### 확인 방법
실측 폴더를 만든 뒤 한 번 돌린다. 답변 근거 수가 그대로여야 한다.

```bash
sudo -u tybot /opt/tybot/.venv/bin/python - <<'PY'
import os, sys
sys.path.insert(0, "/opt/tybot/src")
from tybot.archive.store import ArchiveStore
store = ArchiveStore(os.environ["ARCHIVE_DIR"])
paths = store.source_files()
bad = [p for p in paths if "archive-lab" in str(p)]
print(f"문서 {len(paths)}개, 실측 폴더 유입 {len(bad)}개")
raise SystemExit(1 if bad else 0)
PY
```

## 3. 변환 스크립트 — **하나의 중간표현에서 둘로**

두 스크립트를 따로 만들지 않는다. 따로 만들면 파싱이 갈리고, 그때 재는 것은
**구조 차이가 아니라 두 스크립트의 차이**가 된다.

```
운영 스냅샷 ──▶ 파서 ──▶ 중간표현(채널, 줄, 좌표) ──┬──▶ layout-a 배치
                                                    └──▶ layout-b 배치
```

중간표현이 담는 것: 워크스페이스, 채널 ID, 표시명, 줄(시각·화자·본문·`message_ts`),
첨부 참조(file ID). **본문은 한 글자도 바꾸지 않는다** — 원문 보존(절대 원칙 1)이고,
바꾸면 두 배치의 내용이 달라져 비교가 무의미해진다.

### 검증 조건 (변환이 맞았는지)
변환 스크립트는 **자기 결과를 스스로 검사**해야 한다. 안 하면 「빠른 쪽이 사실은
줄을 흘린 쪽」 이 된다.

- 두 배치의 **줄 수 합계가 같다**
- 두 배치의 **본문 해시 집합이 같다**(순서 무관)
- 채널 수가 같고, 채널별 줄 수도 같다
- 첨부 참조 ID 집합이 같다
- 어느 쪽에도 원본에 없던 줄이 없다

하나라도 어긋나면 **측정하지 않는다.** 그 숫자는 구조가 아니라 버그를 잰 것이다.

## 4. 우리 쪽 읽기 비용 — 색인은 절반만 쓰인다

이 절은 **우리가 치르는 비용**이다. Hermes 가 보는 것은 §5 에서 따로 다룬다 —
둘은 다른 축이고, 섞으면 「Hermes 가 느리다」 와 「우리가 파일을 많이 연다」 를
구분하지 못한다.

### 색인은 이미 잘 만들어져 있다

`raw_line` 에 pg_bigm GIN 인덱스가 걸려 있고, 실측 기록이 스키마 주석에 남아 있다
(2026-08-31, 행 2만).

| 검색어 | pg_bigm | pg_trgm |
|---|---|---|
| 기성(2자) | 인덱스 **0.30ms** | 전체 스캔 8.06ms |
| 김해외동(4자) | 인덱스 0.32ms | 인덱스 0.13ms |

2글자 한국어가 흔한 우리 쓰임(기성·타설·결재·예산)에서 40배 차이라 pg_bigm 을 골랐다.
**질의 자체는 파일 구조와 무관하다** — `channel` + `body ILIKE` 로 돌고 파일을 안 연다.

### 그런데 검색 경로가 파일을 먼저 전부 읽는다

```python
docs = self.visible_docs(ctx)                  # ① 아카이브 전체를 파싱
found = search_index.candidates(query, ...)    # ② DB 색인 질의 (0.3ms)
by_path = {rel_path(d.path): d for d in docs}  # ③ 후보를 ①에서 찾는다
```

**①이 먼저 돈다.** 이유는 권한이다 — 색인에는 `visibility`·`acl` 이 없어서, 「이 줄을
볼 수 있나」 를 파일 프론트매터에서 읽어야 한다.

그래서 색인이 답하는 것은 **「어느 줄이 맞나」 뿐**이고, **「그 줄을 볼 수 있나」 는
여전히 파일에서 온다.** 결과적으로 파일 수와 크기가 읽기 시간에 그대로 들어간다.

### 캐시는 파일 단위다

`ArchiveStore._load()` 가 경로마다 `(mtime_ns, size)` 로 캐시한다. 그래서 무효화
범위가 곧 **구조 차이**다.

| | 메시지 한 건이 들어오면 |
|---|---|
| 구조 2 (날짜별) | 오늘 파일만 무효화. 나머지 날짜는 캐시 유지 |
| 구조 1 (채널당 하나) | **그 채널 전체**가 무효화 → 다음 검색에서 통째로 재파싱 |

반대로 재시작 직후(cold)에는 구조 1 이 유리하다 — 같은 바이트를 읽어도 파일 수가
적어 `stat`·`open` 이 훨씬 적다.

**그래서 읽기는 한 숫자로 안 갈린다.** cold 와 warm 을 따로 재야 한다.

### 구조 1 을 읽기에서 살리는 길은 이미 절반 깔려 있다

`archive_doc` 표에 `visibility`·`acl`·`share_with` 가 **이미 있다**
(`deploy/sql/console_schema.sql`). 지금은 콘솔 스캐너가 채우고 답변 경로는 안 쓴다.

그걸 쓰면 `visible_docs` 가 SQL 이 되고, 파일은 **맞은 줄이 있는 문서만** 열면 된다.
그때는 파일 구조가 읽기 시간에 거의 영향을 주지 않는다 — 어느 구조든 여는 파일이
검색 결과 수만큼으로 줄기 때문이다.

> **이 순서가 중요하다.** 권한이 파일에서 오는 한, 읽기 실측은 「구조」 가 아니라
> 「파일을 몇 개 여느냐」 를 잰다. 그건 구조의 성질이 아니라 **지금 구현의 성질**이다.
> 쓰기 쪽에서 append writer 가 필요한 것과 같은 문제다.

## 5. 실측의 목표 — Hermes 답변이 **같은지** 본다

### 무엇을 재려는 것인가
「비용·시간」 은 우리 파일 I/O 가 아니라 **Hermes 가 답할 때의 시간과 토큰**이다.
Hermes 가 빨리·적게 읽고 답하는 구조를 고르는 것이 목표다.

### 그런데 지금 구조로는 **차이가 날 수 없다**

도구 층이 배치를 지운다.

```python
# ArchiveStore.docs() → _merge()
"""같은 채널의 일자 파일을 합친다."""
```

| | Hermes 가 `read_channel` 했을 때 |
|---|---|
| 구조 1 | 파일 하나 → 문서 하나 → 최근 N줄 |
| 구조 2 | 파일 여럿 → **병합** → 문서 하나 → 최근 N줄 |

`search` 도 같다. DB 색인이 `(doc_path, line_no)` 로 후보를 주고 도구는 **줄만**
렌더링한다. `MAX_TOOL_CHARS = 30_000` 상한도 동일하게 걸린다.

**Hermes 는 우리 파일 구조를 볼 수 없다.** v3 계약에서 archive mount 를 주지 않기로
한 이유가 그것이고, 그 설계가 의도대로 동작하고 있다.

### 그래서 시험의 성격이 바뀐다 — 성능 비교가 아니라 **동등성 증명**

두 구조에 Hermes 를 각각 불러 시간·토큰을 비교하면, 나오는 차이는 구조가 아니라
**모델 샘플링 노이즈**다. 그 방법으로는 「차이를 못 찾았다」 까지만 말할 수 있다.

대신 **도구가 돌려주는 문자열을 바이트 단위로 비교한다.** 그게 Hermes 가 받는
입력의 전부이므로, 같으면 토큰도 시간도 같다 — 재는 것이 아니라 **증명하는** 것이다.

| | 실제 Hermes 호출 비교 | 도구 출력 비교 |
|---|---|---|
| 비용 | 질문 N개 × 2회 × 모델 | **0원** |
| 결정성 | 샘플링마다 다름 | 결정적 |
| 말할 수 있는 것 | 「차이를 못 찾았다」 | **「같다」** |

### 차이가 나오면 그것은 **구조 발견이 아니라 버그다**

도구 출력이 갈리면 두 배치가 **같은 내용을 담고 있지 않다는 뜻**이다. 원인은 셋 중
하나이고 셋 다 고쳐야 할 것이다.

1. 변환 스크립트가 줄을 흘렸거나 순서를 바꿨다
2. `_merge()` 가 날짜 파일을 합칠 때 줄을 잃거나 중복시킨다
3. `_pick_channel` 이 구조에 따라 다른 문서를 고른다

**이 시험의 진짜 값어치가 여기 있다.** 구조를 고르는 근거를 주는 것이 아니라,
어느 구조로 가든 **내용이 보존되는지**를 확인한다.

### 시험 설계

같은 요청 문맥(`RequestContext`)으로 두 배치에 같은 도구 호출을 던지고 출력을 비교한다.

```python
for tool, args in CASES:                      # 아래 목록
    a = ToolBox(store_a, ctx).run(tool, args)
    b = ToolBox(store_b, ctx).run(tool, args)
    assert a == b, (tool, args)
```

`CASES` 는 실제 질문에서 뽑는다 — 지어내지 않는다. `qa-log` 의 최근 질문에서
`task_traces` 의 도구 호출을 그대로 가져온다. 그래야 **사람이 실제로 부르는 모양**을
덮는다.

최소 이만큼은 넣는다.

| 도구 | 경우 |
|---|---|
| `search` | 2글자 한국어, 4글자 이상, 히트 0건, 히트 30건 초과(상한 걸림) |
| `read_channel` | 기본 limit, limit=400, `MAX_TOOL_CHARS` 를 넘는 큰 채널 |
| `read_document` | 일반 문서, 첨부 변환본, 없는 이름 |
| 권한 | 채널 하나만 보이는 ctx, exec ctx, DM ctx |

**권한 경우를 반드시 넣는다.** 구조가 바뀌면 프론트매터가 있는 파일 수가 바뀌고,
그때 ACL 합집합 계산(`_merge`)이 달라질 수 있다. 내용은 같은데 **보이는 범위가
달라지는** 것이 가장 나쁜 실패다.

### 그다음에 실제로 한 번 돌린다

도구 출력이 같음을 증명한 뒤, **확인용으로만** 실제 Hermes 를 몇 번 부른다.
질문 5개면 충분하다 — 증명은 이미 끝났고, 이건 배선이 맞았는지 보는 것이다.

기록: 도구 호출 수, 입력·출력 토큰, 벽시계 시간. **두 배치에서 비슷하면 통과**이고,
크게 갈리면 도구 출력 비교에서 놓친 것이 있다는 뜻이므로 거기로 돌아간다.

## 6. 그러면 구조는 무엇으로 정하나 — **우리 쪽 비용**

Hermes 쪽이 같다면 결정 근거는 우리가 치르는 비용뿐이다.

| # | 무엇 | 왜 | 어느 쪽이 유리한가 |
|---|---|---|---|
| 1 | 메시지 1건 수집 시간 | 실시간 경로. 하루 수천 번 | 구조 2 (지금 writer 가 파일을 통째로 다시 쓴다) |
| 2 | 검색 1회 — warm, 쓰기 중 | 평소 상태 | 구조 2 (무효화가 오늘 파일로 한정) |
| 3 | 검색 1회 — cold | 재시작 직후 | 구조 1 (파일 수가 적어 syscall 이 적다) |
| 4 | 증분 재색인 | 밀리면 검색이 낡는다 | 구조 2 (문서 단위 판정) |
| 5 | PF 기존 아카이브 수용 | 26MB 를 옮겨야 한다 | **구조 1** (그대로 들어온다) |
| 6 | 사람이 열어 읽기 | 점검·감사 | **구조 1** |

### 1·2·4 는 **고칠 수 있는 약점**이다

- 1번 → 구조 1 용 append writer
- 2·4번 → 권한을 `archive_doc` 에서 읽기(표와 열이 이미 있다. 답변 경로만 안 쓴다)

**고칠 수 있는 약점으로 구조를 정하면, 고친 뒤에 그 결정이 틀린 것이 된다.**
그래서 1·2·4 는 「지금 이렇다」 로 기록하되 **결정 근거로 쓰지 않는다.** 대신
「구조 1 을 고르면 무엇을 먼저 고쳐야 하는가」 의 목록이 된다.

### 판정 규칙 — 숫자를 보기 전에 적는다

```
1. 도구 출력이 두 배치에서 같지 않으면 → 구조 결정을 멈추고 원인을 고친다.
   내용이 다른 둘을 비교하는 것은 아무 의미가 없다.

2. 같으면 → Hermes 쪽은 동등하다. 아래로 정한다.
   a. PF 기존 아카이브를 그대로 받을 수 있는가      (구조 1)
   b. 사람이 열어서 읽을 수 있는가                  (구조 1)
   c. 위 둘이 비기면 → 지금 구현에서 덜 고쳐도 되는 쪽 (구조 2)

3. 우리 쪽 비용(1·2·4)은 **고를 때 쓰지 않는다.** 구조 1 을 고른 경우
   「그 전에 무엇을 고쳐야 하는가」 의 목록으로만 쓴다.

4. 어느 한쪽이 운영에 못 쓸 만큼 나쁘면(예: 수집 1건이 1초) 그때는
   탈락시킨다. 이건 우열이 아니라 하한선이다.
```

## 8. 하지 않는 것

- **운영 아카이브를 건드리지 않는다.** 읽기만 한다. 실측은 사본에서 한다
- **운영 DB 의 `raw_line` 을 쓰지 않는다.** 실측용 스키마를 따로 만든다 —
  옛 `doc_path` 행이 안 지워지므로 운영 색인이 오염된다
- **첨부 원본을 복제하지 않는다.** 구조 논쟁의 대상이 아니고(별도 보관 확정),
  용량만 두 배가 된다
- **결론을 실측 전에 문서에 적지 않는다.** §6 은 규칙이지 결론이 아니다
- **같은 질문을 두 구조에 돌려 토큰을 비교하지 않는다.** 도구 출력이 같으면 토큰도
  같고, 다르면 그건 구조가 아니라 버그다. 모델을 불러 노이즈를 재는 대신 도구
  출력을 증명한다(§5)

## 10. 변환 스크립트를 돌려 나온 것 (2026-09-23)

`scripts/archive_layout_convert.py` 로 PF 스냅샷(43채널 2061메시지)을 두 배치로
만들고, `tests/test_archive_layout_equivalence.py` 로 도구 출력을 비교했다.
**실측은 아직 안 했다. 아래는 실측을 돌리기 전에 나온 것이다.**

### 결과: 두 구조는 Hermes 에게 같다 — 다만 그걸 아는 데 버그 둘을 먼저 고쳐야 했다

§5 의 예상대로 도구 출력은 바이트 단위로 같다. 그런데 처음 돌렸을 때는 같지
않았고, 원인은 둘 다 **구조 논쟁과 무관한 우리 버그**였다.

#### 버그 1 — 구조 1 은 애초에 읽히지 않았다

`ArchiveStore._files()` 의 글롭이 `*/channels/*/raw/*.md` 뿐이라, 구조 1
(`channels/<slug>__<id>.md`)은 **한 장도 안 읽혔다.** 파일은 있고 검색만 비었다.

이게 위험한 이유는 동등성 시험이 이것을 **통과시킬 수 있기** 때문이다 — 양쪽이
아무것도 안 읽으면 출력이 똑같이 비어서 「같다」 가 나온다. 그래서 시험에
「구조 1 이 정말 읽혔는가」 를 따로 박았다(`test_structure_one_is_actually_read`).

성능 실측을 먼저 돌렸다면 **「구조 1 이 압도적으로 빠르다」 가 나왔을 것이다.**
아무것도 안 읽으니까. 동등성을 먼저 증명하기로 한 §5 의 판단이 여기서 값을 했다.

> 고침: `_files()` 에 `*/channels/*.md` 글롭 추가. 구조 1 을 채택하지 않더라도
> 읽는 쪽이 이 모양을 알고 있어야 **실측이 거짓말을 하지 않는다.**

#### 버그 2 — 지금 운영 구조에서 검색이 줄을 잃고 있다 ⚠️

이건 실측과 무관하게 **지금 돌고 있는 봇의 문제**다.

`_merge()` 는 일자 파일을 합치면서 모든 줄에 같은 `doc.path`(가장 최근 파일)를
달아 준다. 그런데 `lineno` 는 파일마다 1부터 다시 세므로, **다른 날의 다른 줄이
`(doc.path, lineno)` 로는 같은 키**가 된다. `_rank` 가 그 키로 중복을 지우고
있었기 때문에 둘 중 하나가 검색 결과에서 조용히 빠졌다.

| | 키가 겹치는 줄 |
|---|---|
| 구조 1 (채널당 파일 하나) | 2061줄 중 **0줄** |
| 구조 2 (**지금 운영 구조**) | 2061줄 중 **1750줄** |

증상은 오류도 0건도 아니다. 「그 말은 없었다」 로만 보인다. 사람이 「분명 그런
얘기 했는데」 하고 넘어가는 종류라, 신고가 들어오지 않는다.

> 고침: 키를 `(line.source_path, line.lineno)` 로. 회귀 시험
> `tests/test_search_merged_dedup.py`. 되돌리면 시험이 실패하는 것을 확인했다.

### 이 둘이 실측에 뜻하는 것

**두 버그 다 「구조가 나쁘다」 가 아니라 「우리 구현이 그 구조를 제대로 다루지
못한다」 였다.** §6 이 우리 쪽 비용(1·2·4)을 결정 근거로 쓰지 않기로 한 것과 같은
축이다 — 고칠 수 있는 약점으로 구조를 정하면, 고친 뒤에 그 결정이 틀린 것이 된다.

그리고 버그 2 는 **구조 1 이 이겼을 항목**이었는데, 고치고 나니 무승부가 됐다.
실측 전에 이런 것이 몇 개 더 나올 수 있다고 보는 편이 맞다.

### 변환에서 남은 손실 — 보고서에 그대로 싣는다

| 무엇 | 얼마 | 왜 |
|---|---|---|
| Slack 좌표(`message_ts`) | 2061건 **전부** | PF 자료에 없다. **지어내지 않는다** — 대신 줄마다 `legacy_source_ref`(스냅샷 SHA·파일·줄) |
| 채널 ID | 43채널 전부 | 없다. `legacy-<slug>` 를 쓴다 — 접두어가 「진짜 ID 가 아니다」 를 말한다 |
| 해석 절(`## 참여 기록`·`## 요약`) | 35파일, 파일당 3~4줄 | 봇이 만든 문장이다. 원문이 아니므로 옮기지 않는다(절대 원칙 1) |
| 여러 줄 본문의 줄바꿈 | 다수 | 우리 원문 형식이 한 줄에 한 메시지다. **진짜 손실**이라 여기 적는다 |

`visibility` 는 **`private` 로 넣었다.** PF 자료는 그 채널이 공개였는지 말해 주지
않는다. 공개로 찍었다가 틀리면 사내 대화가 권한 없는 사람에게 열리고, 비공개로
찍었다가 틀리면 사람이 못 볼 뿐이다(절대 원칙 3).

### 재현 — git 체크아웃에서

```bash
python scripts/archive_layout_convert.py --from pf --source <스냅샷> --to a --out <lab>/a
python scripts/archive_layout_convert.py --from pf --source <스냅샷> --to b --out <lab>/b
python scripts/archive_layout_convert.py --verify <lab>/a <lab>/b
python -m pytest tests/test_archive_layout_equivalence.py tests/test_archive_provenance.py \
                 tests/test_search_merged_dedup.py
```

커밋은 `source` 에서 자동으로 읽는다(위 실행에서 `eeb50045fe88…` 이 잡혔다).

### 재현 — ZIP 으로 받은 사본에서

**`--source-commit` 을 손으로 준다.** ZIP 에는 `.git` 이 없어 커밋을 읽을 수 없고,
그대로 두면 manifest 의 `source_commit` 이 `null` 이 된다. 그러면 나중에 「이
변환이 PF 의 어느 release 였나」 를 아무 데서도 못 찾는다.

```bash
unzip pf-hermes-archive.zip -d <lab>/snapshot

python scripts/archive_layout_convert.py --from pf --source <lab>/snapshot --to a \
    --out <lab>/a --source-commit eeb50045fe8813ff2bfb2e7b9a5f8d1e1f227881
python scripts/archive_layout_convert.py --from pf --source <lab>/snapshot --to b \
    --out <lab>/b --source-commit eeb50045fe8813ff2bfb2e7b9a5f8d1e1f227881
python scripts/archive_layout_convert.py --verify <lab>/a <lab>/b
```

**두 실행에 같은 값을 준다.** 다르게 주면 manifest 가 갈리고, 사이드카 바이트
비교가 실패한다 — 구조 차이가 아닌데 그렇게 보인다.

그리고 `source_snapshot_sha256` 이 git 체크아웃에서 돌린 값과 **같은지 본다.**
같으면 ZIP 이 그 커밋의 내용과 일치한다는 뜻이고, 다르면 ZIP 이 다른 시점이거나
푸는 과정에서 무언가 바뀐 것이다. 커밋 SHA 는 그것을 말해 주지 못한다 — 사람이
적어 넣은 값이기 때문이다.

```bash
python -c "import json,sys; print(json.load(open(sys.argv[1],encoding='utf-8'))['source_snapshot_sha256'])" \
    <lab>/a/workspaces/pf/provenance/manifest.json
```

운영 경로(`/var/lib/tybot/archive` 등)를 `--out` 으로 주면 거부한다.

## 11. 출처 사이드카 계약 (2026-09-23 오너 승인)

PF 자료에는 Slack `message_ts` 가 **하나도 없다**(2061건 전부). 변환된 줄을 원본으로
되짚는 길이 `legacy_source_ref` 뿐이므로, 이건 편의가 아니라 **되짚기의 유일한 수단**이다.

### 경로

```
workspaces/<workspace>/provenance/<stable_id>.jsonl
workspaces/<workspace>/provenance/manifest.json
```

`<stable_id>` 는 채널 ID, PF 자료처럼 없으면 `legacy-<16 hex>` 다.

**이름 slug 를 쓰지 않는다.** `_slugify` 는 경로에 못 쓰는 글자를 지우므로,
그 글자만 다른 두 채널(`#팀_자금/주간` · `#팀_자금:주간`)이 **같은 파일**이 된다.
권한이 다른 두 채널이 합쳐지면 그건 유출이다(절대 원칙 3). 해시는
`sha256({"channel":…,"workspace":…})` 의 앞 16자이고 길이도 고정이다.

`legacy-` 접두어는 남긴다 — 이 값이 **Slack ID 가 아니라는 사실**이 경로 이름만
보고도 드러나야 한다. 사람이 이걸 들고 Slack 에서 찾으면 안 된다.

원문 파일명은 여전히 읽힌다 — 구조 1 은 `<slug>__<id>.md` 라 이름이 앞에 온다.

    a_용인8구역__legacy-29899532aeaabd54.md

**쓰기 전에 `(workspace, stable_id)` 중복을 확인하고, 겹치면 멈춘다.** 겹친 채로
쓰면 뒤에 쓴 채널이 앞의 것을 덮는다. 구조 1 은 파일 하나라 통째로 사라지고,
구조 2 는 같은 날짜 파일만 덮여 **일부만** 사라진다. 어느 쪽도 오류를 내지
않는다 — 파일은 멀쩡하고 줄만 없다. 그래서 경고가 아니라 중단이다.

**`channels/` 밖에 둔다.** `ArchiveStore._files()` 가 `*/channels/…` 를 훑으므로,
그 아래 두면 언젠가 글롭에 걸려 답변 근거로 나간다. 확장자가 `.md` 가 아니라
안전한 것이 아니다 — 그건 지금 글롭의 성질이지 구조의 성질이 아니다.

**구조 1 과 구조 2 에서 경로도 바이트도 같다.** 출처는 배치와 무관한 사실이다.
다르면 「어느 배치로 만들었나」 가 되짚기에 영향을 주게 되고, 그건 구조를 고르는
일과 아무 상관이 없어야 한다.

### 한 줄의 모양

```json
{"legacy_source_ref":{"kind":"pf_git_snapshot","snapshot_sha256":"<64 hex>","source_line":11,"source_path":"slack-export/channels/a_용인8구역.md"},"message_ts":null,"ordinal":0,"record_sha256":"<64 hex>","schema_version":1,"source_timestamp_text":"2026-06-11 08:58"}
```

| 칸 | 규칙 |
|---|---|
| `ordinal` | 채널 안 **0-based** 순번 |
| `source_timestamp_text` | `ts` 라고 하지 않는다 — Slack `message_ts` 와 혼동된다 |
| `message_ts` | 없으면 **`null`**. 빈 문자열은 「있는데 비었다」 와 구분되지 않는다 |
| `source_path` | **source 루트 기준 POSIX 상대경로.** basename 도 절대경로도 아니다 |
| `record_sha256` | 본문 동일성 해시. `ordinal` 과 **함께** 쓴다 |

`ordinal` 만 보면 줄이 하나 끼어들었을 때 그 뒤가 전부 어긋난 채 맞아 보이고,
`record_sha256` 만 보면 같은 문장이 두 번 나온 채널에서 어느 쪽인지 못 가린다.

### 결정적 직렬화

UTF-8 · `sort_keys=True` · `separators=(",", ":")` · **LF**.

**해시도 같은 직렬화를 쓴다.** 칸을 이어 붙여 해싱하지 않는다 — 전에는
`"|".join([ts, speaker, text, …])` 이었고, 본문에 `|` 가 들어가면 칸 경계가 밀려
**서로 다른 메시지가 같은 해시**를 냈다. 우리 자료에서 `|` 는 표를 붙여 넣을 때
흔하다. `record_sha256` 과 검증용 해시가 같은 함수(`canonical_digest`)를 쓰므로,
한쪽만 바뀌어 검증이 조용히 약해지는 일도 없다.

`sort_keys` 가 없으면 dict 삽입 순서가 바뀔 때 파일이 달라지고, 텍스트 모드로 쓰면
Windows 에서 CRLF 가 된다. 그 차이는 두 배치 비교에서 **「구조 차이」 로 보인다.**

### 스냅샷 해시 — git 커밋과 **다른 값**이다

manifest 에 둘을 따로 둔다.

| 칸 | 뜻 |
|---|---|
| `source_commit` | 저장소의 어느 지점. 예: `eeb50045fe88…` |
| `source_snapshot_sha256` | **변환에 실제로 넣은 내용.** 예: `12538ec420f2…` |

작업 디렉터리가 더러우면 둘이 갈라지고, 그때 믿을 것은 스냅샷 해시다.

지문은 정렬된 (상대경로, 파일 내용 SHA-256) 을 누적해 만든다. 경로와 내용 사이에
길이를 끼운다 — 없으면 `ab`+`c` 와 `a`+`bc` 가 같은 바이트열이 되어, 이름을 갈라
붙인 다른 스냅샷이 같은 지문을 낸다.

| | |
|---|---|
| 내용이 한 글자 바뀌면 | 지문이 **바뀐다** |
| 내용이 같고 상대경로만 바뀌면 | 지문이 **바뀐다** |
| 절대 경로만 다르면(같은 사본, 다른 자리) | 지문이 **같다** |

기록에는 full 64 hex 를 쓰고 **화면 표시만** 앞 12자를 쓴다. 앞자리만 남기면
언젠가 부딪히고, 부딪힌 날 그 사실을 알아챌 방법이 없다.

