# 파일럿 런북 — TYBot, 워크스페이스 1개

_기존 Hermes(`tec-wmo6240`)와 무관한 독립 파일럿. 중앙 GitHub 아카이브·레거시 DB 연동은 이 단계에서 제외._
_멀티 워크스페이스는 [`docs/multi-workspace.md`](../multi-workspace.md) 참조._

## 0. API 키 전달 — 채팅으로 붙여넣지 말 것
- 키는 **네 로컬 `.env`** 에만. 대화창/이슈/커밋에 붙이면 유출로 간주하고 즉시 폐기·재발급.
- 이 저장소는 3중으로 막아둠: `.gitignore`(`.env`), `.claude/settings.json`의 `Read(./.env)` deny, `.claude/hooks/guard.py`의 토큰 패턴 차단.
- 값 확인은 마스킹 스크립트로만: `python scripts/check_env.py` (앞 6자·뒤 4자만 출력 → 그 출력은 공유해도 안전).

```bash
cp .env.example .env      # 자리표시자 복사
# .env 를 편집기로 열어 값 채우기 (SLACK_BOT_TOKEN / SLACK_APP_TOKEN / ANTHROPIC_API_KEY)
```

## 1. Slack 앱 생성
1. https://api.slack.com/apps → **Create New App → From an app manifest**
2. 파일럿 워크스페이스 선택 → [`slack-app-manifest.yaml`](slack-app-manifest.yaml) 내용 붙여넣기
3. **Basic Information → App-Level Tokens → Generate**: 스코프 `connections:write` → `xapp-...` = `SLACK_APP_TOKEN`
4. **Install to Workspace** → `xoxb-...` = `SLACK_BOT_TOKEN`
5. 테스트 채널에서 `/invite @tybot` — **초대 안 하면 그 채널은 수집·조회 대상에서 빠진다**

### 기존 앱에 `업무 채널 만들기` 추가
1. https://api.slack.com/apps 에서 해당 워크스페이스의 **TYBot 앱**을 연다.
2. 왼쪽 **App Manifest**를 열고 [`slack-app-manifest.yaml`](slack-app-manifest.yaml) 내용으로 갱신한다.
3. **Save Changes**를 누른다. Socket Mode를 사용하므로 Request URL이나 새 인바운드 포트는 필요 없다.
4. 왼쪽 **OAuth & Permissions** → **Reinstall to Workspace**를 누른다.
5. 추가 권한 `commands`, `channels:manage`, `groups:write`를 승인한다.
6. Slack을 새로고침한 뒤 메시지 입력창 왼쪽 `+` → **업무 채널 만들기**가 보이는지 확인한다.

워크스페이스마다 앱이 별도이므로 위 절차도 **각 워크스페이스 앱에서 한 번씩** 해야 한다.
권한을 추가하고 재설치하지 않으면 화면은 열려도 실제 채널 생성에서 `missing_scope`로 실패한다.

## 2. 실행
```bash
python -m venv .venv && .venv/Scripts/activate      # Windows
pip install -e ".[dev]"
python scripts/check_env.py                          # 전부 ✓ 인지 확인
python -m tybot.slack.pilot
```
> 봇 프로세스는 **한 곳에서만** 기동. 두 곳에서 켜면 중복 답변 + LLM 비용 2배.

## 3. 사용법
| 입력 | 동작 |
|---|---|
| 입력창 `+` → `업무 채널 만들기` | 한국어 입력 화면에서 표준 공개·비공개 채널 생성 |
| `/채널` 또는 `/채널 생성` | 위와 같은 업무 채널 생성 화면 |
| `/채널 이름변경` | 현재 채널의 표준 이름 변경(최초 생성 요청자 또는 지정 운영자) |
| (규칙에 맞는 공개 채널 생성) | **봇이 스스로 참여**해 수집 시작 — `/invite` 불필요 |
| (규칙에 맞는 채널 대화) | **실시간 자동 수집** — 봇이 참여한 채널 메시지를 즉시 원문 append |
| (채널에 파일 업로드) | xlsx·docx·pptx·pdf·hwpx 는 **본문을 변환해 수집**(`[첨부추출:파일명]`).<br>스캔 PDF·구형 hwp·이미지·도면은 목록만 |
| `@tybot 전체수집` | 봇이 볼 수 있고 이름 규칙에 맞는 모든 채널 백필. 공개 채널은 자가참여 |
| `@tybot 수집` | 그 채널 최근 15건 + **스레드 답글**(최대 5개 스레드) 백필 |
| `/일정` · `/일정 이번주` · `/일정 9월` | 그룹웨어 팀 일정. **본인에게만** 표시되고 '채널에 공유' 버튼으로만 채널에 올라간다 |
| `/수집상태` | 이 채널이 수집 대상인지, 아니면 **왜 아닌지와 조치 방법** (ephemeral) |
| `/피드백` | **선택 화면**(정확/틀림/근거 없음)이 열린다. 본인의 직전 답변에 연결된다 |
| `/피드백 <내용>` | 적어서 바로 접수. 모달을 띄우지 않는다 |
| `@tybot 상태` | 채널별 원문 줄 수 / 형식 위반 / 실시간 수집 ON·OFF |
| `@tybot 이전 답변 기억나?` | **기억하지 않는다는 사실과 이유**를 설명 + 본인 최근 질문(감사기록) |
| `@tybot 이전 답변 기억나? 그리고 전산팀은 무슨 일 있어?` | 기억 경계를 알린 뒤 **전산팀 원문을 새로 검색**해 두 번째 질문에도 답변 |
| TYBot 답변에 👍 / 👎 | 답변 품질 피드백으로 기록. 취소한 Reaction도 이력으로 남김 |
| 답변 스레드에서 `@tybot 정정: 올바른 내용` | 해당 QA 답변에 사람의 정정 의견을 연결 |
| `@tybot 현재 너의 상태 어때?` | **LLM 분류**가 봇 상태 질문으로 판단 → 연결·수집 현황 (LLM 답변 생성 없음) |
| `@tybot 현재까지 상황 요약해줘` | 기간 스캔 → 채널별 정리 + 출처 |
| `@tybot 이번주/30일/2주 진행상황` | 기간 표현 인식 (기본 7일, 최대 365일) |
| `@tybot 김해외동 기성금 얼마야?` | 핵심어(`김해외동`,`기성금`)만 뽑아 원문 검색 → 답변 + 출처 |
| `@tybot 채널을 잘게 쪼개는 게 나아?` | **판단·권고 요청** → 관련 원문이 있으면 근거로, 없으면 `일반적인 판단` 라벨을 붙여 답변 |
| (검색 0건일 때) | **추측하지 않는다.** 문서 목록 + 다음 행동 안내만 |
| `@tybot --model=claude-opus-4-8 질문` | 모델 지정 |
| 봇에게 DM | 동일 (채널 멤버십 기준 권한 적용) |

### 의도 분류는 LLM 이 한다
정규식으로 자연어를 가르면 표현이 바뀔 때마다 샌다("상태" vs "너의 상태" vs "잘 돌아가?").
질문이 오면 먼저 **저가 모델(Haiku)로 분류**한다 — 질문당 약 $0.0003.

**복합 질문은 분해해서 각각 답한다.** 1차 LLM(저가 모델)이 질문을 하위질문 목록으로
나누고, 하위질문마다 아래 표의 경로를 탄다. 최대 3개이며 넘으면 앞의 것부터 답하고
나머지는 다시 물어달라고 알린다. 분해가 실패하면(모델 장애 등) 절 단위 정규식으로 폴백한다.

수집 지시(`ingest`/`ingest_all`)가 다른 질문과 섞여 오면 **수집만** 실행한다 —
무엇을 실행하는지 모호한 상태로 쓰기를 실행하지 않는다.

| 분류 | 처리 |
|---|---|
| `status` | 결정적 상태 블록 + 질문에 맞춘 첫 문장(저가 모델). LLM 이 죽으면 블록만 |
| `help` | 명령어 목록으로 즉답 (LLM 없음 — 없는 명령을 만들지 않기 위해) |
| `memory` | 기억 정책을 **사실로 넘겨 LLM 이 문장을 쓴다** + 본인 감사기록. **이전 답변을 근거로 쓰지 않는다**(요약 재귀 방지) |
| `summary` | 기간 스캔 후 채널별 정리. 워크스페이스를 명시하면 그 범위만 정리 |
| `search` | 추출된 **핵심어**로 원문 검색 (요청 표현 `알려줘` 등은 검색어에서 제외) |
| `advice` | 판단·권고. 관련 원문이 있으면 근거로 인용, 없으면 일반 판단임을 명시 |
| `smalltalk` | 짧게 안내(저가 모델) |
| `out_of_scope` | 범위를 벗어났다고 즉답. LLM 없음 |

- 분류기는 **답을 만들지 않는다.** 라우팅과 검색어 추출만 한다.

### `/투표` — 채널 투표

Slack 에는 기본 투표 기능이 없어서 직접 만들었다.

| 입력 | 동작 |
|---|---|
| `/투표` | 투표 만들기 화면이 열린다 |
| `/투표 회식 언제 할까요?` | 질문을 미리 채운 채로 화면이 열린다 |
| `/투표 도움말` | 사용법 안내(본인에게만 보인다) |

고를 수 있는 옵션:

| 옵션 | 뜻 |
|---|---|
| 여러 개 선택 | 켜면 여러 항목을 고를 수 있다. 끄면 하나만 |
| 익명 투표 | 누가 무엇을 골랐는지 아무도 볼 수 없다 |
| 변경 불가 | 한 번 고르면 바꿀 수 없다. 끄면 마감 전까지 변경 가능 |
| 결과 공개 시점 | 항상 / 투표한 사람에게만 / 마감 후에만 |
| 마감 | 30분~1주, 또는 만든 사람이 직접 마감 |

투표는 **만든 사람과 채널 관리 권한자만** 마감할 수 있다.
선택지를 다시 누르면 취소된다.

**익명 투표의 실제 동작** — 중복 투표를 막으려면 같은 사람인지 알아야 하므로, 익명 투표는
투표마다 다른 소금값을 섞은 해시를 저장한다. 저장 파일에 Slack 사용자 ID 가 남지 않고,
해시에서 사용자를 되돌릴 수도 없다(`tests/test_polls.py` 에서 검증).

투표 데이터는 `<STATE_DIR>/polls/` 에 있고 **아카이브에는 들어가지 않는다**(원칙 1).

#### 사실과 판단의 경계 (advice 경로)
"출처 없으면 답하지 않는다"는 **사실 조회**의 규칙이다. "어느 방향이 나을까"는 사실 조회가 아니라
판단 요청이라, 같은 규칙을 적용하면 아무 답도 못 한다. 그래서 경로를 나눈다.

| | 사실 (search/summary) | 판단 (advice) |
|---|---|---|
| 근거 | 아카이브 원문**만** | 원문 우선 + 일반 지식 허용 |
| 사내 수치·조직·결정사항 | 원문 그대로만 | **원문 없으면 단정 금지** (프롬프트로 강제) |
| 출력 표시 | 출처 목록 | `💬 판단 요청으로 답합니다` + 원문 없으면 `일반적인 판단입니다` 라벨 |
| 라벨 부착 주체 | — | **코드**가 붙인다 (LLM 이 빼먹을 수 있는 것을 원칙에 맡기지 않음) |

권한 필터는 판단 경로에도 동일하게 적용된다 — 열람 권한 없는 채널 원문은 판단 근거에도 안 들어간다.
- 분류 실패·API 장애 시 **정규식 폴백**으로 자동 전환된다(봇이 멈추지 않음). 로그의 `intent kind=… src=regex` 로 확인.
- `수집`/`전체수집` 은 분류를 거치지 않는 **명시 명령**이다 — LLM 판단으로 수집이 트리거되면 안 되기 때문.

### 수집 범위 — 알아야 할 것
1. **실시간이 본선.** Slack이 2025-05 이후 생성된 비-마켓플레이스 앱의 `conversations.history` 를
   **분당 1요청 / 회당 15건**으로 제한한다. 과거 대화 대량 백필은 사실상 불가.
   대신 `message.channels`/`message.groups` 이벤트로 앞으로의 대화를 전부 잡는다.
2. **채널 이름이 수집 여부를 정한다.** `#<본부|실|팀|현장|프로젝트>-<조직명>_<조직코드>-<업무>`
   형식이면 공개 채널은 봇이 **스스로 참여**한다(`/invite` 불필요). 규칙 밖 이름(잡담·개인 채널)은
   수집하지 않는다. 새 채널·이름 변경은 `channel_created`·`channel_rename` 이벤트로 즉시 반영된다.
3. **비공개 채널은 초대 필수.** 봇 토큰으로는 자가 참여가 불가능하고 목록 조회도 안 된다(Slack 설계).
   따라서 기동 로그에서 미초대 채널 목록을 만들 수도 없다. 일괄 초대는 `scripts/invite_bot.py`
   (관리자 사용자 토큰 필요, **서버에 저장하지 않음**).

#### TYBot으로 비공개 업무 채널 만들기
`업무 채널 만들기` 또는 `/채널 생성`을 쓰면 TYBot이 채널을 직접 만들기 때문에 처음부터
멤버가 되고 별도 `/invite`가 필요 없다. 모달은 두문자·조직명·조직코드·업무명을 각각 받아
`#팀-전산_ABB110-주간회의` 형식으로 조립하며, 규칙 밖 이름은 생성 전에 거부한다.
Slack은 채널명의 영문을 소문자로 저장하므로 실제 화면에서는 조직코드가 `abb110`으로 보일 수
있다. 수집 규칙은 조직코드의 대소문자를 모두 인식한다.

최초 생성 요청자는 `STATE_DIR/channel-owners.json`에 TYBot 논리 관리자로 기록된다. 이 파일은
아카이브 원문이 아니며 검색 근거로 사용하지 않는다. 요청자는 `/채널 이름변경`을 사용할 수 있다.
추가 운영자는 `.env`의 `CHANNEL_ADMIN_USERS`에 Slack 사용자 ID를 지정한다.

Pro 플랜의 Slack Channel Manager는 별도 역할이다. Slack 기본 화면에서 직접 이름 변경·보관까지
하게 하려면 채널 정보 → **Managed by(관리자)** 에서 요청자를 한 번 지정한다. Slack 공개 Web API에는
이 역할을 자동 지정하는 메서드가 없으므로 TYBot의 논리 관리자 기록과 구분한다.

### 수집 경로 세 가지 — 언제 무엇이 쓰이나

| 경로 | 담당 범위 | 한계 |
|---|---|---|
| **실시간**(기본) | 규칙에 맞고 봇이 초대된 채널의 대화·첨부 | 초대 이전 과거는 못 본다 |
| **정기 배치**(`tybot-collect.timer`) | 규칙 채널의 단절 구간·캔버스 스냅샷 | 채널당 매시 15건, 스레드 답글 제외 |
| **수동 `수집`** | ① 새로 초대한 채널의 최근 대화<br>② **스레드 답글**(다른 두 경로가 놓치는 부분)<br>③ 권한·쓰기 동작 확인 | 요청당 15건, 스레드 5개 |

수동 `수집` 이 여전히 필요한 이유는 ②다. `conversations.history` 는 **스레드 답글을 주지 않는다.**
실시간 수집은 답글을 잡지만, 봇이 없던 기간의 답글은 `conversations.replies` 로만 가져올 수 있고
그걸 호출하는 건 수동 `수집` 뿐이다.

### 답변 범위는 질문자 권한
질문자가 멤버인 채널만 근거로 쓴다. 전 채널 통합조회가 필요하면 `.env` 의 `EXEC_USERS` 에
Slack user id 를 넣는다 — **채널 멤버십 필터를 우회하므로 최소 인원만.**
(user id 확인: Slack 프로필 → 더보기 → 멤버 ID 복사)

## 4. 파일럿 합격 기준
- [ ] 아카이브에 있는 사실 → 정확히 답하고 `출처:` 가 붙는다
- [ ] 아카이브에 **없는** 사실 → 지어내지 않고 "근거 못 찾음 + 문서 목록"을 준다
- [ ] 초대되지 않은 채널 내용 → 채널명조차 노출되지 않는다
- [ ] 봇 답변이 아카이브 원문에 되먹임되지 않는다 (`## 원문` 에 봇 발언 없음)
- [ ] 주민번호/등기부등본 포함 메시지는 저장되지 않는다
