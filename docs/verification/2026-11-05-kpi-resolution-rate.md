# KPI「질문 해결률」 — 정의와 재집계 (2026-11-05)

> 전사 KPI 로 쓸 한 수를 정하기 위해 만든 것이다. **실측은 운영 서버에서 뽑는다**
> — 개발 PC 에는 감사 기록(`qa-*.jsonl`)이 없다.

## 정의

```
질문 해결률 = 출처가 붙은 업무 답변 ÷ 사람이 던진 업무 질문 전부
```

| | 조건 |
|---|---|
| 분자 | `intent_kind` 가 업무 · `citations` 가 비어 있지 않음 · 실패 아님 |
| 분모 | `intent_kind` 가 업무인 질문 **전부** (근거 없음·권한 미확인·오류 포함) |

**이름을 「신뢰율」 로 붙이지 않는다.** 정확도를 약속하는 이름인데 정확도를 재지 않는다.

## 콘솔 `groundedRate` 와 왜 다른가

같은 자료를 다르게 센다. **두 수가 달라지는 것이 맞다.**

| | 분자 | 분모 | 쓰임 |
|---|---|---|---|
| 콘솔 `groundedRate` | `hits > 0` | 업무 질문 − 권한 미확인 | **진단** — 원인을 가린다 |
| 이 KPI | `citations` 있음 | 업무 질문 **전부** | **성과** — 결과만 본다 |

- 콘솔이 권한 미확인을 분모에서 빼는 것은 맞다(`console/health.py:289`). Slack 조회
  장애를 「자료 없음」 으로 읽으면 엉뚱한 데를 고친다.
- KPI 는 반대다. 묻는 사람에게 권한 확인 실패는 **답을 못 받은 것**이고 우리 잘못이다.

스크립트는 두 수를 **나란히** 찍는다. 목표치를 정할 때 섞으면 콘솔은 초록인데 KPI 는
미달인 상태가 생기고, 그때부터 둘 다 안 믿게 된다.

## 왜 분모가 「수요」 여야 하는가

이 KPI 설계의 전부다.

| 분모 | 결과 |
|---|---|
| 봇이 답한 것 | **어려운 질문을 피할수록 올라간다.** 원칙대로 「근거 없음」 을 답하면 깎인다 |
| **사람이 물은 것** | 회피해도 분모에 남는다. 올리는 길이 **자료를 쌓고 검색을 고치는 것뿐** |

시험으로 박아 뒀다 — `test_avoiding_hard_questions_does_not_raise_the_number`.

## 분자를 `citations` 로 세는 이유

지금 콘솔 지표의 분자는 `hits > 0` 이다(`health.py:269`, `answer_records.py:223`,
`reader.py:581`). 그건 **검색이 뭔가 걸렸다**는 뜻이지 답에 출처를 붙였다는 뜻이
아니다. 인용 목록은 `QARecord.citations` 로 이미 기록되는데 **어떤 지표도 쓰지 않았다.**

`hits` 로 KPI 를 만들면 검색이 아무거나 1건 걸린 답변이 성과가 된다.

## 돌리는 법

**venv 의 인터프리터를 절대 경로로, 서비스 계정으로** 부른다.

```bash
sudo -u tybot /opt/tybot/.venv/bin/python \
    /opt/tybot/scripts/kpi_resolution_rate.py \
    --days 90 --qa-log /var/lib/tybot/qa-log
```

JSON 으로 받으려면 `--json <경로>` 를 붙인다.

**아무것도 쓰지 않는다.** 질문·답변 본문은 읽지도 찍지도 않는다 — 나가는 것은
건수·비율·사유 코드·워크스페이스 키뿐이다. 감사 기록이 바뀌지 않는 것도
시험으로 묶었다(`test_the_run_writes_nothing`).

## 읽는 법

- **표본 10건 미만이면 비율 대신 「표본 부족」** 이다. `0%` 가 아니다
  (`MIN_SAMPLE` — `console/health.py` 와 같은 값)
- **깨진 줄 수를 같이 찍는다.** 조용히 버리면 분모가 줄어 KPI 가 오른다
- **워크스페이스별 분해를 같이 본다.** 전사 평균만 보면 죽은 워크스페이스가 안 보인다
- 「해결 안 된 이유」 표는 KPI 가 아니라 **고칠 자리**다

## 목표치를 정하기 전에

1. 위 명령으로 **90일 실측**을 뽑는다
2. 워크스페이스별로 본다 — 한 곳이 죽어 있어도 전사 평균은 멀쩡해 보인다
3. 그 실측 위에서 목표를 정한다

기존 운영 임계는 `GROUNDED_WARN = 0.70` / `GROUNDED_BAD = 0.50` 이다(콘솔 진단 기준).
**KPI 목표를 이것과 맞춰 두지 않으면** 두 화면이 서로 다른 말을 한다.

> 새 정의는 지금 콘솔 수치보다 **낮게 나온다.** 분자는 좁아지고(출처 기준) 분모는
> 넓어진다(권한 미확인·오류 포함). 낮다고 성능이 나빠진 것이 아니다 — 재는 대상이
> 다른 것이다.

## 한 수로는 못 잡는 것 — 무효 조건

KPI 는 하나다. 다만 아래가 걸리면 그 기간 수치를 **무효**로 둔다. 지표를 늘리는
것이 아니라 믿을 수 있는 조건이다.

| 조건 | 왜 |
|---|---|
| 👎 비율이 기준을 넘음 | **출처가 붙은 틀린 답**은 이 KPI 에서 만점이다 |
| 업무 질문 10건 미만 | 비율을 내지 않는다 |
