# PF·TY 공통 아카이브 저장 구조 실측 및 권고 보고서

> 작성·최종 실측: 2026-09-23 18:33 KST<br>

> 상태: **실측 완료 · 구조 2 기술 권고 · PF/전산 공동 승인 대기**<br>

## 1. 결론

공통 Archiving Bot의 운영 정본은 다음 **구조 2**를 권고한다.

```text
/var/lib/tybot/archive/workspaces/<workspace-key>/
  channels/<channel-id>__<display-slug>/
    raw/YYYY-MM-DD.md
    attachments/<file-id>/<revision>.md

/var/lib/tybot/objects/workspaces/<workspace-key>/
  channels/<channel-id>/attachments/<file-id>/
```

핵심 근거는 다음과 같다.

1. PF 소규모 자료에서는 구조 1이 빨랐지만, 실제 TY 규모에서는 구조 2가
   **대형 채널 수집 26.7%, warm 검색 43.1~46.4%, 전체 재색인 41.8%** 유리했다.
2. 구조 2의 cold 검색도 구조 1보다 2.3~4.3% 빨랐다. 편차를 고려하면 사실상
   동률이지만, 최소한 구조 1의 예상 장점이 TY 규모에서 확인되지는 않았다.
3. 두 구조의 저장 용량 차이는 28 KB, 약 **0.02%**로 의미가 없었다.
4. 구조 2는 날짜별 파일이라 채널이 커져도 한 번에 다시 쓰는 범위가 제한된다.
5. TY 운영 코드가 이미 구조 2를 사용한다. 구조 1을 선택하면 production writer와
   재색인 단위를 새로 구현한 뒤 다시 실측해야 한다.

구조 1은 PF 원본 수용과 사람이 한 파일로 읽는 데 유리하다. 그러나 이는 일회성
이관·감사 편의이고, 공통 Archiving Bot은 계속 증가하는 전체 워크스페이스를 장기간
운영해야 한다. PF 원본은 구조 1 그대로 **불변 스냅샷으로 별도 보존**하고, 운영
정본만 구조 2로 변환하는 것이 두 요구를 함께 만족시킨다.

> 이 결론은 기존 잠정 결론인 구조 1을 변경한다. 잠정 결론에는 TY 대형 채널과
> M4 재색인이 없었고, 문서 자체가 두 항목에서 결과가 나쁘면 다시 판단하도록
> 명시했다. 이번 서버 실측이 그 누락을 채웠다.

## 2. 비교한 구조

| 구분 | 구조 | 현재 사용처 |
|---|---|---|
| 구조 1(A) | `channels/<slug>__<channel-id>.md` | PF Hermes |
| 구조 2(B) | `channels/<channel-id>__<slug>/raw/YYYY-MM-DD.md` | TYBot |

공통 조건은 다음과 같다.

- 채널은 이름이 아니라 stable channel ID로 식별한다.
- 첨부 원본과 변환 본문은 raw 채팅에서 분리한다.
- 요약과 봇 답변은 raw 원문에 넣지 않는다.
- 변환 전후 메시지 내용·순서·ACL·첨부 참조가 같아야 한다.
- PF 원본에는 없는 Slack `message_ts`를 만들지 않는다.

## 6. PF 로컬 결과와 TY 서버 결과가 다른 이유

PF 최대 채널은 286줄이고 TY 실측 최대 채널은 50,849줄이다. 약 178배 차이다.

- 작은 채널에서는 파일 수가 적은 구조 1의 `open`·`stat` 절감 효과가 컸다.
- 큰 채널에서는 구조 1의 단일 파일 재작성과 재파싱 비용이 커졌다.
- 구조 2는 파일 수가 많지만 날짜별 파일 캐시가 warm 검색에서 효과를 냈다.
- 개발 PC와 DMZ 서버는 OS·파일시스템·캐시 조건도 다르다.

따라서 PF 로컬 수치가 틀린 것이 아니라, **자료 분포에 따라 병목이 바뀐 것**이다.
공통 구조는 현재의 작은 PF 자료보다 향후 전체 워크스페이스의 증가를 기준으로
선택해야 한다.

## 7. 기존 잠정 판정 규칙의 재평가

기존 설계는 PF 원본을 그대로 받을 수 있고 사람이 한 파일로 읽기 쉽다는 이유로
구조 1을 우선했다. 또한 수집·검색·재색인 약점은 고칠 수 있으므로 선택 근거에서
제외했다.

그 규칙을 문자 그대로 적용하면 이번에도 구조 1이 남는다. 그러나 공통 Archiving
Bot의 목표는 **한 번의 PF 이관 편의가 아니라 장기 운영 정본을 정하는 것**이다.
고쳐야 할 production writer와 재색인 구현의 비용을 제외하면 실제 구현·운영 비용을
의사결정에서 누락하게 된다.

따라서 최종 권고에서는 다음처럼 구분한다.

| 요구 | 처리 방식 |
|---|---|
| PF 원본 보존·감사 | 구조 1 원본 ZIP/Git snapshot을 hash와 함께 불변 보관 |
| 공통 운영 정본 | 구조 2로 변환해 Archiving Bot이 계속 기록 |
| 원본 대조 | `legacy_source_ref` provenance sidecar 사용 |
| 사람이 채널 전체 읽기 | console/exporter가 날짜 파일을 순서대로 병합해 제공 |

이 방식은 PF팀의 원본 추적성을 없애지 않으면서 운영 구조를 성장에 맞춘다.

## 8. 적용 조건과 작업 순서

### 공동 승인 항목

1. 구조 2를 PF·TY 공통 운영 정본으로 승인한다.
2. PF 기존 Git/ZIP은 삭제하거나 덮어쓰지 않고 불변 snapshot으로 보존한다.
3. 첨부는 raw 본문에 복제하지 않고 별도 정본으로 저장한다.
4. 요약 승인과 답변은 Hermes가 담당하며 Archiving Bot은 원문·첨부만 기록한다.

### 구현 순서

1. Archiving Bot writer를 구조 2 하나로 고정한다.
2. PF workspace/channel ID와 visibility mapping을 사람이 확인한다.
3. PF snapshot을 구조 2로 dry-run 변환하고 `--verify`를 통과시킨다.
4. `legacy_source_ref`, snapshot SHA-256, source commit을 보존한다.
5. 변환 결과를 답변 근거에 바로 연결하지 않고 격리된 import 경로에 둔다.
6. 기존 PF 수집과 Archiving Bot shadow 수집을 같은 기간 병행한다.
7. 채널별 누락 0, 권한 유출 0, 첨부 손실 0, edit/delete/스레드 보존을 확인한다.
8. TY에서 먼저 writer 소유권을 Archiving Bot으로 전환한다.
9. TY 안정화 후 PF에 같은 구조를 적용한다.

## 10. 보존할 실측 증거

서버에서 다음 파일은 공동 결정이 끝날 때까지 삭제하지 않는다.

```text
/var/lib/tybot/archive-lab/runs/20260923-180306-ty-layout-benchmark/
  snapshot.sha256
  layout-a/
  layout-b/
  reports/bench-20260923-093306.json
  reports/bench-20260923-093306.md
  reports/server-run.log
  bench-index.meta
```

`bench-index.dsn`은 비밀번호가 포함된 임시 시크릿이다. 결과 검증과 전용 DB 삭제가
끝나면 파일을 삭제한다. 보고서나 Git에는 넣지 않는다. 전용 DB와 role도 공동 검토가
끝난 뒤 제거한다.

## 11. 최종 승인 기준

다음 네 항목에 PF팀과 전산팀이 동의하면 구조 결정을 완료한다.

- 운영 정본: **구조 2**
- PF 과거 원본: **구조 1 snapshot 별도 보존**
- 첨부: **별도 정본**, raw에는 ID와 출처만 기록
- 요약 검토: **Hermes 소유**, Archiving Bot 범위 밖

승인 전에는 운영 아카이브 경로를 변환하거나 PF 원본을 삭제하지 않는다.
