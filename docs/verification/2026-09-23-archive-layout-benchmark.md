# 아카이브 저장 구조 실측 보고서

> 잰 날: 2026-09-23
> 계약: [`docs/design/archive-layout-benchmark.md`](../design/archive-layout-benchmark.md) §6·§7
> 잰 곳: **개발 PC(Windows 11, NVMe).** 서버에서 다시 재야 한다 — §「이 보고서의 한계」
> 읽는 사람: 구조를 정하는 사람, 서버 폴더 구조를 정하는 쪽(Codex)

## 무엇을 쟀고 무엇을 안 쟀나 — **먼저 읽는다**

| | |
|---|---|
| 잰 자료 | **프금팀(PF) 자료뿐** — 43채널 2,061메시지 |
| 안 잰 자료 | **우리 수집본(TY).** 서버 `/var/lib/tybot/archive` 에 있고 이 실측은 개발 PC 에서 돌렸다 |
| 잰 자리 | `d:/tmp/tybot-archive-lab/` (개발 PC). 설계 §2 의 `/var/lib/tybot/archive-lab/` **이 아니다** |
| 운영 아카이브 | 읽지도 쓰지도 않았다(§8) |

개발 PC 에는 `/var/lib/tybot` 이 없다. 그래서 설계 §2 의 폴더 구조를 **같은 모양으로**
개발 PC 에 만들었다 — `snapshot` · `layout-a` · `layout-b` · `reports`. 서버에서
다시 잴 때는 §2 경로를 그대로 쓴다(§9).

```text
d:/tmp/tybot-archive-lab/
    snapshot/     ← subbots/pf-hermes-archive 사본 26 MB (읽기 전용으로 씀)
    layout-a/     ← 구조 1 배치 1.6 MB
    layout-b/     ← 구조 2 배치 3.2 MB
    reports/      ← 원자료(json·md)와 벤치 작업 사본
```

> **이 절이 늦게 들어왔다.** 처음 보고서는 잰 자리를 적지 않았고, 실제로는 지워지는
> 임시 폴더에서 돌렸다. 「어디서 쟀는지」 가 없으면 재현도 검증도 안 된다 —
> 숫자만 남고 그 숫자가 무엇을 잰 것인지는 남지 않는다.

## 한 줄

**Hermes 쪽은 두 구조가 같다(증명됨). 우리 쪽 비용은 세 항목 모두 구조 1 이 빠른데,
§6 이 예상한 것과 반대다.** 다만 §6 규칙에 따라 이 숫자는 결정 근거가 아니다.

| | 파일 | 원문 파일 | 디렉터리 | 크기 | 원문 파일 크기(최소/중위/최대) |

| 구조 2 | 887 | 842 | 90 | 1,613 KB | 310 B / 701 B / 8.9 KB |

구조 2 가 218 KB(16%) 더 크다. 파일마다 프론트매터가 붙기 때문이다 — 839개 ×
약 260 B. 파일 수는 **19.6배**, 디렉터리는 22.5배다.

> 「참여 기록(요약)」 절이 들어 있고, 요약은 봇·사람의 **해석**이라 원문으로 옮기지
> 않는다(절대 원칙 1). 35개 파일에서 파일당 3~4줄을 남겨 두었다.

### 전산팀(TY) — **못 쟀다**

운영 아카이브는 서버의 `/var/lib/tybot/archive` 에 있고 이 실측은 개발 PC 에서
돌렸다. §8 에 따라 운영 경로는 읽지도 쓰지도 않았다.

**이 칸을 비워 두는 것이 맞다.** TY 자료는 채널 수·줄 수 분포가 PF 와 다르고(현장
채널이 많고 첨부가 많다), 그 분포가 구조 1 의 약점(큰 파일을 통째로 다시 쓴다)이
어디서 나타나는지를 정한다. PF 최대 채널이 286줄인데, TY 에는 그보다 훨씬 큰
채널이 있다.

서버에서 다음을 돌리면 이 칸이 채워진다.

```bash
sudo -u tybot /opt/tybot/.venv/bin/python /opt/tybot/scripts/archive_layout_convert.py \
    --from ty --source /var/lib/tybot/archive-lab/snapshot --to a \
    --out /var/lib/tybot/archive-lab/layout-a
```

## 2. 동등성 시험 — **통과**

`tests/test_archive_layout_equivalence.py` · 15건 통과.

두 배치에 같은 `RequestContext` 로 같은 도구 호출을 던져 출력을 **바이트로** 비교했다.
`search`(2글자 한국어·긴 낱말·0건·채널 범위), `read_channel`(기본·limit=400·없는 채널),
`read_document`, 그리고 권한 경우 셋(채널 하나만 보이는 ctx · exec · 채널 없음).

**차이 없음.** 그러므로 Hermes 가 받는 입력은 두 구조에서 같고, 토큰도 시간도 같다.
모델을 부르지 않았다 — §5 가 정한 대로 재는 것이 아니라 증명했다.

변환 검증(`--verify`)도 통과: 메시지 수·내용 multiset(중복 보존)·채널별 순서·
ACL/visibility·첨부 참조·출처 사이드카 바이트.

### 이 시험이 잡아낸 것 둘

증명을 세우는 과정에서 **구조 논쟁과 무관한 우리 버그 둘**이 나왔다. 이게 이 시험의
실제 값어치다.

**① 구조 1 은 애초에 읽히지 않았다.** `ArchiveStore._files()` 글롭이
`*/channels/*/raw/*.md` 뿐이라 구조 1 파일이 한 장도 안 걸렸다. 파일은 있고 검색만
비었다.

성능 실측을 먼저 돌렸다면 **「구조 1 이 압도적으로 빠르다」 가 나왔을 것이다** —
아무것도 안 읽으니까. 동등성 시험도 그냥은 통과했을 것이다(양쪽이 아무것도 안 읽으면
출력이 똑같이 빈 문자열이다). 그래서 「구조 1 이 정말 읽혔는가」 를 시험으로 따로 박았다.

**② 지금 운영 구조에서 검색이 줄을 잃고 있었다** — 구조 결정과 무관한 현재 버그.

`_merge()` 가 일자 파일을 합치면서 모든 줄에 같은 `doc.path` 를 달아 주는데 `lineno`
는 파일마다 1부터 다시 세므로, 다른 날의 다른 줄이 같은 키가 됐다. `_rank` 가 그
키로 중복을 지워 둘 중 하나가 검색 결과에서 빠졌다.

| | 키가 겹치는 줄 |
|---|---|
| 구조 1 | 2,061줄 중 **0줄** |
| 구조 2 (**지금 운영 구조**) | 2,061줄 중 **1,750줄** |

오류도 0건도 아니고 「그 말은 없었다」 로만 보인다. 고침은 커밋 `3ff761a`,
회귀 시험 `tests/test_search_merged_dedup.py`.

## 4. §6 이 예상한 것과 **반대로 나왔다**

| # | §6 예상 | 실측 | |
|---|---|---|---|
| 1 수집 | 구조 2 유리 | **구조 1** (1.1~1.7배) | 뒤집힘 |
| 2 검색 warm | 구조 2 유리 | **구조 1** (1.9~3.0배) | 뒤집힘 |
| 3 검색 cold | 구조 1 유리 | **구조 1** (6.9~8.8배) | 맞음 |
| 4 재색인 | 구조 2 유리 | 못 쟀다 | — |

### 왜 뒤집혔나 — 가정이 코드와 달랐다

**수집(1번)**: §6 은 「구조 2 는 오늘 파일만 쓴다」 를 이점으로 봤다. 그런데
`_ingest_locked` 는 중복 검사를 위해 **그 채널의 모든 날짜 파일을 읽는다.**

```python
existing_texts = {path: path.read_text(...) for path in sorted(raw_dir.glob("*.md"))}
```

읽는 바이트는 두 구조가 같고 구조 2 는 파일 수만큼 `open`·`stat` 을 더 한다. 그
위에 쓰기와 프론트매터 갱신이 얹힌다. 그래서 구조 2 는 **엄격히 더 많은 일**을 한다.

**검색 warm(2번)**: §6 은 「구조 2 는 무효화가 오늘 파일로 한정」 을 이점으로 봤다.
맞는 말이지만, `visible_docs` 는 매번 842개 파일을 `stat` 하고 `_merge()` 로 다시
묶는다. 캐시가 아껴 주는 것은 **파싱**이고, 남는 것은 syscall 과 병합이다. 구조 1 은
그 둘이 43분의 1이다.

> **한쪽만 잠금을 잡고 재고 있었다.** 처음 돌렸을 때 M1 에서 구조 1 이 두 배
> 빨랐는데, 상당 부분이 `writer.ingest` 만 `archive_write_lock` 을 잡기 때문이었다.
> 구조가 아니라 안전 장치의 차이였다. 구조 1 쪽에도 같은 잠금과 프론트매터 갱신을
> 넣고 다시 쟀고, 위 표가 그 결과다.

## 5. writer 상태 — **둘 다 「현재본」 이다**

| | 무엇을 썼나 |
|---|---|
| 구조 2 | `writer.ingest` **운영 코드 그대로** |
| 구조 1 | `scripts/archive_layout_bench.py` 안의 `ingest_layout_a`. **append writer 가 아니다** |

구조 1 쪽은 `screen`·`format_line`·`dedupe_line`·`archive_write_lock` 을 writer 의
것을 그대로 부르고, 파일을 통째로 읽고 통째로 다시 쓴다. 그래서 위 숫자는 구조 1 의
**개선 전** 값이다 — append writer 를 만들면 더 빨라진다.

**구조 1 은 개선본으로 잰 것이 아니다.** 「구조 1 이 이미 빠른데 개선까지 하면」 이
아니라 「개선 없이도 빠르다」 로 읽어야 한다.

## 6. §6 규칙을 적용한다 — **적용 과정**

```
1. 도구 출력이 두 배치에서 같지 않으면 → 멈추고 원인을 고친다.
   → 같다(§2). 통과. 실제로 여기서 버그 둘을 찾아 고쳤다.

2. 같으면 → Hermes 쪽은 동등하다. 아래로 정한다.
   a. PF 기존 아카이브를 그대로 받을 수 있는가      → 구조 1
   b. 사람이 열어서 읽을 수 있는가                  → 구조 1
   c. 위 둘이 비기면 → 덜 고쳐도 되는 쪽            → 해당 없음(a·b 가 안 비겼다)

3. 우리 쪽 비용(1·2·4)은 고를 때 쓰지 않는다.
   → 쓰지 않았다. §3 은 참고 기록이다.

4. 어느 한쪽이 운영에 못 쓸 만큼 나쁘면 탈락시킨다.
   → 둘 다 하한선 안이다. 가장 느린 값이 구조 2 의 검색 cold 273 ms 다.
```

### 결론: **구조 1**

2-a 와 2-b 가 모두 구조 1 을 가리키고, 2-c 로 갈 일이 없다.

- **2-a**: PF 아카이브(17.3 MB, 43파일)를 그대로 받는다. 구조 2 로 가면 43개 파일을 839개로
  쪼개야 하고, 쪼개는 순간 PF 쪽 원본과 파일 단위로 대조가 안 된다
- **2-b**: 채널 하나가 파일 하나다. 점검·감사에서 `less` 한 번으로 끝난다.
  구조 2 는 채널 하나를 보려고 최대 40개 파일을 열어야 한다

우리 쪽 비용(§3)은 **결론에 쓰지 않았다.** 다만 「구조 1 을 골랐는데 비용에서도
지지 않는다」 는 사실은, 이 결정이 성능을 희생한 선택이 아님을 말해 준다.

### 이 결론이 뒤집힐 조건

- **M4 증분 재색인에서 구조 1 이 운영에 못 쓸 만큼 나쁘면**(규칙 4). 못 쟀다.
  서버에서 재기 전까지 이 결론은 **잠정**이다
- TY 자료로 다시 쟀을 때 큰 채널에서 수집이 하한선을 넘으면. PF 최대가 286줄인데
  TY 에는 더 큰 채널이 있다

## 7. 구조 1 을 고르면 **먼저 고쳐야 할 것**

| # | 무엇 | 왜 지금이 아니면 안 되나 | 상태 |
|---|---|---|---|
| 1 | `_files()` 에 구조 1 글롭 | 없으면 아카이브가 **통째로 안 보인다** | **완료** (`84fe6fa`) |
| 2 | 구조 1 append writer | 채널이 커질수록 통째 재작성 비용이 는다. PF 최대 42 KB 는 괜찮지만 TY 는 다르다 | 미착수 |
| 3 | 증분 재색인 판정 단위 | 지금은 파일 단위(줄 수 비교)다. 채널당 한 파일이면 그 채널 전체가 매번 재색인 후보가 된다 | 미착수 |
| 4 | 권한을 `archive_doc` 에서 읽기 | 표와 열이 이미 있다(`console_schema.sql`). 답변 경로만 안 쓴다. 이걸 하면 `visible_docs` 가 SQL 이 되고 파일 구조가 읽기에 거의 영향을 안 준다 | 미착수 |
| 5 | 파일명 규칙 고정 | `<slug>__<id>.md`, **채널 이름이 바뀌어도 파일명 유지**. 바꾸면 `doc_path` 가 달라져 색인에 옛 행이 남는다(지우는 경로가 없다) | 문서에 고정 |

**2번과 3번은 이관 전에 해야 한다.** 4번은 나중에 해도 되지만, 하고 나면 이 실측의
읽기 항목이 무의미해진다(구조가 읽기에 영향을 안 준다).

## 8. 이 보고서의 한계

- **PF 자료만 쟀다.** 우리 수집본은 서버에 있고 이 실측은 건드리지 않았다.
  구조 1 의 약점(큰 파일을 통째로 다시 쓴다)은 **큰 채널에서** 나타나는데, PF 최대가
  286줄이다. TY 에는 더 큰 채널이 있으므로 이 항목은 다시 재야 한다
- **잰 자리가 서버가 아니다.** 설계 §2 는 `/var/lib/tybot/archive-lab/` 을 정했지만
  개발 PC 에는 그 경로가 없어 같은 모양을 `d:/tmp/` 아래에 만들었다
- **같은 기계에서도 잰 자리에 따라 30% 움직였다**(§3 마지막). 절대값을 인용하지 않는다
- **개발 PC 에서 쟀다.** Windows 11 · NVMe. 서버는 리눅스이고 파일시스템·페이지
  캐시 동작이 다르다. 파일 수가 19.6배 차이 나는 비교라 **파일시스템이 결론을 바꿀
  수 있다**
- **cold 는 반쪽이다.** `ArchiveStore` 파싱 캐시만 비웠고 OS 페이지 캐시는 그대로다.
  즉 M3 은 「파싱 비용」 이지 「디스크에서 읽는 비용」 이 아니다. 진짜 cold 는
  구조 1 이 더 유리할 것이다(파일 수가 적다)
- **TY 자료를 못 쟀다.** §1 참조
- **M4 를 못 쟀다.** §3 참조. §6 표에서 구조 2 가 유리하다고 본 항목이다
- **구조 1 수집은 개선 전 구현이다.** §5 참조
- PF 자료 하나로만 쟀다. 채널 43개는 통계를 말하기엔 적다

## 9. 재현 — 서버 절차

개발 PC 명령은 여기 적지 않는다. 섞어 두면 서버에서 그대로 친 사람이
`command not found` 만 보고 원인을 모른다(CLAUDE.md). 개발 PC 에서 돌리는 모양은
설계 문서 [§10 재현](../design/archive-layout-benchmark.md) 에 있다.

```bash
VENV=/opt/tybot/.venv/bin/python
LAB=/var/lib/tybot/archive-lab

# 1. 두 배치를 만든다. 운영 아카이브는 읽기만 한다
sudo -u tybot $VENV /opt/tybot/scripts/archive_layout_convert.py     --from ty --source $LAB/snapshot --to a --out $LAB/layout-a
sudo -u tybot $VENV /opt/tybot/scripts/archive_layout_convert.py     --from ty --source $LAB/snapshot --to b --out $LAB/layout-b

# 2. 같은 내용인지 확인한다. 다르면 여기서 멈춘다 — 그 숫자는 버그를 잰 것이다
sudo -u tybot $VENV /opt/tybot/scripts/archive_layout_convert.py     --verify $LAB/layout-a $LAB/layout-b

# 3. 동등성 증명 (모델을 부르지 않는다)
sudo -u tybot $VENV -m pytest /opt/tybot/tests/test_archive_layout_equivalence.py     /opt/tybot/tests/test_archive_provenance.py     /opt/tybot/tests/test_search_merged_dedup.py

# 4. 우리 쪽 비용. 원본을 건드리지 않고 작업 사본에서 잰다
#    M4 증분 재색인은 실측 전용 DSN 을 줘야 잰다 — 운영 DB 를 쓰지 않는다(§8)
sudo -u tybot TYBOT_BENCH_INDEX_DSN=<실측전용DSN>     $VENV /opt/tybot/scripts/archive_layout_bench.py     --a $LAB/layout-a --b $LAB/layout-b --out $LAB/reports --rounds 30
```

PF 자료를 ZIP 으로 받아 돌릴 때는 `--source-commit eeb50045fe8813ff2bfb2e7b9a5f8d1e1f227881`
을 손으로 준다. ZIP 에는 `.git` 이 없어 커밋을 읽을 수 없고, 그대로 두면 manifest 의
`source_commit` 이 `null` 이 된다.

운영 경로(`/var/lib/tybot/archive`·`objects`·`staging`)를 `--source` 나 `--out` 으로
주면 두 스크립트 모두 거부한다.
