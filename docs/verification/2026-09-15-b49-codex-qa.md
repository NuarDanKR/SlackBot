# B-49 Codex QA

> 검증일: 2026-09-15
> 대상: `docs/design/pii-guardrail-and-canvas-artifacts.md` 구현
> 결과: 코드 결함 수정 완료, 운영 Slack 검증 및 셀별 source ID 계약은 남음

## 수정한 결함

1. **기간 파서가 ISO 날짜의 `-`를 기간 구분자로 오인**
   - `2026-03-01 ~ 2026-12-31`이 여러 조각으로 분리될 수 있었다.
   - 날짜 내부 하이픈과 날짜 사이 구분자를 구별하도록 수정했다.

2. **날짜 역검증이 값 손실·순서 변경을 허용**
   - 원문 숫자 일부가 사라지거나 순서가 바뀌어도 집합 포함 검사만 통과하면 됐다.
   - 숫자 개수와 위치를 함께 검사하고, 검증된 두 자리 연도 확장만 예외로 허용했다.

3. **AI 제목 검증 실패 시 fallback이 제목 계약을 우회**
   - 질문에 있는 `Canvas`, URL, Markdown 또는 `· TYBot`이 fallback 제목에 남을 수 있었다.
   - fallback에도 동일한 금지 문법을 적용하고 `research_question`을 우선 사용한다.
   - 숫자 검증도 부분 문자열이 아닌 정확한 숫자 토큰 비교로 바꿨다.

4. **전문 봇 보정 호출의 비용과 횟수가 감사에서 유실**
   - 프롬프트형 어댑터의 두 번째 호출이 첫 호출 비용을 덮어썼다.
   - 총비용과 `format_retry_count=1`을 `SpecialistAnswer` → `Answer` → `QARecord`로 전달한다.
   - 필드가 없는 구형 전문 봇 훅은 `0`으로 읽어 호환성을 유지한다.

5. **`files.list` 경로에서 TYBot 생성 Canvas 재수집 가능**
   - 채널 Canvas 전용 수집은 제외했지만 채널 파일 목록·백필 공통 경로에는 제외가 없었다.
   - 동적 제목 suffix, 구형 제목, 생성 Canvas ID 중 하나가 맞으면 후보에서 제외한다.
   - 스캔과 실제 collect 사이에 상태가 바뀌어도 collect 직전에 다시 검사한다.

6. **`guardrail_result`가 항상 빈 값**
   - 선택 근거와 유일하게 연결되는 첨부 metadata에서 가장 강한 PII 판정 코드만 QA에 남긴다.
   - 같은 채널에 같은 파일명이 여러 개면 임의 연결하지 않고 빈 값으로 둔다.

7. **기존 첨부 재변환 경로가 문서 유형 판정을 우회**
   - `writer.screen()`이 직접 식별자 전용으로 바뀐 뒤에도 재변환 스크립트가 이를
     전체 문서 검사로 사용하고 있었다.
   - 재변환도 파일명과 전체 변환문을 `screen_document()`에 전달하고 판정 metadata를
     함께 갱신하도록 통일했다.

## 확인한 계약

- 위험 용어 한 건만으로 파일을 차단하지 않는다.
- 주민등록번호 형태와 고위험 문서 복합 신호는 계속 파일 전체를 차단한다.
- Canvas 제목은 동적 제목 + ` · TYBot`, 본문 첫 블록은 Disclaimer다.
- 채널 요청은 채널 읽기 권한, DM 요청은 요청자 읽기 권한을 설정한다.
- Hermes에는 근거 질문과 표시 힌트만 전달하고 Canvas 생성·공유는 TYBot이 수행한다.
- 지원하지 않는 Canvas 편집과 실제 캘린더 등록은 실행한 척하지 않는다.

## 남은 검증과 설계 차이

1. **HarnessCell의 셀별 `source_id`가 아직 런타임에 연결되지 않았다.**
   현재 하네스는 Hermes Markdown의 원문 셀을 보존하고 숫자·날짜 역변환을 검사하지만,
   각 셀을 개별 `EvidenceRef`에 연결하지는 않는다. Hermes 구조화 출력에 셀별 근거 좌표를
   추가한 뒤, TYBot이 현재 권한으로 좌표를 다시 열어 검증하는 별도 계약이 필요하다.

2. 실제 Slack에서 채널 구성원·DM 사용자 Canvas 접근, 동적 제목 Canvas의 파일 목록 제외,
   일반 `등기부등본` 일정 이미지 통과와 실제 고위험 문서 차단을 각각 확인해야 한다.

3. 첨부 metadata 조회는 현재 답변 시 staging을 순회한다. 첨부가 크게 늘기 전에 파일 ID
   기반 인덱스 또는 Answer의 attachment metadata 전달 방식으로 성능을 실측해야 한다.
