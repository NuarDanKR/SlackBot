# 마스터·전문 봇 라우팅 검증

_검증일: 2026-09-13_  
_대상 커밋: `68f55d5` 및 그 이전 답변 추적·후속 질문·문서 집합 변경_

## 결론

2026-09-14 후속 결정: 본 문서의 관찰은 당시 커밋 기준이다. 구현 시
[`master-specialist-orchestration.md`](../design/master-specialist-orchestration.md)와
[`hermes-integration-fidelity.md`](../design/hermes-integration-fidelity.md)를 따른다.
도구 연결과 검색 동작 복구가 우선이며, 분류 신뢰도 미달과 전문 봇 실행 장애는
별도로 처리한다. 다른 부서 Hermes와의 실행 동등성은 아직 확인되지 않았다.

최근 변경은 후속 질문의 이전 근거 좌표 복원, 전체 기간 문서 집합 요약, 문서별 근거
배분, 누락 문서 표시와 콘솔 원문 연결을 구현했다. 관련 집중 테스트 138건과 `ruff`는
통과했다.

그러나 현재 구조는 다음 운영 원칙을 아직 충족하지 않는다.

> 마스터 TYBot은 업무 답변을 작성하는 봇이 아니라, 대화 맥락을 해석하고 권한과
> 근거 범위를 판정하여 적절한 전문 봇에 전달하는 오케스트레이터다. 근거에 기반한
> 업무 답변은 전문 봇만 작성한다.

현재는 전문 봇이 없거나 라우팅 신뢰도가 낮거나 호출이 실패하거나 출력 계약을
위반하면 마스터 LLM이 같은 근거로 직접 답한다. 같은 스레드의 이전 근거는 복원할 수
있지만, 전문 봇 선택에는 복원된 맥락이 아니라 현재 질문 문장만 전달된다. 따라서
`내가 이전에 요청했던 내용을 다시 확인해줘` 같은 질문이 Hermes가 아닌 마스터로
흐를 수 있다.

## 발견 사항

### Critical: 전문 봇 실패가 마스터의 업무 답변으로 바뀐다

- `src/tybot/answer.py`의 요약과 일반 답변은 전문 봇 결과가 없으면
  `self._router.complete()`로 마스터 답변을 생성한다.
- 판단·권고 경로는 전문 봇을 호출하지 않고 처음부터 마스터가 답한다.
- `src/tybot/slack/pilot.py`의 전문 봇 훅은 라우팅 실패와 모든 예외를 `None`으로
  바꾸며, 답변 엔진은 이를 마스터 답변 신호로 해석한다.
- 기존 테스트도 전문 봇 무응답, 낮은 신뢰도, 시간 초과, 계약 위반, ACL 위반에서
  마스터가 답하는 동작을 정상으로 고정한다.

이 동작은 새 역할 정의와 정면으로 충돌한다. 업무 답변에서 전문 봇이 실패하면 다음
승인 전문 봇을 시도하거나, 전문 답변을 제공할 수 없다는 결정적 상태 메시지를 보내야
한다. 마스터 LLM이 근거 내용을 바탕으로 대신 답해서는 안 된다.

### High: 복원된 스레드 맥락이 전문 봇 라우터에 전달되지 않는다

`pilot.py`는 이전 질문, 주제, 근거 좌표를 읽고 `ThreadFollowupResolver`로 현재 권한에서
근거를 복원한다. 하지만 `specialist_hook()`은 `route(question, workspace, router)`에
현재 task의 질문 문자열만 넘긴다. 복원된 이전 주제, 부모 QA 레코드, 첨부 상태와
`ResolvedFollowup`은 라우팅 입력에 없다.

따라서 근거 선택은 이전 미수금 문서를 되살렸어도 라우터는 `이전에 요청했던 내용`이라는
모호한 문장만 보고 전문 봇을 선택한다. 화면에 나타난 현상과 일치한다.

### High: 의도와 전문 봇을 별도의 LLM 호출로 두 번 판정한다

의도 분류가 Python 정규식만으로 수행된다는 추정은 현재 코드와 다르다.
`intent.plan()`은 LLM 우선이며 규칙은 실패 시 대체 경로다. 그 뒤
`specialist_router.route()`가 별도의 LLM 호출로 전문 봇을 다시 선택한다.

두 확률적 판정 사이에 독립적으로 이해 가능한 질문을 보장하는 구조화 계약이 없고,
두 번째 판정은 `none`을 정상 선택으로 허용한다. 라우터 오류, 파싱 오류, DB 오류,
신뢰도 미달도 모두 마스터로 간다. 이 때문에 같은 의미의 `주간 보고` 질문도 Hermes와
마스터 사이에서 흔들릴 수 있다.

LLM 마스터가 맥락을 판단하는 방향은 타당하다. 다만 LLM 호출을 하나 더 추가하는 것이
아니라, 현재의 의도 계획과 전문 봇 선택을 **하나의 구조화된 오케스트레이션 판정**으로
합쳐야 한다. 권한, 전문 봇 활성 상태와 근거 ID 검사는 계속 결정적 코드가 담당한다.

### High: DB의 전문 봇 실행 방식이 런타임 객체에서 유실된다

`specialist_router.available()`의 SQL은 `execution_mode`를 조회하지만 `Specialist(...)`
생성자에 그 값을 전달하지 않는다. DB에서 읽은 모든 전문 봇은 기본값 `prompt`가 된다.
따라서 Hermes가 DB에서 `tools`로 설정돼도 `ToolBox`가 연결되지 않는다.

기존 테스트는 SQL 문자열에 열 이름이 존재하는지와 직접 만든 `Specialist` 객체만
확인하여 이 결함을 잡지 못한다. DB 행 매핑 테스트가 필요하다.

### High: 시각 근거가 있으면 전문 봇을 건너뛴다

일반 답변 경로는 `not visual.any`일 때만 전문 봇을 호출한다. 이미지 원본이 선택되면
마스터 LLM이 이미지와 텍스트를 직접 받아 답한다. 이미지 PDF와 첨부 이미지가 많은
현재 업무에서는 새 역할 원칙을 자주 우회할 수 있다.

전문 봇 요청 계약이 권한 검사를 통과한 시각 근거를 지원하도록 확장되어야 한다.
지원하는 전문 봇이 없으면 마스터가 대신 읽지 말고 지원 불가 상태를 명시해야 한다.

### Medium: 라우팅 실패 관측성이 불완전하다

사용 가능한 전문 봇이 하나도 없으면 `none` 판정을 기록하지 않는다. DB 조회 실패도
빈 후보 목록으로 60초간 캐시하고 마스터 답변으로 바꾼다. 이 경우 콘솔에서 동일 질문이
왜 Hermes 대신 마스터로 갔는지 판별하기 어렵다.

업무 질문은 성공 여부와 관계없이 오케스트레이션 판정 ID, 요구 능력, 선택 전문 봇,
최종 응답 주체, 비민감 실패 코드와 폴백 단계를 기록해야 한다. 질문 본문과 근거 원문은
감사 메타데이터에 복제하지 않는다.

## 권장 목표 흐름

```text
Slack 사용자 질문 + 같은 스레드의 이전 사용자 질문/주제/근거 좌표
  -> 마스터 LLM: 맥락 해석 및 단일 구조화 판정
  -> 결정적 검증: 스키마, 채널/DM 범위, ACL, PII, 전문 봇 활성 상태
  -> 현재 권한으로 근거 좌표 복원 및 검색
  -> 선택된 전문 봇에 독립형 질문 + 허용된 근거만 전달
  -> 전문 봇이 업무 답변 생성
  -> TYBot이 근거 ID와 출력 계약 검증 후 출처 링크 부착
  -> Slack 전송 및 비민감 추적 기록
```

마스터 판정의 최소 구조는 다음과 같다.

```text
task_kind              factual | summary | analysis | system | clarify
standalone_question    이전 지칭을 풀어 쓴 독립형 질문
parent_record_ids      참조한 이전 QA 좌표
topic_terms            미수금, 주간업무보고 등
document_query         파일명/문서 종류 후보
time_scope             default | bounded | all
required_capability    internal_document_summary 등
specialist_key         활성 후보 중 하나
confidence             판정 신뢰도
clarification          추가 질문이 필요할 때만 사용
```

`system`과 `clarify`는 마스터가 결정적 문구로 응답할 수 있다. 사실 조회, 요약, 분석과
업무 권고는 반드시 전문 봇을 통과한다. 전문 봇 실패 순서는 다음과 같다.

1. 같은 능력을 가진 다음 승인 전문 봇을 시도한다.
2. 후보가 없거나 모두 실패하면 비민감 실패 코드와 함께 전문 답변 불가를 알린다.
3. 마스터 LLM이 근거를 읽어 대체 업무 답변을 만들지 않는다.

## 필수 회귀 테스트

- `미수금 현황을 확인해줘` 다음의 `내가 이전에 요청했던 내용을 다시 확인해줘`가
  `미수금 현황을 다시 확인해줘`라는 독립형 질문으로 Hermes에 전달된다.
- 같은 스레드의 근거 좌표는 현재 채널과 현재 사용자 ACL로 다시 검증된다.
- 같은 의미의 `주간 보고` 질문을 반복해도 요구 능력과 전문 봇 선택이 일관된다.
- 전문 봇 없음, DB 오류, 낮은 신뢰도, 시간 초과, 계약 위반에서 마스터 업무 답변이
  생성되지 않는다.
- DB 행의 `execution_mode=tools`가 런타임 `Specialist.execution_mode`에 보존된다.
- 시각 근거가 선택돼도 지원 전문 봇으로 전달되며, 미지원이면 명시적으로 중단된다.
- 전문 봇이 ACL 밖 source ID를 반환하면 답변을 폐기하고 마스터 대체 답변도 만들지 않는다.
- 라우팅 실패도 추적 기록에 남되 질문 본문, 근거 원문과 시크릿은 남지 않는다.

## 검증 실행 결과

- 집중 테스트: 138 passed
- `ruff check src tests scripts`: 통과
- 콘솔 TypeScript/Vite 빌드: 재실행 완료, 종료 코드 0으로 통과
- 전체 pytest: 1804 passed, 30 failed

전체 테스트의 30건 실패는 Windows에서 전문 봇 셸 테스트가 WSL용 `bash.exe`를 잡은
환경 문제다. 이번 답변 기능의 집중 테스트는 통과했지만, 새 마스터 역할 원칙을 검증하는
테스트가 아직 없으므로 기능 완료 판정은 할 수 없다.
