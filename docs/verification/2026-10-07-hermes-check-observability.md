# `npm run check` 관측성 — 구현과 측정

> 전제: [`2026-10-07-hermes-archiver-reader-performance.md`](2026-10-07-hermes-archiver-reader-performance.md)
> 담당 분리에서 **Hermes 개발 에이전트** 몫(진행 표시·구간 시간·상한·벤치마크).
> reader(`src/archive-reader/archiver.js`)와 그 시험은 Codex 가 동시에 고치는 중이라
> **건드리지 않았다.**

## 1. 무엇이 문제였나

TYIT 사전 검사에서 `check-brief-split.js` 가 12분 넘게 CPU 한 코어를 먹었다. 화면의
마지막 줄은 **이미 끝난 항목**(`상황판 투영이 필드를 빠뜨리지 않았나`)이었다. 사람이
본 것은 멈춘 화면이고 실제로는 돌고 있었다.

reader 의 반복 파싱이 원인이었지만, **그것과 별개로 두 겹의 관측성 결함**이 있었다.

1. `check-setup.js` 가 `spawnSync(..., {encoding})` 로 자식 출력을 **버퍼에 가둔다.**
   자식이 끝나기 전에는 한 글자도 안 보이고, 중간에 죽으면 그때까지의 출력도 사라진다
2. 자식에 **상한이 없다.** 영원히 돌아도 그대로 기다린다

둘 다 오류가 아니라 **침묵**으로 나타난다. 침묵은 「빠르다」 와 화면에서 같다.

## 2. 무엇을 고쳤나

| 자리 | 바뀐 것 |
|---|---|
| `scripts/_child-run.js` (신규) | 자식 실행·판정을 한 자리로. 시작 즉시 이름, 끝나면 소요 시간, 상한 초과 시 **이름과 파일을 적고** 중단, 중단돼도 **그때까지의 출력**을 보인다 |
| `scripts/check-setup.js` | 자식 실행을 그 러너에 위임. 구간 머리에 `검사 N개 · 개별 상한`, 구간 끝에 `[보임] 코드 일관성 N개 · 합계` |
| `scripts/check-brief-split.js` | 권한 조합 수를 **시작할 때** 적고, 조합마다 **일 전에** 이름을 찍고 끝나면 그 조합의 시간을 붙인다. 끝에 `[보임]` 으로 전체·구간 시간 |

`[보임]`·`[못잼]` 판독은 **그대로**다. 규칙과 그 경위(2026-09-01·2026-09-03 전례)는
`check-setup.js` 에서 `_child-run.js` 의 `visibleLines` 주석으로 옮겼다 — 지우지 않았다.

### 상한

기본 120초, `HERMES_CHECK_TIMEOUT_MS` 로 조정. 읽을 수 없는 값은 **기본값으로 돌아간다** —
`0`·`NaN` 으로 읽으면 모든 검사가 즉시 실패해 관문이 통째로 빨개지고, 그 상태에서
사람이 배우는 것은 관문을 끄는 법이다.

### 왜 여전히 `spawnSync` 인가

진짜 스트리밍은 비동기 `spawn` 이라야 한다. 그러려면 `check-setup.js` 의 여섯 구간을
전부 비동기로 뒤집어야 하는데, 다른 검사가 그 흐름을 흉내 내어 몬다
(`check-check-modes.js`). 이 작업의 범위가 아니다.

대신 **침묵의 길이에 상한을 뒀다.** 자식이 상한 안에 끝나면 그만큼만 조용하고, 넘기면
중단되며 그때까지의 출력이 이름과 함께 나온다. 12분 침묵이 사라지는 자리가 여기다.

## 4. 측정

> **합성 자료다. 운영 서버 수치가 아니다.** 배경 문서의 기준선(11채널)에 맞춰 만든
> 것이고, 목적은 「12분 반복 파싱이 사라졌는지」 를 판별할 자리를 두는 것이다.
> 사업장·사람 이름은 쓰지 않았다.
>
> 환경: Windows 11 · Node 22.19.0 · 개발 PC. 서버는 Node 20 이라 **다시 재야 한다.**

### 4.1 자료 규모

| 모드 | 자료 | 규모 |
|---|---|---|
| `pf` | `slack-export/channels/*.md` 11개 | 340,681줄 · 9.8MB · 문서 36건 |
| `pf-archiver` | Archiver 정본 `archive/raw/*.md` 33개(11채널 × 3일) | 메시지 20,460건 · 3.1MB |

Archiver 쪽 줄 모양·프론트매터는 **실제 writer 가 만든 파일에서 읽어** 흉내 냈고,
생성 20,460건 ↔ reader 가 읽은 20,460건으로 대조했다(모양이 어긋나면 수가 갈린다).

### 4.2 `check-brief-split` 단독 (3회)

| 모드 | wall | CPU user | CPU system | peak RSS |
|---|---|---|---|---|
| `pf` | 1,570 / 1,942 / 2,029ms | 1,312~1,406ms | 281~406ms | 99.3~107.2MB |
| `pf-archiver` | 1,740 / 2,237 / 2,344ms | 1,188~1,515ms | 797~1,047ms | 102.1MB |

**권한 조합 5개** — 공개 전용 · 비공개 멤버 2 · DM(비공개 2개) · 전체.
비공개 채널이 `n` 개면 조합은 `n + 3`(n≥2) 이다.

구간 내역(`pf`, 340,681줄): ①공통 627ms · ②줄 670ms · ③행 44ms.

`pf-archiver` 는 종료코드 1 이다 — 합성 정본에 `### 제목 (N)` 절이 없어 ③ 이 떨어진다.
측정값(①②)에는 영향이 없다.

### 4.3 `check:archive` 전체

| 무엇 | 값 |
|---|---|
| 전체 | **174.5초** (rc 1 — 합성 자료라 내용 검사 여럿이 떨어진다) |
| `[1/6] 코드 일관성` 구간 | **108.5초** · 자식 71개 |
| 그중 `check-brief-split` | **2.1초** (1.2%) |

가장 느린 자식 상위:

| 시간 | 검사 |
|---|---|
| 40.3초 | 선택 의존성이 없어 못 잰 시험이 깨진 시험과 다른 신호를 내나 |
| 7.0초 | 두 언어 공유 규칙 대조 (`check-shared-rules.js`) |
| 6.9초 | pull --rebase 로 해시가 바뀌어도 DM 이 실제로 있는 커밋을 알리나 |
| 6.5초 | 봇이 쓰는 파서가 실물 아카이브 md 를 읽어내나 |

**이 자료 규모에서 `check-brief-split` 은 더 이상 느린 검사가 아니다.** 12분은
reader 의 반복 파싱에서 왔고, 그 수정은 Codex 몫이다 — 여기서는 「느려지면 누가
느린지 화면에 나온다」 를 고정했다.

## 5. PF 개발자 확인 사항 — 어디서 읽나

배경 문서 §PF 개발자 확인 사항의 다섯 중 1·3 은 이제 **검사가 스스로 적는다.**

| 항목 | 어디 |
|---|---|
| 1. 전체 소요 시간 / `check-brief-split` 소요 시간 | `[보임] 코드 일관성 N개 · 합계` · `✓ 색인 공통분 … (N초)` |
| 2. 최대 CPU·RSS | 검사는 안 잰다. `/usr/bin/time -v node scripts/check-setup.js --archive` 로 잰다 |
| 3. 공개·비공개 권한 조합 수 | `[보임] 권한 조합 N개 · 전체 …` |
| 4. raw·첨부·메시지 수 | reader 몫(Codex). 이 작업 범위 밖 |
| 5. manifest 실패 시 접근 차단 | `tests/test_hermes_privacy_runtime.py` 가 고정 |

PF 서버에서 돌릴 때:

```bash
cd /opt/tybot/subbots/hermes
/usr/bin/time -v node scripts/check-setup.js --archive 2>&1 | tee /tmp/pf-check.log
grep -E '\[보임\]|상한을 넘겨' /tmp/pf-check.log
```

상한에 걸리면 **어느 검사인지 그 줄에 적혀 있다.** 느린 서버라면
`HERMES_CHECK_TIMEOUT_MS` 를 올리되, 올린 값과 이유를 함께 남긴다.

## 6. 회귀시험

`tests/test_hermes_check_observability.py` (10건). **먼저 쓰고 10건 전부 실패하는 것을
확인한 뒤** 구현했다.

| 무엇 | 왜 |
|---|---|
| 시작 줄이 자식보다 먼저 나온다 | 끝난 뒤에 찍으면 화면의 마지막 줄은 늘 이미 끝난 항목이다 |
| 끝나면 소요 시간이 보인다 | 「느리다」 를 다음 사람이 숫자로 받는다 |
| 상한 초과 → 실패 + **이름·파일** | 이름 없는 타임아웃은 다시 재현해야 안다 |
| 중단돼도 그때까지의 출력이 남는다 | 12분을 기다린 사람이 빈 화면을 받으면 안 된다 |
| 상한은 환경변수로, 못 읽으면 기본값 | `0` 으로 읽으면 관문이 통째로 빨개진다 |
| `[보임]`·`[못잼]` 판독 유지 | 통과한 검사의 「못 쟀다」 를 삼키지 않는 장치다 |
| 실패한 검사는 사유 전문을 보인다 | 지금 동작 그대로 |
| `check-setup` 이 공통 러너를 쓴다 | 두 벌이면 한쪽만 고쳐지고, 조용해지는 쪽은 늘 운영이다 |
| `check-brief-split` 이 조합 이름을 일 **전에** 찍는다 | 느린 자리가 바로 조합별 색인 생성이다 |
| 조합 수·전체 시간을 `[보임]` 으로 적는다 | 사람이 초시계를 들고 재게 하면 아무도 안 잰다 |

helper 를 따로 둔 이유: `check-setup.js` 는 941줄에 자식 100여 개라 통째로 시험에
넣을 수 없다(네트워크 없이도 수 분). 판정만 떼어내 직접 몬다.

## 7. 남은 것

- **`check-brief-split` 의 `[보임]` 줄은 통과할 때만 올라온다.** 실패하면
  `check-setup` 이 사유 전문을 찍으므로 그 안에 섞여 들어간다 — 읽을 수는 있으나
  통과 화면만큼 눈에 띄지 않는다
- 상한을 **구간 단위**로는 안 뒀다. `[1/6]` 전체가 느려지는 경우는 자식 하나가
  아니라 자식 수가 느는 것이라, 자식 상한으로는 못 잡는다. 지금은 구간 합계를
  `[보임]` 으로 적는 데서 멈춘다
- 진짜 스트리밍(비동기 `spawn`)은 `check-setup.js` 흐름 전체를 뒤집는 일이라 별건이다
