# 3. 【참고】 공통 규칙 — 모든 화면에 적용

## 1. 원문을 표시하지 않습니다

콘솔은 **상태·건수·좌표·오류 코드**만 보여 줍니다. 대화 원문, 첨부 본문, DM 내용은
화면에 올리지 않습니다. 봇과의 DM 은 **그 사람 본인이 DM 에서 물을 때만** 근거가
됩니다 — exec·root·콘솔도 예외가 아닙니다.

## 2. 시크릿은 mask 만

Slack 토큰·DSN·API 키·원문 경로는 API 응답과 로그 **양쪽에서** 가립니다.
저장 후 화면에는 **설정 여부와 마지막 검증 시각**만 보입니다.
**복호화해 돌려주는 라우트는 만들지 않습니다.**

## 3. 모르면 "모른다"고 씁니다

상태를 못 읽었을 때 「정상」이나 「0건」으로 보여 주지 마세요. 못 본 것과 없는 것은
사람이 할 일이 다릅니다. 이 프로젝트에서 반복해 터진 고장이 전부 이 모양입니다 —
오류는 안 나고 0 이 나옵니다.

## 4. 파괴적이거나 비용이 드는 동작은 범위를 명시하게

소급은 채널을 고르게 하고 실행 전에 **분량을 먼저 셉니다.** 보존 집행은 기본이
**읽기 전용 미리보기**이고, 적용에는 실행자 이름이 필요합니다.

## 5. 「저장됨」과 「동작함」을 가릅니다

저장은 값을 넣은 것이고, 그 값이 실제로 통하는지는 다른 문제입니다.
검증 전에는 「검증 안 됨」으로 보여 주세요.

> 항목이 아니라 **상시 규칙**입니다. 모든 화면 작업에 적용됩니다.

**SlackBot 저장소 `tests/`** 에 있으며, **콘솔 저장소의 소스를 읽습니다.**

| 파일 | 시험 수 | 무엇을 강제하나 |
|---|---:|---|
| `tests/test_console_bot_ui_contract.py` | 52 | 봇 관리 화면의 토큰 입력·문구·권한·탭 경로 |
| `tests/test_pf_isolation.py` | 35 | PF 콘솔과 TY 콘솔이 섞이지 않는다 |
| `tests/test_deploy_scripts.py` | 48 | 배포 스크립트 계약([WC-02](#wc-02) 와 직접 연결) |
| `tests/test_manifest_sync.py` | 9 | 화면이 보여 주는 Slack 매니페스트와 실제 파일 일치 |

강제하는 것 중 **보안에 걸리는 것들**입니다. 취향이 아니라 계약입니다.

- 토큰 입력은 `password` 타입이고 저장 후 **지워진다**
- 평문 토큰 필드를 **어떤 경로로도 렌더링하지 않는다**
- 내부 호출 화면에는 토큰 입력이 **없다**
- 메뉴를 옮겨도 **권한이 넓어지지 않는다**
- 옛 URL 은 알려진 경로로 **착지한다**(쿼리는 건드리지 않고)

**[WC-03](#wc-03) 의 Hermes 시크릿 화면도 이 계약을 지켜야 합니다.**

# WC-01. 워크스페이스 등록이 토큰을 요구해 실패한다

| | |
|---|---|
| 상태 | ✅ 완료 — 양쪽 코드 완료 · 운영에서 등록 재확인만 남음 |

> **등록이 되고, Master 도 안 죽고, 봇 관리에서 붙인 Master 토큰이 실제로 먹습니다.**
> 아래 **봇 개발 담당자 할 일**은 끝났고 남은 것은 화면 정리입니다.

## 증상

`운영 > 워크스페이스 관리 > 새 워크스페이스 등록` 에서 키·표시 이름을 넣고 등록하면
저장이 거부됩니다.

```
저장 실패   워크스페이스 설정을 저장하지 못했습니다
            새 워크스페이스에는 봇 토큰과 앱 토큰이 필요합니다.
```

## 원인 — 화면이 아니라 **API** 입니다

이 건은 **웹콘솔 담당자가 고칠 수 없습니다.** 조사 결과를 그대로 적습니다.

화면은 이미 올바릅니다. `console-web/src/pages/Workspaces.tsx:211` 에 주석이 있고,
`:326` 은 "봇 토큰은 이 화면에서 받지 않습니다" 라고 안내하며, `:236` 의 제출
payload 에 `botToken`·`appToken` 이 **없습니다.**

거부하는 쪽은 API 입니다.

| 자리 | 내용 |
|---|---|
| `src/tybot/console/app.py:170-171` | `WorkspaceBody.botToken`/`appToken` 이 `None` |
| `src/tybot/console/app.py:2043-2044` | 그대로 `save_workspace()` 로 전달 |
| `src/tybot/console/workspace_store.py:186` | `if not exists and not encrypted: raise` ← **여기서 막힘** |

봇 토큰은 이제 `봇 관리 > 워크스페이스 연결` 에서 봇별로(Master·Archiver·Hermes)
등록합니다. 워크스페이스 행은 **조직 metadata** 만 들고 있어야 합니다. 토큰을
워크스페이스에 매는 것은 봇이 하나뿐이던 시절의 구조이고, 지금은 한 워크스페이스에
봇이 여럿이라 애초에 한 쌍으로 표현할 수 없습니다.

## 웹콘솔 담당자 회신 (2026-10-12) — **지적이 맞았습니다**

> WC-01 API 쪽 보니까 `workspace_store.py:186` 토큰 조건만 빼면, 토큰 없는
> 워크스페이스 때문에 재시작 때 `workspaces.load_workspaces` 가 `ConfigError` 로
> Master 기동을 막을 것 같아요. ① 토큰 없는 행은 건너뛰기 → ② 필수 조건 제거 →
> ③ Master 가 `bot_connection` 토큰 읽기, 순서로 가야 할 것 같습니다.
> ③ 없으면 봇 관리에서 Master 토큰을 넣어도 실제로 안 붙는다.

**둘 다 코드로 확인했습니다.**

| 지적 | 확인 |
|---|---|
| ① `ConfigError` 로 Master 기동이 막힌다 | ✅ `workspaces.py:234`. **워크스페이스 하나 등록한 대가로 다른 본부 수집이 전부 멈춥니다** — 원래 버그보다 나쁩니다 |
| ③ Master 는 `bot_connection` 을 안 읽는다 | ✅ `bot_admin.py:60` 주석이 직접 적어 뒀습니다 — "Archiver 는 새 `bot_connection` 을 읽는다. **Master 는 아직 `workspace_secret`**… 이 화면의 저장은 **기록이지 적용이 아니다**" |

②가 먼저 커밋됐지만 **배포 전**이라 실제 피해는 없었고, ①③을 같은 배포에 묶어
순서를 지켰습니다.

### ① 이 왜 생겼나

그 분기가 만들어질 땐 토큰 없는 행이 생기는 길이 **하나뿐**이었습니다 —
레지스트리 이전의 깨진 이관. 그땐 크게 소리치는 것이 맞았습니다. WC-01 이
**정상인 길을 하나 더** 만들면서 같은 상태가 두 가지 뜻을 갖게 됐습니다.

고친 방향: 건너뛰되 **WARNING 로그 + `workspaces.pending_connection()`** 으로 목록을
남깁니다. 스키마 주석도 같은 쪽입니다 — `workspace.state`: "등록 오류는 이
워크스페이스만 멈춘다. 다른 봇은 계속 뜬다."

**복호화 실패(`undecryptable`)는 그대로 막습니다.** 그쪽은 토큰이 **있는데** 못 읽는
것이라 그 워크스페이스는 수집 중이었고, 빠지면 그 기간이 영구 유실됩니다(Slack

| | |
|---|---|

나머지가 아직 분리 전 전제로** 돕니다.

## (0) 2026-10-12 실사고 — 배포가 닿지 않는 콘솔이 5일간 돌았다

> **이 항목이 왜 있는지 보여 주는 사례입니다.** 먼저 읽어 주세요.

WC-01 을 고치고 배포했는데 화면에 **같은 옛 오류**가 계속 났습니다. 확인해 보니:

```
브라우저 → nginx :8788 → 127.0.0.1:8789  ← 10-07 에 만든 유닛 tybot-console-next
                         127.0.0.1:8787  ← systemd tybot-console. 새 코드. 아무도 안 봄
```

- 배포는 **성공**으로 끝났습니다
- `/opt/tybot/src` 의 파일은 **새것**이었습니다
- `systemctl restart tybot-console` 도 **돌았습니다**
- 그런데 사람이 보는 화면은 **5일 된 코드**였습니다
- **아무 오류도 안 났습니다**

> **원인 정정(2026-10-22, 웹콘솔 담당자 회신 반영).** 처음에 이 문서는 8789 를
> 「손으로 띄운 uvicorn」 이라고 적었습니다. **틀렸습니다.** 8789 는 10-07 에 8788
> 시험 운영용으로 만든 **systemd 유닛 `tybot-console-next`** 였습니다
> (`/etc/systemd/system/tybot-console-next.service`).
>
> 그래서 교훈이 달라집니다. 문제는 「손으로 띄우면 안 된다」 가 아니라
> **배포 스크립트가 `tybot-console` 하나만 알고 있었다**는 것입니다. 유닛으로
> 올바르게 만들어도 **배포가 이름을 모르면 안 닿습니다.** 틀린 원인을 남겨 두면
> 다음에 같은 자리에서 또 찾게 되므로 고쳐 적습니다.

찾는 데 서버에서 `ps` 를 봐야 했습니다. `systemctl restart tybot-console` 은
**그 유닛만** 내립니다 — 다른 이름의 콘솔은 남고, nginx 가 그쪽을 가리키면 배포가
영원히 안 닿습니다.

**조치**: nginx 를 8787(systemd 관리)로 돌렸고, 8789 프로세스는 정리했습니다.
지금은 8788 하나로 운영합니다.

## (1) 봇 배포가 매번 콘솔을 내린다

`deploy/update.sh:118-120` 이 무조건 `systemctl restart tybot-console` 합니다.
`tybot-update.timer` 로 주기 실행되니 **문서만 고친 배포에서도** 로그인 세션이
끊기고 진행 중이던 배포 승인·소급 실행이 중간에 죽습니다.

**다만 「절대 재시작 안 함」 은 틀립니다.** `tybot-console.service` 가 돌리는 것은
`uvicorn tybot.console.app:app` — **이 저장소의 `src/tybot/console/`** 입니다. 게다가
콘솔 백엔드는 `..archive.store`, `..gateway.router`, `..feedback` 등 공유 모듈 15개
남짓을 import 합니다. 봇 코드가 바뀌면 콘솔이 돌리는 코드도 바뀝니다.

갈라야 할 것은 「재시작하느냐」가 아니라 **「무엇이 바뀌었을 때 재시작하느냐」**.
`update.sh` 는 이미 직전 배포 커밋(`$DEPLOYED`)을 들고 있습니다.

```bash
console_needs_restart() {
  [[ -z "$DEPLOYED" ]] && return 0                  # 모르면 재시작한다
  git -C "$SRC" cat-file -e "$DEPLOYED^{commit}" 2>/dev/null || return 0
  git -C "$SRC" diff --name-only "$DEPLOYED" HEAD -- src/ | grep -q .
}
```

- **모르면 재시작합니다.** 안 내려서 옛 코드가 도는 쪽이 세션 끊김보다 나쁩니다
- `TYBOT_FORCE=1` 이면 조건 없이 재시작
- 건너뛸 때는 **로그에 남깁니다.** 조용히 건너뛰면 아무도 못 알아챕니다

> 완전히 끊으려면 콘솔 백엔드도 별도 저장소·서비스로 옮겨야 합니다. 지금 구조에서는
> 공유 모듈 때문에 불가능합니다. 오너 결정 사항이라 제안만 남깁니다.

# WC-03. Hermes 설정·시크릿을 DB 와 콘솔로

| | |
|---|---|
| 상태 | ⏸ 대기 — 스키마 A/B 결정이 먼저 (B 권고) |
| 우선 | 보통 |
| 담당 | 양쪽 |
| 등록 | 2026-10-12 |

## 배경 — PF 팀용 Hermes 가 들어왔습니다

PF(프로젝트금융) 팀용 Hermes 가 **같은 서버에서** 돕니다. PF 전용 서버는 없습니다.
지금 설정은 서버 파일에 평문으로 있습니다.

```
/etc/tybot-subbots/pf-hermes.env      (root:pf-hermes 0640)
/etc/hermes/<instance>/hermes.env     (인스턴스별)
```

`deploy/setup-pf-hermes-host.sh:129-152` 가 골격을 만들고 **값은 사람이 손으로**
넣습니다. 그 파일에 들어 있는 것:

| 구분 | 키 |
|---|---|
| **시크릿** | `SLACK_BOT_TOKEN` · `SLACK_APP_TOKEN` · **`ANTHROPIC_API_KEY`** |
| 경로(비시크릿) | `HERMES_INSTANCE` · `HERMES_SERVICE_NAME` · `HERMES_*_ROOT` · `HERMES_CONFIG_FILE` |
| 설정(비시크릿) | `ARCHIVE_GIT_REMOTE` · `HERMES_READ_ONLY` |
| 키 **경로**(값 아님) | `CODE_GIT_SSH_KEY` · `ARCHIVE_GIT_SSH_KEY` |

**평문 파일을 장기 원장으로 쓰지 않습니다.** 서버에 들어갈 수 있는 사람은 누구나
읽고, 백업·복사본에 그대로 따라다니며, 누가 언제 바꿨는지 남지 않습니다.

## 이미 있는 패턴을 **재사용합니다** — 새로 만들지 마세요

이 저장소에는 Fernet 암호화 시크릿 표가 **이미 여섯 개** 있습니다.

```
workspace_secret · bot_connection_secret · llm_secret
specialist_secret · specialist_runtime_secret · workspace_service_secret
```

전부 같은 세 규칙을 지킵니다. Hermes 도 **같은 규칙**입니다.

1. **평문 저장 금지** — Fernet 으로 암호화. 키는 DB 밖 파일
   (`/etc/tybot/workspace-secret.key`, 0400). DB 백업만으로는 못 풉니다
2. **복호화 조회 API 금지** — 값을 화면으로 꺼낼 수 있으면 그 순간 브라우저·
   로그·스크린샷이 전부 보관 장소가 됩니다
3. **콘솔은 mask 만 읽습니다** — 예: `sk-ant-…9f0c`

## 여기서 막히는 것 — `llm_secret` 을 그대로 못 씁니다

Anthropic 키는 이미 콘솔에서 관리합니다(`GET/PUT /api/llm-secrets`,
`deploy/sql/llm_secret_schema.sql`). 그런데 그 표는 이렇습니다.

```sql
CREATE TABLE llm_secret (
    provider text PRIMARY KEY          -- ← 전역 1개
             CHECK (provider IN ('anthropic', 'openai')),
    ...
);
```

**`provider` 가 PRIMARY KEY 라 Anthropic 키가 시스템 전체에 하나뿐입니다.**

PF Hermes 는 **자기 키**가 필요합니다. `setup-pf-hermes-host.sh:140` 의 주석이
그 이유입니다 — "모델 — 계정과 일일 상한의 주인은 프금팀이다". 비용 청구와 상한의
주인이 다르므로 키를 같이 쓸 수 없습니다.

→ **스키마 변경이 필요합니다.** 선택지 둘:

| 안 | 모양 | 평 |
|---|---|---|
| A | `llm_secret` 에 `scope` 열 추가, PK 를 `(provider, scope)` 로 | 기존 행은 `scope='global'`. 화면 하나로 통합 |
| B | `hermes_instance_secret` 표를 따로 | 인스턴스 설정과 한 화면에 모임 |

**B 를 권합니다.** Hermes 는 Slack 토큰 두 개도 함께 필요하고, 그 둘은 `llm_secret`
에 넣을 수 없습니다. 한 인스턴스의 시크릿 세 개가 한 자리에 있는 편이 교체·폐기·
감사에서 섞이지 않습니다.

> **⚠️ 이 선택이 먼저입니다.** 정해 주시면 봇 개발 담당자가 스키마·API 를 만들고 이 항목을
> 갱신합니다. 그 전에는 화면 착수를 권하지 않습니다 — 필드가 바뀝니다.

## 제안 계약

### 비시크릿 설정 — `hermes_instance`

```
instance      text PK      -- 'pf', 'ty', …
workspace     text         -- 어느 워크스페이스의 Hermes 인가
domain        text         -- domain profile
enabled       boolean
read_only     boolean      -- HERMES_READ_ONLY
archive_git_remote text
expected_team_id   text    -- 기동 시 신원 대조용
expected_bot_id    text
updated_at / updated_by
```

**경로는 DB 에 넣지 않습니다.** `HERMES_*_ROOT` 는 서버가 인스턴스 이름으로
계산합니다. DB 에 두면 한 인스턴스가 다른 인스턴스의 경로를 가리킬 수 있고,
그건 화면에서 한 글자 고쳐서 일어납니다.

### 시크릿 — `hermes_instance_secret`

```
instance   text
kind       text CHECK (kind IN ('slack_bot', 'slack_app', 'anthropic'))
ciphertext bytea
mask       text
enabled    boolean
previous_ciphertext / previous_until   -- 무중단 교체용
updated_at / updated_by
PRIMARY KEY (instance, kind)
```

`previous_*` 는 `specialist_runtime_secret` 과 같은 이유입니다 — 교체 시 구/신 키를
잠깐 겹치지 않으면 무중단 전환이 안 됩니다.

### API

```http
GET  /api/hermes/instances                 → 목록 + 설정 여부 + mask + 마지막 검증
PUT  /api/hermes/instances/{instance}      → 비시크릿 설정
PUT  /api/hermes/instances/{instance}/secrets/{kind}          → 시크릿 저장(쓰기 전용)
PUT  /api/hermes/instances/{instance}/secrets/{kind}/verify   → 저장 후 실제 검증
```

**복호화해 돌려주는 라우트는 만들지 않습니다.**

## 2026-10-15 추가: 검토 상태 DM과 같은 날 증분 재검토

오너 결정: 후보 0건이어도 검토자는 정상 확인인지 오류인지 알 수 있어야 한다.
TYBot Python 구현 진행중이며 서버 배포/실발송 검증 전이다. PF Hermes 후보 생성
RPC는 Claude가 별도로 구현 중이므로 현재 배포가 이미 RPC로 전환됐다고 표시하지 않는다.

- `model-empty`: 원문을 확인했으며 모델이 후보를 제안하지 않음.
- `no-new-source`: 마지막 처리 이후 새로 수집된 원문 없음. Slack 전체를 조회했다는
  뜻이 아니며 수집 중단 여부와 별도로 표시한다.
- `no-accepted-candidate`: 제안은 있었지만 원문 검증에서 전부 탈락. 정상 0건 아님.
- `generation-retry-deferred`: 실패 후 재시도 대기.
- `source-already-processed`: 동일 원문 구간 재사용으로 모델 호출 생략.

예약 시각 이후 정상 빈 상태와 오류 상태를 각각 채널/검토자/KST 날짜별로 중복 제한한다.
`summary_review_status_delivery`는 후보/승인 이력과 별개다. `sending`은 발송 중 또는
결과 미확정, `sent`는 성공, `failed`는 확정 실패, `ambiguous`는 응답 유실 등으로
성공 여부 미확정이다. `sending`/`ambiguous`를 성공이나 미발송 확정으로 표시하지 않는다.
오류나 미확정 기록에 자동 재발송 버튼을 연결하지 말고 서버 재확인 경로를 먼저 정한다.
확정 실패는 1시간 뒤 재시도 가능하다. 실제 후보가 이미 발송된 날에는 빈 상태 DM은
생략하고, 빈 상태를 먼저 받았더라도 이후 실제 후보 검토 DM은 받을 수 있다.

같은 날 재생성을 무조건 막던 규칙은 15분 생성 간격 + 원문 커서/digest 기반으로 바꾼다.
동일 구간을 다시 모델에 보내지 않고, 실패 백오프·게이트웨이 예산·단일 실행 잠금을
유지한다. 전부 검증 탈락한 구간은 성공 처리하지 않고 커서를 보존한다.
콘솔 즉시 실행 결과 JSON은 `statusSent`/`statusFailed`를 후보 `sent`/`failed`와
구분해 제공한다. 상태 DM을 후보 승인 완료나 원문 아카이브 작성으로 계산하지 않는다.

배포 시 `deploy/sql/summary_review_schema.sql`의 상태 DM 테이블/권한 적용이 필요하다.
추가 테이블 미적용을 "보낼 내용 없음"으로 표시하지 않는다. Master 없는 TEC의
TYBot 발송 신원 부재는 별도 제한이며 Archiver 수집 실패로 표시하지 않는다.

**2026-10-15 RPC 배선 보강 (서버 구현, 운영 검증 전):** 별도
`TYBOT_HERMES_REVIEW_WORKSPACES` 허용 workspace의
예약·소급 후보 생성은 PF Hermes `review_candidates_v1`을 사용한다. 미지원 capability,
잘못된 응답 서명, 모델 오류를 기존 Haiku 생성으로 우회하거나 정상 0건으로 표시하지
않는다. 실패 상세는 `generation-error=<사유 코드>`로 전달하며 본문/키는 포함하지 않는다.
`no-new-source`, `model-empty`, `no-accepted-candidate`, `generate-failed`를 구분한다.
워커 생성 성공만으로 DM 발송 성공을 표시하지 않는다. 정상 0건/오류 상태 DM 이력은
`summary_review_status_delivery`이며 후보 발송·승인 권한 이력과 별개다.
이 허용 목록은 기본 OFF, Master v2 허용 목록의 부분집합이다. Q&A RPC 전환과
예약 요약 검토 RPC 전환을 각각 표시하고, 콘솔 설정 관리 이관 대상에 포함한다.

## 데이터 계약

`channel_reviewer` 의 검토 예약은 세 값으로 정합니다.

| 필드 | 값 | 규칙 |
|---|---|---|
| `schedule_kind` | `daily` 또는 `weekly` | 기존 행 기본값 `daily` |
| `weekday` | `0..6` 또는 `NULL` | Python 기준 월요일 `0`, 일요일 `6` |
| `send_at` | PostgreSQL `time` | KST 기준 검토 DM 발송 시각 |

유효한 조합은 **두 가지뿐**입니다.

```
daily  + weekday NULL
weekly + weekday 0..6
```

`daily + 요일`, `weekly + NULL`, 범위 밖 요일은 저장 단계에서 거부합니다.

## 읽기 API

`GET /api/channels` 의 각 `rows[]`:

```json
{ "reviewers": ["U123"], "sendAt": "09:00:00",
  "scheduleKind": "weekly", "weekday": 2, "scheduleLabel": "매주 수요일 09:00" }
```

주기 문구를 다시 조립하지 말고 **`scheduleLabel` 을 우선** 표시합니다. 값이 없는
구버전 응답에 한해서만 `sendAt` 을 대체 표시합니다.

`GET /api/summary-review/rounds` 의 `schedule`:

```json
{ "channels": 3, "due": 1, "waiting": 2,
  "nextSendAt": "수요일 09:00", "timezone": "Asia/Seoul" }
```

`nextSendAt` 은 일간이면 `HH:MM`, 주간이면 `요일 HH:MM`. 화면 문구는 "설정 시각"이
아니라 일간·주간을 포괄하는 **"예약 시점"** 을 씁니다.

## 화면 순서

채널 **수정**: 업무명 → 채널 관리자 → 요약 검토 주기 → 주 1회 검토 요일(`weekly`
일 때만, 필수) → 검토 시각 → 검토 승인자

채널 **생성**(관리자를 따로 고르지 않음): 채널 기본 정보·추가 참여자 → 요약 검토
주기 → 주 1회 검토 요일 → 검토 시각 → 검토 승인자

`daily` 를 고르면 요일 입력을 숨기고 저장값도 `NULL` 로 만듭니다. `weekly` 를
고르면 요일을 보인 뒤 선택 전에는 저장할 수 없어야 합니다. **이전에 선택한 요일이
`daily` 전환 뒤 몰래 제출되면 안 됩니다.**

- `active` 는 **그 채널의 운영 원문 주인이 바뀝니다**(Master → Archiver).
  누르기 전에 **무엇이 바뀌는지** 문장으로 보여 주세요
- `paused` 는 인수 중간 단계입니다. 둘 다 안 씁니다 — 그 사이는 **공백**이고,
  공백은 나중에 소급으로 메울 수 있습니다. 반대로 둘이 동시에 쓰면
  **겹침**이고 그건 못 고칩니다

`gatedModes` 에 들어 있는 모드는 **스키마 검증 전에는 못 누릅니다.**
`schemaGate.verified` 가 `false` 면 버튼을 회색으로 두고 `schemaGate.reason` 을
그대로 보여 주세요(WC-06 과 같은 규칙).

### 2. 소급 — **분량을 먼저 세고** 범위를 명시하게

소급은 비용이 들고 시간이 깁니다. CLAUDE.md:

> (예: 소급은 채널을 고르게 하고, 실행 전에 분량을 먼저 센다)

- [ ] Slack 백필은 **분당 1요청**입니다. 예상 소요를 보여 주세요

### 3. 런타임 — 「돌고 있나」 와 「반영됐나」 를 가른다

### (1) 링크가 옛 흐름을 가리킨다 — 콘솔

`수집 > 수집 현황` 의 「조치 필요」 를 누르면 **워크스페이스 관리**로 갑니다.

```

안내 문구도 같습니다 — *「마지막 수집 시각과 **Slack 연결 상태**를 확인합니다」*.

- [ ] 안내 문구를 **채널 모드·Archiver 런타임** 기준으로 고쳐 쓴다

### (2) 숫자가 Archiver 수집을 **포함하지 않는다** — 봇 개발 담당자

확인했습니다. **포함하지 않습니다.**

```python
# src/tybot/console/reader.py:196
store = store or ArchiveStore(archive_dir())     # ← ARCHIVE_DIR 하나만
```

수집 현황은 **운영 루트(`ARCHIVE_DIR`) 파일만** 셉니다. 그런데 Archiver 는
채널 모드에 따라 두 곳에 씁니다.

| 채널 모드 | Archiver 가 쓰는 곳 | 수집 현황에 |
|---|---|---|
| `shadow` | `ARCHIVER_SHADOW_DIR` | **안 보임** |
| `active` | `ARCHIVE_DIR` | 보이지만 **누가 썼는지 모름** |

## 그래서 생기는 오표시

**shadow 로 넘긴 워크스페이스가 「수집 중단」 으로 뜹니다.**

`_health()`(`reader.py:180`)는 `last_ingested` 가 `STALLED_HOURS` 보다 오래되면
`stalled` 입니다. 그 값은 **운영 루트 문서**에서만 옵니다. 채널을 shadow 로
넘기면 운영 루트에는 새 줄이 안 쌓이므로, **Archiver 가 멀쩡히 수집하는 동안
화면은 「수집 중단 · 조치 필요」** 라고 말합니다.

그리고 그 빨간 줄을 누르면 워크스페이스 관리로 가서 **고칠 것이 없습니다.**
전환 중에는 이게 정상 상태인데 화면은 사고라고 합니다.

있습니다(`live` / `shadow`). 누가 어디에 썼는지 이미 구분해 둡니다.

- [x] 「수집 중단」 판정이 **두 루트 중 새 쪽**을 본다 (2026-10-14)
- [x] 집계를 **운영 · 그림자로 나눠서** 돌려준다. 합치지 않는다
- [x] 마지막 수집 시각을 **루트별로** 든다
- [x] 그림자 루트를 **못 읽으면 0 이 아니라 사유**를 돌려준다
- [x] 그림자에만 있는 워크스페이스도 목록에 **나온다**

| `lastIngestedAt` · `health` | 둘 중 **새 쪽** 기준 — 전환 중 오표시가 사라집니다 |

기존 `docs` · `rawLines` 는 **운영 루트 그대로**입니다. 화면이 갑자기 다른 숫자를
보면 안 되므로 바꾸지 않았습니다.

**`shadowDocs` 가 `null` 이면 「0건」 이 아니라 「못 읽었다」 입니다.**
`shadowError` 를 그대로 보여 주세요 — 0 으로 그리면 「그림자 수집이 안 되고
있다」 로 읽힙니다.

### 웹콘솔 담당자 할 일

- [ ] 「수집 중단」·「미초대 채널」 링크를 **Archiver 운영 화면**(WC-16)으로
- [ ] 안내 문구를 **채널 모드·Archiver 런타임** 기준으로 고쳐 쓴다
- [ ] 수집량을 **운영 n · 그림자 m** 으로 나란히 표시
- [ ] `shadowError` 가 있으면 숫자 대신 **사유**를 보여 준다

> **두 루트를 합쳐 읽는 기능을 만들자는 것이 아닙니다.** 답변 근거의 단일 루트
> 원칙(2026-10-02 오너 결정)은 그대로입니다. 여기서 필요한 것은 **현황판이 두
> 곳을 각각 세어 나란히 보여 주는 것**뿐입니다.

# WC-20. 운영 상태 감지·알림 — 「조용한 채널」 과 「고장」 을 가른다

| | |
|---|---|

**상태 🔴 요청됨 · 봇 개발 담당자: 감지 API · 웹콘솔 담당자: 운영 상태 화면**
**근거 B-02**(운영 관리 채널 리포트) · **B-46**(파일 누락 정기 점검) 연결

## 왜 지금인가

지금 아카이브가 조용히 고장나면 **아무도 모릅니다.** 사람이 `상태` 를 물어야
드러납니다(B-01 에 적어 둔 그대로입니다).

그런데 더 나쁜 것은 **지금 있는 경보가 거짓말을 한다**는 점입니다.
정리 잡(`src/tybot/tidy.py:131`)은 세 가지 전혀 다른 상황에 **같은 문장**을 냅니다.

```
3.0일째 수집 없음 — 봇 초대·권한 확인
```

| 실제 상황 | 사람이 할 일 | 지금 화면 |
|---|---|---|
| 수집기가 죽었다 | **지금 당장 재기동** | 위 문장 |
| 봇이 채널에서 나갔다 | 재초대 | 위 문장 |
| 그 채널에 3일간 아무도 말을 안 했다 | **아무것도** | 위 문장 |

셋째가 문제입니다. 조용한 채널은 **정상**인데 경보로 올라옵니다. 그런 줄이
매일 수십 개 뜨면 사람은 경보를 안 보게 되고, 그때 첫째가 와도 똑같이 묻힙니다.

이 문서가 요구하는 것은 **경보를 더 내는 것이 아니라, 경보가 아닌 것을 경보에서
빼는 것**입니다.

## 1. 세 가지 사실을 **합치지 않습니다**

「수집이 안 된다」 는 한 칸이 아닙니다. 서로 독립인 사실 셋이고, 사람이 할 일이
각각 다릅니다. 한 칸으로 접으면 위의 표가 됩니다.

| 사실 | 근거 (이미 있습니다) | 답하는 질문 |
|---|---|---|
| **수집기가 살아 있나** | `heartbeat` 상태 파일 `updated_at` (`STALE_AFTER_SECONDS` 180초) · Archiver 런타임 | 프로세스가 도나 |
| **이 채널을 볼 자격이 있나** | `archive_channel_mode.membership` · `membership_checked_at` · `operator_hold` · `mode` | 봐도 되나 |
| **이 채널에 말이 있었나** | `archive_channel_mode.last_event_at` | 들어올 것이 있었나 |
| **들어온 것을 썼나** | `archive_ingest_state.state` · `written_to` · `updated_at` | 받은 것을 저장했나 |

> DB 주석이 이미 이렇게 말하고 있습니다 — *「`active` 는 프로세스가 떠 있다는
> 뜻일 뿐, 이벤트가 들어왔다는 증거가 아니다」*(`archiving_schema.sql:96`).
> 화면도 같아야 합니다.

### 판정표 — 이 조합으로 결정합니다

| 수집기 | 자격 | 이벤트 | 저장 | 판정 | 경보? |
|---|---|---|---|---|---|
| 죽음 | — | — | — | **수집기 장애** | 🔴 즉시 |
| 삶 | `left`·`unknown` | — | — | **자격 없음** — 재초대 필요 | 🟠 |
| 삶 | `operator_hold` | — | — | **사람이 껐음** | ⚪ 경보 아님 |
| 삶 | `joined` | 최근 | 최근 | **정상** | 🟢 |
| 삶 | `joined` | 최근 | **밀림·`failed`** | **쓰기 장애** | 🔴 즉시 |
| 삶 | `joined` | 오래됨 | — · **다른 채널은 들어옴** | **조용한 채널** | ⚪ 경보 아님 |
| 삶 | `joined` | 오래됨 · **워크스페이스 전체가 같은 시각에 멈춤** | — | **수집기 장애 의심** | 🔴 즉시 |

두 줄이 핵심입니다.

- **「쓰기 장애」** — 이벤트는 들어오는데 저장이 안 됩니다. 지금은 「조용한 채널」 과
  화면상 **구별되지 않습니다**(둘 다 원문이 안 늘어납니다). 그런데 하나는 아무
  일도 없는 것이고 하나는 자료가 **지금 사라지는 중**입니다.
- **「조용한 채널 ↔ 수집기 장애 의심」** — 같은 「오래됨」 인데 **옆 채널을 봐야**
  갈립니다. 한 채널만 보면 영원히 구별할 수 없습니다. 판정은 반드시
  **워크스페이스 단위로 가로질러** 봐야 합니다.

### 조용한 채널을 어떻게 다루나

**경보로 올리지 않습니다. 목록에는 남깁니다.**

- 경보(🔴·🟠)는 **사람이 지금 할 일이 있을 때만** 씁니다
- 조용한 채널은 회색 줄로 「N일째 조용함」 — 누르면 마지막 이벤트 시각을 봅니다
- 「조용함」 에 기본 임계를 두지 않습니다. 채널마다 주기가 다릅니다(주간보고
  채널은 6일 조용한 것이 정상입니다). 필요하면 채널별로 사람이 겁니다

> 왜 이렇게까지 하는가: 요약 검토에서 이미 겪었습니다. 사람이 찾아가야 하는
> 자리에 일거리를 쌓아 두면 **「대기 31건·처리 0건」** 이 됩니다. 경보도 같습니다 —
> 평시에 울리는 경보는 경보가 아니라 배경음입니다.

화면이 🟢 일 때 그것이 「방금 확인했고 정상」 인지 「6시간 전 결과를 아직 들고
있는 것」 인지 **지금은 구별되지 않습니다.**

점검마다 **따로** 내려갑니다. 하나로 합치면 가장 오래된 것이 전부를 물들입니다.

| 칸 | 시각 필드 | 주기 |
|---|---|---|
| 수집기 생존 | `collectorSeenAt` (heartbeat `updated_at`) | 봇이 상시 |
| 멤버십 | `membershipCheckedAt` (**DB 에 이미 있습니다**) | 동기화 주기 |

### 규칙

- 시각이 **없으면** 「정상」 도 「0건」 도 아닙니다. **「모름」** 입니다
- 모든 상태 칸 옆에 그 칸의 점검 시각을 **같이** 표시합니다. 접지 마세요

> WC-19 에서 합의한 것과 같은 원칙입니다 — `shadowDocs` 가 `null` 이면 「0건」 이
> 아니라 「못 읽었다」. 여기서도 **못 본 것과 없는 것은 다릅니다.**

## 3. 진단 실패 — **점검이 못 돈 것도 상태입니다**

점검이 실패하면 그 화면의 녹색은 전부 근거가 없습니다. 그러므로 **진단 실패는
그 자체로 경보**입니다. 조용히 옛 결과를 들고 있으면 안 됩니다.

세 갈래를 가릅니다. 하나로 접으면 사람이 할 일이 달라지는데 같아 보입니다.

| 코드 | 뜻 | 사람이 할 일 |
|---|---|---|
| `not_run` | 돌 차례였는데 안 돌았다(타이머 미기동·락 선점) | 타이머·락 확인 |
| `failed` | 돌다가 터졌다 | 사유 코드로 추적 |
| `partial` | 일부만 돌았다 | **어디까지 돌았는지** 범위를 표시 |

### 표시 규칙

- `partial` 결과를 **전체 결과로 말하지 않습니다.** 「누락 3건」 이 아니라
  「확인한 12/36채널에서 누락 3건 · 24채널 미확인」
- 사유는 **코드와 예외 이름만** 올립니다. B-46 수동 CLI 오류는
  `{"read_only": true, "error": "<ExceptionType>"}`, 정기 상태는
  `last_run.error_code`입니다(§4). SDK 응답 본문·시크릿·원문은 올리지 않습니다
- `not_run` 이 2회 연속이면 그 점검은 **없는 것으로 봅니다.** 🟢 를 주지 않습니다

## 4. B-46 파일 누락 정기 점검을 **같은 화면에**

파일 누락은 지금 서버 CLI 로만 봅니다. 별도 화면을 새로 만들지 말고 **이 운영
상태 화면의 한 칸**으로 붙여 주세요 — 「수집이 되고 있나」 와 「들어온 것이
빠짐없나」 는 사람이 같은 순간에 묻는 질문입니다.

### 자료원 (읽기 전용 · B-46 정기 실행 결과)

```bash
sudo cat /var/lib/tybot/file-audit/status.json
```

2026-10-16 계약 대조: 콘솔은 `tybot.archiver.file-audit.status.v1` 상태를 읽습니다.
생산자는 `tybot-file-audit.service/.timer`이며 기본 일 1회·최대 1시간, 설치만으로
켜지지 않습니다. 활성화와 상세 계약은 [정기 점검 운영 절차](deploy/channel-file-sync.md#정기-누락-점검-b-46-2026-10-16)를 참조하세요.
**다운로드·자동 등록·복구는 하지 않습니다.** 조회만입니다. 웹 요청에서 점검을 실행하지 않습니다.

`last_run`이 최신 실행이고 `last_success`는 마지막 전체 완료입니다. 최근 실패를
과거 성공으로 덮어 표시하지 않습니다. `completed`는 점검 완료이지 누락 0건이 아닙니다.
`running/completed/partial/failed`를 API의 `running/ok/partial/failed`로 대응합니다.
아직 실행이 없으면 `not_run`, 파일 읽기/스키마 실패면 상태 확인 불가입니다.
freshness는 기본 36시간(`read_status()` 기준, 129600초)입니다. §2의 주기 2배보다
보수적인 파일 점검 전용 기준이며, API에 기준을 명시하고 UI도 같은 값을 씁니다.
오래된 running은 systemd 상태와 함께 판단하며 녹색을 주지 않습니다.

기존 `audit_archiver_files.py --result-json`은 매번 **새 파일**에만 저장하는 수동 진단
도구입니다. 같은 고정 경로로 매일 실행하면 두 번째부터 덮어쓰기 거부로 실패하므로
정기 자료원으로 직접 쓰지 않습니다. 아래 표는 원본 진단 필드와 저장된 요약 필드의 대응입니다.

### 화면이 지켜야 할 것 — B-46 의 규칙이 그대로 적용됩니다

| 원본 진단 → `last_run.workspaces[].channels[]` 요약 | 화면 표기 | **하지 말 것** |
|---|---|---|
| `missing_after_record_check` → `missing` (건수) | **누락** | — |
| `existing_needs_review` → `existing_needs_review` (건수) | **확인 필요** (다른 칸) | 누락과 합산 |
| `shadow_only_ids` → `shadow_only` (건수) | 「그림자에만」 | 누락으로 표시 — 전환 중 정상일 수 있습니다 |
| `files_seen` → `files_seen` | 「Slack 목록 N건」 | **폴더 파일 수로 말하기** |
| `live_metadata_records` → `live_metadata_records` | 「수집 기록 N건」 | **변환·보관 완료로 세기** |
| `list_complete` → `list_complete` | false면 **「목록 미완」**, null이면 미확인 | 그 수를 전체로 말하기 |
| `db_joined_not_in_slack` → workspace의 `membership_mismatches` (건수) | 「DB 에만 있는 채널」 | 조용히 버리기 |

`coverage`는 회차와 workspace별로 있습니다. `target_channels`는 DB에서 수집 허용된
채널 수(현재 Slack 참여를 확인하지 못한 채널도 포함), `attempted_channels`는 시도한 수,
`complete_channels`는 목록과 대조를 끝낸 수, `unconfirmed_channels`는 대상에서 완료를
뺀 수입니다. 실패 채널은 시도했어도 완료에 넣지 않습니다. 설정/멤버십을 못 읽어 전체
범위를 모르면 분모와 미확인 수는 null이고 `unknown_workspaces`가 증가합니다.
이때는 「확인한 12채널 · 전체 범위 미확인」처럼 쓰고 12/12로 만들지 않습니다.

채널 조회 실패의 건수는 null입니다. 부분 조회의 알려진 건수는 하한값이며,
집계 역시 확인 범위만의 합계입니다. workspace별 `missing/needsReview/shadowOnly`는
각 채널의 알려진 값만 합산하되 값이 전혀 없으면 null입니다(전체 완료·대상 0개인
회차만 실제 0). 목록 미완 채널 수는 `list_complete is false`만 세고, null인 실패
채널을 목록 완료로 취급하지 않습니다. `last_success`의 이전 수치를 최신 칸에 합치지 않습니다.
workspace 전체가 `failed`면 멤버십·건너뜀의 기본 집계값 역시 확인된 0건으로 표시하지
않습니다. API의 해당 진단 값은 null로 내려갑니다. UI가 상태를 무시하고 숫자만 합치면 안 됩니다.

마지막 두 줄이 특히 중요합니다. **metadata 가 있다는 것은 staging 을 시도했다는
뜻일 뿐**이고(`file_inventory.preview` 의 주석 그대로), 보관·변환·검색 가능을
뜻하지 않습니다. 「수집 기록 10건」 을 「파일 10개 다 읽었다」 로 읽히게 쓰면
B-46 이 고치려던 바로 그 착각이 화면으로 되살아납니다.

### 복구는 이 화면에서 실행하지 않습니다

점검 결과에서 복구로 바로 이어지지 않습니다. 복구(`recover_archiver_files.py
--apply --by`)는 **별도 승인·별도 범위 명시**가 필요한 동작입니다(공통 규칙 4).
이 화면은 「무엇이 빠졌나」 까지입니다. 복구 화면은 그 결과가 쌓인 뒤 별도
항목으로 올리겠습니다.

## 1. 수집과 변환을 구분한다

Archiver는 계속 메시지·원본 첨부를 수집한다. 로컬 추출/OCR 후 필요한 페이지만
별도 비동기 Vision worker가 처리한다. 수집 프로세스에 LLM 키를 주거나 모델 응답을
기다리게 하지 않는다. Hermes Q&A 모델·요약 검토 모델·Master 기본 모델과 별도 용도다.
Master 없는 workspace에도 적용 가능해야 하며 Master 토큰 등록을 요구하지 않는다.
원본 PDF를 질문 때마다 PF Hermes로 보내는 기능은 이번 범위가 아니다.

HWP도 지원 범위에 포함한다. 현재 HWP는 kordoc 단일 경로이므로 먼저 로컬 추출과
설치된 변환기의 HWP→PDF 지원을 확인한다. 성공한 렌더링본의 페이지만 동일 Vision
경로로 처리한다. HWP 바이너리를 직접 외부 모델로 전송하지 않는다.
원본 형식·로컬 추출·렌더링·OCR·Vision 실패를 구분하고, 암호/손상/미지원·변환기
미설치·timeout·빈 출력 코드를 표시한다. HWPX의 XML 폴백과 HWP를 같은 경로로 보지 않는다.

## 2. 모델과 정책 편집

전역 기본 정책과 workspace별 override를 DB로 관리한다. 매 workspace마다 env와
키를 새로 만들게 하지 않는다. override가 없으면 상속된 실효 값과 출처를 표시한다.
모델 선택은 모델 ID 텍스트 자유 입력이 아니라 서버가 확인한 Vision 지원·민감도·
허용 provider/리전·credential 조건을 충족하는 카탈로그에서 한다. 확인 불가는 선택 불가다.
Q&A 모델 변경이 이 정책을 바꾸거나, 이 정책이 Hermes 모델을 바꾸어서는 안 된다.

| 관리 항목 | 요구사항 |
|---|---|
| 사용 여부 | 전역/해당 workspace 모두 기본 OFF, 적용 가능한 조건과 차단 사유 표시 |
| 모델·자격증명 | provider/model 선택, 기존 LLM secret 관리 재사용. 키 값 조회·중복 저장 금지 |
| 처리 대상 | OCR 실패·partial·혼합 이미지 페이지 의심을 구분, 암호/손상 PDF는 별도 실패 |
| 범위·상한 | 파일/작업당 페이지·출력 토큰·시간·재시도·동시 실행 상한 |
| 비용 | 용도별 및 workspace별 일일·작업당 예산, 예약 중/실사용/추정 비용 구분 |
| 자동 처리 | 자동 적용 허용 범위와 전송 승인 범위를 구분. 모델 선택만으로 외부 전송 승인 금지 |
| 상태 | 저장 revision·worker 적용 revision·실효 설정 출처·최근 정상 처리 시각 |

필수 상한이 없거나 정책 조회에 실패하면 호출하지 않는다. Master 기본 모델이나 env
모델로 조용히 되돌아가지 않는다. 폴백 모델도 별도 허용 목록과 전송 정책을 충족해야 한다.
전역 변경으로 활성 workspace가 새 provider/정책을 승인 없이 상속하지 않도록 변경 영향
범위와 재승인 대상을 표시한다. 기존 작업은 정책 snapshot을 보존하되 OFF/승인 취소/
예산은 실행 직전에 다시 확인한다. 구 버전 덮어쓰기는 revision 충돌로 거절한다.

## 3. 외부 전송 승인

**OCR이 실패한 파일은 텍스트 기반 PII 검사가 충분하지 않았을 수 있다.**
변환 후 PII 검사는 필요하지만 이미 외부로 보낸 원본을 되돌릴 수는 없다.
따라서 전송 전의 명시적 승인 또는 서버가 검증하는 동등한 사전 안전 판정이 필요하다.
단순 채널 열람 권한·모델 저장·전역 ON을 외부 전송 승인으로 해석하지 않는다.

- 승인 범위: workspace·file ID·원본 SHA-256·페이지 집합·provider·정책 revision·만료.
- 반려/PII 차단·원본 변경·승인 취소·만료는 실행 시 다시 확인한다. 관리자가 승인해도
  수집 금지 자료의 차단을 해제하지 않는다. 승인자와 실행자를 감사 기록에 남긴다.
- 승인 전 원본 열람도 기존 열람·감사 정책을 따른다. 목록의 제목·미리보기·오류 로그가
  비공개 파일 내용을 다른 workspace에 노출해서는 안 된다.
- 관리자만 정책 변경·전송 승인·취소·재처리 요청 가능. 개발자/일반 사용자에게는
  기존 workspace 열람 범위 안의 진단만 제공한다. 서버에서 권한을 강제한다.

## 4. 작업 목록과 처리 결과

`변환 대기`, `외부 전송 승인 대기`, `실행 중`, `완료`, `부분 완료`, `실패`,
`예산 보류`, `차단`, `취소`를 구분한다. 마지막 상태와 마지막 성공 시각도 구분한다.
`preflight_rejected`(호출 전 거절)는 입력·좌표·정책·승인 불일치로 모델 호출 전에
닫힌 상태다. 모델 실패·전송 횟수·실사용 비용으로 합산하지 않는다. 승인 대기와
예산 보류도 별개이며, 호출 미확정은 전송 0회로 단정하지 않는다.
페이지 수는 전체/시도/추출/미확인으로 나누고 **추출 완료를 정확성 검증 완료로 표시하지 않는다**.
모델 자기 confidence나 글자 수만으로 성공 판정을 만들지 않는다.

원본 해시·페이지·실제 사용 모델·policy revision·변환 revision·토큰/비용·실패 코드와
재처리 이력을 제공한다. 원문·추출 본문을 운영 로그나 목록 API에 넣지 않는다.
HWP는 원본 해시와 렌더링 PDF 해시·변환기/폰트 설정 판을 함께 기록한다. 페이지는
`원본 PDF` 또는 `렌더링본` 기준을 명시하며, HWP 원본의 인쇄 페이지와 같다고 표시하지 않는다.
텍스트 추출만 가능하고 쪽 범위를 모르면 전체 페이지 완료가 아니라 범위 미확인이다.
같은 파일명 대신 file ID와 해시로 대조하고, workspace를 넘는 전사 캐시 재사용은 금지한다.
추출·검사 통과·아카이브 파생본 발행·검색 색인 완료는 별개 상태로 표시한다.
`coordinate_mismatch`, `model_not_approved`는 각각 좌표 불일치·승인 밖 모델로 표시한다.
품질 코드는 서버 허용 목록만 표시하고 `unreadable` 자유 문장은 본문과 같은 권한으로
취급한다. 목록/운영 현황에는 판독 불가 건수만 보낸다. 120자 제한도 비식별화가 아니다.
재처리는 범위 확인·승인·중복 방지를 거치고 원본/기존 변환본을 덮어쓰지 않는다.
취소 직전 이미 전송된 페이지는 전송 이력에 남긴다. 미확정 실행을 자동 재전송하지 않는다.

## 5. 서버 계약 초안과 완료 기준

다음은 **제안 경로**다. 구현·권한 검수 후 OpenAPI와 이 항목을 함께 확정한다.

| 동작 | 제안 API |
|---|---|
| 실효 정책/상속/worker 상태 | `GET /api/archiver/vision/policy?workspace=...` |
| 정책 변경 (expectedRevision 필요) | `PUT /api/archiver/vision/policy` |
| 가능한 모델 목록 | 기존 `/api/models` 확장 또는 용도 전용 카탈로그, 미지원 값을 허용하지 않음 |
| 진단·작업 목록/상세 | `GET /api/archiver/vision/jobs` 및 `GET /api/archiver/vision/jobs/{id}` |
| 파일·페이지 전송 승인 | `POST /api/archiver/vision/approvals` |
| 승인 취소 | `POST /api/archiver/vision/approvals/{id}/revoke` |

# WC-26. Hermes 토큰 등록과 PF Hermes RPC 라우트 구분

| | |
|---|---|
| 상태 | ✅ 완료 — 화면 완료(10-12) · 전환 설정은 WC-27 |
| 우선 | 보통 |
| 담당 | 웹콘솔 |
| 등록 | 2026-10-12 |

### 무엇이 안 되는가

2026-10-12 TYIT 운영 확인에서 `봇 관리 > 워크스페이스 연결`로 Hermes의 Bot/App
Token을 등록했지만, PF Hermes RPC 라우트는 계속 꺼진 상태였습니다.

```text
specialist       | hermes
workspace        | tyit
route_mode       | disabled
fallback_bot_key | master
updated_by       | dan@taeyoung.com
```

서버의 `/etc/hermes/tyit/hermes.env`에도 이미 `SLACK_BOT_TOKEN`과
`SLACK_APP_TOKEN`이 있습니다. 두 토큰 저장소는 자동 동기화되지 않으며, 어느 쪽도
PF Hermes RPC 라우트를 켜는 설정이 아닙니다.

현재 화면에서는 아래 두 연결이 같은 "Hermes 연결"처럼 보여 운영자가 Slack 토큰을
등록하면 Master의 PF Hermes RPC 호출도 활성화된 것으로 오해합니다.

| 연결 | 정본 | 토큰 |
|---|---|---|
| Slack에서 `@Hermes` 직접 호출 | `bot_connection(hermes, slack_socket)` | Bot/App Token 필요 |
| TYBot Master가 PF Hermes RPC 호출 | `specialist_route(hermes, workspace)` | Slack Token 없음 |

### 무엇을 만들어야 하는가

1. Hermes 연결 상세에 `Slack 직접 연결`과 `PF Hermes RPC (Master 내부 호출)`을 별도
   행 또는 별도 섹션으로 표시합니다.
2. Bot/App Token 저장 성공을 RPC 활성화 성공처럼 표시하지 않습니다. 토큰 저장 뒤에도
   RPC 라우트가 `disabled`이면 그대로 `꺼짐`으로 표시합니다.
3. PF Hermes RPC에는 별도의 `disabled / shadow / active` 제어를 제공합니다. 변경 시
   사유를 필수로 받고 기존 API를 호출합니다.

```http
PUT /api/workspaces/{workspace}/bot-routes/{bot_key}
Content-Type: application/json

{"mode":"active","fallbackBotKey":"master","reason":"PF Hermes RPC TYIT 베타 활성화"}
```

4. 변경 성공 뒤 목록을 다시 읽어 실제 `route_mode`를 표시합니다. 낙관적으로 버튼만
   바꾸지 않습니다.
5. `active` 전환이 거부되면 전문봇 배정, runtime `enabled`, health `ok` 중 어느 조건이
   부족한지 API 오류를 그대로 사람이 이해할 수 있게 표시합니다.
6. 화면 명칭은 `내부 Hermes`가 아니라 **`PF Hermes RPC`**로 통일합니다. TYIT의
   Master v2에서는 기존 Python `ToolSpecialist`가 아니라 Unix socket의 Node.js Hermes를
   호출하기 때문입니다.

### 완료 조건

- TYIT Hermes 화면에서 Slack 직접 연결과 PF Hermes RPC 상태를 동시에 구분할 수 있다.
- 토큰 등록만 했을 때 RPC 상태는 계속 `disabled`로 정확히 보인다.
- 사유를 입력해 RPC를 `active`로 바꾸면 재조회 결과도 `active`다.
- 토큰 원문은 화면, 응답, 로그 어디에도 나오지 않는다.
- 다른 워크스페이스의 라우트는 바뀌지 않는다.

긴급도: **TYIT 베타 검증 차단 중**. PF Hermes RPC 호출 시험을 계속하려면 이 구분과

여러 워크스페이스가 하나의 worker를 사용하되 요청별 ACL·도구 토큰·근거는 TYBot이
분리한다. 기존 개별 worker 연결도 유지하므로 화면은 워크스페이스와 실행 인스턴스가
일대일이라고 가정하지 않는다. 공유/개별 연결 대상을 표시하고 공유 worker 장애는
연결된 전체 대상에 영향을 준다고 보여줘야 한다.
구현 인계: [공유 RPC 계약](verification/2026-10-12-hermes-shared-rpc-handoff.md).
공유 선택 설정 `TYBOT_HERMES_SHARED_WORKSPACES`도 전환 설정 관리 범위에 포함한다.

새 관리 메뉴를 추가하지 않고 **기존 봇 관리의 전문봇 연결·라우팅 화면을 대체**합니다.
PF Hermes RPC가 향후 전문봇 호출 기준이며, 기존 내부 Python Hermes의 배정이나
`active` 라우트를 PF RPC 활성화로 보여주는 화면은 대체 대상입니다.
Master와 Archiver의 등록·수집 관리는 유지합니다. Slack 직접 연결이 필요한 경우에는
앞 요청처럼 RPC와 분리해 표시합니다.

### 무엇을 만들어야 하는가

1. 워크스페이스별 `PF RPC 전환` 토글을 기존 봇 관리에 제공합니다. 기본값은 OFF이며
   대상은 Slack team ID가 아닌 등록된 워크스페이스 key(`tyit`, `mgmt` 등)입니다.
   TYIT 베타에서 한 곳씩 확산하며, 신규 워크스페이스는 자동 활성화하지 않습니다.
2. 전환 설정, 전문봇 배정, `disabled / shadow / active` 라우트, 인스턴스별 RPC worker
   health를 각각 표시합니다. 전환 OFF이면 라우트가 active여도 `PF RPC 미적용`으로
   표시하며, 전환 ON이지만 전문봇이 없으면 `Master 직접 답변`으로 표시합니다.
3. 요청된 설정과 실행 중인 TYBot의 실제 적용값을 구분해 표시합니다. 저장 이후
   재시작이나 설정 반영이 필요하면 `적용 대기`로 표시하고, 재조회로 적용을 확인합니다.
4. 인스턴스별 계정·환경파일·고유 HMAC·소켓 접근·서명된 health 준비 여부를 표시합니다.
   전역 `specialist_bot.health=ok`만으로 다른 워크스페이스 worker도 준비됐다고
   판단하지 않습니다. 시크릿 값은 반환하지 않습니다.
5. 설정 변경에는 사유와 실행자, 대상 워크스페이스, 이전·이후 값과 적용 결과를
   감사 기록으로 남깁니다. 특정 워크스페이스 변경이 다른 곳을 활성화하지 않아야 합니다.
6. 기존 내부 Hermes에서 PF RPC로 바뀌었는지는 최근 실행의 `phase=external-v3`와
   성공·실패 기록으로 확인할 수 있게 합니다. 등록 상태와 실제 호출 상태를 구분합니다.

### 봇 개발 담당자와 웹콘솔 담당자의 작업 분담

- **봇 개발 담당자**: 전환 설정 저장소와 조회·변경 API, 런타임 반영, 기존 환경변수와의

  적용 대기·실행 결과를 표시합니다. 웹 프로세스가 직접 서버 env 파일을 수정하거나

- API 필드와 반영 방식은 두 프로젝트가 합의한 뒤 문서화합니다. 환경변수는 이관 기간의

### 완료 조건

- 현재 상태에서 TYIT만 PF RPC 적용으로 보이고 mgmt·pilot은 기존 실행 경로로 보인다.

2026-10-14 TEC 운영 요구: 프로젝트 금융팀은 TYBot Master 없이 Archiver와 Hermes만
사용할 수 있다. 콘솔에서 Master 등록을 Archiver 활성화의 선행조건으로 요구하지 않는다.
기존 DB 기동 함수와 Python loader가 Master 부재를 거절하던 조건은 봇 개발 담당자가 수정한다.

- 연결 등록 완료와 수집 프로세스 실행/멤버십 동기화/실제 이벤트 수신을 구분해 표시한다.
- "등록/연결 검증" 이후 승인된 수집기 기동 요청을 서버 관리 API에 연결한다.

- Master 없는 workspace에 불필요한 Master 앱/토큰 등록을 안내하지 않는다.
- shadow 수집기 기동과 active 운영 writer 인수 승인을 분리한다. 등록 버튼만으로
  cutover/writer_owner/전역 쓰기 게이트를 자동 변경하지 않는다.
- 연결이 없거나 토큰/신원 검증이 부족하면 조건별 사유를 표시한다. 단순 "config 없음"으로

# WC-30. Archiver 이미지 설명·무료 Vision LLM 라우팅

| | |
|---|---|
| 상태 | 🟠 진행중 — 읽기 API 구현 · 변경 API·전용 LOGIN·서비스 기동 남음 |
| 우선 | 높음 |
| 담당 | 양쪽 |
| 등록 | 2026-10-27 |

## 목적과 경계

Archiver가 먼저 보관한 PNG/JPEG/WebP 원본을 별도 비동기 worker가 짧게 설명해
사진 검색용 파생 색인을 만든다([B-81](../BACKLOG.md#b-81)). 원본 수집은 LLM을
기다리지 않는다. 이 기능은 [WC-21](#wc-21)의 PDF 페이지 전사, Hermes Q&A 모델,
Master 기본 모델과 **서로 다른 용도·정책·예산·적용 revision**을 쓴다.

HWP는 rhwp가 PDF로 변환하는 운영 경로를 사용하므로 WC-30의 선행 조건이 아니다.
다만 봇이 만든 변환본·이미지는 사람 원본처럼 다시 수집하거나 설명하지 않는다.

## `무료`의 계약

모델 ID 자유 입력이나 가격란의 숫자 `0`을 무료의 근거로 쓰지 않는다. 서버가 확인한
카탈로그에서 아래 조건을 **모두** 만족한 모델만 선택할 수 있다.

| 조건 | 화면 표기 |
|---|---|
| `supportsVision=true` | 이미지 입력 확인됨 |
| `zeroCostVerified=true` | 무료 조건과 마지막 확인 시각 |
| 민감도·리전 정책 충족 | 허용 범위와 차단 사유 |
| `credentialReady=true` | 자격증명 준비 여부만. 값은 반환하지 않음 |
| 무료 quota 확인 가능 | 남은 양·초기화 시각 또는 `모름` |

후보가 없거나 무료 조건·quota를 확인할 수 없으면 호출하지 않는다. 무료 한도 소진이나
모델 장애를 유료 모델로 조용히 폴백하지 않는다. 이때 원본 수집은 성공일 수 있으며
이미지 설명 작업만 `차단` 또는 `무료 한도 보류`가 된다.

## 화면 계약

기존 `수집 > Archiver 운영` 상세에 **`이미지 설명·LLM`** 탭을 둔다.

- 전역 기본 정책과 workspace override를 함께 보여 주고, 실효값과 출처
  (`global`/`workspace`)를 표시한다.
- 저장 revision과 실행 중 worker 적용 revision을 다른 칸에 둔다. 저장 성공을
  적용·호출 성공으로 표시하지 않는다.
- 기본값은 OFF다. 모델 저장, 자격증명 준비, 외부 전송 승인은 서로 다른 상태다.
- 활성화 전에 처리 파일 형식, workspace·채널 범위, 출력 길이·시간·동시성·재시도
  상한과 외부 전송 승인 범위를 확인한다.
- 수집 ACK와 설명 작업 상태를 분리한다. `대기`, `실행 중`, `설명 완료`, `불확실`,
  `실패`, `정책 차단`, `무료 한도 보류`, `취소`를 접지 않는다.
- 작업 목록은 file ID·원본 SHA-256 마스크·좌표·prompt revision·실제 model/provider,
  토큰·비용·종료 코드만 보여 준다. 원본 bytes, 설명 본문, provider 응답은 운영 목록에
  싣지 않는다. 설명 본문 열람이 필요하면 현재 원본 ACL을 다시 검사하는 별도 상세가 필요하다.
- 파생 설명은 `[AI 이미지 설명·검색용]`으로 표시한다. 사람 원문이나 사실 근거로
  인용하지 않으며 검색 후보를 찾은 뒤 현재 권한으로 원본 사진을 다시 연다.
- 얼굴 신원·차량 번호, 공정률·치수·수량, 하자·안전 여부를 확정한 것처럼 표시하지 않는다.

## 서버 API

| 동작 | 제안 API |
|---|---|
| 실효 정책·상속·worker revision·무료 모델·최근 작업 | `GET /api/archiver/image-description/policy?workspace=...` — **구현됨** |
| 정책 변경(`expectedRevision`·사유 필수) | `PUT /api/archiver/image-description/policy` |
| 선택 가능한 무료 Vision 모델 | `GET /api/archiver/image-description/models?workspace=...` |
| 작업 목록·상세 | `GET /api/archiver/image-description/jobs` 및 `GET .../jobs/{id}` |
| 승인된 재처리·취소 | `POST .../jobs`, `POST .../jobs/{id}/cancel` |

구현된 GET은 관리자 전용이며 워크스페이스 범위를 서버에서 검사한다. 원본 bytes·경로,
설명 본문, provider 응답, 승인 사유, 정책/카탈로그 snapshot JSON은 반환하지 않는다.
전용 `TYBOT_VISION_DATABASE_URL`이 없거나 읽지 못하면 빈 목록이나 정상으로 바꾸지 않고
`503`과 고정 코드를 반환한다. `workerAppliedRevision=null`은 **미적용 확인 전**이며
`applicationState=not_configured`를 함께 표시한다.

아직 없는 변경 API·worker는 화면에서 `미구현`으로 표시하고 조작을 비활성화한다. 정책 저장만으로
기존 파일을 일괄 전송하지 않는다. 재처리는 원본 해시·현재 ACL·PII·봇 생성 여부·무료
조건을 실행 직전에 다시 검사하며 기존 원본과 파생 revision을 덮어쓰지 않는다.

## 작업 분담과 완료 조건

- **봇 개발 담당자**: 모델 카탈로그, 정책·감사 원장, 비동기 worker, 불변 파생 색인,
  현재 ACL 재검사, 관리자 API와 OpenAPI를 구현한다.
- **웹콘솔 담당자**: API 확정 뒤 위 탭과 상태·차단 사유·revision·작업 목록을 연결한다.
  웹 프로세스가 env 파일을 직접 고치거나 provider SDK를 호출하지 않는다.
- Claude/Codex 코드 분담은
  `docs/verification/2026-10-27-archiver-image-description-handoff.md`를 따른다.

완료 조건: 정책 OFF, 후보 없음, 무료 확인 실패·quota 소진, credential 없음, ACL 실패,
PII 차단, 봇 생성 파일, 원본 해시 변경에서 외부 호출 0회다. 비민감 합성 이미지로
설명 생성 → 검색 후보 → 현재 ACL로 원본 좌표 재확인까지 검증한 뒤 workspace 하나씩 켠다.
