1. **항목 ID(`WC-xx`)는 재사용하지 않습니다.** 완료돼도 번호를 비우거나 다른
   항목에 주지 않습니다. 새 요청은 늘 다음 번호입니다.
2. **완료 항목을 지우지 않습니다.** 상태를 `완료`로 바꾸고 §100 아래로 옮깁니다.
   지우면 반년 뒤에 같은 요청이 다시 올라옵니다 — 이 문서가 있는 이유가 그것입니다.
3. **완료 보고는 그 항목 안에 적습니다.** 각 항목 끝의 `완료 보고` 칸에
   커밋·날짜·확인 방법을 써 주세요.
4. **새 요청은 맨 아래 `WC-신규` 구역에 append 합니다.** 우리가 받아서 번호를
   붙이고 현황판에 올립니다.

# WC-01. 워크스페이스 등록이 토큰을 요구해 실패한다

| | |
|---|---|
| 상태 | 🟠 **서버 작업 완료(①②③) · 콘솔 화면 정리 대기** |
| 담당 | ~~TYBot 팀(서버)~~ → 콘솔 담당자(화면 정리) |
| 등록 | 2026-10-12 |
| 서버 완료 | 2026-10-12 |

> **등록이 되고, Master 도 안 죽고, 봇 관리에서 붙인 Master 토큰이 실제로 먹습니다.**
> 아래 **TYBot 팀 할 일**은 끝났고 남은 것은 화면 정리입니다.

## 증상

`운영 > 워크스페이스 관리 > 새 워크스페이스 등록` 에서 키·표시 이름을 넣고 등록하면
저장이 거부됩니다.

```
저장 실패   워크스페이스 설정을 저장하지 못했습니다
            새 워크스페이스에는 봇 토큰과 앱 토큰이 필요합니다.
```

## 원인 — 화면이 아니라 **API** 입니다

이 건은 **콘솔 담당자가 고칠 수 없습니다.** 조사 결과를 그대로 적습니다.

화면은 이미 올바릅니다. `console-web/src/pages/Workspaces.tsx:211` 에 주석이 있고,
`:326` 은 "봇 토큰은 이 화면에서 받지 않습니다" 라고 안내하며, `:236` 의 제출
payload 에 `botToken`·`appToken` 이 **없습니다.**

거부하는 쪽은 API 입니다.

| 자리 | 내용 |
|---|---|
| `src/tybot/console/app.py:170-171` | `WorkspaceBody.botToken`/`appToken` 이 `None` |
| `src/tybot/console/app.py:2043-2044` | 그대로 `save_workspace()` 로 전달 |
| `src/tybot/console/workspace_store.py:186` | `if not exists and not encrypted: raise` ← **여기서 막힘** |

봇 토큰은 이제 `봇 관리 > 워크스페이스 연결` 에서 봇별로(Master·Archiver·Hermes)
등록합니다. 워크스페이스 행은 **조직 metadata** 만 들고 있어야 합니다. 토큰을
워크스페이스에 매는 것은 봇이 하나뿐이던 시절의 구조이고, 지금은 한 워크스페이스에
봇이 여럿이라 애초에 한 쌍으로 표현할 수 없습니다.

## 콘솔 담당자 회신 (2026-10-12) — **지적이 맞았습니다**

> WC-01 API 쪽 보니까 `workspace_store.py:186` 토큰 조건만 빼면, 토큰 없는
> 워크스페이스 때문에 재시작 때 `workspaces.load_workspaces` 가 `ConfigError` 로
> Master 기동을 막을 것 같아요. ① 토큰 없는 행은 건너뛰기 → ② 필수 조건 제거 →
> ③ Master 가 `bot_connection` 토큰 읽기, 순서로 가야 할 것 같습니다.
> ③ 없으면 봇 관리에서 Master 토큰을 넣어도 실제로 안 붙는다.

**둘 다 코드로 확인했습니다.**

| 지적 | 확인 |
|---|---|
| ① `ConfigError` 로 Master 기동이 막힌다 | ✅ `workspaces.py:234`. **워크스페이스 하나 등록한 대가로 다른 본부 수집이 전부 멈춥니다** — 원래 버그보다 나쁩니다 |
| ③ Master 는 `bot_connection` 을 안 읽는다 | ✅ `bot_admin.py:60` 주석이 직접 적어 뒀습니다 — "Archiver 는 새 `bot_connection` 을 읽는다. **Master 는 아직 `workspace_secret`**… 이 화면의 저장은 **기록이지 적용이 아니다**" |

②가 먼저 커밋됐지만 **배포 전**이라 실제 피해는 없었고, ①③을 같은 배포에 묶어
순서를 지켰습니다.

### ① 이 왜 생겼나

그 분기가 만들어질 땐 토큰 없는 행이 생기는 길이 **하나뿐**이었습니다 —
레지스트리 이전의 깨진 이관. 그땐 크게 소리치는 것이 맞았습니다. WC-01 이
**정상인 길을 하나 더** 만들면서 같은 상태가 두 가지 뜻을 갖게 됐습니다.

고친 방향: 건너뛰되 **WARNING 로그 + `workspaces.pending_connection()`** 으로 목록을
남깁니다. 스키마 주석도 같은 쪽입니다 — `workspace.state`: "등록 오류는 이
워크스페이스만 멈춘다. 다른 봇은 계속 뜬다."

**복호화 실패(`undecryptable`)는 그대로 막습니다.** 그쪽은 토큰이 **있는데** 못 읽는
것이라 그 워크스페이스는 수집 중이었고, 빠지면 그 기간이 영구 유실됩니다(Slack
백필 분당 1회). 조치도 다릅니다 — 키 불일치 확인.

# WC-02. 봇 배포와 콘솔 배포를 끝까지 가른다

| | |
|---|---|
| 상태 | 🔴 요청됨 |

| 등록 | 2026-10-12 |

화면 빌드는 `05d60f6` 으로 갈라졌습니다(`install.sh:327`). 그런데 **배포 스크립트의
나머지가 아직 분리 전 전제로** 돕니다.

## (0) 2026-10-12 실사고 — 배포가 닿지 않는 콘솔이 5일간 돌았다

> **이 항목이 왜 있는지 보여 주는 사례입니다.** 먼저 읽어 주세요.

WC-01 을 고치고 배포했는데 화면에 **같은 옛 오류**가 계속 났습니다. 확인해 보니:

```
브라우저 → nginx :8788 → 127.0.0.1:8789  ← 10월 7일에 손으로 띄운 uvicorn
                         127.0.0.1:8787  ← systemd. 새 코드. 아무도 안 봄
```

- 배포는 **성공**으로 끝났습니다
- `/opt/tybot/src` 의 파일은 **새것**이었습니다
- `systemctl restart tybot-console` 도 **돌았습니다**
- 그런데 사람이 보는 화면은 **5일 된 코드**였습니다
- **아무 오류도 안 났습니다**

찾는 데 서버에서 `ps` 를 봐야 했습니다. `systemctl restart` 는 **자기가 만든
프로세스만** 내립니다 — 손으로 띄운 것은 남고, nginx 가 그쪽을 가리키면 배포가
영원히 안 닿습니다.

**조치**: nginx 를 8787(systemd 관리)로 돌렸고, 8789 프로세스는 정리했습니다.
지금은 8788 하나로 운영합니다.

### 이 사고에서 고친 것 (TYBot 팀, 2026-10-12)

- [x] **nginx 판정을 파일 이름이 아니라 내용으로** — `nginx_proxies_port()`.
      전에는 `/etc/nginx/conf.d/tybot-console.conf` 하나만 봤는데 실제 파일은
      `tybot-console-next.conf` 였습니다. 그래서 nginx 가 받고 있는데도
      「안 받는다」 로 판정해 **평문 바인딩(0.0.0.0)을 계속 유지**했습니다
- [x] **systemd 밖의 콘솔을 센다** — `warn_about_consoles_outside_systemd()`.
      배포 때 PID·기동 시각·명령행을 찍습니다
- [x] **PF 콘솔 포트 충돌을 막는다** — 8788 은 이제 nginx 가 쥐고 있습니다.
      **PF 콘솔은 운영하지 않기로 했으므로**(2026-10-12 오너 확인) 지금은 돌지
      않습니다. 나중에 누가 되살리면 둘 중 하나가 조용히 못 뜨므로 경고만 남겼습니다

### 포트 배치 (2026-10-12 확정)

```

                 └─proxy_pass→ 127.0.0.1:8787  tybot-console (systemd)
```

|---|---|

| ~~8789~~ | 손으로 띄웠던 프로세스. 정리됨 |

**아직 평문 HTTP 입니다.** nginx 가 앞에 온 것과 TLS 는 다른 일입니다 — [WC-04](#wc-04)

## (1) 봇 배포가 매번 콘솔을 내린다

`deploy/update.sh:118-120` 이 무조건 `systemctl restart tybot-console` 합니다.
`tybot-update.timer` 로 주기 실행되니 **문서만 고친 배포에서도** 로그인 세션이
끊기고 진행 중이던 배포 승인·소급 실행이 중간에 죽습니다.

**다만 「절대 재시작 안 함」 은 틀립니다.** `tybot-console.service` 가 돌리는 것은
`uvicorn tybot.console.app:app` — **이 저장소의 `src/tybot/console/`** 입니다. 게다가
콘솔 백엔드는 `..archive.store`, `..gateway.router`, `..feedback` 등 공유 모듈 15개
남짓을 import 합니다. 봇 코드가 바뀌면 콘솔이 돌리는 코드도 바뀝니다.

갈라야 할 것은 「재시작하느냐」가 아니라 **「무엇이 바뀌었을 때 재시작하느냐」**.
`update.sh` 는 이미 직전 배포 커밋(`$DEPLOYED`)을 들고 있습니다.

```bash
console_needs_restart() {
  [[ -z "$DEPLOYED" ]] && return 0                  # 모르면 재시작한다
  git -C "$SRC" cat-file -e "$DEPLOYED^{commit}" 2>/dev/null || return 0
  git -C "$SRC" diff --name-only "$DEPLOYED" HEAD -- src/ | grep -q .
}
```

- **모르면 재시작합니다.** 안 내려서 옛 코드가 도는 쪽이 세션 끊김보다 나쁩니다
- `TYBOT_FORCE=1` 이면 조건 없이 재시작
- 건너뛸 때는 **로그에 남깁니다.** 조용히 건너뛰면 아무도 못 알아챕니다

> 완전히 끊으려면 콘솔 백엔드도 별도 저장소·서비스로 옮겨야 합니다. 지금 구조에서는
> 공유 모듈 때문에 불가능합니다. 오너 결정 사항이라 제안만 남깁니다.

## (2) `CONSOLE_DIST` 를 봇 배포가 소유하고 있다

`deploy/install.sh:414-417` 이 `$APP_DIR/console-web/dist` 를 적어 넣는데, 이

그리고 **조용합니다.** `src/tybot/console/app.py:2950` 의 `mount_frontend()` 는

```python
if not (root / "index.html").exists():

# WC-03. Hermes 설정·시크릿을 DB 와 콘솔로

| | |
|---|---|
| 상태 | 🔴 요청됨 — **스키마 안을 먼저 정해야 합니다** |
| 담당 | TYBot 팀(스키마·API) + **콘솔 담당자(신규 화면)** |
| 등록 | 2026-10-12 |
| 연계 | B-75 |

## 배경 — PF 팀용 Hermes 가 들어왔습니다

PF(프로젝트금융) 팀용 Hermes 가 **우리 서버에서** 돕니다. PF 전용 서버는 없습니다.
지금 설정은 서버 파일에 평문으로 있습니다.

```
/etc/tybot-subbots/pf-hermes.env      (root:pf-hermes 0640)
/etc/hermes/<instance>/hermes.env     (인스턴스별)
```

`deploy/setup-pf-hermes-host.sh:129-152` 가 골격을 만들고 **값은 사람이 손으로**
넣습니다. 그 파일에 들어 있는 것:

| 구분 | 키 |
|---|---|
| **시크릿** | `SLACK_BOT_TOKEN` · `SLACK_APP_TOKEN` · **`ANTHROPIC_API_KEY`** |
| 경로(비시크릿) | `HERMES_INSTANCE` · `HERMES_SERVICE_NAME` · `HERMES_*_ROOT` · `HERMES_CONFIG_FILE` |
| 설정(비시크릿) | `ARCHIVE_GIT_REMOTE` · `HERMES_READ_ONLY` |
| 키 **경로**(값 아님) | `CODE_GIT_SSH_KEY` · `ARCHIVE_GIT_SSH_KEY` |

**평문 파일을 장기 원장으로 쓰지 않습니다.** 서버에 들어갈 수 있는 사람은 누구나
읽고, 백업·복사본에 그대로 따라다니며, 누가 언제 바꿨는지 남지 않습니다.

## 이미 있는 패턴을 **재사용합니다** — 새로 만들지 마세요

이 저장소에는 Fernet 암호화 시크릿 표가 **이미 여섯 개** 있습니다.

```
workspace_secret · bot_connection_secret · llm_secret
specialist_secret · specialist_runtime_secret · workspace_service_secret
```

전부 같은 세 규칙을 지킵니다. Hermes 도 **같은 규칙**입니다.

1. **평문 저장 금지** — Fernet 으로 암호화. 키는 DB 밖 파일
   (`/etc/tybot/workspace-secret.key`, 0400). DB 백업만으로는 못 풉니다
2. **복호화 조회 API 금지** — 값을 화면으로 꺼낼 수 있으면 그 순간 브라우저·
   로그·스크린샷이 전부 보관 장소가 됩니다
3. **콘솔은 mask 만 읽습니다** — 예: `sk-ant-…9f0c`

## 여기서 막히는 것 — `llm_secret` 을 그대로 못 씁니다

Anthropic 키는 이미 콘솔에서 관리합니다(`GET/PUT /api/llm-secrets`,
`deploy/sql/llm_secret_schema.sql`). 그런데 그 표는 이렇습니다.

```sql
CREATE TABLE llm_secret (
    provider text PRIMARY KEY          -- ← 전역 1개
             CHECK (provider IN ('anthropic', 'openai')),
    ...
);
```

**`provider` 가 PRIMARY KEY 라 Anthropic 키가 시스템 전체에 하나뿐입니다.**

PF Hermes 는 **자기 키**가 필요합니다. `setup-pf-hermes-host.sh:140` 의 주석이
그 이유입니다 — "모델 — 계정과 일일 상한의 주인은 프금팀이다". 비용 청구와 상한의
주인이 다르므로 키를 같이 쓸 수 없습니다.

→ **스키마 변경이 필요합니다.** 선택지 둘:

| 안 | 모양 | 평 |
|---|---|---|
| A | `llm_secret` 에 `scope` 열 추가, PK 를 `(provider, scope)` 로 | 기존 행은 `scope='global'`. 화면 하나로 통합 |
| B | `hermes_instance_secret` 표를 따로 | 인스턴스 설정과 한 화면에 모임 |

**B 를 권합니다.** Hermes 는 Slack 토큰 두 개도 함께 필요하고, 그 둘은 `llm_secret`
에 넣을 수 없습니다. 한 인스턴스의 시크릿 세 개가 한 자리에 있는 편이 교체·폐기·
감사에서 섞이지 않습니다.

> **⚠️ 이 선택이 먼저입니다.** 정해 주시면 우리가 스키마·API 를 만들고 이 항목을
> 갱신합니다. 그 전에는 화면 착수를 권하지 않습니다 — 필드가 바뀝니다.

## 제안 계약

### 비시크릿 설정 — `hermes_instance`

```
instance      text PK      -- 'pf', 'ty', …
workspace     text         -- 어느 워크스페이스의 Hermes 인가
domain        text         -- domain profile
enabled       boolean
read_only     boolean      -- HERMES_READ_ONLY
archive_git_remote text
expected_team_id   text    -- 기동 시 신원 대조용
expected_bot_id    text
updated_at / updated_by
```

**경로는 DB 에 넣지 않습니다.** `HERMES_*_ROOT` 는 서버가 인스턴스 이름으로
계산합니다. DB 에 두면 한 인스턴스가 다른 인스턴스의 경로를 가리킬 수 있고,
그건 화면에서 한 글자 고쳐서 일어납니다.

### 시크릿 — `hermes_instance_secret`

```
instance   text
kind       text CHECK (kind IN ('slack_bot', 'slack_app', 'anthropic'))
ciphertext bytea
mask       text
enabled    boolean
previous_ciphertext / previous_until   -- 무중단 교체용
updated_at / updated_by
PRIMARY KEY (instance, kind)
```

`previous_*` 는 `specialist_runtime_secret` 과 같은 이유입니다 — 교체 시 구/신 키를
잠깐 겹치지 않으면 무중단 전환이 안 됩니다.

### API

```http
GET  /api/hermes/instances                 → 목록 + 설정 여부 + mask + 마지막 검증
PUT  /api/hermes/instances/{instance}      → 비시크릿 설정
PUT  /api/hermes/instances/{instance}/secrets/{kind}          → 시크릿 저장(쓰기 전용)
PUT  /api/hermes/instances/{instance}/secrets/{kind}/verify   → 저장 후 실제 검증
```

**복호화해 돌려주는 라우트는 만들지 않습니다.**

## 콘솔 담당자 할 일 — 화면 계약

> 그러면 `완료`로 옮기고 다시 묻지 않겠습니다.

## 데이터 계약

`channel_reviewer` 의 검토 예약은 세 값으로 정합니다.

| 필드 | 값 | 규칙 |
|---|---|---|
| `schedule_kind` | `daily` 또는 `weekly` | 기존 행 기본값 `daily` |
| `weekday` | `0..6` 또는 `NULL` | Python 기준 월요일 `0`, 일요일 `6` |
| `send_at` | PostgreSQL `time` | KST 기준 검토 DM 발송 시각 |

유효한 조합은 **두 가지뿐**입니다.

```
daily  + weekday NULL
weekly + weekday 0..6
```

`daily + 요일`, `weekly + NULL`, 범위 밖 요일은 저장 단계에서 거부합니다.

## 읽기 API

`GET /api/channels` 의 각 `rows[]`:

```json
{ "reviewers": ["U123"], "sendAt": "09:00:00",
  "scheduleKind": "weekly", "weekday": 2, "scheduleLabel": "매주 수요일 09:00" }
```

주기 문구를 다시 조립하지 말고 **`scheduleLabel` 을 우선** 표시합니다. 값이 없는
구버전 응답에 한해서만 `sendAt` 을 대체 표시합니다.

`GET /api/summary-review/rounds` 의 `schedule`:

```json
{ "channels": 3, "due": 1, "waiting": 2,
  "nextSendAt": "수요일 09:00", "timezone": "Asia/Seoul" }
```

`nextSendAt` 은 일간이면 `HH:MM`, 주간이면 `요일 HH:MM`. 화면 문구는 "설정 시각"이
아니라 일간·주간을 포괄하는 **"예약 시점"** 을 씁니다.

## 화면 용어

| 이전 | 변경 |
|---|---|
| 채널 수정 담당자 | 채널 관리자 |
| 요약 검토자 | 검토 승인자 |

## 화면 순서

채널 **수정**: 업무명 → 채널 관리자 → 요약 검토 주기 → 주 1회 검토 요일(`weekly`
일 때만, 필수) → 검토 시각 → 검토 승인자

채널 **생성**(관리자를 따로 고르지 않음): 채널 기본 정보·추가 참여자 → 요약 검토
주기 → 주 1회 검토 요일 → 검토 시각 → 검토 승인자

`daily` 를 고르면 요일 입력을 숨기고 저장값도 `NULL` 로 만듭니다. `weekly` 를
고르면 요일을 보인 뒤 선택 전에는 저장할 수 없어야 합니다. **이전에 선택한 요일이
`daily` 전환 뒤 몰래 제출되면 안 됩니다.**

# WC-14. Master 가 `bot_connection` 토큰을 읽는다

| | |
|---|---|
| 상태 | ✅ **완료** (2026-10-12) |
| 담당 | TYBot 팀 · 콘솔 변경 없음 |
| 등록 | 2026-10-12 (콘솔 담당자 지적 ③) |

## 무엇이 문제였나

Archiver 만 새 `bot_connection` 을 읽고 **Master 는 `workspace_secret` 만** 봤습니다.
그래서 `봇 관리 > 워크스페이스 연결`에서 Master 토큰을 넣어도 **실제로 안 붙었습니다.**
코드 주석이 직접 적어 뒀습니다 — "이 화면의 저장은 **기록이지 적용이 아니다**".

WC-01 과 겹치면 반쪽이 됩니다. 토큰 없이 등록은 되는데 붙일 방법이 없고,
**아무 오류도 안 납니다.**

## 어떻게 고쳤나

`runtime_workspaces()` 가 두 출처를 함께 읽고 Python 이 고릅니다
(`pick_runtime_tokens`).

| 상태 | 쓰는 토큰 |
|---|---|
| `bot_connection` 에 쌍이 있음 | **`bot_connection`** (정본) |
| 없음 · `workspace_secret` 에 쌍 | `workspace_secret` (전환 중 폴백) |
| 어느 쪽도 **반쪽** | 안 씀 — 섞지 않는다 |
| 둘 다 없음 | 안 뜸(WC-01 ①이 건너뜀) |

**섞지 않는 것이 핵심입니다.** 봇 토큰과 앱 토큰이 서로 다른 앱의 것이 되면 Slack 은
연결 실패로만 알려 주고, 담당자는 어느 쪽이 틀렸는지 화면에서 못 봅니다.

연결을 받는 조건은 Archiver 함수(`archiver_connection_config`)와 **같은 넷**입니다 —
`bot_key='master'` · `connector_type='slack_socket'` · `state='enabled'` ·
`identity_ok IS TRUE`. 느슨하게 하면 확인 안 된 토큰으로 기동하고, 토큰을 잘못
붙이면 **다른 워크스페이스에 수집합니다.** 그건 오류가 아니라 유출입니다.

**스키마 변경은 없습니다.** `tyslackai` 가 이미 `bot_connection` ·
`bot_connection_secret` 에 SELECT 권한을 갖고 있어 지문이 그대로입니다
(`b96ee558a1b8`).

각 행에 `token_source` 를 실어 보냅니다 — 전환 중에는 「콘솔에서 본 값」 과
「봇이 쓰는 값」 이 다를 수 있고, 그 간극은 조용합니다.

## 콘솔에 영향

없습니다. 다만 **봇 관리의 「기록이지 적용이 아니다」 안내 문구는 Master 에 대해
더 이상 맞지 않습니다** — 이제 적용됩니다. 화면에 그 취지의 문구가 있으면 고쳐

# WC-16. 【최우선】 Archiver 운영 화면 — 수집 전환·소급

| | |
|---|---|

| 담당 | **콘솔 화면** · API 는 전부 준비됨 |
| 등록 | 2026-10-14 |

## 왜 최우선인가

수집이 **Archiving Bot 기준**으로 넘어갔습니다. 그런데 **그 조작을 콘솔에서 할
수 없습니다.** 지금 채널을 Archiver 수집으로 전환하거나 소급을 돌리려면
**서버에 SSH 로 들어가야** 합니다.

이건 이 저장소의 원칙 위반이기도 합니다(CLAUDE.md):

> **새로 만드는 운영 기능은 관리 콘솔에서 쓸 수 있어야 한다.** 서버에 SSH 로
> 들어가 명령을 치는 것을 전제로 설계하지 않는다. … 서버 명령은 **쓸 수 있는
> 사람이 한 명**이고, 그 사람이 없으면 기능이 없는 것과 같다.

## 지금 있는 것 / 없는 것

`console-web/src/components/ArchivingPanel.tsx` 가 `워크스페이스 관리 > 상세`
안에서 돕니다. 쓰는 것은 셋뿐입니다.

| 화면에 **있음** | |
|---|---|
| `PUT .../archiving/channels/{id}/hold` | 운영자 보류 |
| `PUT .../archiving/flags` | 기능 스위치 |
| `PUT .../archiving/retention` | 보존 기간 |

| 화면에 **없음** (API 는 있음) | 무엇을 못 하나 |
|---|---|
| `PUT .../archiving/channels/{id}` | **채널 모드 전환** — `off`/`shadow`/`active`/`paused`, writer 인수 |
| `GET .../archiver/runtime` | Archiver 가 지금 무엇을 하고 있나 |
| `PUT .../archiver/desired` | 원하는 상태 지정 |
| `POST .../archiver/backfill` | **소급 수집 실행** |
| `PUT .../archiver/backfill/{id}/cancel` | 소급 취소 |

**정작 「이 채널을 Archiver 가 수집하게 한다」 를 못 누릅니다.** 보류는 되는데
전환이 안 됩니다.

## 화면 계약

### 1. 채널 모드 전환 — 한 방향씩, 범위를 보이게

모드는 넷입니다. 화면은 **지금 모드에서 갈 수 있는 곳만** 보여 주세요.

```
off → shadow → (paused) → active
```

- `shadow` 는 운영 원문을 건드리지 않습니다. 안전한 연습 상태입니다
- `active` 는 **그 채널의 운영 원문 주인이 바뀝니다**(Master → Archiver).
  누르기 전에 **무엇이 바뀌는지** 문장으로 보여 주세요
- `paused` 는 인수 중간 단계입니다. 둘 다 안 씁니다 — 그 사이는 **공백**이고,
  공백은 나중에 소급으로 메울 수 있습니다. 반대로 둘이 동시에 쓰면
  **겹침**이고 그건 못 고칩니다

`gatedModes` 에 들어 있는 모드는 **스키마 검증 전에는 못 누릅니다.**
`schemaGate.verified` 가 `false` 면 버튼을 회색으로 두고 `schemaGate.reason` 을
그대로 보여 주세요(WC-06 과 같은 규칙).

### 2. 소급 — **분량을 먼저 세고** 범위를 명시하게

소급은 비용이 들고 시간이 깁니다. CLAUDE.md:

> 파괴적이거나 비용이 드는 동작은 콘솔에서 **범위를 명시**하게 만든다
> (예: 소급은 채널을 고르게 하고, 실행 전에 분량을 먼저 센다)

- [ ] **채널을 고르게** 한다. 「전부」 를 기본값으로 두지 않는다
- [ ] 시작일·회차 상한을 받는다
- [ ] **실행 전에 몇 건인지 센다.** 숫자를 보기 전에 실행 버튼을 누르게 하지 않는다
- [ ] 진행 중 상태와 **취소**를 같은 화면에서
- [ ] Slack 백필은 **분당 1요청**입니다. 예상 소요를 보여 주세요

### 3. 런타임 — 「돌고 있나」 와 「반영됐나」 를 가른다

`GET .../archiver/runtime` 과 `PUT .../archiver/desired` 는 **원하는 상태**와
**실제 상태**를 따로 듭니다. 한 배지로 합치지 마세요 — 합치면 「껐는데 계속
돈다」 를 설명할 수 없습니다(WC-05 의 보존 집행과 같은 축).

### 4. 어디에 둘 것인가

지금은 `워크스페이스 관리 > 상세` 안에 묻혀 있습니다. 수집 운영이 매일 쓰는
기능이 되었으니 **`수집` 메뉴 아래 독립 화면**을 권합니다.

```
수집
├ 수집 현황
├ Archiver 운영      ← 신규: 채널 모드 · 소급 · 런타임
├ 아카이브 진단
└ ...
```

## 참고 — 수집은 Master 없이도 됩니다

「Master 연결이 끊겨 수집이 안 된다」 는 **이제 아닙니다.**
`archiver_connection_config` 가 완화됐습니다.

```sql
AND (m.id IS NULL OR ( m.identity_ok IS TRUE AND ... ))
```

Master 연결 행이 **아예 없으면** Archiver 는 그냥 돕니다. Master 가 필요한 것은
**DM 인계**뿐입니다(Master 의 봇 발언을 걸러내야 해서).

단, Master 연결이 **있는데 신원 확인이 안 됐으면** 그 워크스페이스의 Archiver 가
거부됩니다. 화면이 그 상태를 **사유와 함께** 보여 주면 좋겠습니다.

# WC-19. 수집 현황이 Archiver 수집을 못 본다

| | |
|---|---|
| 상태 | 🔴 **높음** — [WC-16](#wc-16) 과 한 묶음 |
| 담당 | **TYBot 팀(집계)** + **콘솔 담당자(링크)** |
| 등록 | 2026-10-14 |

## 두 가지가 겹쳐 있습니다

### (1) 링크가 옛 흐름을 가리킨다 — 콘솔

`수집 > 수집 현황` 의 「조치 필요」 를 누르면 **워크스페이스 관리**로 갑니다.
TYBot Master 가 수집하던 시절의 흐름입니다.

```tsx
// Dashboard.tsx:79 — 수집 중단
href={user.role === 'admin'
  ? `#/manage/workspaces?workspace=${w.key}`     // ← 옛 목적지
  : `#/collect?workspace=${w.key}&state=stalled`}

// Dashboard.tsx:98 — 미초대 채널
href={user.role === 'admin' ? '#/manage/workspaces' : '#/collect'}
```

안내 문구도 같습니다 — *「마지막 수집 시각과 **Slack 연결 상태**를 확인합니다」*.
지금 수집의 주인은 Archiver 이므로, 가야 할 곳은 **[WC-16](#wc-16) 의 Archiver
운영 화면**(채널 모드·런타임·소급)입니다.

- [ ] 「수집 중단」 → Archiver 운영 화면의 그 워크스페이스
- [ ] 「미초대 채널」 → 같은 화면의 채널 목록
- [ ] 안내 문구를 **채널 모드·Archiver 런타임** 기준으로 고쳐 쓴다

> WC-16 이 먼저입니다. 갈 곳이 없으면 링크를 고칠 수 없습니다.

### (2) 숫자가 Archiver 수집을 **포함하지 않는다** — TYBot 팀

확인했습니다. **포함하지 않습니다.**

```python
# src/tybot/console/reader.py:196
store = store or ArchiveStore(archive_dir())     # ← ARCHIVE_DIR 하나만
```

수집 현황은 **운영 루트(`ARCHIVE_DIR`) 파일만** 셉니다. 그런데 Archiver 는
채널 모드에 따라 두 곳에 씁니다.

| 채널 모드 | Archiver 가 쓰는 곳 | 수집 현황에 |
|---|---|---|
| `shadow` | `ARCHIVER_SHADOW_DIR` | **안 보임** |
| `active` | `ARCHIVE_DIR` | 보이지만 **누가 썼는지 모름** |

## 그래서 생기는 오표시

**shadow 로 넘긴 워크스페이스가 「수집 중단」 으로 뜹니다.**

`_health()`(`reader.py:180`)는 `last_ingested` 가 `STALLED_HOURS` 보다 오래되면
`stalled` 입니다. 그 값은 **운영 루트 문서**에서만 옵니다. 채널을 shadow 로
넘기면 운영 루트에는 새 줄이 안 쌓이므로, **Archiver 가 멀쩡히 수집하는 동안
화면은 「수집 중단 · 조치 필요」** 라고 말합니다.

그리고 그 빨간 줄을 누르면 워크스페이스 관리로 가서 **고칠 것이 없습니다.**
전환 중에는 이게 정상 상태인데 화면은 사고라고 합니다.

## 고치는 방향 — `archive_ingest_state` 가 이미 답을 압니다

파일을 세지 말고 ACK 표를 보는 쪽을 권합니다. 그 표에 **`written_to`** 가
있습니다(`live` / `shadow`). 누가 어디에 썼는지 이미 구분해 둡니다.

- [ ] 「수집 중단」 판정에 **채널 모드**를 넣는다. shadow 인 채널의 운영 루트가
      조용한 것은 **정상**이다
- [ ] 집계를 **운영 n건 · 그림자 m건**으로 **나눠서** 보여 준다.
      합치지 않는다 — 합치면 인수 전후를 대조할 수 없다
- [ ] 마지막 수집 시각을 **루트별로** 든다

> **두 루트를 합쳐 읽는 기능을 만들자는 것이 아닙니다.** 답변 근거의 단일 루트
> 원칙(2026-10-02 오너 결정)은 그대로입니다. 여기서 필요한 것은 **현황판이 두
> 곳을 각각 세어 나란히 보여 주는 것**뿐입니다.

## 확인 방법

전환한 채널이 있는 워크스페이스에서:

```bash
# 운영 루트에 최근 줄이 있나
sudo -u tybot ls -lt /var/lib/tybot/archive/*/*/raw/*.md 2>/dev/null | head -3
# 그림자 루트에는
sudo -u tybot ls -lt /var/lib/tybot/archiver-shadow/**/raw/*.md 2>/dev/null | head -3
```

그림자 쪽만 최신이면 **수집은 되고 있고 화면만 모르는 것**입니다.

# 3. 【참고】 화면 계약 시험 — 모르면 우리 배포가 깨집니다

> 항목이 아니라 **상시 규칙**입니다. 모든 화면 작업에 적용됩니다.

화면 문구·필드·경로를 바꾸면 아래 시험이 깨집니다. 콘솔 저장소에는 없고
**TYBot 저장소 `tests/`** 에 있으며, **콘솔 저장소의 소스를 읽습니다.**

| 파일 | 시험 수 | 무엇을 강제하나 |
|---|---:|---|
| `tests/test_console_bot_ui_contract.py` | 52 | 봇 관리 화면의 토큰 입력·문구·권한·탭 경로 |
| `tests/test_pf_isolation.py` | 35 | PF 콘솔과 TY 콘솔이 섞이지 않는다 |

강제하는 것 중 **보안에 걸리는 것들**입니다. 취향이 아니라 계약입니다.

- 토큰 입력은 `password` 타입이고 저장 후 **지워진다**
- 평문 토큰 필드를 **어떤 경로로도 렌더링하지 않는다**
- 내부 호출 화면에는 토큰 입력이 **없다**
- 메뉴를 옮겨도 **권한이 넓어지지 않는다**
- 옛 URL 은 알려진 경로로 **착지한다**(쿼리는 건드리지 않고)

**WC-03 의 Hermes 시크릿 화면도 이 계약을 지켜야 합니다.**

```bash

CONSOLE_WEB_DIR=/path/to/console-web REQUIRE_CONSOLE_WEB=1 \

`REQUIRE_CONSOLE_WEB=1` 을 **꼭 붙여 주세요.** 없으면 소스를 못 찾았을 때 실패가

# 4. 【참고】 공통 규칙 — 모든 화면에 적용

## 1. 원문을 표시하지 않습니다

콘솔은 **상태·건수·좌표·오류 코드**만 보여 줍니다. 대화 원문, 첨부 본문, DM 내용은
화면에 올리지 않습니다. 봇과의 DM 은 **그 사람 본인이 DM 에서 물을 때만** 근거가
됩니다 — exec·root·콘솔도 예외가 아닙니다.

## 2. 시크릿은 mask 만

Slack 토큰·DSN·API 키·원문 경로는 API 응답과 로그 **양쪽에서** 가립니다.
저장 후 화면에는 **설정 여부와 마지막 검증 시각**만 보입니다.
**복호화해 돌려주는 라우트는 만들지 않습니다.**

## 3. 모르면 "모른다"고 씁니다

상태를 못 읽었을 때 「정상」이나 「0건」으로 보여 주지 마세요. 못 본 것과 없는 것은
사람이 할 일이 다릅니다. 이 프로젝트에서 반복해 터진 고장이 전부 이 모양입니다 —
오류는 안 나고 0 이 나옵니다.

## 4. 파괴적이거나 비용이 드는 동작은 범위를 명시하게

소급은 채널을 고르게 하고 실행 전에 **분량을 먼저 셉니다.** 보존 집행은 기본이
**읽기 전용 미리보기**이고, 적용에는 실행자 이름이 필요합니다.

## 5. 「저장됨」과 「동작함」을 가릅니다

저장은 값을 넣은 것이고, 그 값이 실제로 통하는지는 다른 문제입니다.
검증 전에는 「검증 안 됨」으로 보여 주세요.

## Hermes 토큰 등록과 PF Hermes RPC 라우트를 구분해 주세요

### 무엇이 안 되는가

2026-10-12 TYIT 운영 확인에서 `봇 관리 > 워크스페이스 연결`로 Hermes의 Bot/App
Token을 등록했지만, PF Hermes RPC 라우트는 계속 꺼진 상태였습니다.

```text
specialist       | hermes
workspace        | tyit
route_mode       | disabled
fallback_bot_key | master
updated_by       | dan@taeyoung.com
```

서버의 `/etc/hermes/tyit/hermes.env`에도 이미 `SLACK_BOT_TOKEN`과
`SLACK_APP_TOKEN`이 있습니다. 두 토큰 저장소는 자동 동기화되지 않으며, 어느 쪽도
PF Hermes RPC 라우트를 켜는 설정이 아닙니다.

현재 화면에서는 아래 두 연결이 같은 "Hermes 연결"처럼 보여 운영자가 Slack 토큰을
등록하면 Master의 PF Hermes RPC 호출도 활성화된 것으로 오해합니다.

| 연결 | 정본 | 토큰 |
|---|---|---|
| Slack에서 `@Hermes` 직접 호출 | `bot_connection(hermes, slack_socket)` | Bot/App Token 필요 |
| TYBot Master가 PF Hermes RPC 호출 | `specialist_route(hermes, workspace)` | Slack Token 없음 |

### 무엇을 만들어야 하는가

1. Hermes 연결 상세에 `Slack 직접 연결`과 `PF Hermes RPC (Master 내부 호출)`을 별도
   행 또는 별도 섹션으로 표시합니다.
2. Bot/App Token 저장 성공을 RPC 활성화 성공처럼 표시하지 않습니다. 토큰 저장 뒤에도
   RPC 라우트가 `disabled`이면 그대로 `꺼짐`으로 표시합니다.
3. PF Hermes RPC에는 별도의 `disabled / shadow / active` 제어를 제공합니다. 변경 시
   사유를 필수로 받고 기존 API를 호출합니다.

```http
PUT /api/workspaces/{workspace}/bot-routes/{bot_key}
Content-Type: application/json

{"mode":"active","fallbackBotKey":"master","reason":"PF Hermes RPC TYIT 베타 활성화"}
```

4. 변경 성공 뒤 목록을 다시 읽어 실제 `route_mode`를 표시합니다. 낙관적으로 버튼만
   바꾸지 않습니다.
5. `active` 전환이 거부되면 전문봇 배정, runtime `enabled`, health `ok` 중 어느 조건이
   부족한지 API 오류를 그대로 사람이 이해할 수 있게 표시합니다.
6. 화면 명칭은 `내부 Hermes`가 아니라 **`PF Hermes RPC`**로 통일합니다. TYIT의
   Master v2에서는 기존 Python `ToolSpecialist`가 아니라 Unix socket의 Node.js Hermes를
   호출하기 때문입니다.

### 완료 조건

- TYIT Hermes 화면에서 Slack 직접 연결과 PF Hermes RPC 상태를 동시에 구분할 수 있다.
- 토큰 등록만 했을 때 RPC 상태는 계속 `disabled`로 정확히 보인다.
- 사유를 입력해 RPC를 `active`로 바꾸면 재조회 결과도 `active`다.
- 토큰 원문은 화면, 응답, 로그 어디에도 나오지 않는다.
- 다른 워크스페이스의 라우트는 바뀌지 않는다.

긴급도: **TYIT 베타 검증 차단 중**. PF Hermes RPC 호출 시험을 계속하려면 이 구분과
라우트 제어가 필요합니다.

## 기존 봇 관리에서 워크스페이스별 PF RPC 전환까지 관리해 주세요

### 무엇이 안 되는가

2026-10-12 TYIT에서 PF Hermes RPC 답변을 검증했습니다. 서버의 전환 설정은 현재
`/etc/tybot/tybot.env`의 `TYBOT_MASTER_V2_WORKSPACES=tyit`입니다.
`mgmt`, `pilot`도 `specialist_route.route_mode=active`이지만, 이 환경변수에 없으므로
그 상태만으로 PF Hermes RPC가 적용됐다고 표시할 수 없습니다.

`src/tybot/master_v2_rollout.py`는 현재 환경변수의 워크스페이스 key 목록을 읽습니다.
이 설정은 LLM Master 라우팅과 외부 v3 전문봇 호출, 전문봇 미배정 시 Master 직접
답변 경로까지 바꾸는 워크스페이스별 전환 설정입니다. Hermes 하나의 켜짐 상태와
구분해야 합니다. 환경변수만 변경하면 실행 중인 TYBot에는 재시작 전까지 반영되지
않습니다.

### 기존 화면을 대체하는 범위

**2026-10-12 후속 오너 결정: 공유 Hermes RPC worker를 기본으로 구현한다.**
워크스페이스마다 서비스 계정과 프로세스를 복제하는 절차는 기본 운영에서 대체한다.
여러 워크스페이스가 하나의 worker를 사용하되 요청별 ACL·도구 토큰·근거는 TYBot이
분리한다. 기존 개별 worker 연결도 유지하므로 화면은 워크스페이스와 실행 인스턴스가
일대일이라고 가정하지 않는다. 공유/개별 연결 대상을 표시하고 공유 worker 장애는
연결된 전체 대상에 영향을 준다고 보여줘야 한다.
구현 인계: [공유 RPC 계약](verification/2026-10-12-hermes-shared-rpc-handoff.md).
공유 선택 설정 `TYBOT_HERMES_SHARED_WORKSPACES`도 전환 설정 관리 범위에 포함한다.

새 관리 메뉴를 추가하지 않고 **기존 봇 관리의 전문봇 연결·라우팅 화면을 대체**합니다.
PF Hermes RPC가 향후 전문봇 호출 기준이며, 기존 내부 Python Hermes의 배정이나
`active` 라우트를 PF RPC 활성화로 보여주는 화면은 대체 대상입니다.
Master와 Archiver의 등록·수집 관리는 유지합니다. Slack 직접 연결이 필요한 경우에는
앞 요청처럼 RPC와 분리해 표시합니다.

### 무엇을 만들어야 하는가

1. 워크스페이스별 `PF RPC 전환` 토글을 기존 봇 관리에 제공합니다. 기본값은 OFF이며
   대상은 Slack team ID가 아닌 등록된 워크스페이스 key(`tyit`, `mgmt` 등)입니다.
   TYIT 베타에서 한 곳씩 확산하며, 신규 워크스페이스는 자동 활성화하지 않습니다.
2. 전환 설정, 전문봇 배정, `disabled / shadow / active` 라우트, 인스턴스별 RPC worker
   health를 각각 표시합니다. 전환 OFF이면 라우트가 active여도 `PF RPC 미적용`으로
   표시하며, 전환 ON이지만 전문봇이 없으면 `Master 직접 답변`으로 표시합니다.
3. 요청된 설정과 실행 중인 TYBot의 실제 적용값을 구분해 표시합니다. 저장 이후
   재시작이나 설정 반영이 필요하면 `적용 대기`로 표시하고, 재조회로 적용을 확인합니다.
4. 인스턴스별 계정·환경파일·고유 HMAC·소켓 접근·서명된 health 준비 여부를 표시합니다.
   전역 `specialist_bot.health=ok`만으로 다른 워크스페이스 worker도 준비됐다고
   판단하지 않습니다. 시크릿 값은 반환하지 않습니다.
5. 설정 변경에는 사유와 실행자, 대상 워크스페이스, 이전·이후 값과 적용 결과를
   감사 기록으로 남깁니다. 특정 워크스페이스 변경이 다른 곳을 활성화하지 않아야 합니다.
6. 기존 내부 Hermes에서 PF RPC로 바뀌었는지는 최근 실행의 `phase=external-v3`와
   성공·실패 기록으로 확인할 수 있게 합니다. 등록 상태와 실제 호출 상태를 구분합니다.

### TYBot와 콘솔의 작업 분담

- **TYBot 프로젝트**: 전환 설정 저장소와 조회·변경 API, 런타임 반영, 기존 환경변수와의
  우선순위·초기 이관 정책, 워크스페이스별 준비 상태 조회 및 감사 기록을 구현합니다.
  현재 이 전환 설정을 변경하는 API는 없으므로 기존 라우트 PUT API만으로는 부족합니다.
- **웹콘솔 프로젝트**: 위 API를 연결해 기존 전문봇 관리 화면을 대체하고, 토글·준비 상태·
  적용 대기·실행 결과를 표시합니다. 웹 프로세스가 직접 서버 env 파일을 수정하거나
  임의 systemctl 명령을 실행하는 방식으로 구현하지 않습니다.
- API 필드와 반영 방식은 두 프로젝트가 합의한 뒤 문서화합니다. 환경변수는 이관 기간의
  호환 수단으로 두고, 설정 정본과 우선순위를 명확히 정해야 합니다.

### 완료 조건

- 현재 상태에서 TYIT만 PF RPC 적용으로 보이고 mgmt·pilot은 기존 실행 경로로 보인다.
- 준비된 워크스페이스 한 곳의 전환을 켜면 실제 런타임에 반영되고 external-v3 호출을 확인한다.
- 전환 ON에서 전문봇 미배정 요청은 기존 설계대로 Master 직접 답변을 선택한다.
- 전환·배정·라우트·worker health를 독립적으로 표시하고 실제 적용 전에는 완료로 표시하지 않는다.
- 다른 워크스페이스와 Master·Archiver 수집 상태는 영향을 받지 않는다.

긴급도: **TYIT 베타 검증 완료, 나머지 워크스페이스 확산 운영에 필요**.

## Master 없는 Archiver + Hermes 운영과 수집기 기동 상태

2026-10-14 TEC 운영 요구: 프로젝트 금융팀은 TYBot Master 없이 Archiver와 Hermes만
사용할 수 있다. 콘솔에서 Master 등록을 Archiver 활성화의 선행조건으로 요구하지 않는다.
기존 DB 기동 함수와 Python loader가 Master 부재를 거절하던 조건은 TYBot 측에서 수정한다.
Master가 등록되어 있으면 신원 검증과 앱 분리는 계속 강제하고, Master 없는 workspace는
Master DM 인계만 비활성화한다. Archiver 자체 토큰/신원 검증과 채널 writer 인수는 유지한다.

- Archiver 연결이 enabled/identity_ok이고 자체 Bot/App 토큰이 있으면 독립 기동 가능하다.
- 연결 등록 완료와 수집 프로세스 실행/멤버십 동기화/실제 이벤트 수신을 구분해 표시한다.
- "등록/연결 검증" 이후 승인된 수집기 기동 요청을 서버 관리 API에 연결한다.
  기동 API와 감독 서비스는 별도 서버 구현이 필요하며 현재 자동 기동된다고 표시하지 않는다.
- Master 없는 workspace에 불필요한 Master 앱/토큰 등록을 안내하지 않는다.
- shadow 수집기 기동과 active 운영 writer 인수 승인을 분리한다. 등록 버튼만으로
  cutover/writer_owner/전역 쓰기 게이트를 자동 변경하지 않는다.
- 연결이 없거나 토큰/신원 검증이 부족하면 조건별 사유를 표시한다. 단순 "config 없음"으로
  접지 않는다. 실제 토큰 값은 반환하지 않는다.
