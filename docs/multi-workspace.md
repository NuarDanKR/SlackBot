# 멀티 워크스페이스 운영

_봇을 두 번째·세 번째 워크스페이스에 올리고, 워크스페이스 간 자료 공유를 켜는 절차._

---

## 1. 설치 방식 — 왜 "앱을 워크스페이스마다 따로" 인가

Slack 에서 한 앱을 여러 워크스페이스에 넣는 방법은 두 가지다.

| | A. 워크스페이스마다 앱 분리 **(채택)** | B. 단일 앱 배포(distribution) |
|---|---|---|
| 토큰 | 워크스페이스마다 봇 토큰 + 앱 토큰 | 앱 토큰 1개 + 워크스페이스별 봇 토큰 |
| 설치 절차 | 각 워크스페이스에서 매니페스트로 앱 생성 → 설치 | OAuth 설치 링크 |
| **인바운드 포트** | **불필요** | **필요** — OAuth 리다이렉트 URL을 받을 HTTPS 엔드포인트 |
| 격리 | 강함(앱·토큰이 완전히 분리) | 약함(한 앱이 모든 설치를 관장) |
| 관리 부담 | 워크스페이스 수만큼 앱 관리 | 앱 하나 |

우리 보안 경계는 **인바운드 포트 0개**(Socket Mode 아웃바운드 전용)다. B는 OAuth 리다이렉트를 받을
공개 엔드포인트가 필요해 그 경계를 깬다. 워크스페이스가 수십 개로 늘면 B + 설치 저장소(InstallationStore)로
가는 게 맞지만, 지금 규모에선 A가 단순하고 격리도 강하다.

봇은 워크스페이스마다 Socket Mode 연결을 하나씩 열고, **한 프로세스**에서 모두 처리한다.
아카이브·감사기록·LLM 게이트웨이는 공유하고, **조회 권한만 워크스페이스 경계로 분리**한다.

## 2. 새 워크스페이스 추가 절차

### 2-0. 먼저 '키'를 정한다
워크스페이스 키는 짧은 ASCII 식별자 하나이고, 세 곳에 동시에 쓰인다.

| 쓰이는 곳 | 키가 `mgmt` 일 때 |
|---|---|
| 관리 콘솔·DB | `workspace.key = mgmt` |
| 아카이브 디렉터리 | `archive/workspaces/mgmt/` |
| 프론트매터·권한 판정·감사 로그 | `workspace: mgmt` |

디렉터리와 권한 식별자로 쓰므로 키는 **소문자 ASCII 로 짧게** 정한다. 사람이 볼 한글 이름은
관리 콘솔의 표시 이름에 따로 입력한다.

⚠️ **이미 수집을 시작한 워크스페이스의 키는 바꾸지 않는다.** 수집된 MD 의 디렉터리명과
프론트매터 `workspace:` 값에 키가 박혀 있어서, 바꾸면 권한 판정이 어긋나 **기존 원문이 안 보인다.**
부득이 바꿀 때는 디렉터리 이동 + 모든 파일의 프론트매터를 함께 고쳐야 한다.

### 2-1. Slack 앱 생성
1. 새 워크스페이스 계정으로 https://api.slack.com/apps → **Create New App → From a manifest**
2. 대상 워크스페이스 선택 → [`docs/pilot/slack-app-manifest.yaml`](pilot/slack-app-manifest.yaml) 붙여넣기
3. **Basic Information → App-Level Tokens → Generate**: 스코프 `connections:write` → `xapp-...`
4. **OAuth & Permissions → Install to Workspace** → `xoxb-...`
5. **App Home → Show Tabs → Messages Tab** 활성화 +
   *"Allow users to send Slash commands and messages from the messages tab"* **체크**
   - 이걸 빼면 DM 입력창이 "이 앱으로 메시지를 보내는 기능이 꺼져 있습니다" 로 막힌다.
     매니페스트로 만들었으면 이미 켜져 있다(`messages_tab_read_only_enabled: false`).
6. 수집 대상 채널마다 `/invite @tybot`

### 2-2. 서버 설정
관리 콘솔의 **워크스페이스 관리**에서 키, 표시 이름, 등급, 사용 상태, 열람 대상과 두 Slack
토큰을 함께 저장한다. 토큰은 DB에 암호화되어 저장되고 화면에는 마스크만 다시 표시된다.

DB 설정이 있으면 봇은 이를 우선 사용한다. 기존 서버를 이전하는 동안에는 같은 키의
`WORKSPACES`, `SLACK_BOT_TOKEN_*`, `SLACK_APP_TOKEN_*` 설정을 임시 대체 경로로 사용할 수 있다.
각 워크스페이스 행에서 **편집 → DB로 이전 및 저장**을 마친 뒤 봇 기동을 확인하고 해당
워크스페이스 환경변수를 제거한다.

DB와 `/etc/tybot/workspace-secret.key`를 읽지 못하면 DB 토큰을 복호화할 수 없다. 평문 비상
대체 설정까지 제거한 운영 방식에서는 이 경우 봇 기동을 막는다. 보안상 평문 제거와 DB 장애 시
Slack 연결 유지 중 어느 쪽을 택할지 운영 정책으로 정해야 한다.

```bash
sudo systemctl restart tybot
journalctl -u tybot -n 30
```

기동 로그에서 워크스페이스별 연결과 크로스 열람 설정을 확인한다:
```
워크스페이스 연결 — pilot(파일럿) bot=xoxb-1234… readable=없음 / 실시간수집=True / 크로스열람=없음
워크스페이스 연결 — mgmt(경영본부) bot=xoxb-5678… readable=['pilot'] / 실시간수집=True / 크로스열람=['pilot']
기동 완료 — 워크스페이스 2개: ['pilot', 'mgmt']
```

Slack 에서 `@tybot 상태` 를 치면 첫 줄에 나온다:
```
*워크스페이스*: 경영본부 (`mgmt`) · 크로스 열람 허용: pilot
```

## 3. 권한 3층 — 독립된 축이다

자료가 새는 지점이라 축을 세 개로 분리했다. **하나가 다른 것을 대신하지 않는다.**

| 축 | 통제 대상 | 정하는 주체 | 설정 위치 |
|---|---|---|---|
| ① 채널 멤버십 | 같은 워크스페이스에서 **어느 채널**을 보나 | Slack 초대 | `/invite` |
| ② `share_with` | 이 문서를 **어느 동등 워크스페이스**에 넘길지 | 자료 소유 쪽 사람 | MD 프론트매터 |
| ③ root 워크스페이스 | 산하 자료를 취합·열람하는 상위 조직 | 관리자 | 콘솔의 워크스페이스 관리 |

### ① 같은 워크스페이스 — 소속 채널만
**공개 채널이어도 그 채널에 들어가 있지 않으면 답하지 않는다.** 봇을 통한 우회 열람을 막는다.

예외는 `visibility: public` 하나다. 이건 사람이 "이 문서는 워크스페이스 전체 공개"라고
명시적으로 표시한 경우이고, **크로스 워크스페이스와는 무관하다.**

### ② 동등(peer) 워크스페이스 — 문서가 지목한 것만
파일럿과 팀A 처럼 등위 조직끼리는, 문서 프론트매터에 상대를 적어야 넘어간다.

```yaml
share_with: [team_a]
```
`CROSS_WS_READ` 화이트리스트는 '넘어갈 수 있는 후보'만 정한다. 실제로 무엇을 넘길지는
소유 쪽이 문서 단위로 정한다. 둘 다 있어야 조회된다.

### ③ root 워크스페이스 — 회사 전체 자료
임원이 사용하는 회사 최상위 취합·열람 조직은 관리 콘솔에서 등급을 `상위 워크스페이스`로
지정한다.
root 는:
- 등록된 모든 워크스페이스의 자료를 **문서 표시와 무관하게** 열람한다
  (`share_with` 를 일일이 지정하지 않아도 된다)
- **자기 워크스페이스 안에서 채널 멤버십 필터를 받지 않는다** — 소속되지 않은 채널도 조회 가능

`상태` 응답에 등급이 표시된다:
```
*워크스페이스*: 경영본부 (`mgmt`) · 등급: 상위(root) - 회사 전체 자료 열람
*크로스 열람 허용*: 모든 등록 워크스페이스
```

### 왜 이렇게 나눴나 — `public` 하나로는 위험하다
초기 설계는 `visibility: public` 하나가 두 가지를 동시에 열었다.

1. 화이트리스트에 **제3의 동등 워크스페이스**가 추가되면 그쪽도 같은 문서를 읽는다.
   상위 조직에만 올리려던 자료가 옆 조직에 노출된다.
2. 같은 워크스페이스 안에서 **소속되지 않은 채널** 내용까지 열린다.
   크로스 공유를 켜려고 `public` 을 찍는 순간 내부 격리가 함께 풀린다.

축을 나누면 "경영본부만 본다"와 "팀A에도 공유한다"와 "우리 워크스페이스 전체 공개"가
서로 독립적으로 표현된다.

### 공유 상태 확인·변경

```bash
cd /opt/tybot
# 현재 상태 (내부공개 / 공유대상을 따로 표시)
sudo -u tybot ARCHIVE_DIR=/var/lib/tybot/archive .venv/bin/python scripts/share.py --list

# 동등 워크스페이스에 공유 (root 에게는 불필요)
sudo -u tybot .venv/bin/python scripts/share.py <파일.md> --share-with team_a
# 공유 해제
sudo -u tybot .venv/bin/python scripts/share.py <파일.md> --unshare
# 자기 워크스페이스 전체 공개 (멤버십 면제)
sudo -u tybot .venv/bin/python scripts/share.py <파일.md> --public
```
모든 변경은 프론트매터만 건드리고, 원문이 한 글자라도 바뀌면 중단·되돌린다.

### 회귀 테스트로 고정된 규칙
`tests/test_multi_workspace.py`:
- 소속되지 않은 채널은 같은 워크스페이스라도 차단(공개 채널 포함)
- 동등 워크스페이스는 `share_with` 없으면 아무것도 못 봄
- `visibility: public` 은 크로스 워크스페이스를 열지 않음
- root 는 모든 워크스페이스의 private 자료까지 열람, 자기 워크스페이스 멤버십 면제
- 화이트리스트는 단방향

## 4. 아카이브 구조

```
/var/lib/tybot/archive/workspaces/
├── pilot/channels/C01__프로젝트-업데이트/raw/2026-08-31.md
└── mgmt/channels/C02__경영_주간보고/raw/2026-08-31.md
```

워크스페이스별 디렉터리가 **물리 격리 계층**이고, 변경되지 않는 Slack 채널 ID가 채널의
소유 키다. 상세와 v1 전환 절차는 [archive-v2.md](design/archive-v2.md)를 따른다.

## 5. 주의사항

- **봇 프로세스는 여전히 한 곳에서만** 기동한다. 워크스페이스가 여러 개여도 프로세스는 하나다.
  같은 토큰으로 두 프로세스가 붙으면 중복 답변 + LLM 비용 2배.
- 워크스페이스마다 앱이 다르므로 **매니페스트를 고치면 모든 앱에 반영**해야 한다.
  한 곳만 바꾸면 그 워크스페이스만 스코프가 달라져 '조용한 고장'이 된다.
- LLM 비용 상한(`DAILY_COST_LIMIT_USD`)은 **전 워크스페이스 합산**이다. 워크스페이스가 늘면 같이 올린다.
- 감사 기록은 워크스페이스 구분 없이 한 파일에 쌓이고, 각 줄에 `workspace` 필드가 있다.
